# Chapter 1.1 · Shell, Files and Permissions

{{diagram ch-1-1-01.jsx | Ch 1.1 at a glance}}

## The problem: a thousand servers have no screen

Engineers still drive servers through a text shell because text commands can be repeated, combined, scripted and sent to a thousand machines at once; mouse clicks cannot.

A server in a data centre has no monitor, keyboard or mouse. You reach it over the network, and what you get is a text prompt. Every Kubernetes node is a Linux machine like this, and when a container misbehaves, `kubectl exec` drops you into a shell inside it.

Text also scales in a way clicks never do:

- **Repeatable.** A command you typed once can run again tomorrow, unchanged.
- **Composable.** Small programs connect into bigger ones with pipes, so you rarely need a new tool.
- **Automatable.** A list of commands is a script, and scripts are the first step towards the automation every cloud platform depends on.
- **Reviewable.** Text can be put in git, diffed and code-reviewed, unlike a sequence of clicks.

**Key idea.** Unix was designed around small programs that each do one thing well and talk through plain text. That design, from the early 1970s, is why a 2026 cloud engineer still lives in a terminal.

## How it works, part 1: the shell, streams and pipes

The shell is an ordinary program that reads a line you type, starts the programs it names, connects their inputs and outputs, and waits for them to finish.

When you type `ls -l /etc`, bash looks for a program called `ls` in each directory listed in the `PATH` variable, starts it with the arguments `-l` and `/etc`, and waits. Ch 1.2 shows the two system calls that do this, `fork` and `exec`.

Every program starts with three open *file descriptors*, numbered channels for reading and writing:

| Number | Name | Default |
| --- | --- | --- |
| 0 | standard input (stdin) | the keyboard |
| 1 | standard output (stdout) | the terminal |
| 2 | standard error (stderr) | the terminal |

The shell can rewire these before the program starts. `>` sends stdout to a file, `2>` sends stderr to a file, `<` reads stdin from a file. The pipe `|` connects one program's stdout to the next program's stdin:

{{diagram ch-1-1-02.jsx | a pipeline · ps aux | grep python}}

Neither `ps` nor `grep` knows the other exists. Each reads and writes plain text, and the kernel moves bytes between them. This is why small tools combine so well, and why error messages still appear on your screen while normal output flows into the pipe.

**Exit codes.** Every program ends with a number: `0` means success, anything else means failure. `echo $?` shows the last one. `&&` runs the next command only on success; `||` only on failure. Scripts, CI pipelines and Kubernetes exec health checks all decide what to do from exit codes.

## How it works, part 2: one tree of files

Linux has exactly one tree of files, starting at `/`, and many things that are not files on a disk appear in it as if they were.

Windows gives each disk a letter (`C:`, `D:`). Linux instead attaches every disk somewhere inside one tree; this is called *mounting*, and Ch 1.3 covers it. A *path* names a place in the tree:

- **Absolute path:** starts at the root, for example `/etc/hostname`.
- **Relative path:** starts where you are now. `.` means this directory, `..` the parent, `~` your home directory.
- **Hidden files** start with a dot, for example `~/.bashrc`. `ls` hides them; `ls -a` shows them.

The main directories follow the [Filesystem Hierarchy Standard](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/index.html):

| Directory | What lives there | You will meet it in |
| --- | --- | --- |
| `/etc` | System configuration, as plain text files | Every lab |
| `/home/<user>` | Each user's own files; `/root` for the root user | Lab 1.1 |
| `/usr/bin`, `/usr/lib` | Installed programs and their libraries; on Ubuntu `/bin` is a link to `/usr/bin` | Lab 1.1 |
| `/var` | Data that changes while the system runs: logs (`/var/log`), caches, databases | Ch 1.3 |
| `/tmp` | Short-lived temporary files; never keep work here | Ch 1.1 (sticky bit), Ch 1.3 |
| `/proc` | Not on disk: a live view of every running process and kernel setting | Ch 1.2 |
| `/sys` | Not on disk: a live view of devices and kernel subsystems, including cgroups | Ch 1.5 |
| `/dev` | Devices as files: disks (`/dev/sda`), the bit bucket (`/dev/null`), random numbers (`/dev/urandom`) | Ch 1.3 |
| `/run` | Runtime state such as process ID files and sockets; emptied at every boot | Ch 1.3 |

**"Everything is a file."** A disk, a process, a kernel setting and a network socket can all be read and written with the same `open`, `read` and `write` operations. That is why `cat /proc/cpuinfo` shows your CPU and why containers can be configured by writing to files under `/sys/fs/cgroup`.

## How it works, part 3: users, groups and permissions

Every file has one owning user, one owning group and nine permission bits; the kernel checks them on every open, so they are the first line of defence on any server.

The kernel does not know names. It knows numbers: a **user ID (UID)** and **group IDs (GIDs)**. `/etc/passwd` and `/etc/group` map them to names. The user with UID 0 is **root**, the administrator. `sudo` runs one command as root after checking that you are allowed to.

Run `ls -l` and each line starts with a ten-character string. Here is how to read it:

{{diagram ch-1-1-03.jsx | reading a permission string · -rw-r----- alice wallet}}

Each of `r`, `w`, `x` is one bit worth 4, 2 and 1. Add them for each class to get the octal digits `chmod` takes: `rw-` = 4 + 2 = 6.

**How the kernel decides.** It checks only one class, in this order: if you own the file, the owner bits apply; otherwise, if you are in the file's group, the group bits apply; otherwise the "everyone else" bits apply. Root skips almost all of these checks, which is why running as root is dangerous; Ch 1.5 shows how *capabilities* split root's power into smaller pieces.

On a directory the same bits mean something different, and this trips up even experienced engineers:

| Bit | On a file | On a directory |
| --- | --- | --- |
| `r` read | Read the contents | List the names inside (`ls`) |
| `w` write | Change the contents | Create, delete or rename entries inside |
| `x` execute | Run it as a program | Enter it (`cd`) and reach files inside by name |

So deleting a file needs write *and* execute permission on the **directory**, and no permission at all on the file. One exception: a directory with the *sticky bit*, such as `/tmp` (mode `drwxrwxrwt`, note the final `t`), lets each user delete only their own files. You will prove the main rule in Lab 1.1, Part C.

## Commands you will use in the lab

Every command in Lab 1.1 is listed here once; `man <command>` gives the full story, and `<command> --help` a short one.

| Command | What it does | Example |
| --- | --- | --- |
| `pwd`, `cd`, `ls -la` | Where am I, move, list (with hidden files and details) | `cd /etc && ls -la` |
| `cat`, `less`, `head`, `tail` | Print a file; page through it; first or last lines | `head -5 /etc/passwd` |
| `echo` | Print its arguments | `echo $PATH` |
| `grep` | Keep lines that match a pattern | `grep bash /etc/passwd` |
| `cut -d: -f1,7` | Keep fields 1 and 7 of each line, split on `:` | `cut -d: -f1,7 /etc/passwd` |
| `sort`, `uniq -c`, `wc -l` | Sort lines; count repeats of adjacent lines; count lines | `sort file \| uniq -c` |
| `tr` | Replace characters | `tr ':' '\n'` turns colons into new lines |
| `du -sh` | Disk space used by a directory | `du -sh /usr/*` |
| `ps aux`, `pgrep -a` | List processes; find one by name | `pgrep -a python3` |
| `which` | Show which file runs for a command name | `which ls` |
| `chmod`, `chown`, `chgrp` | Change mode, owner, group | `chmod 640 file` |
| `id`, `groupadd`, `useradd` | Show a user's IDs and groups; create a group; create a user | `sudo useradd -m -G wallet eve` |
| `sudo`, `sudo -u eve` | Run one command as root; as another user | `sudo -u eve cat file` |
| `curl` | Make an HTTP request | `curl localhost:8080/alice` |

**Just enough networking for Part D** (Vol 2 teaches it properly). A *port* is a number that identifies one program listening on a machine, so many servers can share one address. `localhost` (127.0.0.1) means "this machine". An HTTP reply starts with a *status code*: `200` means OK, `404` means not found, and codes from `500` to `599` mean the server itself failed.

## In production

At big-tech scale nobody fixes servers by hand, yet the shell remains the tool of last resort, and file permissions remain the last wall around every secret.

**Cattle, not pets.** Large fleets replace a broken machine instead of logging in to repair it. Changes go through code and automation (Vol 7). Engineers open a shell to *investigate*: `kubectl exec` into a container, `kubectl debug` onto a node, or SSH to a machine that automation cannot explain.

**Permissions guard secrets.** Private keys, kubeconfig files and database passwords live in files. Tools refuse to work when those files are too open: OpenSSH, for example, ignores a private key that other users can read. The rule of thumb:

| File | Typical mode | Why |
| --- | --- | --- |
| SSH private key, `~/.kube/config` | `600` | Only the owner may read; anyone who reads it becomes you |
| Config read by a service's group | `640` | Service account reads, nobody else |
| Program or script | `755` | Everyone may run it; only the owner may change it |
| Anything | `777` | Never. It means "anyone may change this", which hands control to any process on the box |

**One shell line can delete a home directory.** In January 2015 users reported that Steam for Linux deleted every file they owned ([issue #3671](https://github.com/valvesoftware/steam-for-linux/issues/3671)). The line suspected in the thread was `rm -rf "$STEAMROOT/"*`. If `STEAMROOT` is empty, it expands to `rm -rf "/"*`. The habits that prevent this:

- Start every bash script with `set -euo pipefail`. `-u` makes an unset variable an error instead of an empty string (Ch 1.4).
- Write `"${STEAMROOT:?}"` so the script stops if the variable is empty.
- Never run day-to-day work as root; use `sudo` for the one command that needs it.
