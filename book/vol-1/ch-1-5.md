# Chapter 1.5 · Isolation: Namespaces, cgroups and Capabilities

{{diagram ch-1-5-01.jsx | Ch 1.5 at a glance}}

## The problem: many programs share one kernel and must not see or starve each other

A container is not a small virtual machine: it is an ordinary Linux process that the kernel shows a smaller world, gives a budget, and takes powers away from. This chapter builds one from those parts.

Put the wallet, a database and a stranger's batch job on one server, and four things go wrong unless something stops them:

1. **They see each other.** Every process can list every other process in `/proc`, read the same `/tmp`, and bind the same port numbers. The stranger's job can read the wallet's command line, which may hold a password.
2. **They starve each other.** One process with a memory leak takes all the RAM, and the kernel's OOM killer (Ch 1.2) may kill the *wallet* instead of the leaking program. One busy loop on every core makes everyone else slow.
3. **They are too powerful.** A program running as root can load kernel modules, change the clock, or reboot the machine. Most programs need none of that, yet a single bug hands those powers to an attacker.
4. **They disagree about files.** The wallet wants Python 3.12 and the batch job wants Python 3.9, both at `/usr/bin/python3`.

Virtual machines solve all four by running a separate kernel for each program, at the cost of a whole operating system per program. Linux solves them inside *one* kernel with four mechanisms, and each one fixes one of the problems above:

| Problem | Mechanism | Question it answers |
| --- | --- | --- |
| They see each other | **Namespaces** | What can this process see? |
| They starve each other | **cgroups** (control groups) | How much can this process use? |
| They are too powerful | **Capabilities** and **seccomp** | What is this process allowed to do? |
| They disagree about files | **A root filesystem** and `pivot_root` | Which files are `/` for this process? |

Docker, containerd, Podman and every Kubernetes node use exactly these four kernel features. In Lab 1.5 you combine them yourself with `unshare`, a root filesystem copied out of a Docker image, `pivot_root` and `systemd-run`, without `sudo` on most machines. Then you compare your container with one from `docker run` and see the same parts.

**Why this matters for Kubernetes.** A Pod's `resources.limits.memory` becomes a cgroup file called `memory.max`, a Pod's `securityContext.capabilities` edits the capability list, and `hostUsers: false` puts a Pod in its own user namespace. When a Pod is `OOMKilled` or throttled, the explanation is in this chapter.

## How it works, part 1: namespaces decide what a process can see

A namespace wraps one kind of global resource, such as the list of processes or the hostname, so that the processes inside it get their own private copy; every process belongs to exactly one namespace of each kind.

The [namespaces(7)](https://man7.org/linux/man-pages/man7/namespaces.7.html) manual page lists eight kinds. Each has a flag that the `clone(2)` and `unshare(2)` system calls accept, and the `unshare` command has one option per kind:

| Namespace | `unshare` option | What it isolates | What a process inside sees |
| --- | --- | --- | --- |
| PID | `--pid` | Process IDs | Itself as PID 1, and only its own children |
| Mount | `--mount` | Mount points | Its own list of mounted filesystems |
| UTS | `--uts` | Hostname and NIS domain name | Its own hostname |
| Network | `--net` | Network devices, addresses, ports, routes, firewall | Only a loopback device, switched off |
| IPC | `--ipc` | System V IPC, POSIX message queues | Its own shared-memory segments |
| User | `--user` | User and group IDs, capabilities | Itself as `root`, mapped to an ordinary user outside |
| Cgroup | `--cgroup` | The cgroup root directory | Its own cgroup as the top of the tree |
| Time | `--time` | Boot and monotonic clocks | Its own uptime offset |

You can see the namespaces of any of your processes. Each one is a symbolic link in `/proc/<pid>/ns/`, and the number in brackets is the namespace's identity: two processes are in the same namespace exactly when the numbers match. This is the test machine's shell:

```text
$ ls -l /proc/$$/ns | cut -c43-
cgroup -> cgroup:[4026532210]
ipc -> ipc:[4026532199]
mnt -> mnt:[4026532211]
net -> net:[4026531833]
pid -> pid:[4026532213]
...
user -> user:[4026531837]
uts -> uts:[4026532212]
```

Nothing is copied or emulated. There is still one kernel and one list of processes; the kernel simply answers each question ("which processes exist?", "what is my hostname?") from the namespace of the process that asks. The same wallet process is PID 1 when it asks, and PID 383998 when the host asks. The kernel even records both numbers: the `NSpid` line of `/proc/<pid>/status` lists the PID in every namespace from the host inwards.

{{diagram ch-1-5-02.jsx | the same wallet process seen from the host and from inside · 5 namespaces}}

Each row is one namespace kind. The left column is what your shell sees; the right column is what the wallet sees inside the Lab 1.5 container. Both questions go to the same kernel.

You already run namespaced programs. On the test machine, `lsns` listed Google Chrome's renderer processes in their own PID and user namespaces: the browser sandbox is built from the same parts as a container.

## How it works, part 2: user namespaces and capabilities decide what root means

Inside a user namespace a process can be `root` with every capability, while to the rest of the system it is still your ordinary user; that is why you can build a container without `sudo`.

**Capabilities.** Linux does not treat root as one all-or-nothing power. It splits root's powers into about forty separate *capabilities*, each named `CAP_SOMETHING` and listed in [capabilities(7)](https://man7.org/linux/man-pages/man7/capabilities.7.html): `CAP_NET_BIND_SERVICE` binds ports below 1024, `CAP_SYS_ADMIN` mounts filesystems and changes the hostname, `CAP_KILL` signals other users' processes, and so on. The kernel on the test machine knows 41 of them. Every process carries a set of capabilities it may use right now, shown as a hexadecimal bit mask on the `CapEff` line of `/proc/<pid>/status`. Your shell's mask is `0000000000000000`: no powers at all.

**User namespaces.** A user namespace has its own table of user IDs, linked to the outside by a *map*. `unshare --user --map-root-user` creates one with a one-line map: user 0 inside is your user ID (1000 on the test machine) outside. The [user\_namespaces(7)](https://man7.org/linux/man-pages/man7/user_namespaces.7.html) page says the first process in a new user namespace gains a full set of capabilities in that namespace. On the test machine:

```text
$ unshare --user --map-root-user bash -c 'id; cat /proc/self/uid_map; grep CapEff /proc/self/status'
uid=0(root) gid=0(root) groups=0(root),65534(nogroup),...
         0       1000          1
CapEff:	000001ffffffffff
```

The catch is that those capabilities count only for things *owned by that namespace*. The new root can change the hostname of a UTS namespace it created, and mount filesystems in a mount namespace it created. It still cannot write `/etc` on the host (`Permission denied`), because to the host's files it is still user 1000. Files owned by host users it has no map for, such as root's `/etc/shadow`, show up as owner `65534`, the overflow ID for "nobody I know".

This gives you two very different meanings of "root in a container", and the lab measures both:

| Container | User namespace? | `root` inside is, outside... | Capabilities inside |
| --- | --- | --- | --- |
| Your Lab 1.5 container (`unshare --user`) | yes, a new one | your own user (1000) | all 41, valid only inside |
| `docker run` with default settings | no: the host's own user namespace | the real root of the host | 14 that Docker keeps by default ([Docker docs](https://docs.docker.com/engine/containers/run/)); the rest are dropped |
| Kubernetes Pod with `hostUsers: false` | yes, chosen by the kubelet | an unprivileged range of host IDs | as set in the Pod's `securityContext` |

Docker can also use a user namespace (its [userns-remap](https://docs.docker.com/engine/security/userns-remap/) mode), but it is not the default. Kubernetes added user namespaces for Pods in v1.28 and lists the feature as [stable since v1.36](https://kubernetes.io/docs/concepts/workloads/pods/user-namespaces/); a Pod opts in with `spec.hostUsers: false`.

A capability can also be dropped on purpose. Every process has a *bounding set*: capabilities it can never get back, not even by running a program as root. `setpriv --bounding-set -sys_admin hostname box` inside your user namespace fails, because `hostname` needs `CAP_SYS_ADMIN` and it is gone. Dropping everything a program does not need is the cheapest hardening there is; the hardened `wallet.service` in the Milestone runs with an empty bounding set.

## How it works, part 3: a root filesystem, and why pivot\_root beats chroot

A container's files are just a directory on the host, such as an unpacked Alpine Linux image; the kernel is told to treat that directory as `/` for the container's processes.

You get such a directory from any container image: `docker export` writes the files of a container as one tar archive, and `tar -x` unpacks it. Alpine 3.21 unpacks to 8.1 MB on the test machine: a shell (BusyBox), a C library, `/etc` and empty mount points. There is no kernel in it, because the container uses the host's kernel.

There are two ways to make that directory the root:

- **`chroot(dir)`** changes one pointer: where path lookups that start with `/` begin. It is old and simple, and the [chroot(2)](https://man7.org/linux/man-pages/man2/chroot.2.html) manual page warns that it "is not intended to be used for any kind of security purpose". It does not change the current working directory, so a process that was standing outside the new root is *still* outside it. In the lab, a shell started this way prints Alpine's `/etc/alpine-release` and then reads the host's `/etc/os-release` through `../../../../`.
- **`pivot_root(new, old)`** swaps the whole mount tree of a mount namespace: `new` becomes `/`, and the old root is moved to the directory `old` inside it ([pivot\_root(2)](https://man7.org/linux/man-pages/man2/pivot_root.2.html)). The container then unmounts `old`, and the host's files are no longer reachable by any path. Container runtimes such as runc do it this way.

{{diagram ch-1-5-03.jsx | chroot and pivot_root, side by side}}

On the left, `chroot` moved only the starting point of `/`; the working directory is still on the host, and `..` walks out. On the right, `pivot_root` moved the whole tree and the old root is then unmounted, so no path is left.

The chroot leak is not a classroom curiosity. In January 2024, runc 1.1.11 and earlier had a bug in which a leaked file descriptor gave a new container process "a working directory in the host filesystem namespace", allowing a container escape ([CVE-2024-21626](https://nvd.nist.gov/vuln/detail/CVE-2024-21626)). It is the same mistake: a working directory left outside the new root.

## How it works, part 4: cgroups decide how much a process can use

A cgroup (control group) is a directory in `/sys/fs/cgroup` that holds a set of processes and a set of limit and counter files; the kernel charges every page of memory and every slice of CPU time to the cgroup of the process that used it.

Modern systems use *cgroup v2*, one single tree described in the kernel's [Control Group v2](https://docs.kernel.org/admin-guide/cgroup-v2.html) documentation. You can check with `stat -fc %T /sys/fs/cgroup`, which prints `cgroup2fs` (v1 prints `tmpfs`). Kubernetes has [deprecated cgroup v1 since v1.35](https://kubernetes.io/docs/concepts/architecture/cgroups/); by default the kubelet no longer starts on a v1 node.

On a systemd machine, systemd owns the tree and makes one cgroup per unit. Every service, every login session and every `systemd-run` command gets its own directory, and a process's cgroup is the one line in `/proc/<pid>/cgroup`. The tree is the drawing at the end of this part.

Each cgroup directory holds files from the *controllers* switched on for it. The user's systemd instance on the test machine was allowed three of them: `cpu`, `memory` and `pids` (`cat .../user@1000.service/cgroup.subtree_control`). These are the files you will use, and the systemd setting that writes each:

| File | Meaning | systemd setting | Read on the test machine |
| --- | --- | --- | --- |
| `memory.max` | Hard limit in bytes. At the limit the kernel reclaims; if it cannot, the OOM killer runs *inside this cgroup* | `MemoryMax=` | `134217728` (128 MiB) for the hardened wallet |
| `memory.swap.max` | How much of the cgroup may be pushed to swap | `MemorySwapMax=` | `max` (no limit) unless set |
| `memory.current`, `memory.peak` | Memory in use now, and the highest value so far | read only | `15433728` (about 15 MiB) |
| `memory.events` | Counters: `max` (times the limit was hit), `oom_kill` (processes killed) | read only | `oom_kill 1` after the lab's memory hog |
| `cpu.max` | Quota and period in microseconds: at most *quota* of CPU time per *period* | `CPUQuota=` | `50000 100000` for `CPUQuota=50%` |
| `cpu.weight` | Share of CPU when there is contention (default 100) | `CPUWeight=` | `100` |
| `pids.max` | Maximum number of processes and threads | `TasksMax=` | `32` |
| `memory.pressure`, `cpu.pressure` | The PSI stall times of Ch 1.4, for this cgroup only | read only | `some avg10=5.12 ...` |

The kernel documentation is precise about `memory.max`: "If a cgroup's memory usage reaches this limit and can't be reduced, the OOM killer is invoked in the cgroup." That is the difference between Ch 1.2 and this chapter. In Ch 1.2 the OOM killer chose a victim from the whole machine; with a cgroup limit, only the processes in that cgroup are candidates, and the rest of the machine never notices. A Kubernetes container's `resources.limits.memory` is written into exactly this file, which is why a Pod can be `OOMKilled` on a node with gigabytes free.

CPU is different. A process cannot be killed for being busy, so `cpu.max` *throttles*: once the cgroup has used its quota in the current 100 ms period, its processes wait for the next period. A program limited to 50 percent of one CPU therefore runs in bursts, and its slowest requests get slower. Kubernetes documents that a CPU limit is [enforced by throttling](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/); `cpu.stat` counts how often it happened (`nr_throttled`).

You do not need root to use cgroups. `systemd-run --user --scope -p MemoryMax=64M <command>` asks your own systemd instance to create a new cgroup (a *scope*), set the limit, and run the command in it. That is how the lab limits its container.

{{diagram ch-1-5-04.jsx | the cgroup tree on the test machine · paths and values read from /sys/fs/cgroup}}

The left column is the path every one of your user units sits under; the three leaves are cgroups you create in Lab 1.5 and the Milestone, with values read from their files on the test machine. A limit set on a parent also caps everything below it.

## How it works, part 5: seccomp and no\_new\_privs shrink what a process can ask the kernel

Seccomp (secure computing) attaches a filter to a process that the kernel runs on every system call; a call that is not on the allow list fails, so a bug cannot use kernel features the program never needed.

A process makes requests to the kernel through system calls (Ch 1.2), and Linux has more than 300 of them. A web service such as the wallet needs a few dozen of them. The [seccomp(2)](https://man7.org/linux/man-pages/man2/seccomp.2.html) system call installs a small filter program, and once installed it can never be removed, only made stricter. The `Seccomp` line of `/proc/<pid>/status` says `0` for no filter and `2` for a filter. Docker installs a default profile in every container; its documentation says the profile [disables around 44 system calls out of 300+](https://docs.docker.com/engine/security/seccomp/). In the Milestone, systemd's `SystemCallFilter=@system-service` does the same job for the wallet service.

**no\_new\_privs** is a single flag (`NoNewPrivs` in `/proc/<pid>/status`) set with `prctl(2)`. Once it is set, running a program can never *add* privileges: the setuid bit of `sudo` or `passwd` is ignored. It is inherited by every child and cannot be cleared. systemd sets it with `NoNewPrivileges=yes`, and Kubernetes with `allowPrivilegeEscalation: false`.

## How it works, part 6: a container is just a process with all of the above

Put the five parts together and you have a container: an ordinary process, started in new namespaces, inside a cgroup with limits, with a reduced set of capabilities and a seccomp filter, whose `/` is an unpacked image.

`docker run` does not do anything else. Docker asks containerd, containerd asks runc, and runc makes the same system calls you make in the lab with `unshare`, `mount`, `pivot_root` and the cgroup files. Vol 4 opens that chain up; here you only need to know that the parts are the same. The lab measured three "containers" on the test machine by reading `/proc/<pid>/ns`, `/proc/<pid>/status` and the cgroup files:

{{diagram ch-1-5-05.jsx | two roads to the same five kernel features}}

Docker's road has more layers, but it ends at the same kernel features as yours. The one your road skips is seccomp: `mini.sh` installs no filter, which the table below shows as `Seccomp: 0`.

| Property | Your Lab 1.5 container | `docker run -m 64m alpine` | Hardened `wallet.service` (Milestone) |
| --- | --- | --- | --- |
| New namespaces | user, PID, mount, UTS, IPC, network, cgroup | PID, mount, UTS, IPC, network, cgroup | user, mount (systemd adds them for sandboxing) |
| User namespace | new: root inside is user 1000 outside | the host's own (`user:[4026531837]`) | new |
| `CapEff` | `000001ffffffffff`: all 41, inside its own namespaces only | `00000000a80425fb`: 14 | `0000000000000000`: none |
| `Seccomp` | `0`: no filter | `2`: Docker's default profile | `2`: `SystemCallFilter=` |
| `NoNewPrivs` | `0` | `0` | `1` |
| Memory limit | `memory.max` = 64 MiB via `systemd-run` | `memory.max` = `67108864` | `memory.max` = 128 MiB |
| Root filesystem | Alpine, via `pivot_root` | image layers on OverlayFS (Ch 1.3) | the host's `/`, read-only (`ProtectSystem=strict`) |

Read the table by column and three lessons appear. Your hand-made container is well isolated by namespaces but has no seccomp filter and full capabilities inside. Docker's container drops capabilities and filters system calls, but its root is the host's root. The hardened service is not a container at all, yet systemd used the same kernel features to lock it down further than either. Isolation is not one switch; it is a set of choices, and production systems combine all of them.

## In production: noisy neighbours, escapes and rootless containers

Teams that run thousands of containers per cluster treat these mechanisms as their safety net and their most common source of confusion, because every symptom first shows up as "the app is slow" or "the app died".

| What people say | What is usually happening | What engineers do |
| --- | --- | --- |
| "The Pod was `OOMKilled` but the node has 10 GB free" | The container reached its own `memory.max` (its `limits.memory`). The node is fine; the cgroup is not | Read the container's `memory.events` and `memory.peak`; raise the limit or fix the leak. The node's `free -m` is the wrong place to look |
| "p99 latency doubled but CPU use is only 40 percent" | A CPU limit is throttling the container in short bursts; the average hides it | Read `cpu.stat` (`nr_throttled`, `throttled_usec`) and `cpu.pressure`; raise or remove the CPU limit and keep a CPU request |
| "One customer's batch job slows everyone down" (the *noisy neighbour*) | Processes without limits share the same CPU, memory and disk | Put each workload in its own cgroup with requests and limits; Kubernetes does this per Pod and per container |
| "`fork: Cannot allocate memory`, but memory is fine" | A PID limit (`pids.max`) was reached (bash then says Resource temporarily unavailable), or the PID namespace's PID 1 has exited (that gives Cannot allocate memory) (Lab 1.5 Break it) | Check `pids.current` against `pids.max`; check that PID 1 is alive and reaps its children |
| "Root in the container could write to the host" | A container ran as root in the host's user namespace and something gave it a path to the host: a mounted host directory, a runtime bug, extra capabilities | Run as non-root, drop all capabilities, keep seccomp on, use user namespaces (`hostUsers: false`), patch the runtime |
| "We have to give the CI runner `--privileged` to build images" | `--privileged` turns off capability dropping, seccomp and device restrictions in one flag | Use a rootless builder, or a separate build cluster; never mount the Docker socket into a workload |

Two container escapes in runc, the runtime under Docker, containerd and most Kubernetes nodes, show why defenders stack every layer. In 2019, [CVE-2019-5736](https://nvd.nist.gov/vuln/detail/CVE-2019-5736) let a process running as root inside a container "overwrite the host runc binary (and consequently obtain host root access)". In 2024, [CVE-2024-21626](https://nvd.nist.gov/vuln/detail/CVE-2024-21626) left a new container's working directory in the host filesystem, the chroot mistake from part 3. Both are far worse when root inside the container is root on the host. A user namespace turns "root inside" into an ordinary user outside, so a process that escapes holds no more power than that user.

That idea is called a **rootless container**: the runtime itself runs as an ordinary user and uses a user namespace for root inside, exactly as your Lab 1.5 container does. Podman runs rootless by default for ordinary users, Docker has a rootless mode, and Kubernetes Pods can opt in with `hostUsers: false`. The price is a few missing features: a rootless container cannot bind host ports below 1024 or create real network devices without help, which is why the lab's container either shares the host network or has only a loopback device.

Distributions are also tightening the entry point. Ubuntu 24.04 lets unprivileged, unconfined programs create user namespaces but [denies them any capabilities inside](https://documentation.ubuntu.com/release-notes/24.04/) unless an AppArmor profile allows it. That restriction exists because user namespaces expose more kernel code to unprivileged users. Lab 1.5 tells you how to check for it.
