# Chapter 1.4 · The Operator's Toolkit

## The problem: when a server is slow you need a method, not guesses

A machine that misbehaves gives you a few minutes and a hundred symptoms; a method turns those symptoms into a short list of suspects and tells you which tool to run next.

Every operator spends the working day on four jobs, and this chapter gives you a tool and a habit for each:

1. **Get software onto the machine and trust it.** Packages, repositories and signatures, so that you install what you meant to install.
2. **Get onto the machine and prove who you are.** SSH and key pairs, so that no password crosses the network and no stranger can pose as your server.
3. **Automate without causing an outage.** Shell scripts that stop at the first mistake instead of carrying on and deleting the wrong directory.
4. **Find what is wrong, fast.** The USE method and a fixed set of commands, so that you check every resource once instead of staring at whichever graph you like best.

**Why this matters for Kubernetes.** Every Kubernetes node is a Linux machine. When a node is `NotReady`, when a Pod is throttled or evicted, when a container cannot reach its database, someone logs in to a node or reads its metrics and asks the same questions this chapter asks: which resource is busy, which is queueing, which is failing? Kubernetes adds a layer of names on top, but the evidence is still CPU, memory, disk and network.

## How it works, part 1: packages and apt

A package is one archive file (a `.deb` on Ubuntu) holding the files of a program plus its metadata: name, version, the packages it depends on, and scripts to run at install time; `dpkg` unpacks one archive, and `apt` finds, downloads, verifies and orders many of them.

Two tools, two jobs. `dpkg` knows nothing about the network: given a `.deb` it copies the files into place and records what it did in `/var/lib/dpkg`. `apt` is the layer above it: it reads the list of *repositories* (servers that publish packages), downloads their indexes, works out which dependencies are missing, downloads those `.deb` files and hands them to `dpkg`. Almost everything you type is `apt`; `dpkg` is how you ask "which package owns this file?" afterwards.

The list of repositories lives in `/etc/apt/sources.list.d/`. This is the main Ubuntu entry on the test machine, in the *deb822* format that Debian's [sources.list(5)](https://manpages.debian.org/trixie/apt/sources.list.5.en.html) describes (the older one-line format is deprecated there):

```text
Types: deb
URIs: http://id.archive.ubuntu.com/ubuntu/
Suites: resolute resolute-updates resolute-backports
Components: main universe restricted multiverse
Signed-By: /usr/share/keyrings/ubuntu-archive-keyring.gpg
```

`Suites` names the release (the test machine runs Ubuntu 26.04, codename `resolute`; your 24.04 shows its own codename) and its update streams; `Components` selects sections of the archive. `Signed-By` is the trust anchor: it requires this repository to pass apt's signature check (apt-secure(8)) with the keys in that keyring, instead of trusting every key on the machine.

## How it works, part 2: SSH and keys

SSH (Secure Shell) gives you a shell on another machine over an encrypted connection, and it proves identity in both directions: you prove who you are with a private key, and the server proves who it is with its own host key.

**Your key pair.** `ssh-keygen -t ed25519` creates two files. The *private key* (`id_ed25519`) stays on your machine and is never copied anywhere. The *public key* (`id_ed25519.pub`) is safe to hand out: you append it as one line to `~/.ssh/authorized_keys` on every server you want to enter. At login the server sends a challenge, your SSH client signs it with the private key, and the server checks the signature against the public key. Nothing secret crosses the network, so there is no password to guess or steal. The private key file must be readable by you alone (mode `600`); OpenSSH refuses to use a key that other users can read. Protect it with a passphrase and let `ssh-agent` hold it unlocked for the session.

**The server's key.** The first time you connect, the server shows its *host key* fingerprint and your client stores it in `~/.ssh/known_hosts`. Every later connection is checked against that record. If it no longer matches, the client stops and prints `REMOTE HOST IDENTIFICATION HAS CHANGED`: either the machine was rebuilt, or someone is standing between you and it. Find out which before you delete the old line with `ssh-keygen -R`. Never switch checking off to make the warning go away.

{{diagram ch-1-4-03.jsx | SSH public-key login · 4 messages}}

**What else SSH does.** Beyond a shell it can run one command (`ssh host 'uptime'`), copy files (`scp`, `sftp`) and carry other traffic through the encrypted channel. A *local port forward*, `ssh -L 9091:localhost:8080 host`, makes port 9091 on your laptop reach port 8080 on the server's own loopback address; that is how you reach a service that must not be exposed to the network. You will build a tiny SSH server in the lab, so every one of these is something you run, not something you read about.

## How it works, part 3: scripts that fail safely

By default a bash script keeps going after an error, so a script that fails in line 3 can still do damage in line 5; three settings and a few habits make it stop instead.

Here is a backup script with three bugs. It is the kind of script that runs from cron for years before it hurts someone:

```bash
#!/usr/bin/env bash
cd /nonexistent/backups
echo "cleaning $PWD"
rm -f "$BACKUP_DIR"/*.old
curl -s http://localhost:1/data | wc -l
echo "backup finished"
```

Run as it stands, it prints a `cd` error, then `cleaning /home/…` (it never left the directory it started in), then `0`, then `backup finished`, and exits with status `0`: success. Three separate lies. The fix is one line at the top:

```bash
set -euo pipefail
```

{{diagram ch-1-4-04.jsx | the fragile backup script, before and after}}

| Setting | What it does | The bug it catches above |
| --- | --- | --- |
| `-e` | Exit as soon as a command fails | `cd` fails, so the script stops before `rm` runs in the wrong place |
| `-u` | Treat an unset variable as an error | `$BACKUP_DIR` is empty; without `-u` the `rm` line expands to `rm -f /*.old` |
| `-o pipefail` | A pipeline fails if any stage fails, not only the last | `curl` fails with status 7, but `wc -l` succeeds, so the pipeline reported success |

These settings are a safety net, not a guarantee. `-e` has exceptions: the bash manual lists commands that are tested by `if`, `while`, `&&` or `||`, or that are not the last stage of a pipeline, and a failure there does not stop the script. Greg's Wiki's [BashFAQ/105](https://mywiki.wooledge.org/BashFAQ/105) explains why `set -e` does not always do what you expect. Keep it, and add the habits below.

| Habit | Why |
| --- | --- |
| Quote every expansion: `"$file"` | An unquoted `$file` holding `my file.txt` becomes two arguments, and `touch $file` creates two files ([ShellCheck SC2086](https://www.shellcheck.net/wiki/SC2086)) |
| Require a variable with a message: `"${BACKUP_DIR:?set BACKUP_DIR}"` | The error names the missing variable instead of a bare "unbound variable" |
| Clean up on every exit: `tmp=$(mktemp -d); trap 'rm -rf "$tmp"' EXIT` | The temporary directory is removed whether the script ends normally, fails, or gets `SIGTERM` (Ch 1.2); only SIGKILL skips it, because nothing can catch that signal |
| Handle an expected failure yourself: `curl … > out \|\| { echo "wallet not answering" >&2; exit 1; }` | You choose the message and the exit code; the script does not rely on `-e` alone |
| Run `shellcheck script.sh` before you ship | A free linter that found the unchecked `cd` above (rule SC2164) |

## How it works, part 4: the USE method

The USE method says: for every resource, check utilization, saturation and errors, and do not look at anything else until you have done so. Brendan Gregg, a performance engineer, wrote it down: "For every resource, check utilization, saturation, and errors" ([The USE Method](https://www.brendangregg.com/usemethod.html), last updated 24 August 2017).

Gregg's definitions are short enough to memorise:

- A **resource** is a physical server component: CPUs, memory, disks, network interfaces. He adds that software resources and software-imposed limits can be considered too.
- **Utilization** is "the average time that the resource was busy servicing work".
- **Saturation** is "the degree to which the resource has extra work which it can't service, often queued".
- **Errors** is "the count of error events".

A checkout counter makes the three words concrete. Utilization: the cashier is busy 90 percent of the time. Saturation: six people stand in the queue. Errors: the card reader rejected three cards. A cashier at 90 percent with no queue is fine; a cashier at 60 percent with a growing queue has a problem utilization alone would never show you. That is why saturation and errors come first: they are easy to read and they point at trouble directly.

{{diagram ch-1-4-05.jsx | USE method decision flow · 3 questions per resource}}

Gregg publishes a [USE checklist for Linux](https://www.brendangregg.com/USEmethod/use-linux.html) with a tool for every cell. This table keeps the commands you will use in Lab 1.4 and names the one number to read in each:

| Resource | Utilization | Saturation | Errors |
| --- | --- | --- | --- |
| **CPU** | `mpstat -P ALL 1`, `vmstat 1` (`us` + `sy`), `top` | `vmstat 1` column `r` (runnable tasks) compared with `nproc`; load average in `uptime` | Rare; Gregg lists CPU performance counters read with `perf` |
| **Memory** | `free -m` (read `available`, not `free`) | `vmstat 1` columns `si` and `so` (pages swapped in and out); the OOM killer as the last stage | `dmesg` or `journalctl -k` showing `out of memory: Killed process`; `oom_kill` in `/proc/vmstat` |
| **Disk** | `iostat -xz 1` column `%util`; `df -h` for space | `iostat` columns `aqu-sz` (queue length) and `await` (ms per request) | Kernel log I/O errors; `smartctl` on real hardware |
| **Network** | `ip -s link` (bytes per second against the link speed) | Dropped packets and retransmits; `ss -ltn` on a listening socket: `Recv-Q` above `Send-Q` | `ip -s link` error counters; `nstat -az TcpExtListenOverflows TcpExtListenDrops` |

Two details in the network row are worth a sentence. For a *listening* socket, `ss` shows in `Recv-Q` the number of connections waiting to be accepted and in `Send-Q` the size of that waiting line (the backlog), as the [sock\_diag(7)](https://man7.org/linux/man-pages/man7/sock_diag.7.html) manual page defines them. When the line is full the kernel drops new connections and adds one to `TcpExtListenOverflows`, as the [kernel's SNMP counter documentation](https://docs.kernel.org/networking/snmp_counter.html) describes. A server whose CPU is idle can still refuse customers this way.

**Pressure stall information.** Linux can also measure saturation directly. The kernel's PSI files, `/proc/pressure/cpu`, `/proc/pressure/memory` and `/proc/pressure/io`, report the share of time in which tasks were stalled waiting for that resource: the `some` line counts time when at least one task was stalled, and `total` is the stall time in microseconds ([PSI, kernel documentation](https://docs.kernel.org/accounting/psi.html)). Every cgroup has the same three files (`cpu.pressure` and so on), which Ch 1.5 uses.

**Exonerate as well as accuse.** Gregg and the Netflix team stress "checked and exonerated": once CPU, memory, disk and network show no saturation and no errors, you have narrowed the search by elimination, and the cause is probably in the software. The lab ends on exactly such a case.

## How it works, part 5: reading the tools without fooling yourself

Most of the tools you need are one-line views of counters the kernel keeps in `/proc`, and each has one trap that makes beginners misread it.

| Tool | Read this | The trap |
| --- | --- | --- |
| `vmstat 1` | `r` (tasks wanting a CPU), `b` (tasks blocked on I/O), `si` and `so` (swap in and out), `us sy id wa` | The first line is the average since boot, not now. Ignore it and read the lines after |
| `uptime` | Three load averages over 1, 5 and 15 minutes | On Linux the number counts tasks that want a CPU and tasks in uninterruptible I/O (Ch 1.2), so high load with idle CPUs often means a disk problem. It also lags: a 10-second burst barely moves the 1-minute value |
| `free -m` | `available` | `free` is small on a healthy machine, because the kernel fills spare RAM with the page cache (Ch 1.2) |
| `top` | The header lines first (`%Cpu(s)`, `MiB Mem`, `load average`), then the process list | A busy process list does not say which *resource* is short. Note `ni` (CPU time of niced processes) in the CPU line: it points at low-priority background work |
| `mpstat -P ALL 1` | One row per core | An average over 12 cores hides one core stuck at 100 percent; single-threaded programs do exactly that |
| `iostat -xz 1` | `%util`, `aqu-sz`, `r_await`, `w_await` per device (`-z` hides idle devices) | `%util` close to 100 means saturation only for devices that serve one request at a time; the iostat manual warns that for RAID arrays and modern SSDs it does not reflect their limits. Read it with `aqu-sz` and `await` |
| `pidstat -d 1` | Which *process* reads and writes | Needs `sysstat`; it turns "the disk is busy" into a name |
| `ss -ltn` and `ss -s` | `Recv-Q` against `Send-Q` on listeners; the socket counts | A listener whose `Recv-Q` has reached its `Send-Q` is refusing new connections even though the server may look idle |
| `lsof -p <pid>`, `lsof -i :8080` | Which files and sockets a process holds | Every network socket is a file descriptor, so a process that leaks them hits `Too many open files` (the per-process limit is in `/proc/<pid>/limits`) |

The `iostat` caveat about `%util` is general: a percentage of "time busy" says little about a device that can serve many requests at once, which is why queue length and wait time sit next to it in Gregg's checklist. Sampling matters too. A tool that prints one number per second (`vmstat 1`) catches a spike that lasts a few seconds; a monitoring system that scrapes every minute misses it.

## In production: the first 60 seconds, and what the symptoms really mean

On-call engineers do not improvise: they run the same ten commands in the same order, so that nothing gets skipped at 3 a.m. The Netflix performance engineering team, with Brendan Gregg among its authors, published their list in [Linux Performance Analysis in 60,000 Milliseconds](https://techblog.netflix.com/2015/11/linux-performance-analysis-in-60s.html) (Netflix Tech Blog, 30 November 2015; the post is also listed on [Gregg's own page](https://www.brendangregg.com/linuxperf.html)). Their advice: "Look for errors and saturation metrics, as they are both easy to interpret, and then resource utilization." The ten commands, and what each one answers:

| # | Command | Question it answers | Resource |
| --- | --- | --- | --- |
| 1 | `uptime` | Is the load rising or falling? (three averages: 1, 5, 15 minutes) | CPU, disk |
| 2 | `dmesg \| tail` | Did the kernel report an error, an OOM kill or dropped packets? | all (errors) |
| 3 | `vmstat 1` | Run queue `r`, swapping `si`/`so`, CPU split `us sy id wa` | CPU, memory |
| 4 | `mpstat -P ALL 1` | Is one core pinned while the average looks fine? | CPU |
| 5 | `pidstat 1` | Which process is using the CPU? | CPU |
| 6 | `iostat -xz 1` | Is a disk busy or queueing? | disk |
| 7 | `free -m` | How much memory is `available`? | memory |
| 8 | `sar -n DEV 1` | How much traffic does each network interface carry? | network |
| 9 | `sar -n TCP,ETCP 1` | TCP connection rates and retransmits | network |
| 10 | `top` | Does the process list tell the same story? | all |

In Lab 1.4 you run the whole list. Commands 8 and 9 come from `sysstat`'s `sar`, which needs a background data collector that the authors did not set up; the lab uses `ip -s link`, `ss` and `nstat`, which read the same kernel counters.

When a real incident reaches you, it rarely arrives labelled with a resource. These are the translations engineers make most often:

| What people say | What is usually happening | What engineers do |
| --- | --- | --- |
| "Load average is 20 but the CPUs are idle" | Tasks blocked on disk count towards load (Ch 1.2), so storage is the bottleneck | `vmstat 1` column `b`, `iostat -xz 1`, then `pidstat -d 1` for the process |
| "The disk is 90 percent busy but writes crawl at a few MB/s" | Many small synchronous writes, each waiting for the disk (Lab 1.4 fault 3 does exactly this) | Find the writer with `pidstat -d`; batch the writes or stop forcing every one to disk |
| "Latency spikes, but average CPU is low" | One core is pinned, or a cgroup CPU limit is throttling the process (Ch 1.5). Kubernetes documents that a CPU limit is [enforced by throttling](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/) | `mpstat -P ALL 1`; read `cpu.stat` and the PSI files of the cgroup |
| "Clients time out, yet the server CPU is idle" | The listen queue is full and the kernel drops new connections (Lab 1.4 fault 4) | `ss -ltn`, `nstat -az TcpExtListenOverflows`; accept faster, or raise the backlog |
| "The Pod was OOMKilled but the node has free memory" | The container hit its own cgroup `memory.max`; the node is fine (Ch 1.5) | Compare the container's memory with its limit; the node's `free -m` is the wrong place to look |
| "Every dashboard is green and users still wait" | No hardware resource is short; a program is waiting on something (a lock, a slow dependency, a stuck connection) | Exonerate the four resources, then look inside the process: that is the lab's Break it |
| "`REMOTE HOST IDENTIFICATION HAS CHANGED`" after a rebuild | The machine got a new host key, or the connection is intercepted | Confirm the change with whoever rebuilt it, then `ssh-keygen -R <host>`; never disable the check |
| "The nightly backup says success but the file is empty" | A pipeline hid a failed first stage because `pipefail` was off | `set -euo pipefail`, and test the failure path on purpose |
