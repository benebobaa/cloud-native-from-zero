# Chapter 1.3 · Filesystems, Boot and systemd

{{diagram ch-1-3-01.jsx | Ch 1.3 at a glance}}

## The problem: data must outlive processes, and services must outlive you

A process forgets everything when it exits, and nobody wants to log in at 3 a.m. to restart a crashed service; filesystems keep data across restarts, and an init system keeps services running across crashes and reboots.

Wallet v0 already depends on both. Its balances live in a file, so they survive when the process stops. But the process itself only runs while your terminal is open; close the laptop lid and the wallet is gone.

This chapter answers three questions:

1. **How does Linux store files?** Names, inodes, links and mounts, and why a full disk is not always full.
2. **How do containers get a filesystem cheaply?** By stacking read-only layers with OverlayFS; every container image you will build in Vol 4 works this way.
3. **Who starts and restarts programs?** The boot sequence, systemd services, logs, and scheduled jobs. A systemd unit with `Restart=on-failure` is the small ancestor of a Kubernetes Deployment.

## How it works, part 1: inodes, links and mounts

A file's data and details live in an *inode*, identified by a number; a file name is only a directory entry that points to an inode, so one file can have several names, and deleting a name does not always free the space.

**Inodes.** An inode stores everything about a file except its name: owner, mode, size, timestamps, and where its data blocks are on disk. `ls -i` shows inode numbers; `stat` shows the rest. A *directory* is a table of names and inode numbers.

**Links.**

|  | Hard link | Symbolic (soft) link |
| --- | --- | --- |
| Created with | `ln target name` | `ln -s target name` |
| What it is | A second name for the same inode | A tiny file that contains a path |
| Inode number | Same as the target | Its own |
| If the original name is deleted | Still works: the data stays while any name remains | Breaks: it points to a path that no longer exists |
| Can cross filesystems or point to directories | No | Yes |

`ls -l` shows a *link count* in the second column. The kernel frees a file's data only when the link count reaches zero **and** no process still has the file open. Remember that second condition; it explains a classic production puzzle below.

**Mounts.** Each disk or partition holds a *filesystem* (Ubuntu uses ext4 by default). Mounting attaches a filesystem to a directory in the one tree. Not every filesystem is on a disk: `/proc` and `/sys` are generated by the kernel, and `tmpfs` lives in RAM. `findmnt` lists what is mounted where, `lsblk` lists disks, `df -h` shows space and `df -i` shows inodes; a filesystem can run out of either.

## How it works, part 2: OverlayFS, the filesystem behind every container

OverlayFS stacks a writable *upper* directory on top of one or more read-only *lower* directories and shows the result as a single *merged* directory; this is how a container gets a full filesystem without copying its image.

You mount it by naming the layers: `mount -t overlay overlay -o lowerdir=L,upperdir=U,workdir=W M`. Three rules then decide what you see in `M` ([kernel docs](https://docs.kernel.org/filesystems/overlayfs.html)):

1. **Read:** you get the file from the highest layer that has it.
2. **Change a lower file:** the kernel first *copies it up* into the upper layer, then changes the copy. The lower layer is never modified.
3. **Delete a lower file:** the kernel cannot remove it from the read-only layer, so it writes a *whiteout*, a special character device numbered 0,0, in the upper layer. The whiteout hides the file in the merged view.

## How it works, part 3: boot, systemd and logs

After the kernel starts, it runs one program as PID 1, which on Ubuntu is systemd; systemd then starts every service in dependency order, restarts the ones that fail, and collects their logs.

{{diagram ch-1-3-03.jsx | the boot sequence · firmware to services}}

**Units.** systemd manages *units*, each described by a small text file:

| Unit type | Describes | Example |
| --- | --- | --- |
| `.service` | A program to run and keep running | `ssh.service`, your `wallet.service` |
| `.timer` | When to start a service | `wallet-backup.timer` |
| `.socket` | A socket systemd listens on, starting the service on first connection | `ssh.socket` |
| `.mount` | A filesystem to mount | `home.mount` |
| `.target` | A named group of units, like a checkpoint in the boot | `multi-user.target` |

System units live in `/etc/systemd/system/` and need root; each user can also have their own units in `~/.config/systemd/user/`, controlled with `systemctl --user`. Lab 1.3 uses user units so you need no `sudo`. A service for the wallet:

```ini
[Unit]
Description=Wallet v0

[Service]
WorkingDirectory=%h/cn-lab/wallet
ExecStart=/usr/bin/python3 %h/cn-lab/wallet/wallet.py
Restart=on-failure
RestartSec=2

[Install]
WantedBy=default.target
```

(`%h` means your home directory.) `Restart=on-failure` is the heart of it: if the process dies with a non-zero exit code or a signal, systemd starts it again after `RestartSec`. To stop it, `systemctl stop` sends `SIGTERM`, waits, then sends `SIGKILL`, the same pattern Kubernetes uses.

**Crash loops.** If a service fails again and again, systemd gives up: by default after 5 starts within 10 seconds it marks the unit `failed` with `Start request repeated too quickly`. Kubernetes' `CrashLoopBackOff` is the same idea with a growing delay instead of a hard stop.

**Logs.** Whatever a service writes to stdout or stderr goes to the *journal*. `journalctl -u <unit>` shows one unit's logs, `-f` follows them live, `--since "10 min ago"` filters by time, and `-p err` shows only errors. Your program never needs to manage log files itself; Kubernetes uses the same rule for containers.

## How it works, part 4: scheduled jobs

Work that must run on a schedule, such as backups and reports, is started either by cron, the classic Unix scheduler, or by a systemd timer; the Kubernetes CronJob you will meet in Ch 5.2 reuses cron's schedule syntax.

**cron.** Each user has a *crontab* (`crontab -e` edits it). Each line is five time fields and a command:

```text
# min  hour  day-of-month  month  day-of-week  command
*/15   *     *             *      *            /home/you/bin/report.sh
0      2     *             *      *            /home/you/bin/backup.sh
```

The first line runs every 15 minutes; the second at 02:00 every day. cron runs commands with a minimal environment: `/bin/sh`, a short `PATH`, your home directory as the working directory, and none of your interactive shell's variables. That difference is the usual reason a script "works by hand but not from cron" (Review 1.1, Q5).

**systemd timers.** A `.timer` unit starts a matching `.service` unit on a schedule, for example `OnCalendar=*-*-* 02:00:00` or `OnUnitActiveSec=10min`. Compared with cron, timers log every run to the journal, can catch up a run missed while the machine was off (`Persistent=true`), and reuse all of systemd's restart and resource controls. Lab 1.3 builds one to back up the wallet's balances.

## In production

Most filesystem incidents are "the disk is full", and most of those are not what they first look like.

| What you see | What is really happening | What engineers do |
| --- | --- | --- |
| `df` says the disk is full, but `du` cannot find the space | A large log file was deleted while a process still had it open; the data stays until that process closes it | `lsof +L1` finds it; restart or signal the process to reopen its logs |
| `No space left on device`, yet `df -h` shows free space | The filesystem ran out of inodes, usually from millions of tiny files | `df -i` confirms it; delete or archive the small files |
| A container writes a big file and becomes slow | Each first write to a lower-layer file is a full copy-up into the upper layer | Write data to a volume, not the container's own filesystem (Ch 5.4) |
| A container is recreated and its data is gone | The upper layer belongs to that one container and is deleted with it | Keep state in a volume or a database, never in the container layer |
| A service restarts forever in a tight loop | `Restart=always` with a bug that fails at once | Read the journal for the first failure; rely on the start limit, as Kubernetes does with back-off |

Logs need a size limit too. journald rotates its own storage, and the kubelet rotates container logs by size; a service that writes its own log files must rotate them, or it becomes the first row of this table.
