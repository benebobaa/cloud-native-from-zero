# Chapter 1.2 · Processes, System Calls and Memory

{{diagram ch-1-2-01.jsx | Ch 1.2 at a glance}}

## The problem: hundreds of programs, one machine

A laptop runs hundreds of programs at once on a handful of CPU cores and one block of memory; the kernel's job is to share them so that no program can starve, spy on or crash another.

Run `ps aux | wc -l` and you will count well over a hundred processes, yet your CPU has perhaps 4 or 8 cores. Three questions follow, and this chapter answers each:

1. **Who runs now?** The kernel switches between programs many times a second so each one seems to have a CPU to itself.
2. **Whose memory is this?** Every program believes it owns a large, private block of memory starting at the same addresses. The kernel maps those private addresses onto real memory and stops programs from touching each other's.
3. **How does a program ask for anything?** A program cannot touch the disk, the network card or another program directly. It must ask the kernel, through a *system call*.

**Why this matters for Kubernetes.** A container is a process. When Kubernetes reports `OOMKilled`, exit code `137`, `CrashLoopBackOff` or CPU throttling, it is reporting something this chapter's kernel did. Engineers who understand processes read those messages as clues; everyone else reads them as noise.

## How it works, part 1: user space, the kernel and system calls

A program runs in *user space*, where it can compute but cannot touch any hardware; to read a file, use the network or start another program it must make a *system call*, a request the kernel checks and carries out.

The CPU itself enforces this split. Code in user space runs with fewer privileges; only the kernel runs with full control of the hardware. A system call is the one door between the two: the program puts a request number and its arguments in agreed places, the CPU switches into kernel mode, the kernel checks permissions and does the work, then returns a result. Linux has a few hundred system calls; a handful do most of the work.

{{diagram ch-1-2-02.jsx | the system call boundary · wallet v0 serving one request}}

The syscall names in the diagram are real. Running wallet v0 under `strace` while it answered one `curl` request recorded this (trimmed):

```text
accept4(3, {sa_family=AF_INET, sin_port=htons(53340), sin_addr=inet_addr("127.0.0.1")}, ...) = 4
openat(AT_FDCWD, "balances.json", O_RDONLY|O_CLOEXEC) = 5
read(5, "{\"alice\": 100, \"bob\": 50}\n", 27) = 26
close(5)                          = 0
write(2, "127.0.0.1 - - [16/Nov/2026 11:25"..., 65) = 65
sendto(4, "HTTP/1.0 200 OK\r\nServer: BaseHTT"..., 124, 0, NULL, 0) = 124
sendto(4, "{\"account\": \"alice\", \"balance\": "..., 37, 0, NULL, 0) = 37
close(4)                          = 0
```

Read it line by line: accept a connection (it becomes file descriptor 4), open the data file (descriptor 5), read it, close it, write the access log to stderr (descriptor 2), send the reply, close the connection. Every Python line you wrote turned into a few of these requests. You will produce this trace yourself in Lab 1.2.

## How it works, part 2: the life of a process

Every process is created by copying an existing one with `fork`, becomes a new program with `exec`, ends with `exit`, and is finally removed when its parent collects its exit code with `wait`.

A *process* is a running program plus everything the kernel tracks about it: a process ID (PID), its parent's ID (PPID), its memory, open file descriptors, current directory, user and group. Every process except the very first has a parent, so all processes form one tree with PID 1 at the root (`pstree -p` draws it).

{{diagram ch-1-2-03.jsx | process lifecycle · fork, exec, exit, wait}}

Why two steps instead of one "start program" call? Between `fork` and `exec` the child is still running bash's code, so bash can prepare it: redirect its stdout to a file, connect a pipe, change directory. That is exactly how the shell built the pipelines in Ch 1.1.

A finished child stays in the process table as a *zombie* until its parent calls `wait`. A zombie uses no CPU or memory, only a slot in the table; but a buggy parent that never waits can fill that table. You will create a zombie on purpose in Lab 1.2.

## How it works, part 3: signals and exit codes

A *signal* is a small numbered message the kernel delivers to a process; it is how Linux tells a program to stop, reload or pay attention, and the exit code is how the program reports how it ended.

A program may *catch* most signals with a handler and decide what to do. If it does not, the kernel applies the default action, usually "terminate". `kill -l` lists them all. These are the ones you will meet every week:

| Signal | Number | Sent when | Default | Can be caught? |
| --- | --- | --- | --- | --- |
| `SIGINT` | 2 | You press `Ctrl+C` | Terminate | Yes |
| `SIGTERM` | 15 | Someone asks politely: `kill <pid>`, systemd, Kubernetes | Terminate | Yes, so the program can clean up |
| `SIGKILL` | 9 | `kill -9`, or the OOM killer | Terminate at once | **No** |
| `SIGHUP` | 1 | The terminal closed; many daemons treat it as "reload config" | Terminate | Yes |
| `SIGCHLD` | 17 | A child process exited | Ignore | Yes |
| `SIGSTOP`, `SIGCONT` | 19, 18 | Pause and resume (`Ctrl+Z`, then `fg`) | Stop, continue | `SIGSTOP`: no |
| `SIGSEGV` | 11 | The program touched memory it does not own | Terminate with a core dump | Yes, rarely useful |

**Exit codes.** When a process ends it leaves one number for its parent:

| Exit code | Meaning |
| --- | --- |
| `0` | Success |
| `1`–`125` | The program chose to fail; each program documents its own codes |
| `126` | The file was found but is not executable |
| `127` | Command not found |
| `128 + N` | Killed by signal N: `130` = `Ctrl+C`, `137` = `SIGKILL`, `143` = `SIGTERM` |

Memorise `137` and `143`. In Kubernetes, a container that exits with `137` was killed with `SIGKILL`, very often by the OOM killer; `143` means it obeyed a polite `SIGTERM`.

**Graceful shutdown.** A well-written service catches `SIGTERM`, stops taking new work, finishes what it started and exits. In bash that is a `trap`:

```bash
trap 'echo "got TERM, cleaning up"; exit 0' TERM
```

Kubernetes relies on exactly this: to stop a container it sends `SIGTERM`, waits for the Pod's grace period (30 seconds unless you set `terminationGracePeriodSeconds`), and only then sends `SIGKILL`.

## How it works, part 4: CPU time and memory

The kernel shares CPU time by switching between runnable processes many times a second, and shares memory by giving every process a private, virtual view of it that the kernel maps onto real RAM.

**Scheduling.** The scheduler decides which runnable process gets a CPU core next and for how long. Since Linux 6.6 the kernel has been moving its default scheduler from CFS to EEVDF ([kernel docs](https://docs.kernel.org/scheduler/sched-eevdf.html)); it aims to give each process a fair share, weighted by its *nice* value (from −20, most favoured, to 19, least). `ps` and `top` show each process's state:

| State | Meaning |
| --- | --- |
| `R` | Running, or ready and waiting for a core |
| `S` | Sleeping until something happens, such as data on a socket; most processes, most of the time |
| `D` | Uninterruptible sleep, usually waiting for disk; even `SIGKILL` waits |
| `T` | Stopped by `SIGSTOP` or `Ctrl+Z` |
| `Z` | Zombie: finished, but the parent has not collected its exit code |

The *load average* in `uptime` is the average number of processes in state `R` or `D` over the last 1, 5 and 15 minutes. Compare it with your number of cores (`nproc`).

**Virtual memory.** Every process sees its own address space, as if it had the machine's memory to itself. The kernel splits memory into pages (4 KiB on x86-64) and keeps a table per process mapping its virtual pages to physical ones. A page is only given real memory when the program first touches it. That is why `ps` shows two sizes: `VSZ`, everything the process has mapped, and `RSS`, what is actually in RAM now.

**The page cache.** RAM that programs are not using is not wasted: the kernel fills it with recently read file data, so the next read is fast. `free -h` shows this as `buff/cache`; the `available` column is the number to watch, because the kernel gives cache back the moment programs need it.

**The OOM killer.** Linux lets programs reserve more memory than exists, betting they will not all use it. When memory really runs out, the out-of-memory (OOM) killer picks a victim, mostly by how much memory it uses, adjusted by its `oom_score_adj` (−1000 to 1000), and sends `SIGKILL`. With a memory limit on a group of processes (a *cgroup*, Ch 1.5), the OOM killer fires inside that group alone. That is exactly what a Kubernetes container memory limit is, and why an over-limit container dies with exit code `137` and the reason `OOMKilled`.

## Commands you will use in the lab

Install the one missing tool first: `sudo apt install -y strace`.

| Command | What it does | Example |
| --- | --- | --- |
| `strace -f -e trace=<calls> -o <file> <cmd>` | Run a command and log its system calls (`-f` follows child processes) | `strace -f -e trace=openat,read -o t.txt ls` |
| `strace -c <cmd>` | Count system calls instead of listing them | `strace -c ls /` |
| `ps -o pid,ppid,stat,comm` | Show chosen columns: ID, parent ID, state, name | `ps -o pid,ppid,stat,comm --ppid 1234` |
| `pstree -p`, `ps -ef --forest` | Show processes as a family tree | `pstree -p $$` |
| `top` | Live view of CPU and memory per process; `q` quits | `top` |
| `kill -<SIG> <pid>`, `kill -l` | Send a signal; list signal names | `kill -TERM 1234` |
| `trap '<cmd>' <SIG>` | Run a command when this shell receives a signal | `trap 'echo bye' TERM` |
| `<cmd> &`, `$!`, `wait`, `jobs`, `fg` | Run in the background; its PID; wait for it; list and resume jobs | `sleep 60 & echo $!` |
| `echo $?` | Exit code of the last command | `false; echo $?` |
| `free -h`, `uptime`, `nproc` | Memory use; load average; number of CPU cores | `free -h` |
| `cat /proc/<pid>/status` | A process's state, memory and IDs, as the kernel sees them | `grep -E 'State\|VmRSS' /proc/$$/status` |
| `systemd-run --user --scope -p MemoryMax=50M <cmd>` | Run a command inside its own cgroup with a memory limit, no root needed | used in Part D |

## In production

Four of the most common Kubernetes incidents are really this chapter's kernel behaviour wearing a Kubernetes label.

| What you see | What the kernel did | What engineers do |
| --- | --- | --- |
| Pod status `OOMKilled`, exit code `137` | The container used more memory than its limit, so the OOM killer sent `SIGKILL` inside its cgroup | Measure real memory use, then set the limit above the peak; check that the language runtime knows the limit, as some older runtimes sized their heap from the whole machine |
| Slow responses but low average CPU | The container hit its CPU limit; the kernel paused it until the next period (CPU *throttling*) | Watch throttling metrics, not only average CPU; many teams set CPU requests carefully and are cautious with CPU limits on latency-sensitive services |
| A Pod takes exactly 30 seconds to stop | The app ran as PID 1 and installed no `SIGTERM` handler, so the signal was ignored and the kubelet waited the full grace period before `SIGKILL` | Handle `SIGTERM` in the app, or run a tiny init such as `tini` (`docker run --init`) as PID 1 |
| `CrashLoopBackOff` | The process keeps exiting with a non-zero code; the kubelet restarts it with a growing delay, 10 s, 20 s, 40 s and so on, capped at five minutes by default | Read the exit code and the previous logs (`kubectl logs --previous`); the cause is in the process, not in Kubernetes |

**Why PID 1 is special.** Inside its PID namespace, a container's first process acts like `init`. The kernel only delivers a signal to an `init` process if it has a handler for that signal; `SIGKILL` and `SIGSTOP` from outside are the exceptions ([pid\_namespaces(7)](https://man7.org/linux/man-pages/man7/pid_namespaces.7.html)). PID 1 must also collect the exit codes of orphaned processes, or they pile up as zombies. A shell script or a web server started as PID 1 often does neither.
