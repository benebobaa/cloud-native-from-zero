## The problem: how replicas agree on one history when nodes and links fail

To survive the loss of a machine you keep copies of your data, and then every copy must apply the same changes in the same order, even while machines crash and messages vanish.

Lab 3.1 showed what happens without that guarantee: the AP register let two nodes accept different writes, and one write silently disappeared. For a wallet's balances that is unacceptable. For Kubernetes it is worse: the cluster's own record of what should be running must never fork into two versions. So Kubernetes stores everything in a small, strongly consistent database, **etcd**, built on a *consensus algorithm* called **Raft**.

The idea behind both is the *replicated state machine*. Take a program that is deterministic (the same inputs in the same order always give the same state). Run identical copies on several servers. Give each a *log*, an ordered list of the commands to apply. If every server applies the same log, every server ends in the same state. The whole problem therefore shrinks to one question: **how do servers agree on the contents and order of the log while some of them are failing?** That agreement is called *consensus*.

The answer rests on one piece of arithmetic. A *majority* of n servers is more than half of them. **Any two majorities of the same group share at least one server.** That shared server carries what the first majority decided into the second. Everything in Raft, and in Paxos before it, is built on that overlap.

**Why this matters for Kubernetes.** The Kubernetes documentation describes etcd as a "consistent and highly-available key value store used as Kubernetes' backing store for all cluster data" ([architecture overview](https://kubernetes.io/docs/concepts/architecture/)). Every Pod, Deployment and Secret you create ends up as keys in etcd. If etcd cannot elect a leader, the documentation is blunt about the effect: "a cluster cannot make any changes to its current state, which implies no new pods can be scheduled" ([Operating etcd clusters](https://kubernetes.io/docs/tasks/administer-cluster/configure-upgrade-etcd/)). Running containers keep running; nothing new can be decided.

## How it works, part 1: majorities

A *majority* of n servers is more than half of them: n/2 + 1, rounded down. A group that needs a majority to act keeps working while any minority fails, and it never acts on two sides of a partition at once, because only one side can hold a majority.

{{diagram ch-3-2-02.jsx | majority overlap · 5 servers}}

The table below is the etcd project's own ([etcd FAQ](https://etcd.io/docs/latest/faq/)). Look at the pairs: 3 and 4 members both survive one failure, but 4 needs three acknowledgements for every write, so the fourth member only costs you speed.

| Cluster size | Majority needed | Failures tolerated |
| --- | --- | --- |
| 1 | 1 | 0 |
| 2 | 2 | 0 |
| 3 | 2 | 1 |
| 4 | 3 | 1 |
| 5 | 3 | 2 |
| 6 | 4 | 2 |
| 7 | 4 | 3 |

The FAQ also says to use an odd number, because "an odd number of members guarantees that there will always be a majority partition" when the network splits in two, and that a cluster "probably should have no more than seven nodes" since every write must be copied to a majority. The Kubernetes documentation recommends five members in production and one only for testing ([Operating etcd clusters](https://kubernetes.io/docs/tasks/administer-cluster/configure-upgrade-etcd/)).

## How it works, part 2: leader election

Raft keeps exactly one leader at a time: followers wait for the leader's heartbeat, and a follower that hears nothing for a random time starts an election.

The algorithm comes from Diego Ongaro and John Ousterhout's paper *In Search of an Understandable Consensus Algorithm* ([USENIX ATC 2014](https://raft.github.io/raft.pdf)); every rule below is from its Figure 2 and section 5.2. Each server is a **follower**, a **candidate** or the **leader**. Time is cut into *terms*, numbered 1, 2, 3 and so on. A term is Lamport's logical clock applied to leadership: it only grows, and every message carries the sender's term.

{{diagram ch-3-2-03.jsx | Raft server states · 3 states, 6 transitions}}

1. **Followers** answer requests from the leader and from candidates. If an *election timeout* passes without a heartbeat from the current leader (and without granting a vote), the follower becomes a candidate.
2. A **candidate** adds 1 to its term, votes for itself, restarts its timer and sends `RequestVote` to every other server. If a majority vote for it in that term it becomes leader and sends heartbeats at once. If it hears from a server with an equal or higher term that claims leadership, it steps down. If the timer runs out with no winner (a *split vote*), it starts a new election in a higher term.
3. Each server grants **at most one vote per term**, first come first served, and only to a candidate whose log is at least as up to date as its own (section 5.4.1; part 3 explains this).
4. **Any** message with a higher term makes the receiver adopt that term and become a follower. This is how an old leader learns that it has been replaced.

Rules 1 and 3 give the *Election Safety* property of the paper's Figure 3: at most one leader can be elected in a given term, because two leaders would each need a majority, and two majorities share a voter who votes only once.

{{diagram ch-3-2-04.jsx | election after a leader crash · 3 servers, term 4 to 5}}

Read the timeline left to right. While S1 leads, it sends heartbeats and both followers reset their timers each time. When S1 crashes the timers keep running. S2's randomly chosen timeout is shorter, so S2 fires first, becomes a candidate in term 5 and asks for votes. S3 grants its vote and resets its own timer, which therefore never fires. S2 reaches a majority and starts heartbeats. The service was unavailable between the crash and the new leader.

**Why random timers.** If every follower used the same timeout they would all become candidates together, split the votes and repeat. The paper chooses timeouts "randomly from a fixed interval (e.g., 150–300ms)", which "spreads out the servers so that in most cases only a single server will time out". etcd uses the same idea: in its Raft library the timeout is drawn from the range from the election timeout up to twice that value ([etcd-io/raft](https://github.com/etcd-io/raft/blob/main/raft.go)), with defaults of a 100 ms heartbeat and a 1000 ms election timeout ([etcd tuning guide](https://etcd.io/docs/latest/tuning/)). With two followers left, the first to fire is the smaller of two random draws, so the expected outage is about 1.33 times the election timeout plus one vote round trip. Lab 3.2 measures it.

**Timing is where Raft depends on the clock.** The paper states the requirement as broadcastTime ≪ electionTimeout ≪ MTBF: a message round to all servers must be much shorter than the election timeout (so heartbeats arrive before timers fire), which must in turn be much shorter than the time between failures of one server (so the cluster is not constantly electing). The etcd guide turns that into rules: the heartbeat should be about the round-trip time between members, and election timeouts "must be at least 10 times the round-trip time"; the guide also warns that "an etcd cluster is very sensitive to disk latencies", because a slow disk delays heartbeats. Set the timeout too low and a slow disk or a busy network triggers needless elections; set it too high and a real crash takes long to repair.

## How it works, part 3: log replication and safety

Once a leader exists, a write is three steps: append to the leader's log, copy to the followers, apply when a majority has it.

Each *log entry* holds an index (its position), a term (the term of the leader that created it) and a command. The leader sends entries to followers in an `AppendEntries` message, which doubles as the heartbeat when it carries no entries. Every such message also names the entry just before the new ones (its index and term), and a follower accepts it only if its own log has that exact entry. If not, the follower refuses, the leader steps back one entry for that follower and retries, until the logs agree; the follower then overwrites whatever differs after that point. This is the *consistency check* of section 5.3.

{{diagram ch-3-2-05.jsx | log replication · 3 servers, 6 entries, commit at 5}}

The paper's definition of commitment is short: "A log entry is committed once the leader that created the entry has replicated it on a majority of the servers", which also commits every earlier entry in the leader's log. The leader reports its highest committed index in later `AppendEntries` messages, and each follower applies committed entries to its state machine in log order. A follower that is far behind or has been away can be sent a *snapshot* instead of every missed entry (section 7). Before answering, each server writes the entry to disk: the paper notes that Raft's messages "typically require the recipient to persist information to stable storage", which is why disk speed matters (see In production).

Five properties hold at all times (Figure 3 of the paper):

| Property | Meaning |
| --- | --- |
| Election Safety | At most one leader can be elected in a given term |
| Leader Append-Only | A leader never overwrites or deletes entries in its log; it only appends |
| Log Matching | If two logs contain an entry with the same index and term, the logs are identical in all entries up through that index |
| Leader Completeness | If an entry is committed in a given term, it is present in the logs of the leaders of all higher-numbered terms |
| State Machine Safety | If a server has applied an entry at an index to its state machine, no other server will ever apply a different entry for that index |

**Why committed entries survive leader changes.** Two rules combine. First, an entry is committed only when a majority hold it. Second, a server grants its vote only to a candidate whose log is at least as up to date as its own: "If the logs have last entries with different terms, then the log with the later term is more up-to-date. If the logs end with the same term, then whichever log is longer is more up-to-date." A candidate needs votes from a majority, and that majority overlaps the majority that holds the committed entry (the picture in part 1). At least one voter has the entry and will refuse a candidate whose log lacks it. So every possible winner holds every committed entry: Leader Completeness.

One subtlety deserves a sentence. A new leader may not decide that an entry left over from an *earlier* term is committed just because a majority holds it; the paper shows an example where such an entry can still be overwritten (section 5.4.2). "Raft never commits log entries from previous terms by counting replicas. Only log entries from the leader's current term are committed by counting replicas." Once a current-term entry commits, everything before it commits too. In Lab 3.2 you will see the log index rise by one after every election, which fits a new leader writing an entry of its own term first; we did not inspect that entry.

## How it works, part 4: etcd

etcd is a replicated state machine whose commands are key-value operations, so everything above (elections, logs, majorities) is hidden behind a simple interface.

{{diagram ch-3-2-06.jsx | etcd in a Kubernetes cluster · 3 members}}

The API server is the front end of the control plane and "scales by deploying more instances" ([architecture overview](https://kubernetes.io/docs/concepts/architecture/)); etcd holds the data behind it. Five ideas make etcd more than a map:

| Feature | What it gives you | You will see it in Lab 3.2 | Where Kubernetes uses it |
| --- | --- | --- | --- |
| Revisions | Every change gets a number from one cluster-wide counter, which is a total order of all changes; each key remembers its `create_revision`, `mod_revision` and `version` | `etcdctl get -w json` | Every object carries a `resourceVersion`, "the version of that resource as stored in the underlying persistence layer" ([API concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/)) |
| Watch | A stream of changes after a chosen revision; etcd replays history, then sends new events | `etcdctl watch /key --rev=2` | Controllers list objects, then watch from the returned `resourceVersion`; clusters using etcd 3 "preserve changes in the last 5 minutes by default" |
| Transactions | "If these conditions hold, do A, else do B", atomically: a compare-and-swap | `etcdctl txn` | The primitive behind optimistic concurrency: change an object only if nobody else changed it first |
| Leases | A key tied to a time limit; it vanishes unless the holder renews | `etcdctl lease grant`, `put --lease` | Leader election between copies of a controller: `kube-controller-manager` defaults to a 15 s lease, a 10 s renew deadline and a 2 s retry period ([reference](https://kubernetes.io/docs/reference/command-line-tools-reference/kube-controller-manager/)) |
| Snapshots | One consistent file of the whole database | `etcdctl snapshot save` | The standard backup ([Operating etcd clusters](https://kubernetes.io/docs/tasks/administer-cluster/configure-upgrade-etcd/)) |

etcd documents its guarantees precisely ([API guarantees](https://etcd.io/docs/latest/learning/api_guarantees/)). Operations are atomic and "occur in a total order, consistent with real-time order". Reads are *linearizable* by default: "Linearizability guarantees the read returns the most current value", and such reads go through Raft, which costs latency. A client may instead ask for a *serializable* read, which "may access stale data with respect to quorum" but is faster and is served by any single member. That is PACELC in one flag, and Lab 3.2 shows the serializable read still answering after quorum is lost. Watches are ordered by revision and do not silently drop events inside the retained history.

## Commands you will use in the lab

The lab uses `etcdctl`, the etcd command-line client that ships inside the etcd image, and the Docker commands from Lab 3.1. The etcd image contains no shell, so you run `etcdctl` with `docker exec`.

| Command | What it does | Example |
| --- | --- | --- |
| `etcdctl member list`, `endpoint status`, `endpoint health` | Who is in the cluster; each member's leader flag, Raft term and Raft index; whether it can commit a proposal | `docker exec etcd1 etcdctl --endpoints=etcd1:2379,etcd2:2379,etcd3:2379 endpoint status -w simple` |
| `etcdctl put <key> <value>`, `get <key>` (`--prefix`, `--rev=<n>`, `-w json`) | Write a key; read it (all keys with a prefix, an old revision, or with metadata) | `etcdctl get /wallet/greeting -w json` |
| `etcdctl watch <key> --rev=<n>` | Print every change to a key from revision n on, then keep waiting (Ctrl+C ends it) | `etcdctl watch /wallet/greeting --rev=2` |
| `etcdctl txn -i` | Atomic if-then-else: lines of comparisons, then success requests, then failure requests, each block ended by an empty line | see Part C |
| `etcdctl lease grant <seconds>`, `put <key> <value> --lease=<id>` | Create a lease; attach a key to it | `etcdctl lease grant 5` |
| `etcdctl get <key> --consistency=s` | A serializable read: answered by the member you ask, possibly stale | Part D |
| `etcdctl snapshot save <file>`, `etcdutl snapshot status <file>` | Back up the database; inspect a backup | Part E |
| `docker kill <n>`, `docker start <n>` | Crash a member; bring it back with its data | Part D |
| `python3 elect.py <trials> <label>` | Kill the leader repeatedly and time the outage | Part F |

## In production

Most etcd incidents are about time (disks and networks that are too slow for the timers) or space (a database that outgrew its quota), not about Raft itself.

| What you see | What really happens | What engineers do |
| --- | --- | --- |
| The API server is slow, and etcd leaders change often | "An etcd cluster is very sensitive to disk latencies. Competing disk activity can cause long `fsync` times, which can lead to missed heartbeats and temporary leader loss" ([etcd tuning](https://etcd.io/docs/latest/tuning/)) | Put etcd on fast, dedicated disks; Kubernetes advises running it "on dedicated machines or isolated environments"; raise its disk priority with `ionice` |
| Elections every few seconds (an *election storm*) with healthy machines | The election timeout is too short for the real network round trip, or heartbeats are delayed by CPU or disk starvation | Measure the round-trip time; heartbeat about equal to it, election timeout at least 10 times it, the same values on every member; then fix the starvation |
| Every write fails with `etcdserver: mvcc: database space exceeded`; reads and deletes still work | The database passed its space quota (2 GB by default, per the etcd FAQ), so etcd raised a `NOSPACE` alarm and accepts only reads and deletes ([maintenance guide](https://etcd.io/docs/latest/op-guide/maintenance/)) | Compact old revisions, defragment each member, then clear the alarm with `etcdctl alarm disarm`; find out why the keyspace grew. 8 GB is the suggested maximum |
| After two of three members died, nothing can be created or changed | No majority, so no leader can commit. Kubernetes states the effect: "no new pods can be scheduled" | Bring a member back; if its data is gone, restore from a snapshot taken earlier |
| Someone asks for 4 or 6 members "for safety" | Even sizes tolerate no more failures than the odd size below them and cost more per write | Run 3 for small clusters or 5 for production, as Kubernetes recommends; never more than 7 |

**Backups.** Kubernetes says plainly: "make sure you have a back up plan for the data". The built-in tool is `etcdctl snapshot save backup.db`, checked with `etcdutl snapshot status backup.db` ([maintenance guide](https://etcd.io/docs/latest/op-guide/maintenance/)). A backup you have never restored is a hope, not a backup: schedule a restore test.

## Project card: etcd

| Field | Content |
| --- | --- |
| Problem | Keep a small amount of critical data identical on several machines, survive the loss of a minority of them, and tell clients when the data changes |
| Layer / interface | The datastore under the Kubernetes API server. Clients use a gRPC API (key-value, watch, lease) with a JSON gateway (the Lab 3.2 timing script uses it); `etcdctl` is the command-line client and `etcdutl` works on files offline |
| Architecture | A cluster of 3 or 5 members running Raft: one leader accepts writes and copies a log to the followers; each member keeps a write-ahead log, snapshots and a versioned key-value store with revisions, watches, leases and transactions |
| Alternatives | **Consul**: Raft-based, adds service discovery and health checks; the docs recommend 3 or 5 servers ([consensus](https://developer.hashicorp.com/consul/docs/concept/consensus)). Pick it where an existing stack already depends on it. **A SQL database through K3s**: K3s can use SQLite, MySQL, MariaDB or PostgreSQL instead of etcd; SQLite "cannot be used on clusters with multiple servers" ([K3s datastore](https://docs.k3s.io/datastore)). Pick it for single-node or edge clusters |
