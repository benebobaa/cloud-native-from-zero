## The problem: keeping a fleet right when nobody is watching

A service with many processes drifts away from what you wanted all the time, so something must notice the difference and repair it, forever, without a human.

Chapters 3.1 and 3.2 were about data: how copies of state agree while machines and links fail. This chapter is about the machines and processes themselves. Your wallet now runs as several `wallet-worker` processes that settle transfers. Suppose you want three of them. You start three by hand. Then one crashes at 03:00, a laptop sleeps, a container is removed by mistake, or a colleague starts a fourth to debug something and forgets it. Each event is small. Together they mean the system you have is never quite the system you asked for.

The obvious fix is a script: "start three workers". That works once. Run it again and you have six. Make it smarter ("if one dies, start another") and it fails the first time it misses the death, for example because the script itself was restarted at that moment. Lab 3.3 shows both failures on your laptop.

The idea that works is old and simple. **Write down what you want, look at what you have, and fix the difference; then do it again.** That is a *control loop*, and a thermostat is the classic example. Kubernetes is built from dozens of them.

**Why this matters for Kubernetes.** Every object you create in Kubernetes is a written-down wish: "a Kubernetes object is a 'record of intent'--once you create the object, the Kubernetes system will constantly work to ensure that the object exists" ([Objects in Kubernetes](https://kubernetes.io/docs/concepts/overview/working-with-objects/)). The parts that do the constant work are *controllers*. When a node dies and its Pods come back elsewhere, no one ran a recovery script: a controller saw three Pods where it wanted four, and made one. This chapter builds that machine in about 70 lines of Python, so that in Vol 5 the real one holds no mystery.

## How it works, part 1: processes you can throw away

A loop can only repair a fleet if any process in it can be killed and replaced by a fresh copy without losing anything.

The *Twelve-Factor App*, a set of rules for building services written by Adam Wiggins from the team's "work on the Heroku platform", states the two properties that make this true. Factor VI: "Execute the app as one or more stateless processes"; "Twelve-factor processes are stateless and share-nothing. Any data that needs to persist must be stored in a stateful backing service, typically a database" ([processes](https://12factor.net/processes)). Factor IX: "The twelve-factor app's processes are disposable, meaning they can be started or stopped at a moment's notice" ([disposability](https://12factor.net/disposability)).

The same page asks for three behaviours, and the wallet worker has each:

| Rule from Factor IX | What the wallet worker does |
| --- | --- |
| "Processes should strive to minimize startup time." | Connects to Postgres and starts polling; no warm-up |
| "Processes shut down gracefully when they receive a SIGTERM signal from the process manager." | Catches `SIGTERM`, finishes the current batch, prints `stopped cleanly` (you met `SIGTERM` in Ch 1.2) |
| "Processes should also be robust against sudden death, in the case of a failure in the underlying hardware." | Settles each transfer inside one database transaction, so a `SIGKILL` halfway leaves the transfer `pending`, never half-applied |

The last row is the important one. All the worker's state lives in Postgres, and each change is all-or-nothing. A dead worker leaves nothing to clean up, and the replacement simply picks up the pending transfers. Two workers never take the same transfer, because the worker selects rows with `FOR UPDATE SKIP LOCKED`, which locks the rows it took and makes the others skip them. So the number of workers is a knob you can turn freely, which is exactly what a control loop needs.

## How it works, part 2: desired state and actual state

There are two ways to tell a system what to do: give it commands (*imperative*), or describe the result you want and let it work out the commands (*declarative*).

An imperative instruction is a verb: "start a worker", "stop that one". It is correct only for the state it was written against. Run it twice and it acts twice. A declarative instruction is a fact about the goal: "there should be three workers". It can be applied any number of times, and it says nothing about how many exist now. Something else has to compare it with reality.

{{diagram ch-3-3-02.jsx | imperative vs declarative · the same input applied twice}}

Read the two panels as one experiment: the same input is applied twice. The script has no idea what exists, so its second run doubles the fleet. The goal is compared with reality first, so its second application finds nothing to do.

Kubernetes names the two halves. "Almost every Kubernetes object includes two nested object fields that govern the object's configuration: the object spec and the object status". The *spec* is "its desired state"; "the status describes the current state of the object, supplied and updated by the Kubernetes system and its components" ([Objects in Kubernetes](https://kubernetes.io/docs/concepts/overview/working-with-objects/)). You write the spec. Controllers write the status and do the work in between.

The `kubectl` documentation describes both styles. With imperative commands "a user operates directly on live objects in a cluster", and "because this technique operates directly on live objects, it provides no history of previous configurations". With declarative configuration the user edits files, and "create, update, and delete operations are automatically detected per-object by kubectl" ([object management](https://kubernetes.io/docs/concepts/overview/working-with-objects/object-management/)). In Lab 3.3 the declarative record is one etcd key, `/wallet/desired`, holding a number.

## How it works, part 3: the reconcile loop

A controller repeats three steps forever: read the desired state, observe the actual state, and act to shrink the difference.

The Kubernetes documentation borrows the thermostat: "In robotics and automation, a control loop is a non-terminating loop that regulates the state of a system." You set the temperature (the desired state), the room has a temperature (the current state), and "the thermostat acts to bring the current state closer to the desired state, by turning equipment on or off" ([Controllers](https://kubernetes.io/docs/concepts/architecture/controller/)). The Kubernetes contributor guide gives the whole design in four lines of Go and one sentence ([Writing Controllers](https://github.com/kubernetes/community/blob/master/contributors/devel/sig-api-machinery/controllers.md)):

```go
for {
  desired := getDesiredState()
  current := getCurrentState()
  makeChanges(desired, current)
}
```

"Watches, etc, are all merely optimizations of this logic." The one pass of that loop is called *reconciling*, and Google used the same idea in all three of its cluster managers. The engineers who built them write: "The idea of a reconciliation controller loop is shared throughout Borg, Omega, and Kubernetes to improve the resiliency of a system: it compares a desired state (e.g., how many pods should match a label-selector query) against the observed state (the number of such pods that it can find), and takes actions to converge the observed and desired states" ([Burns et al., *Borg, Omega, and Kubernetes*, ACM Queue 2016](https://research.google.com/pubs/archive/44843.pdf)).

{{diagram ch-3-3-03.jsx | one reconcile pass · 4 steps, then wait}}

Read it left to right, then back along the top. The goal comes from etcd, the facts come from Docker, and only step 3 decides anything. Step 4 changes the world; the next pass sees the change and finds no difference.

Three properties make a reconcile pass safe to run again and again:

1. **It acts on the difference, not on events.** "Want 3, have 2" leads to one start. "Want 3, have 3" leads to nothing. A pass in a correct system is a no-op.
2. **It is idempotent.** An operation is *idempotent* when doing it twice has the same effect as doing it once (Ch 3.1 used the word for transfer ids). Running a whole pass twice in a row gives the same fleet as running it once, because the second pass sees no difference.
3. **It owns what it labels.** The loop must tell its own workers from everything else, or it will count and kill strangers. Kubernetes controllers use labels for this: "The Job controller does not delete the Pods that your Deployment created, because there is information (labels) the controllers can use to tell those Pods apart" ([Controllers](https://kubernetes.io/docs/concepts/architecture/controller/)). Your controller in Lab 3.3 only touches containers labelled `cnlab.role=wallet-worker`.

## How it works, part 4: level-triggered, not edge-triggered

A controller that reacts to *changes* breaks the first time it misses one; a controller that reacts to *the current state* cannot miss anything.

The terms come from electronics. An *edge-triggered* circuit acts when a signal changes; a *level-triggered* one acts on the signal's value. An edge-triggered controller says "a worker died, so start one". A level-triggered controller says "there are two workers and there should be three, so start one". They behave the same until an event is lost: a crash during a restart, a dropped connection, a full buffer. Then the edge-triggered controller is wrong forever, and the level-triggered one is right on its next pass.

{{diagram ch-3-3-04.jsx | level vs edge · one death while the controller is down}}

Read the drawing as one experiment run twice. A worker dies while the controller is restarting. The upper controller waits for an event, and the event has already gone by. The lower one only has to look at the state on its next pass, and the state still says "have 2".

The Kubernetes API conventions make this a rule. If a value "is changed from 2 to 5 in one PUT and then back down to 3 in another PUT the system is not required to 'touch base' at 5 before changing the status to 3. In other words, the system's behavior is *level-based* rather than *edge-based*. This enables robust behavior in the presence of missed intermediate state changes" ([API conventions](https://github.com/kubernetes/community/blob/master/contributors/devel/sig-architecture/api-conventions.md)). The controller guide puts it as advice: "Level driven, not edge driven. Just like having a shell script that isn't running all the time, your controller may be off for an indeterminate amount of time before running again."

Events are still useful, as a hint to look *now* instead of at the next tick. Real controllers do both: they watch for changes to react fast, and they also re-read everything from time to time in case a change was missed. You will measure what each part buys in Lab 3.3.

## How it works, part 5: many small loops, and what they do when things fail

Kubernetes is not one big controller but dozens of small ones, each owning one kind of object and creating objects that the next one owns.

"As a tenet of its design, Kubernetes uses lots of controllers that each manage a particular aspect of cluster state. ... It's useful to have simple controllers rather than one, monolithic set of control loops that are interlinked. Controllers can fail, so Kubernetes is designed to allow for that" ([Controllers](https://kubernetes.io/docs/concepts/architecture/controller/)). The built-in ones run inside one program, `kube-controller-manager`. A Deployment you create is turned into Pods by a chain of loops, and none of them calls the next one directly: each only writes objects through the API server and watches the objects it cares about.

The Borg authors call this "control through choreography—achieving a desired emergent behavior by combining the effects of separate, autonomous entities that collaborate", and explain why it survives failures: "Because all action is based on observation rather than a state diagram, reconciliation loops are robust to failures and perturbations: when a controller fails or restarts it simply picks up where it left off" ([Burns et al.](https://research.google.com/pubs/archive/44843.pdf)).

**When the desired state cannot be read.** A controller depends on a store such as etcd, and Ch 3.1 showed that a store under partition must choose between answering and being consistent. The controller faces the same choice one level up. If it cannot read `/wallet/desired`, it can stop everything (safe but harmful), or keep acting on the last value it saw (available, possibly stale). Good designs keep what already runs running. Borg's paper calls this "a key design feature": "already-running tasks continue to run even if the Borgmaster or a task's Borglet goes down" ([Verma et al., EuroSys 2015](https://research.google.com/pubs/archive/43438.pdf)). AWS calls the property *static stability*: "In a statically stable design, the overall system keeps working even when a dependency becomes impaired" ([AWS Builders' Library](https://aws.amazon.com/builders-library/static-stability-using-availability-zones/)). Your controller does this: if etcd does not answer, it keeps the last known value.

**Two copies of one controller.** You want the controller itself to survive a crash, so you run two copies. Now two loops see "want 3, have 2" at the same moment and both start one, and both may then stop one. The fix is to let only one copy act at a time: *leader election* with a lease, as you did with `/wallet/leader` in Lab 3.2. The controller guide recommends exactly this, and adds a warning: "Even leader election is imperfect; even when using leader election it is still possible --- although very unlikely --- that multiple copies of your controller may be active." Lab 3.3's Break it shows the fight; Milestone 3 asks you to end it.

## Commands you will use in the lab

The lab reuses the etcd cluster and helper functions from Lab 3.2, and adds Docker's label and event commands. A *label* is a `key=value` tag stuck on a container when it is created; filters select containers by it.

| Command | What it does | Example |
| --- | --- | --- |
| `docker run -d --label <k=v> --name <n> ...` | Start a container in the background with a label your controller can find | `docker run -d --label cnlab.role=wallet-worker --name ww-hand1 ... wallet:v1 python3 worker.py` |
| `docker ps -a --filter label=<k=v> --format '{{.Names}} {{.State}}'` | List every container with that label, running or not, one line each | the controller's *observe* step |
| `docker events --filter label=<k=v> --filter event=die` | Print a line each time a matching container stops; runs until Ctrl+C | the edge-triggered script, and the controller's `--events` hint |
| `docker kill <n>` / `docker stop <n>` / `docker rm <n>` | Crash a container with `SIGKILL`; stop it politely with `SIGTERM`; delete a stopped one | Parts B and C |
| `e put /wallet/desired <N>`, `e get /wallet/desired` | Write and read the desired state in etcd (`e` is the helper from Lab 3.2) | `e put /wallet/desired 5` |
| `python3 controller.py --interval <s> [--events]` | Run the reconcile loop: a pass every s seconds, and at once on a death if `--events` is set | Part C |
| `python3 measure.py <trials> <label> <controller args>` | Kill a worker repeatedly and time how long the repair takes | Part D |
| `docker stop etcd2 etcd3` | Take away etcd's majority, so nothing can be read with quorum | Part E |

## In production

Real control loops fail in a few repeating ways: they react too hard, they fight each other, or they trust a picture of the world that is wrong.

| What you see | What really happens | What engineers do |
| --- | --- | --- |
| After a database blip, every worker restarts at once and the database falls over again | All replacements hit the recovering dependency together. AWS: "When failures are caused by overload, retries that increase load can make matters significantly worse" ([Builders' Library](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)) | Back off and add *jitter*, randomness that "spread\[s\] the retries around in time". The kubelet restarts a crashing container "with an exponential backoff delay (10s, 20s, 40s, …), that is capped at 300 seconds"; that state is `CrashLoopBackOff` ([Pod lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)) |
| The replica count flips between two values every few minutes | Two writers own the same field. With an autoscaler on, "any time a change to that object is applied, for example via `kubectl apply -f deployment.yaml`", Kubernetes scales back to the file's value, "resulting in thrashing or flapping behavior" ([HPA docs](https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale/)) | Give every field exactly one owner: remove `replicas` from the file when an autoscaler owns it. For two copies of one controller, use leader election |
| A manual fix made with `kubectl edit` vanishes an hour later | The desired state in Git or in the manifest still says the old thing, and the next reconcile restores it (Vol 7 does this on purpose with GitOps) | Change the desired state, not the live object. Treat drift as a finding, not a fix |
| A controller uses a whole CPU and floods the API server with the same failing request | It retries an error at once, forever: a *hot loop* | Requeue with a rate limit; the guide says to "allow simple requeuing with reasonable backoffs" ([Writing Controllers](https://github.com/kubernetes/community/blob/master/contributors/devel/sig-api-machinery/controllers.md)) |
| Right after a restart, a controller deletes healthy objects | It acted before its local copy of the world was loaded, saw "nothing exists", and reconciled toward that | "Wait for your secondary caches" before the first pass, and never treat "I cannot see it" as "it does not exist" |
| The controller process is down; nothing breaks, but nothing heals | Static stability: what runs keeps running, but deaths are not repaired and changes are not applied | Run two copies with one leader; alert when the controller itself stops making progress |
