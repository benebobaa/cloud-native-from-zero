# Chapter 3.1 · Why Distributed Systems Are Hard

{{diagram ch-3-1-01.jsx | Ch 3.1 at a glance}}

## The problem: one machine fails whole, many machines fail in parts

A program on one machine either runs or has crashed; a program on many machines can be half broken, and nobody can tell which half.

A *distributed system* is a set of computers that cooperate only by sending each other messages, so that the user sees one service. Your wallet already is one: the API, the worker and Postgres are three programs that talk over a network. In 1987 Leslie Lamport put the danger in one sentence: "A distributed system is one in which the failure of a computer you didn't even know existed can render your own computer unusable" ([his message](https://lamport.azurewebsites.net/pubs/distributed-system.txt)).

Three things change when you leave one machine:

1. **Parts fail separately.** On one machine a crash takes every thread with it. Across machines one can die while the rest carry on, and the network between them can fail while every machine is healthy.
2. **There is no shared memory and no shared clock.** A machine knows only what messages tell it, and any message can be lost, delayed, duplicated or reordered.
3. **A silent machine is ambiguous.** When no reply arrives you cannot tell whether the machine is dead, slow, or its reply was lost. Everything else in this chapter follows from that one fact.

**Why this matters for Kubernetes.** A cluster is a distributed system: kubelets, the API server and etcd talk only through messages. When `kubectl get nodes` shows `NotReady`, the control plane has only stopped hearing from the node. It cannot know whether the node or the network failed, so by default it waits 50 seconds before marking the node unhealthy (`--node-monitor-grace-period`, [kube-controller-manager reference](https://kubernetes.io/docs/reference/command-line-tools-reference/kube-controller-manager/)). Every number like that 50 is a guess made under this chapter's uncertainty.

## How it works, part 1: the network lies

Every distributed program quietly assumes things about the network that are false, and eight such assumptions explain most outages. L. Peter Deutsch listed seven of them in 1994 and James Gosling added the eighth around 1997 ([history](https://en.wikipedia.org/wiki/Fallacies_of_distributed_computing)); they are called the *fallacies of distributed computing*.

| # | Fallacy: "the programmer assumes..." | Why it is false | Where you meet it |
| --- | --- | --- | --- |
| 1 | The network is reliable | Packets are dropped; links, switches and cables fail | Lab 3.1 Part C: a dropped link makes the wallet hang |
| 2 | Latency is zero | Every message takes time, and chatty protocols multiply it | Lab 3.1 Part B: 50 ms added delay costs the wallet 300 ms per request |
| 3 | Bandwidth is infinite | Links have a limit; big transfers queue behind small ones | Raft sends snapshots to slow followers (Ch 3.2) |
| 4 | The network is secure | Anyone on the path can read or forge traffic unless it is authenticated | Vol 6: mTLS, NetworkPolicy |
| 5 | Topology does not change | Machines and routes appear, vanish and move | A rescheduled Pod gets a new IP address (Vol 5) |
| 6 | There is one administrator | Different teams and providers own different parts | A managed database you cannot log in to |
| 7 | Transport cost is zero | Serialising, sending and paying for bytes costs CPU and money | Cross-zone traffic on a cloud bill |
| 8 | The network is homogeneous | Hardware, operating systems and protocol versions differ | A rolling upgrade runs two versions side by side |

The first two fallacies create the central problem of the chapter. Because a message may be lost or late, a sender who gets no reply cannot know what happened.

{{diagram ch-3-1-02.jsx | silence · four causes, one symptom}}

Read the four rows. In rows 1 and 2 the server did not finish the work. In rows 3 and 4 it did, but the client does not know. The client's only tool is a *timeout*, a guess that "no reply by now probably means failure". Every retry policy, every health check and every failover in this volume is built on such a guess.

The practical rule follows from rows 3 and 4: make operations safe to repeat. An operation is *idempotent* when doing it twice has the same effect as doing it once. The wallet's `POST /transfers` takes a client-chosen `id`, and a second request with the same `id` creates no second transfer. That one design choice is what makes a blind retry safe.

## How it works, part 2: how machines fail

A *failure model* is a promise about how components may misbehave; the weaker the promise you accept, the harder the algorithm and the more machines it needs.

| Model | What a failed machine does | Example | What tolerating it takes |
| --- | --- | --- | --- |
| Crash-stop | Stops for good | Power cut, node never repaired | A majority of machines still working |
| Crash-recovery | Stops, may restart with its disk but not its memory | Reboot, OOM kill and restart | Write state to disk before replying |
| Omission | Drops some messages it sends or receives | Full buffer, lossy link, partition | Acknowledgements and retries |
| Timing | Answers correctly but too late | Garbage-collection pause, swapping, a busy disk | Timeouts; to others it looks like a crash |
| Byzantine | Does anything, including lying | Bug, bit flip, attacker | At least 3f + 1 machines to tolerate f liars |

The last row is from Lamport, Shostak and Pease's 1982 paper on the Byzantine Generals: with oral messages, "no solution with fewer than 3m + 1 generals can cope with m traitors" ([paper](https://lamport.azurewebsites.net/pubs/byz.pdf)). Raft, and so etcd and Kubernetes, do not defend against Byzantine machines. The Raft paper states its assumption exactly: servers "are assumed to fail by stopping; they may later recover from state on stable storage and rejoin the cluster", and the network may suffer "delays, partitions, and packet loss, duplication, and reordering" ([Ongaro and Ousterhout, 2014](https://raft.github.io/raft.pdf)).

**Timeouts are the only failure detector, and they are guesses.** A machine can decide another is dead only because it heard nothing for a while. Fischer, Lynch and Paterson proved in 1985 that when message delay has no bound, "every protocol for this problem has the possibility of nontermination, even with only one faulty process" ([FLP, JACM 1985](https://groups.csail.mit.edu/tds/papers/Lynch/jacm85.pdf)); the problem is *consensus*, getting machines to agree on one value (Chapter 3.2). Real systems escape by assuming that delays are usually bounded. Raft shows the standard compromise: its safety never depends on timing ("They do not depend on timing to ensure the consistency of the logs"), but its progress does. Remember this split: **safety must hold even when clocks and networks misbehave; liveness may need them to behave.**

## How it works, part 3: clocks and ordering

Two machines never agree exactly on the time, so a distributed system must order events by the messages they exchange, not by the clocks they carry.

Every machine has a quartz clock that drifts, and a time service such as NTP corrects it, sometimes by stepping it, even backwards. Programs therefore have two clocks, and mixing them up is a classic bug:

- **Wall clock** (`time.time()` in Python): tells the date; can jump forwards or backwards when corrected. Never use it to measure how long something took, and never use it to order events on two machines.
- **Monotonic clock** (`time.monotonic()`): only moves forward; use it for durations on one machine. Its values mean nothing on another machine.

At midnight UTC on 1 January 2017 a leap second made Go's `time.Now()` go backwards on Cloudflare's servers. Their DNS code subtracted two readings to get a round-trip time, got a negative number, and crashed a random-number call; at the peak about 0.2% of DNS queries failed ([Cloudflare post-mortem](https://blog.cloudflare.com/how-and-why-the-leap-second-affected-cloudflare-dns/)). In Lab 3.1 you will make a wrong clock silently lose a write.

**Ordering without clocks.** In 1978 Lamport defined *happened before* (written a → b) from three rules: (1) if a and b are in the same process and a comes first, a → b; (2) sending a message happens before receiving it; (3) if a → b and b → c then a → c ([Lamport, CACM 1978](https://lamport.azurewebsites.net/pubs/time-clocks.pdf)). Two events with no such chain are *concurrent*: neither can have affected the other. This is a *partial* order, since concurrent pairs are not ordered at all.

{{diagram ch-3-1-03.jsx | Lamport clocks · 3 processes, 3 messages, 9 events}}

A *Lamport clock* is a counter per process that respects this order. In the drawing, b (2) is sent to P2 and received as d (3), so the counter grew. But c (1) has a smaller number than b (2) while being unrelated to it. To detect concurrency you need a *vector clock*: one counter per process, compared element by element. Amazon's Dynamo stores a vector clock with each version of an object to tell "this update replaces that one" from "these two updates conflict" ([Dynamo, SOSP 2007](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf)).

## How it works, part 4: CAP, PACELC and consistency

When the network splits a replicated service in two, each half must either answer with possibly old data or refuse to answer; that is all the CAP theorem says.

Eric Brewer conjectured it in a 2000 keynote: "You can have at most two of these properties for any shared-data system", the properties being Consistency, Availability and tolerance to network Partitions ([PODC 2000 slides](https://people.eecs.berkeley.edu/~brewer/cs262b-2004/PODC-keynote.pdf)). Seth Gilbert and Nancy Lynch proved a precise version in 2002 ([paper](https://www.comp.nus.edu.sg/~gilbert/pubs/BrewersConjecture-SigAct.pdf)). Their three definitions are the ones to use:

- **Consistency** means *atomic*, also called *linearizable*: "there must exist a total order on all operations such that each operation looks as if it were completed at a single instant." In practice, a read that starts after a write finished must return that write or a later one.
- **Availability** means "every request received by a non-failing node in the system must result in a response."
- **Partition tolerance** means "the network will be allowed to lose arbitrarily many messages sent from one node to another."

Theirs is *Theorem 1*: in the asynchronous network model it is impossible to implement a read/write object that is both available and atomically consistent in all executions, including those where messages are lost. The proof is the picture below.

{{diagram ch-3-1-04.jsx | CAP in one picture · 2 nodes, 1 partition}}

Read the drawing. Client A writes x = 1 to node 1; the copy to node 2 is lost; client B then reads from node 2. Node 2 cannot tell "nothing was written" from "a write is stuck behind the partition". It may answer 0, which is stale, or refuse. No algorithm escapes this, because the missing information is exactly what the partition removed.

**Reading CAP correctly.**

- *"Pick two of three" misleads.* You cannot pick "no partitions": links fail (fallacy 1). The real choice arises only while a partition lasts, and it is consistency or availability.
- *The definitions are strict.* "Available" means every non-failing node answers, including one stranded in a minority. A system that serves only the majority side is not "available" in CAP's sense, though most users never notice. Martin Kleppmann argues that, because of such gaps, CAP is of limited use for analysing real systems and proposes judging operation latency under network delay instead ([A Critique of the CAP Theorem, 2015](https://arxiv.org/abs/1509.05393)). Treat "CP" and "AP" as descriptions of behaviour in a partition, not as grades.
- *CAP is silent about normal operation.* Daniel Abadi: "CAP only posits limitations in the face of certain types of failures, and does not constrain any system capabilities during normal operation." Yet the tradeoff between consistency and latency "arguably has been more influential on DDBS design than the CAP tradeoffs" ([Abadi, IEEE Computer 2012](https://www.cs.umd.edu/~abadi/papers/abadi-pacelc.pdf)).

Abadi's fix is *PACELC* (said "pass-elk"): "if there is a partition (P), how does the system trade off availability and consistency (A and C); else (E), when the system is running normally in the absence of partitions, how does the system trade off latency (L) and consistency (C)?" Replicating data to several machines before answering costs latency, so a system that wants fast answers must sometimes answer from a replica that has not yet seen the latest write.

{{diagram ch-3-1-05.jsx | PACELC grid · 4 cells}}

The three quiet cells repeat Abadi's 2012 classification; systems change, so treat them as examples, not as current facts. The two bold entries are ours: etcd refuses writes without a majority (you will see it in Lab 3.2) and gives linearizable reads by default, and the wallet refuses requests when its one Postgres is unreachable (Lab 3.1). Both choose consistency over availability and over latency.

**Consistency is a spectrum.** "Consistent" can mean several things, and each weaker model gives something up so that the system can be faster or stay up in a partition:

| Model | The promise | Cost / typical user |
| --- | --- | --- |
| Linearizable | Each operation appears to take effect at one instant between its start and end; reads see the latest completed write ([Herlihy and Wing, 1990](https://cs.brown.edu/~mph/HerlihyW90/p463-herlihy.pdf)) | Needs coordination on every write; etcd, a single Postgres primary |
| Causal | If a happened before b, everyone sees a before b; concurrent updates may appear in different orders | Can stay available in a partition; some collaborative editors and geo-replicated stores |
| Eventual | If updates stop, "eventually all accesses will return the last updated value" ([Vogels, 2008](https://www.allthingsdistributed.com/2008/12/eventually_consistent.html)); no promise before that | Fastest and most available; DNS, Dynamo-style stores |

[Jepsen's consistency map](https://jepsen.io/consistency) names and relates many more models. When a vendor says "consistent", ask which row of this table they mean.

## Commands you will use in the lab

The lab needs eight tools, none used before. Docker only provides cheap, disposable machines here; Vol 4 explains how it works.

| Command | What it does | Example |
| --- | --- | --- |
| `docker network create <net>` | Make a virtual network on which containers reach each other by name | `docker network create cnlab-vol3` |
| `docker run -d --name <n> --net <net> <image> <cmd>` | Start a container in the background on that network | `docker run -d --name pg --net cnlab-vol3 postgres:17` |
| `docker run -d --net container:<n> --cap-add NET_ADMIN <image> sleep infinity` | Start a *sidecar* that shares container `<n>`'s network interfaces and firewall, so you can cut or slow that container's network without touching the container itself | `docker run -d --name api-net --net container:api --cap-add NET_ADMIN cnlab-nettools sleep infinity` |
| `docker exec <n> <cmd>` | Run a command inside a running container | `docker exec api-net curl -s localhost:8080/healthz` |
| `docker kill <n>`, `docker rm -f <n>`, `docker logs <n>` | Crash a container with SIGKILL; delete it; show what it printed | `docker logs api` |
| `curl -s --max-time <s> -o /dev/null -w '%{http_code} %{time_total}' <url>` | Time one HTTP request; give up after `<s>` seconds (status `000` = no answer at all) | `curl -s --max-time 5 -o /dev/null -w '%{http_code} %{time_total}' localhost:8080/readyz` |
| `tc qdisc add dev eth0 root netem delay 100ms` (or `loss 30%`; `replace` changes it, `del` removes it) | Delay or randomly drop every packet that leaves interface `eth0` | `tc qdisc replace dev eth0 root netem loss 100%` |
| `nft add table inet <t>`, `nft add chain ...`, `nft add rule ...`, `nft delete table inet <t>` | Firewall rules (nftables). `drop` discards a packet silently; `reject with tcp reset` refuses it loudly | `nft add rule inet cnlab out ip daddr 172.22.0.2 drop` |

Two more facts you need. `getent hosts <name>` prints the IP address behind a container name. And never run `nft flush ruleset` in these containers: it also deletes the rule Docker uses to resolve container names, and the container can no longer find its database (this happened while testing the lab). Delete only your own table.

## In production

Most real outages in distributed systems are one of this chapter's four problems (silence, partial failure, wrong clocks, or a forced consistency choice) wearing a product name.

| What you see | What really happened | What engineers do |
| --- | --- | --- |
| GitHub degraded for 24 h 11 min after a 43-second network loss (21 October 2018) | A brief loss of connectivity made the MySQL failover tool promote primaries in the other data centre. Each side then held writes the other lacked, so GitHub could not safely fail back ([post-incident analysis](https://github.blog/news-insights/company-news/oct21-post-incident-analysis/)) | Stop automatic promotion across regions; fail forward to protect data; add fault injection and chaos tests |
| About 0.2% of Cloudflare DNS queries failed at the peak of a leap second (1 January 2017) | A clock moved backwards, a time difference went negative, and code that assumed time never runs backwards crashed ([Cloudflare](https://blog.cloudflare.com/how-and-why-the-leap-second-affected-cloudflare-dns/)) | Use monotonic clocks for durations; never assume time only moves forward; review all interval code |
| A node flips between `Ready` and `NotReady` | Its heartbeats arrive late (a timing failure from load or a busy disk), so a healthy node is judged dead | Fix the load; tune the grace period only after you understand the delay (default 50 s) |
| A recovering service is knocked over again by its own clients | Every client timed out together and retried together | Exponential backoff **with jitter** ("The solution isn't to remove backoff. It's to add jitter", [AWS Architecture Blog](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/)) plus idempotent requests |
| Two workers both believe they hold the lock and both write | A lease expired while the first holder was paused; it woke up unaware and wrote stale data ([Kleppmann](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)). A Jepsen test of etcd 3.4.3 found its locks "fundamentally unsafe" ([report](https://jepsen.io/analyses/etcd-3.4.3)) | Fencing tokens: the lock service hands out an ever-increasing number and the storage layer rejects any write carrying an older one |

The etcd lock finding does not mean etcd's data is unreliable: the same report found reads, writes and transactions behaved as strict serializable, which includes linearizable. It means a lock built on timing (a lease) is a guess, and chapter 3.3 returns to this when controllers elect a leader.
