## The problem: one computer is not enough

Cloud native computing exists because modern services must keep running while machines fail, traffic changes by the minute, and teams ship code many times a day.

Picture the digital wallet you will build in this book. On day one it runs as one program on one laptop. Then it gets real users:

1. **Machines fail.** A disk dies or a power supply burns out. If the wallet lives on one machine, every user loses access.
2. **Load changes.** Payday brings ten times the normal traffic for a few hours. You cannot buy hardware for the peak and leave it idle the rest of the month.
3. **Teams change code daily.** Ten engineers ship fixes every day. Each release must reach users without downtime and roll back if it is broken.
4. **The system grows.** One program becomes an API, a database, a payment worker and a fraud checker, each owned by a different team.

The answer the industry arrived at has three ideas, and this whole book teaches them:

- **Package each program with everything it needs** so it runs the same on any machine. That package is a *container* (Vol 1 and Vol 4).
- **Treat many machines as one computer.** An *orchestrator* decides which machine runs which container, restarts what dies and moves work off failing machines. Kubernetes is that orchestrator (Vol 5).
- **Declare what you want, not how to get it.** You write "three copies of the wallet API must run". Software compares that *desired state* with the *actual state* and fixes the difference, forever. This is the *control loop* (Vol 3).

The Cloud Native Computing Foundation defines cloud native in the same spirit: technologies such as containers, service meshes, microservices, immutable infrastructure and declarative APIs that let teams build and run scalable applications in dynamic environments ([CNCF definition](https://github.com/cncf/toc/blob/main/DEFINITION.md)).

**Key idea.** Cloud native is not "running in someone else's data centre". It is a way of building software that expects failure and recovers from it automatically.

## History: sixty years of sharing a computer

Every step from mainframes to Kubernetes answers one question: how do we share hardware safely while wasting less of it?

{{diagram ch-0-1-02.jsx | history · four eras of sharing a computer}}

Notice two things. First, the isolation tricks Kubernetes depends on (chroot, namespaces, cgroups) are decades old; Vol 1 teaches them directly. Second, Kubernetes was not invented from nothing: it is Google's third cluster manager, after Borg and Omega ([Borg, Omega, and Kubernetes](https://queue.acm.org/detail.cfm?id=2898444)).

## The stack map

A request to the wallet passes through seven layers, and each layer is a part of this book.

{{diagram ch-0-1-03.jsx | the cloud-native stack · 7 layers, hardware to application}}

When something breaks in production, the first question is always: which layer? An engineer who knows only the top two layers can describe the symptom but cannot find the cause. That is why this book starts at the bottom.

**Two words you will need from now on.** The *kernel* is the core program of an operating system. It runs with full control of the hardware and shares the CPU, memory, disks and network among every other program. A *process* is one running program; the kernel keeps processes apart so one cannot read or crash another. Containers, which this book builds in Ch 1.5, are processes the kernel isolates more strongly.

## How the CNCF works, and why Kubernetes is built from plug-ins

The CNCF is a neutral home for open-source cloud-native projects, and its maturity level tells you how much to trust a project in production.

The Cloud Native Computing Foundation is part of the Linux Foundation. No single company owns a CNCF project; the foundation holds the trademark and the project's own maintainers decide its direction. Each project sits at one of three maturity levels ([CNCF project metrics](https://www.cncf.io/project-metrics/)):

| Level | CNCF's own description | What it means for you |
| --- | --- | --- |
| Sandbox | Experimental, not yet widely tested in production | Learn from it; do not bet a bank on it |
| Incubating | Used in production by a small number of users, healthy contributor pool | Reasonable for production with care |
| Graduated | Stable, widely adopted, production ready | The safe default; Kubernetes, etcd, containerd, Cilium and Argo are all here |

To move up a level, a project must show real adoption, contributors from more than one company and a security-practices badge, and convince the CNCF Technical Oversight Committee. Not every tool in this book is a CNCF project: Calico, Flannel and gVisor, for example, are open source but hosted elsewhere. The CNCF Landscape Map tab lists each project's level.

**The key idea: interfaces.** Kubernetes itself does not run containers, wire networks or attach disks. It defines a contract for each job and lets other projects fill it:

{{diagram ch-0-1-04.jsx | plug-in interfaces · API, CRI, CNI, CSI}}

- **Kubernetes API.** Any program can watch objects and act on them. Argo CD, Kyverno and KEDA are all just programs that do this (Ch 3.3, Ch 6.3, Ch 7.1, Ch 7.3).
- **CRI, the Container Runtime Interface.** The kubelet asks a runtime to start containers. containerd and CRI-O both implement it, so you can swap one for the other (Vol 4, Ch 5.5).
- **CNI, the Container Network Interface.** A plug-in gives each Pod an IP address and connects it. You build a tiny one by hand in Ch 2.5, then install Cilium in Ch 6.1.
- **CSI, the Container Storage Interface.** A driver creates and attaches disks (Ch 5.4).

Once you understand these four contracts, a new CNCF project stops being magic: you ask which interface it implements, and you already know half of how it works.

## The running case study: a digital wallet

You will build, run and operate one small digital-wallet app for the whole book, so every new layer solves a problem you have already felt.

A wallet is small enough to understand in an hour, yet it has the concerns real systems have: money must never be lost or counted twice, balances must be consistent, and every change must be auditable.

{{diagram ch-0-1-05.jsx | the digital wallet · 3 components}}

A user asks `wallet-api` to move money. The API records a *pending* transfer in Postgres and replies at once. `wallet-worker` picks up pending transfers and moves the money inside one database transaction, so a crash halfway never leaves money missing.

| Volume | What the wallet becomes |
| --- | --- |
| Vol 1 · Linux | Plain Linux processes, then a systemd service with logs in journald |
| Vol 2 · Networking | Reachable by name over HTTPS with a certificate you issue yourself |
| Vol 3 · Distributed systems | Several API copies; you watch what a network partition does to them |
| Vol 4 · Containers | Three container images run together with Compose |
| Vol 5 · Kubernetes | Deployments, a StatefulSet for Postgres, Services, ConfigMaps and Secrets |
| Vol 6 · Networking & security | Network policies, encrypted service-to-service traffic, signed images |
| Vol 7 · Platform | Deployed from git by Argo CD, observed with metrics and traces, autoscaled; survives the capstone chaos test |
