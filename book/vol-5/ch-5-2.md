# Chapter 5.2 · Workloads

{{diagram ch-5-2-01.jsx | Ch 5.2 at a glance}}

The five workload kinds differ in what they promise about their Pods: how many, how they are named, where they run, and when they stop.

## The problem

A Pod is a single, mortal copy of an application, so running a real service means a controller must keep the right Pods alive, in the right shape, all the time.

The Kubernetes documentation is blunt about it: a Pod is scheduled once in its life and is never "rescheduled" to another node ([Pod lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)). If the node dies, the Pod is gone. In Ch 5.1 you stopped the controller-manager, deleted a Pod, and nothing replaced it. A bare Pod has no one watching it.

The wallet already needs four different promises from the cluster:

1. **The API** is stateless. Run several identical copies, send traffic to the healthy ones, and replace them with a new version without dropping requests.
2. **The worker** is also stateless, but it takes no traffic. Run two copies and keep both alive.
3. **Postgres** is the opposite. It needs one stable name, one disk that follows it, and never two copies writing the same files.
4. **The nightly audit and the schema setup** run once and stop. A controller that restarts them forever would be a bug.

One controller cannot make all four promises, so Kubernetes ships one for each shape:

| Shape of the program | The question it asks | Object you write | What it creates |
| --- | --- | --- | --- |
| Stateless service | Keep N identical copies; replace them gradually | Deployment | a ReplicaSet per version, then Pods |
| Stateful service | Give each copy a stable name and its own disk; start them in order | StatefulSet | Pods named `name-0`, `name-1`, plus one PVC each |
| Per-node agent (log shipper, network plug-in) | Exactly one copy on every node | DaemonSet | one Pod per node |
| Task that ends | Run until it succeeds, retry on failure | Job | Pods that must finish |
| Task on a clock | Start a Job every night at a given time | CronJob | a Job per tick |

**Why this matters in production.** Almost every outage that starts with "the deploy broke it" is a mismatch between the promise a workload needed and the controller it was given: a database in a Deployment, a migration in a Deployment that restarts it forever, an agent that was meant to run once per node but runs where the scheduler likes. Picking the right object is the first design decision, before any YAML detail.

## How it works · Controllers, ownership and garbage collection

Every workload object is only a wish; a controller makes it true by creating other objects, and a field called ownerReferences records who made what.

In Ch 5.1 you met the reconcile loop: a controller *watches* objects, *compares* desired with actual state, and *acts* to close the gap. Controllers never call each other. They talk only by writing objects to the API server, and the next controller wakes up because it is watching for that object. Creating one Deployment of two Pods in Lab 5.1 produced this chain of events, each line written by a different component:

| Order | Event reason | Written by | Meaning |
| --- | --- | --- | --- |
| 1 | `ScalingReplicaSet` | deployment-controller | "Scaled up replica set web-5db6cf96 from 0 to 2" |
| 2 | `SuccessfulCreate` | replicaset-controller | "Created pod: web-5db6cf96-bmwtd" |
| 3 | `Scheduled` | default-scheduler | "Successfully assigned default/web-5db6cf96-bmwtd to cnlab-vol5-worker" |
| 4 | `Pulled`, `Created`, `Started` | kubelet | the container runs on that node |

The link that ties the chain together is `metadata.ownerReferences`. Each Pod carries a reference to its ReplicaSet, and each ReplicaSet to its Deployment. The lab printed them:

```text
$ kubectl get pod web-5db6cf96-678n8 -o jsonpath='{.metadata.ownerReferences}'
[{"apiVersion":"apps/v1","blockOwnerDeletion":true,"controller":true,"kind":"ReplicaSet","name":"web-5db6cf96","uid":"e5935e98-fb36-4c0b-a34b-08a7d270559e"}]
```

Three rules follow from this one field:

1. **A Pod has one controller owner.** `controller: true` marks the owner that manages it. A ReplicaSet acquires Pods that match its label selector and have no controller owner yet ([ReplicaSet](https://kubernetes.io/docs/concepts/workloads/controllers/replicaset/)). That is why you must never give two controllers overlapping selectors.
2. **Deleting an owner deletes its dependents.** The garbage collector does this in the background by default. Foreground deletion makes the owner wait for dependents that have `blockOwnerDeletion=true`. You can also *orphan* the dependents, which leaves them running ([Garbage collection](https://kubernetes.io/docs/concepts/architecture/garbage-collection/)).
3. **Labels are how an owner finds its children.** Change a Pod's labels so they no longer match and its owner stops counting it, and it creates a replacement.

{{diagram ch-5-2-02.jsx | ownership and deletion · measured in Lab 5.2 Part A}}

Read the three lanes top to bottom: the default delete removes the whole tree, `--cascade=orphan` removes only the top, and re-applying the same Deployment lets the surviving ReplicaSet find its new owner. Production teams use the orphan trick when they must recreate a Deployment (for example to change its immutable selector) without restarting any Pod ([Deployment docs](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)).

## How it works · ReplicaSets and Deployment rollouts

A Deployment never touches Pods itself; it moves replicas between ReplicaSets, one ReplicaSet for each version of the Pod template.

A **ReplicaSet** has three fields that matter: `replicas`, a label `selector`, and a Pod `template`. It counts the Pods that match the selector and creates or deletes Pods until the count equals `replicas`. You almost never write one by hand.

A **Deployment** adds history and a rollout policy on top. A rollout starts only when `.spec.template` changes (a new image, an environment variable, a probe). Changing `replicas` just scales the current ReplicaSet ([Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)). On a change the controller creates a new ReplicaSet and names it `<deployment>-<pod-template-hash>`. The controller adds the `pod-template-hash` label to every ReplicaSet it creates or adopts, and the docs say plainly: do not change it. The label keeps the selectors of old and new ReplicaSets from overlapping, which you can see in the lab output:

```text
$ kubectl -n wallet get rs
NAME                       DESIRED   CURRENT   READY   AGE   CONTAINERS   IMAGES      SELECTOR
wallet-api-ffd6cb76b       2         2         0       10s   api          wallet:v1   app=wallet-api,pod-template-hash=ffd6cb76b
wallet-worker-6cbdf67665   2         2         2       9s    worker       wallet:v1   app=wallet-worker,pod-template-hash=6cbdf67665
```

The rollout itself is a loop with two limits, `maxSurge` and `maxUnavailable`. Each can be a number or a percentage. A percentage of `maxSurge` rounds up, and one of `maxUnavailable` rounds down (`kubectl explain deploy.spec.strategy.rollingUpdate` says so). They cannot both be 0. The defaults are 25% and 25%, so the docs promise at least 75% of the desired Pods up and at most 125%.

1. Scale the new ReplicaSet up, never above `replicas + maxSurge` Pods in total.
2. Wait until the new Pods are *available*, which means their readiness probe passes.
3. Scale the old ReplicaSet down, never below `replicas - maxUnavailable` available Pods.
4. Repeat until the old ReplicaSet is at 0 and the new one is at `replicas`.

{{diagram ch-5-2-03.jsx | rolling update, 4 replicas · maxSurge 1, maxUnavailable 0}}

The readiness probe is the link between a rollout and your users. The controller trusts the probe to say when a new Pod can take traffic. A weak probe lets a broken version replace a working one at full speed.

The next chart shows the two settings on the same Deployment of four wallet-api Pods, drawn from watch events recorded in the lab:

{{diagram ch-5-2-04.jsx | measured with a Pod watcher in Lab 5.2 Part B · 2 runs, 4 replicas · rows in the widget}}

With 25% and 25% the controller was allowed one Pod above and one Pod below, so it started a replacement and removed an old Pod at the same time. The Ready count touched 3. With `maxSurge: 1, maxUnavailable: 0` it only removed an old Pod after a new one was Ready, so the Ready count stayed at 4 and the total never went above 5 non-terminating Pods. The price is time and spare capacity: one extra Pod's worth of CPU and memory during the update.

Why does each step take seconds? In the first run one new Pod was created, then scheduled 0.1 s later, spent 2.0 s creating its sandbox and starting the container, and then 1.8 s until its first passing readiness probe (the lab Deployment probes every 2 s). Each old wallet-api Pod then took about 2.4 s to leave, because the API handles SIGTERM and stops its server.

**Revisions and rollback.** The Deployment keeps old ReplicaSets, scaled to 0, so `kubectl rollout undo` can scale one back up. `.spec.revisionHistoryLimit` defaults to 10. In the lab a deliberately bad image (`wallet:nope`) produced this picture, and `undo` fixed it:

```text
$ kubectl -n wallet set image deploy/wallet-api api=wallet:nope
$ kubectl -n wallet get pods -l app=wallet-api
NAME                          READY   STATUS             RESTARTS   AGE
wallet-api-8454cbcd7c-z6x4p   0/1     ImagePullBackOff   0          31s
wallet-api-ffd6cb76b-hk5vk    1/1     Running            0          66s
wallet-api-ffd6cb76b-jxdf7    1/1     Running            0          67s
wallet-api-ffd6cb76b-pzsqk    1/1     Running            0          72s
wallet-api-ffd6cb76b-wndxt    1/1     Running            0          71s
$ kubectl -n wallet get deploy wallet-api
NAME         READY   UP-TO-DATE   AVAILABLE   AGE
wallet-api   4/4     1            4           3m13s
```

The controller stopped at one new Pod and kept four old Pods serving, because `maxUnavailable: 0` forbade removing any of them. `kubectl rollout status` waits, and after `progressDeadlineSeconds` (600 s by default) the Deployment reports that it failed to progress. It does **not** roll back by itself. A pipeline must watch for that and call `rollout undo`.

**Other strategy.** `strategy.type: Recreate` kills every old Pod before it creates a new one. It causes downtime, and you choose it only when two versions must never run at the same time.

## How it works · Pod lifecycle, probes and termination

A Pod moves through a few phases, but what your users feel is decided by three probes and by how the process reacts to SIGTERM.

The Pod phase is a coarse summary ([Pod lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)):

| Phase | Meaning (from the docs) |
| --- | --- |
| `Pending` | accepted by the cluster, but one or more containers is not set up and ready to run |
| `Running` | bound to a node, all containers created, at least one running or starting or restarting |
| `Succeeded` | all containers ended in success and will not restart |
| `Failed` | all containers ended and at least one ended in failure |
| `Unknown` | the state of the Pod could not be obtained |

What `kubectl get pods` prints in the STATUS column is richer. `CrashLoopBackOff`, `ImagePullBackOff`, `OOMKilled` and `Terminating` are not phases; they are reasons the tooling shows for a container or a deletion.

**Restarts.** The Pod's `restartPolicy` is `Always` (the default), `OnFailure` or `Never`. A Deployment allows only `Always`. A Job uses `OnFailure` or `Never`. The *kubelet* on the Pod's node performs the restart, inside the same Pod on the same node: it makes a replacement container, not a replacement Pod. After a crash it waits 10 s, then 20 s, 40 s and so on, capped at 300 s, and it resets the delay after the container has run 10 minutes without a problem. In the lab a Pod with a 50 MiB limit that allocates memory in a loop showed exactly the Ch 1.2 story, now in Kubernetes words:

```text
$ kubectl get pod hungry
NAME     READY   STATUS      RESTARTS      AGE
hungry   0/1     OOMKilled   2 (24s ago)   26s
$ kubectl get pod hungry -o jsonpath='{.status.containerStatuses[0].lastState.terminated}'
{"exitCode":137,"reason":"OOMKilled", ...}
```

**Probes.** The kubelet runs up to three kinds of probe against each container. A probe uses one mechanism: an HTTP GET, a TCP connect, a command inside the container, or gRPC ([Pod lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/), [probe tasks](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/)).

| Probe | The question it answers | When it fails | Runs |
| --- | --- | --- | --- |
| startup | Has the application finished starting? | the kubelet kills the container and applies the restart policy | only at startup; liveness and readiness wait for it |
| liveness | Is the process stuck? | the kubelet restarts the container | the whole life |
| readiness | Can it take traffic now? | the EndpointSlice controller removes the Pod's IP from every matching Service; no restart | the whole life |

Each probe has the same dials: `initialDelaySeconds`, `periodSeconds`, `timeoutSeconds` (the docs say it defaults to 1 s) and `failureThreshold`. The wallet uses two different endpoints on purpose. `/healthz` answers 200 if the process is alive and never touches the database. `/readyz` answers 200 only if Postgres is reachable. Readiness may depend on the database, because sending traffic to an API that cannot reach it only produces errors. Liveness must not: restarting every API Pod does not bring a database back.

The next timeline shows what a failing liveness probe really costs. A Pod served `/ok` for about 20 s, then the file vanished. Readiness failed first, so the Pod left the Service. Three liveness failures later the kubelet killed the container. Yet the new container only started 30 s after that:

{{diagram ch-5-2-05.jsx | measured in Lab 5.2 Part D · flaky Pod, events and polling}}

The kubelet kept to the rules; the program did not. The process in this Pod was `python3 -m http.server` running as PID 1, and PID 1 has no default signal handlers: it ignores SIGTERM unless the program installs a handler (Ch 1.2). The kubelet therefore waited out `terminationGracePeriodSeconds`, which defaults to 30 s, then sent SIGKILL. The `Killing` event is at 28 s and the new container's `Created` event is at 58 s.

**Termination sequence.** The same path runs for a rolling update, a scale-down, a drain and `kubectl delete pod` ([Termination of Pods](https://kubernetes.io/docs/concepts/workloads/pods/pod-termination/)):

1. The API server records the deletion and the grace period. The Pod shows `Terminating`.
2. A `preStop` hook, if there is one, runs first.
3. The kubelet sends SIGTERM to the main process of each container.
4. At the same time the control plane removes the Pod from the Services' EndpointSlices. Step 3 does not wait for this, so a few requests can still arrive after the signal.
5. After the grace period expires, the kubelet sends SIGKILL to whatever remains.
6. The Pod object is removed.

A program that handles SIGTERM, stops accepting new connections and finishes the work in flight leaves in a second or two. The wallet API does that: during the rollout above each old Pod stayed `Terminating` for about 2.4 s. A program that ignores it holds every rollout, drain and restart for 30 s.

**Init containers and sidecars.** *Init containers* run one after another to completion before the app containers start. Use them for "wait for the database" or one-time setup. A *sidecar* is an init container with `restartPolicy: Always`: it starts before the app, keeps running next to it, and is stopped after it. Native sidecars are stable since Kubernetes v1.33 ([init containers](https://kubernetes.io/docs/concepts/workloads/pods/init-containers/), [sidecar containers](https://kubernetes.io/docs/concepts/workloads/pods/sidecar-containers/)).

## In production

Most workload incidents are one of these patterns, and each one can be reproduced in Lab 5.2.

| Symptom | Real cause | What engineers do |
| --- | --- | --- |
| A deploy "hangs": `kubectl rollout status` keeps waiting, the new Pod is `ImagePullBackOff` or `0/1`, users see nothing wrong | The controller will not remove an old Pod until a new one is available (Lab 5.2 Part B). After `progressDeadlineSeconds` (default 600) the Deployment reports `ProgressDeadlineExceeded`, but it keeps retrying and never rolls back ([Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)). | The pipeline runs `kubectl rollout status --timeout=...` and calls `kubectl rollout undo` when it fails. They read the new Pod's Events first. |
| The deploy finished, every Pod is `1/1 Ready`, and users get errors | The readiness probe was too weak (an open port, or "the process is alive"), so a broken version replaced a working one at full speed. `minReadySeconds` defaults to 0, so a Pod counts as available the moment it is Ready ([Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)). Reproduced in Break it. | Readiness exercises the real request path. `minReadySeconds` makes a new Pod stay Ready for a while before the rollout goes on. Error rate is watched during every rollout. |
| Every API Pod restarts together when the database has a short outage, and restarts pile up | The liveness probe checks the database. The kubelet restarts healthy processes, which cannot fix a database (measured in Lab 5.2 Part D). | Liveness checks only the process. Readiness may check dependencies. A `startupProbe` covers slow starts, for example 30 tries every 10 s gives 300 s ([probe tasks](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/)). |
| `CrashLoopBackOff`, with longer and longer gaps between restarts | The container keeps exiting. The kubelet restarts it with a delay of 10 s, 20 s, 40 s and so on, capped at 300 s, and resets the delay after 10 minutes without a problem ([Pod lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)). | They read the exit code and `Last State` in `kubectl describe pod`, and the container logs. A crash on start-up is usually a missing config value or an unreachable dependency. |
| `OOMKilled`, exit code 137, restart count grows, no error in the application log | The container passed its memory limit and the kernel ended it, as in Ch 1.2. It looks like a restart, not a crash, because the process got no warning (measured in Lab 5.2 Part D). | They compare real memory use with the limit, then raise the limit or fix the leak. They set requests close to real use so the scheduler places Pods honestly. |
| Pods vanish from a node under memory or disk pressure | Node-pressure eviction: the kubelet ends Pods to protect the node. A hard threshold such as `memory.available<100Mi` ends them with no grace period. Pods using more than their requests go first, then lower Priority ([node-pressure eviction](https://kubernetes.io/docs/concepts/scheduling-eviction/node-pressure-eviction/)). | They read the node's conditions with `kubectl describe node`, set requests from measured use, and keep critical Pods at their requests so they are evicted last. The controller replaces the evicted Pods; nothing else does. |
| `kubectl drain` never finishes during an upgrade | A PodDisruptionBudget allows zero voluntary evictions, for example `minAvailable` equal to the replica count. "The drain never completes" is the documented behaviour ([PDB task](https://kubernetes.io/docs/tasks/run-application/configure-pdb/)). | They set a budget that leaves room for one eviction (the wallet uses `minAvailable: 1` with 2 replicas). A one-replica service accepts brief downtime or gets a second replica. |
| A Pod always takes 30 s to stop; rollouts and drains are slow | PID 1 ignores SIGTERM, so the kubelet waits out `terminationGracePeriodSeconds` and sends SIGKILL (measured in Lab 5.2 Part D). Often a shell wrapper is PID 1 and does not pass the signal on. | They start the program with `exec`, handle SIGTERM, and use a `preStop` hook only for work the program cannot do itself ([Pod termination](https://kubernetes.io/docs/concepts/workloads/pods/pod-termination/)). |
| A CronJob did not run, or ran twice | Jobs can start "at least once", so they must be idempotent. After more than 100 missed schedules the controller stops catching up and records `TooManyMissedTimes` ([CronJob](https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/)). Finished Jobs also stay until `ttlSecondsAfterFinished` removes them ([Job](https://kubernetes.io/docs/concepts/workloads/controllers/job/)). | They write idempotent jobs (the wallet's transfer ids already are), set `concurrencyPolicy` and `startingDeadlineSeconds`, and set a TTL on Jobs. |

## Going deeper (optional)

**PodDisruptionBudgets.** A rollout is not the only thing that removes Pods. A node drain does too, and a PodDisruptionBudget (PDB) tells the drain how many Pods of one application may be down at once. PDBs are stable since Kubernetes v1.21 ([Disruptions](https://kubernetes.io/docs/concepts/workloads/pods/disruptions/)). The wallet ships this one for the API:

```text
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: {name: wallet-api, namespace: wallet}
spec:
  minAvailable: 1
  selector:
    matchLabels: {app: wallet-api}
```

Five rules from the [PDB task page](https://kubernetes.io/docs/tasks/run-application/configure-pdb/) and the [Disruptions page](https://kubernetes.io/docs/concepts/workloads/pods/disruptions/) explain most surprises:

1. **Voluntary only.** A budget limits evictions made through the Eviction API, which `kubectl drain` uses. It cannot stop a node failure or a kernel panic.
2. **Deleting bypasses it.** Deleting a Pod or a Deployment directly is not constrained by a PDB.
3. **Rollouts ignore it.** Pods removed by a rolling update count against the budget, but a Deployment's update is limited by its own `maxUnavailable`, not by the PDB.
4. **Zero means stuck.** With `minAvailable` equal to the replica count, or `maxUnavailable: 0`, a drain of a node running one of those Pods never completes. Ch 5.5 shows the drain retrying against the wallet's budget.
5. **Percentages round up.** `minAvailable: "50%"` of 7 Pods means 4 must stay. A percentage `maxUnavailable` also rounds up, so a disruption can exceed the percentage you wrote.

The default `unhealthyPodEvictionPolicy` is `IfHealthyBudget`: a Pod that is Running but not yet healthy can be evicted only while the budget is still met. The docs recommend `AlwaysAllow` so a drain can remove misbehaving Pods.

**Pod lifecycle details** that this chapter only touched: the restart delay cap of 300 s is a default that a node can lower with the kubelet setting `crashLoopBackOff.maxContainerRestartPeriod` (beta since v1.35, on by default), and the alpha gate `ReduceDefaultCrashLoopBackOffDecay` starts delays at 1 s with a 60 s cap ([Pod lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)). A `preStop` hook must finish before SIGTERM is sent, and its time counts against the grace period; if it overruns, the kubelet grants one extra 2 s ([Pod termination](https://kubernetes.io/docs/concepts/workloads/pods/pod-termination/), [lifecycle hooks](https://kubernetes.io/docs/concepts/containers/container-lifecycle-hooks/)).
