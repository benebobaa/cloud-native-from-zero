# Chapter 5.5 · Cluster Operations

## At a glance

{{diagram ch-5-5-01.jsx | Ch 5.5 at a glance · six jobs, two graded by Milestone 5}}

Read the snake from 1 to 6: build the cluster, make its certificates trustworthy, give it a runtime, protect its state, empty nodes safely, and fix what breaks.

## The problem

**A real cluster has six jobs that `kind` hides from you: build it, trust it, run containers on it, back it up, empty nodes of it, and repair it.** In Ch 5.1 to 5.4 `kind` built a cluster in about 30 seconds. On two Ubuntu VMs nobody does that for you, and on a production cluster the same six jobs repeat for years.

Each job has a failure that stays silent until it hurts:

1. **Build.** A control plane is four programs, a set of certificates and a kubelet that starts them. By hand that is a long, error-prone recipe. `kubeadm` is the standard script for it.
2. **Trust.** Every component proves who it is with an X.509 certificate. Client certificates made by kubeadm expire after 1 year ([kubeadm certs](https://kubernetes.io/docs/tasks/administer-cluster/kubeadm/kubeadm-certs/)). A cluster that nobody upgraded for a year stops answering its own components.
3. **Run.** The kubelet does not start containers itself. It asks a container runtime through the CRI. When that runtime is stuck, `kubectl` can still look fine while Pods do not start.
4. **Back up.** All cluster state lives in etcd. If the data is lost, the API server cannot start. The kubelets keep running the Pods they already have, but nothing can be changed until someone restores the data ([cluster failure modes](https://kubernetes.io/docs/tasks/debug/debug-cluster/)).
5. **Empty nodes.** Kernels need patches, so nodes must be emptied. We measured the cost. Draining a node cleanly failed 0 of 33 probe requests. Draining the node that holds Postgres on node-local storage failed 104 of 119.
6. **Repair.** When something breaks you need an order of checks, not a web search.

The wallet makes this concrete. Milestone 5 asks for an etcd backup you have restored and a node drain the wallet survives. Both look easy in a diagram. Both have a catch that you will meet in the lab.

## How it works · kubeadm builds a control plane in a fixed order of phases

**`kubeadm init` does not run the control plane. It writes files and lets the kubelet start them.** That is the key idea. The kubelet reads a *static Pod path* (`staticPodPath: /etc/kubernetes/manifests` in `/var/lib/kubelet/config.yaml`) and runs every Pod manifest it finds there, with no API server involved. A *static Pod* is such a Pod. So the control plane can start before any API server exists.

We ran `kubeadm init --dry-run` with kubeadm v1.37.0 on a kind node and kept the transcript. It prints each phase as a bracketed tag. The first five phases only write files under `/etc/kubernetes`. The rest talk to the API server that the kubelet started.

{{diagram ch-5-5-02.jsx | kubeadm init phases · transcript of kubeadm v1.37.0 init --dry-run on a kind node, 2026-11-16}}

Two phases deserve a closer look.

- **`[mark-control-plane]`** gives the node the taint `node-role.kubernetes.io/control-plane:NoSchedule`. That is why ordinary Pods do not land on the control-plane node.
- **`[bootstrap-token]`** is what lets other machines join. The transcript shows kubeadm creating RBAC rules so that bootstrap tokens can post certificate signing requests, so that the `csrapprover` controller approves them automatically, and so that node client certificates can rotate.

**Joining a node.** The last lines of `kubeadm init` print the join command. Its form, from [Creating a cluster with kubeadm](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/create-cluster-kubeadm/):

```text
kubeadm join <control-plane-host>:<control-plane-port> --token <token> --discovery-token-ca-cert-hash sha256:<hash>
```

The token is a *bootstrap token*, "used for establishing bidirectional trust between a node joining the cluster and a control-plane node" ([kubeadm token](https://kubernetes.io/docs/reference/setup-tools/kubeadm/kubeadm-token/)). `kubeadm init` creates one with a 24-hour TTL. After it expires, `kubeadm token create --print-join-command` makes a new one. The hash lets the joining node check that it talks to the right control plane before it sends the token.

**The network add-on.** Cluster DNS "will not start up before a network is installed", so a new kubeadm cluster needs a CNI plug-in (Vol 6). In `kind` the plug-in, kindnet, is installed for you.

**High availability.** One control-plane node is one failure away from an outage. kubeadm supports two layouts ([HA topology](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/ha-topology/)).

| Layout | etcd runs | Minimum hosts | Trade-off |
| --- | --- | --- | --- |
| Stacked etcd (kubeadm default) | On each control-plane node | 3 control-plane nodes | Simpler. Losing one node loses an etcd member and an API server together. |
| External etcd | On separate hosts | 3 control-plane and 3 etcd hosts | Failure domains are separate. Twice the hosts. |

See Field Guide → 1 · Architecture → kubeadm and cluster bootstrap for the field-by-field card.

## How it works · certificates: three CAs, eleven leaves, one year

**kubeadm creates three certificate authorities and eleven leaf certificates. Each leaf expires 1 year after creation unless something renews it.** An X.509 certificate binds a name to a public key and carries the signature of a *certificate authority* (CA). A component trusts a peer when the peer's certificate was signed by a CA it knows. Every connection inside the control plane, and every `kubectl` call, depends on this.

`kubeadm certs check-expiration` lists them. This is real output from the control-plane node of our test cluster, minutes after `kind` built it:

{{diagram ch-5-5-03.jsx | kubeadm certificate tree · from kubeadm certs check-expiration on a new kind cluster, 2026-11-16}}

The `kubeadm-config` ConfigMap of the same cluster says `certificateValidityPeriod: 8760h0m0s` and `caCertificateValidityPeriod: 87600h0m0s`. The `.conf` rows are client certificates embedded in kubeconfig files, so `admin.conf`, the file behind your own `kubectl`, expires too.

Three rules keep a cluster from going dark ([kubeadm certs](https://kubernetes.io/docs/tasks/administer-cluster/kubeadm/kubeadm-certs/)):

1. **Upgrades renew.** "kubeadm renews all the certificates during control plane upgrade." A cluster upgraded at least once a year never expires. Pass `--certificate-renewal=false` to opt out.
2. **Manual renewal exists.** `kubeadm certs renew all` renews them. On a replicated control plane run it on every control-plane node.
3. **Renewal needs a restart.** The control-plane Pods must be restarted afterwards, because not every component reloads certificates on its own. Static Pods cannot be restarted with `kubectl`. Move the manifest out of `/etc/kubernetes/manifests/`, wait 20 seconds, and move it back.

The kubelet is the exception. kubeadm sets it up for automatic renewal with rotatable certificates under `/var/lib/kubelet/pki`, which is why `kubelet.conf` is not in the list.

## How it works · the container runtime behind the CRI

**The kubelet never starts a container itself. It sends calls over the Container Runtime Interface (CRI) to a runtime on a Unix socket, and the runtime does the work.** The CRI is a gRPC API. Anything that speaks it can be a runtime.

{{diagram ch-5-5-04.jsx | CRI layers · socket paths and config files from kubernetes.io container-runtimes page, version from crictl on a kind node}}

Three facts from [Container Runtimes](https://kubernetes.io/docs/setup/production-environment/container-runtimes/) matter for an operator:

- **CRI v1 is mandatory.** "Kubernetes 1.37 requires that you use a runtime that conforms with the Container Runtime Interface (CRI)." If a runtime does not support v1, "the kubelet will not register as a node."
- **Dockershim is gone.** The special built-in Docker Engine support was removed in Kubernetes 1.24. The runtimes page lists containerd, CRI-O, Docker Engine and Mirantis Container Runtime. Most clusters use containerd or CRI-O.
- **The cgroup driver must match.** "It's critical that the kubelet and the container runtime use the same cgroup driver." With cgroup v2, use `systemd`. The kubelet on our kind node says `cgroupDriver: systemd`. In 1.37 the `KubeletCgroupDriverFromCRI` feature gate lets the kubelet ask the runtime instead. The page warns that in 1.38 "this fallback behavior will be dropped, and older versions of containerd will fail with newer kubelets."

You can look through the CRI yourself with `crictl`. These are real views from the worker node of the test cluster (the wallet was running):

(The tables are trimmed to the columns that fit. `crictl ps` showed exactly these four containers, and `crictl pods` more Pods than the two shown.) Note the two levels. `crictl pods` lists *Pod sandboxes*, the shared network and namespaces of a Pod. `crictl ps` lists the containers inside them. `kubectl` shows the Pod. `crictl` shows what the runtime did about it.

Why this view matters: when `kubectl get nodes` says `NotReady` or a Pod stays in `ContainerCreating`, the API is fine and the fault is below it. `crictl` is how you ask the layer below. The runtime's address is one line in the kubelet's configuration (`containerRuntimeEndpoint: unix:///run/containerd/containerd.sock` on our nodes), which is why swapping runtimes is a per-node operation (Lab 5.5 part D).

## How it works · etcd backup and restore

**All cluster state is one etcd database, so a snapshot of etcd is a backup of the cluster.** Deployments, Secrets, ConfigMaps, PVC objects and the rest are keys in etcd (Ch 5.1, Lab 5.1 part B). A snapshot is one file. Restoring it puts the cluster back to the moment it was taken.

{{diagram ch-5-5-05.jsx | etcd snapshot and restore · measured on a kind cluster, etcd 3.7.0, 2026-11-16}}

The tested sequence, in four steps ([Operating etcd clusters for Kubernetes](https://kubernetes.io/docs/tasks/administer-cluster/configure-upgrade-etcd/)):

1. **Save** from a live member. The page says this "will not affect the performance of the member". We ran `etcdctl` inside the etcd Pod, with the certificates from its manifest.
2. **Check** the file with `etcdutl snapshot status`. It prints a hash, the etcd revision, the key count and the size.
3. **Restore** with `etcdutl snapshot restore --data-dir <new-dir>`. This only writes files. It does not touch the running etcd. In the lab we added --bump-revision 1000000000 --mark-compacted, two etcd 3.7.0 flags: without them kube-proxy kept a stale view of the cluster after the restore (Lab 5.5, B4).
4. **Switch** etcd to the new directory. For a kubeadm cluster etcd is a static Pod, so you edit its manifest. The page changes `volumes.hostPath.path` for `etcd-data`. We changed the `--data-dir` flag to a sub-directory of the same mount, which has the same effect. On a kubeadm cluster, also set `etcd.local.dataDir` in the `kubeadm-config` ConfigMap, or the next `kubeadm upgrade` writes a manifest for the old directory.

The measured result is in the diagram. A ConfigMap created after the snapshot was gone after the restore. A ConfigMap deleted after the snapshot was back. Nothing else in the cluster needed repair.

**Two tools, two jobs.** `etcdctl` is the network client. `etcdutl` "operates directly on etcd data files", for restore, defragmentation and consistency checks. The page marks `etcdctl snapshot status` and `etcdctl snapshot restore` as deprecated since etcd 3.5 in favour of `etcdutl`. Our etcd is 3.7.0 and both tools are in its image.

**Rules for a real restore.**

- Stop all API servers first, restore every etcd member, then start the API servers again. On our kind cluster, leaving the API server running made kubectl give disagreeing answers for at least 3 minutes (Lab 5.5, B4), so the documentation's order is not optional.
- Restart the scheduler, controller manager and kubelets afterwards, so none of them keeps stale data. "During the restoration, critical components will lose leader lock and restart themselves."
- If a majority of etcd members are lost for good, the cluster cannot change state any more. Plan for three members, and back up before every upgrade.
- **Treat the snapshot as a secret.** Secrets are stored in etcd as plain bytes unless you turn on encryption at rest. A raw `etcdctl get` of a test Secret returned its value in clear text. The page says: "encrypt the snapshot files."
- A snapshot holds objects, not volume contents. The data inside a PersistentVolume needs its own backup, and the files kubeadm wrote under `/etc/kubernetes` (certificates, kubeconfigs) are not in etcd either.

See Field Guide → 11 · Operations → etcd backup and restore, and 1 · Architecture → etcd.

## How it works · taking a node out: cordon, drain, eviction, PDB

**`kubectl drain` empties a node politely. It marks the node unschedulable, asks the API server to evict each Pod, and the API server refuses any eviction that would break a PodDisruptionBudget.** Kernel patches, hardware swaps and Kubernetes upgrades all start this way ([Safely drain a node](https://kubernetes.io/docs/tasks/administer-cluster/safely-drain-node/)).

{{diagram ch-5-5-06.jsx | kubectl drain flow · retry text from a real drain, see the measured section below}}

The pieces:

- **Cordon** sets the node unschedulable. Existing Pods keep running. `kubectl cordon NODE` does only this step, and `kubectl uncordon NODE` reverses it. The page warns that Pods which tolerate the `node.kubernetes.io/unschedulable` taint can still land on a drained node, so "avoid tolerating that taint other than for DaemonSets".
- **Eviction** is a request to the Eviction API on the Pod (`POST .../pods/NAME/eviction`). Unlike a delete, it is checked against budgets. The drain page says it "will respect the PodDisruptionBudgets you have specified".
- **PodDisruptionBudget (PDB)** is an object that says how many Pods of an app must stay up. Ours is `minAvailable: 1` on `app: wallet-api`. Field Guide → 7 · Scheduling and capacity → PodDisruptionBudget has the full card.
- **DaemonSet Pods** cannot be rescheduled elsewhere, so `--ignore-daemonsets` leaves them running. A real drain prints `Warning: ignoring DaemonSet-managed Pods: kube-system/kindnet-bzlrs, kube-system/kube-proxy-sdpht`.
- **Bare Pods** (no controller) have nothing to recreate them. Drain refuses: `cannot delete Pods that declare no controller (use --force to override): wallet/probe`. We hit this when our probe Pod ran loose on a node we drained. `--force` would delete it for good.

A clean drain looks like this (real output, node `cnlab-vol5-worker2`, which held one `wallet-api` and one `wallet-worker` Pod):

```text
$ kubectl drain cnlab-vol5-worker2 --ignore-daemonsets --delete-emptydir-data --timeout=120s
node/cnlab-vol5-worker2 cordoned
Warning: ignoring DaemonSet-managed Pods: kube-system/kindnet-bzlrs, kube-system/kube-proxy-sdpht
evicting pod wallet/wallet-worker-6cbdf67665-5bz67
evicting pod wallet/wallet-api-ffd6cb76b-pzsqk
pod/wallet-worker-6cbdf67665-5bz67 evicted
pod/wallet-api-ffd6cb76b-pzsqk evicted
node/cnlab-vol5-worker2 drained
```

The drain page gives one more piece of advice that the next section shows to be important: set `unhealthyPodEvictionPolicy: AlwaysAllow` on your budgets. "The default behavior is to wait for the application pods to become healthy before the drain can proceed."

| `kubectl create configmap <name> --from-literal=k=v`, `kubectl delete configmap <name>` | Make and remove a small object to lose and recover. ConfigMaps are from Ch 5.3. |

## In production

Cluster operations fail in slow, predictable ways: a date passes, a version drifts, a disk fills, a majority is lost. Each row below names the symptom you will see and the check that finds the cause.

| Symptom | Real cause | What engineers do |
| --- | --- | --- |
| An upgrade is refused, or a node misbehaves after one | Skipping a minor version is unsupported (1.36 to 1.37, not 1.35 to 1.37). A kubelet must not be newer than the API server, and may be at most three minor versions older ([upgrade](https://kubernetes.io/docs/tasks/administer-cluster/kubeadm/kubeadm-upgrade/), [skew policy](https://kubernetes.io/releases/version-skew-policy/)). | Upgrade one minor at a time: kubeadm, control plane, then each node. Run `kubeadm upgrade plan` first. Drain a node before a minor kubelet upgrade. Match kubelet and kubeadm versions, as the page recommends. |
| `kubeadm upgrade` stops halfway | An unexpected shutdown left a mix of old and new files. The command is idempotent, so running it again finishes the job. It also keeps backups of the static Pod manifests and of the local etcd data in `/etc/kubernetes/tmp` ([upgrade, recovery](https://kubernetes.io/docs/tasks/administer-cluster/kubeadm/kubeadm-upgrade/)). | Run `kubeadm upgrade` again, or `kubeadm upgrade apply --force` on the same version. If the automatic rollback fails, copy the manifests or the etcd data back from the backup folders. Take an etcd snapshot before every upgrade. |
| `kubectl` and the control plane fail with x509 errors after about a year | kubeadm client certificates expire after 1 year, and nobody upgraded the cluster in that time. Not every component reloads a new certificate by itself ([kubeadm certs](https://kubernetes.io/docs/tasks/administer-cluster/kubeadm/kubeadm-certs/)). | Alert on `kubeadm certs check-expiration` before the date. Run `kubeadm certs renew all` on every control-plane node, then restart the control-plane static Pods by moving each manifest out of `/etc/kubernetes/manifests/` for 20 seconds. Upgrading also renews. |
| One node's kubelet cannot reach the API server and the log says `x509: certificate has expired or is not yet valid` | The kubelet's own client certificate should rotate by itself. When the rotation fails, the old certificate runs out ([troubleshooting kubeadm](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/troubleshooting-kubeadm/)). | Follow the page: back up and delete that node's `kubelet.conf` and `kubelet-client*` files, create a new `kubelet.conf` with `kubeadm kubeconfig user` on a working control-plane node, copy it over and restart the kubelet. |
| Every write to the cluster fails, reads still work | etcd passed its space quota and raised the `NOSPACE` alarm. It then "only accepts key reads and deletes". Compaction frees space inside the file, but only defragmentation returns it to the disk ([etcd maintenance](https://etcd.io/docs/v3.7/op-guide/maintenance/)). | Compact old revisions, run `etcdctl defrag` on each member, then `etcdctl alarm disarm`. Defragmentation is expensive, so schedule it (Kubernetes suggests the `etcd-defrag` tool, [etcd page](https://kubernetes.io/docs/tasks/administer-cluster/configure-upgrade-etcd/)) and alert on disk use. |
| The API server is down and `kubectl` times out, but running Pods keep serving | A majority of the etcd members is gone. A 3-member cluster survives 1 failure and needs 2 to agree ([etcd FAQ](https://etcd.io/docs/v3.7/faq/)). Running Pods continue, but "no new pods can be scheduled" ([etcd page](https://kubernetes.io/docs/tasks/administer-cluster/configure-upgrade-etcd/)). | Run an odd number of members, 3 at least, on separate failure domains. Keep a recent snapshot off the node. Restore as in Lab 5.5 part B, on every member, with the API servers stopped. |
| `kubectl drain` hangs, then times out | A PodDisruptionBudget refuses the next eviction. We measured it: repeated `Cannot evict pod as it would violate the pod's disruption budget`, then a 2-minute timeout. A bare Pod, or a missing `--ignore-daemonsets`, also stops a drain ([safely drain a node](https://kubernetes.io/docs/tasks/administer-cluster/safely-drain-node/)). | Read the retry message: it names the Pod. Fix the cause, such as an unhealthy replica or a budget that is too strict. Set `unhealthyPodEvictionPolicy: AlwaysAllow` on budgets. Do not delete the budget to get past it. |
| Node is `NotReady`, or Pods stay in `ContainerCreating`, while the API answers | The kubelet cannot talk to the runtime: the socket path in its config is wrong, the runtime is stopped, or the two use different cgroup drivers ([container runtimes](https://kubernetes.io/docs/setup/production-environment/container-runtimes/)). | On the node: `systemctl status kubelet containerd`, then `crictl ps`. Compare `containerRuntimeEndpoint` and `cgroupDriver` in `/var/lib/kubelet/config.yaml` with the runtime config. Read the kubelet log with `journalctl -u kubelet`. |
| The kubelet will not start on a new or rebooted node | Swap is on. "By default, the kubelet will not start on a Linux node that has swap enabled" ([swap memory management](https://kubernetes.io/docs/concepts/cluster-administration/swap-memory-management/)). A kubeadm upgrade also needs swap disabled. | `swapoff -a` and remove the swap line from `/etc/fstab` so it stays off after a reboot ([install kubeadm](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/install-kubeadm/)). Or set `failSwapOn: false` on purpose and decide on `swapBehavior`. |

The order of checks is always the same: is the API answering (`kubectl get --raw /readyz`), is the node Ready, is the runtime answering (`crictl ps`), is etcd healthy. Fix the lowest layer that is broken first.

| Problem | Run the containers Kubernetes asks for, and nothing more: a runtime built only to serve the kubelet. |
| Layer / interface | The Container Runtime Interface (CRI), a gRPC API on `unix:///var/run/crio/crio.sock` (the default socket on the [container runtimes page](https://kubernetes.io/docs/setup/production-environment/container-runtimes/)). Below it, any OCI runtime (runc by default). Beside it, CNI for Pod networking. |
| Architecture | One daemon, `crio`, that implements the CRI. It uses the containers image library to pull images, the containers storage library to keep image layers, an OCI runtime to start containers and CNI plug-ins for networking ([CRI-O README](https://github.com/cri-o/cri-o)). Out of scope by design: building and pushing images, and a user-facing CLI. Use `crictl` to talk to it. Its minor versions follow the Kubernetes minor versions (`v1.37` pairs with Kubernetes 1.37). |
| Alternatives | **containerd** (CNCF Graduated, accepted March 29, 2017, graduated February 28, 2019, per [cncf.io/projects/containerd](https://www.cncf.io/projects/containerd/)) is the runtime on our kind nodes and the usual default; pick it for the widest tooling and the largest user base. Pick CRI-O when you want a runtime whose release line tracks Kubernetes exactly and does only CRI work. Docker Engine works only through the extra `cri-dockerd` adapter. |
| CNCF maturity | Graduated, as listed on [cncf.io/projects/cri-o](https://www.cncf.io/projects/cri-o/) on 2026-11-16 (accepted April 8, 2019 at Incubating, graduated July 19, 2023). Docs and install: [cri-o.io](https://cri-o.io/) and [cri-o/packaging](https://github.com/cri-o/packaging). |

*The kubelet cannot tell the two runtimes apart. That is the point of the CRI, and why Lab 5.5 part D can swap one for the other on a running node. See Field Guide → 1 · Architecture → Container runtime (CRI).*
