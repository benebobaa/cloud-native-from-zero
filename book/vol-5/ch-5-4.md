# Chapter 5.4 · Storage and Scheduling

## At a glance

{{diagram ch-5-4-01.jsx | Ch 5.4 at a glance · storage objects on the left, scheduling on the right}}

Read the two black arrows first: they are the whole chapter. The scheduler's choice of node can decide where a volume is created, and an existing volume can decide which node the Pod must use.

## The problem

A stateful Pod needs two things a container runtime does not give it: files that outlive the container, and a placement that respects both its resource needs and the place where its data lives.

In Vol 4 you saw that a container's writable layer is deleted with the container. In Ch 5.2 the wallet's Postgres became a StatefulSet and quietly received a volume. This chapter opens that black box and its twin, the scheduler. Three questions drive it:

1. **Where does data live so that it survives a Pod?** Answer: a *volume* that is not part of the container, described by a PersistentVolume.
2. **How does a Pod ask for storage without knowing the storage system?** Answer: a PersistentVolumeClaim, matched or provisioned through a StorageClass.
3. **Which node does a Pod get?** Answer: the kube-scheduler, which filters out nodes that cannot run the Pod, scores the rest, and binds the Pod to the winner.

**Why this matters.** The two answers interact. On the test cluster, draining the node that held Postgres' volume left `postgres-0` Pending for 2 min 23 s with the event `0/3 nodes are available: 1 node(s) didn't match PersistentVolume's node affinity, 1 node(s) had untolerated taint(s), 1 node(s) were unschedulable`. Nothing was broken. The scheduler was obeying the volume, and you will learn to read that sentence by the end of this chapter.

## How it works · Part 1: volumes and their lifetimes

A volume is a directory that the kubelet mounts into a container, and its lifetime is set by what stands behind the directory, not by the container. A container's own writable layer dies when the container restarts. Kubernetes lists volumes under `spec.volumes` and mounts them with `volumeMounts` ([Volumes](https://kubernetes.io/docs/concepts/storage/volumes/)).

{{diagram ch-5-4-02.jsx | volume lifetimes · what survives a restart, a Pod, a node}}

One Pod can mount directories with very different lifetimes. The table lists them from shortest to longest.

| Storage behind the mount | Container restarts | Pod deleted | Node lost | Typical use |
| --- | --- | --- | --- | --- |
| Container writable layer | lost | lost | lost | nothing you care about |
| `emptyDir` | kept | lost | lost | scratch space, caches |
| `hostPath` or a local volume | kept | kept | lost | node agents, test clusters like kind |
| Network or replicated storage through CSI | kept | kept | kept | databases, queues, anything stateful |

The last row is what a production database needs, and the first three rows are what a laptop cluster gives you. In this chapter's lab you use the third row, because kind has no cloud disk. Keep that limit in mind: it explains the drain failure in the previous section.

**Why not put the data path in the Pod?** A Pod is disposable and its name and IP change when it is replaced. A path such as `/mnt/data` on one particular node would tie the Pod to that node by hand. Kubernetes turns that tie into two objects the scheduler can understand, described next.

## How it works · Part 2: PersistentVolume, PersistentVolumeClaim and StorageClass

Kubernetes splits storage into three objects, so the people who run storage and the people who use it never have to meet. Each object has one job:

| Object | Scope | Who writes it | Job |
| --- | --- | --- | --- |
| **PersistentVolume (PV)** | cluster | admin, or a provisioner | One piece of real storage: capacity, access modes, reclaim policy, where it lives, optional `nodeAffinity` |
| **PersistentVolumeClaim (PVC)** | namespace | the app team | A request: size, access modes, `storageClassName`. A Pod names it in `volumes[].persistentVolumeClaim.claimName` |
| **StorageClass** | cluster | admin | A recipe: which `provisioner`, its `parameters`, `reclaimPolicy`, `volumeBindingMode`, `allowVolumeExpansion` |

See Field Guide → 6 · Storage → PersistentVolume, PersistentVolumeClaim and StorageClass for one card each.

The matching is done by the **PV controller** inside kube-controller-manager. The [PV docs](https://kubernetes.io/docs/concepts/storage/persistent-volumes/) put it in one line: a control loop "watches for new PVCs, finds a matching PV (if possible), and binds them together". This is the same watch-and-reconcile loop from Ch 5.1, applied to storage.

{{diagram ch-5-4-03.jsx | PV controller binding decision · 3 outcomes}}

The decision is short, and every outcome was measured on the test cluster:

- **Match an existing PV.** A PV matches when its storage class equals the claim's, its capacity is at least the request, and its access modes cover the claim's (a claim may also carry a label `selector`). Binding is one to one and writes both sides of the link: `PV.spec.claimRef` and `PVC.spec.volumeName`. The user gets at least what was asked, possibly more. In Lab 5.4 a claim for `300Mi` bound a `500Mi` PV and showed `CAPACITY 500Mi`.
- **Provision a new PV.** If no PV fits and the class names a provisioner, the provisioner creates one. A dynamically provisioned PV is always bound to the claim that caused it. kind ships the `rancher.io/local-path` provisioner and a default class called `standard` (annotation `storageclass.kubernetes.io/is-default-class`), so a PVC with no class gets a volume with no admin work.
- **Wait.** A claim for `2Gi` in class `manual`, where the only PV was too small and no StorageClass object named `manual` existed, stayed `Pending` with the event `storageclass.storage.k8s.io "manual" not found`. The docs say claims "remain unbound indefinitely if a matching volume does not exist".

Two escape hatches are worth knowing. A claim with `storageClassName: ""` opts out of dynamic provisioning and can only bind to a PV that has no class. A claim with `volumeName: foo-pv` asks for one named PV, and a PV with `claimRef` reserves itself for one named claim ([PV docs, Reserving a PersistentVolume](https://kubernetes.io/docs/concepts/storage/persistent-volumes/)).

**Access modes** describe how many nodes may mount the volume, not how many Pods. `ReadWriteOnce` allows one node (several Pods on that node can still share it), `ReadOnlyMany` and `ReadWriteMany` allow many nodes, and `ReadWriteOncePod` (stable since v1.29, CSI volumes only) allows exactly one Pod in the whole cluster. Most block storage offers only `ReadWriteOnce`.

## How it works · Part 3: dynamic provisioning and WaitForFirstConsumer

A StorageClass has a `volumeBindingMode` that decides when a volume is created, and the right mode depends on whether the storage can be reached from every node. With `Immediate` (the default when unset), binding and provisioning happen the moment the PVC exists. The [StorageClass docs](https://kubernetes.io/docs/concepts/storage/storage-classes/) warn that for topology-constrained storage this "may result in unschedulable Pods": the volume is created in some place, and the Pod may be unable to run there. With `WaitForFirstConsumer`, binding and provisioning wait until a Pod uses the claim, and the volume is then created "conforming to the topology that is specified by the Pod's scheduling constraints".

kind's `standard` class uses `WaitForFirstConsumer`. The steps below happened on the test cluster:

{{diagram ch-5-4-04.jsx | WaitForFirstConsumer · 9 steps across 5 actors}}

- **Step 2 is visible.** `kubectl get pvc notes` showed `Pending` with the event `waiting for first consumer to be created before binding`, written by `persistentvolume-controller`. The claim was not stuck. It was waiting for step 3.
- **Steps 4 to 7 are quick.** In the 3-replica StatefulSet of Lab 5.2, each Pod sat unscheduled for about 4.0 s (4.03 s, 4.05 s, 4.03 s between creation and the node being assigned) while its volume was provisioned, then started. A StatefulSet creates its Pods one at a time, so three volumes took three waits.
- **The result carries the choice.** The new PV had `nodeAffinity: required: kubernetes.io/hostname In [cnlab-vol5-worker2]`, and a `hostPath` under `/var/local-path-provisioner/` on that node. From now on, any Pod that uses this claim can run only on that node.

That last point is the root of the drain failure from the start of the chapter, and it is worth saying plainly: **with node-local storage, deleting a Pod never moves its data.** A replacement Pod must go back to the same node, or it stays Pending. Replicated storage, covered by the Longhorn and Rook cards below, removes that coupling.

The VolumeBinding scheduler plugin takes part in the filter step. The [scheduler configuration reference](https://kubernetes.io/docs/reference/scheduling/config/) describes it as checking "if the node has or if it can bind the requested volumes".

**Reclaim policy: what happens when the claim goes away.** The PV keeps a `persistentVolumeReclaimPolicy`. Dynamically provisioned PVs inherit it from the class, and the class default is `Delete` ([PV docs](https://kubernetes.io/docs/concepts/storage/persistent-volumes/)). The PV's phase tells you where it stands:

| Phase | Meaning (from the PV docs) | Measured in Lab 5.4 |
| --- | --- | --- |
| `Available` | free, not yet bound to a claim | too short to see: `pv-manual-1` was already Bound 4 s after creation |
| `Bound` | bound to a claim | `pv-manual-1` once `claim-fits` appeared |
| `Released` | the claim was deleted, the storage is not yet reclaimed | `pv-manual-1` (policy `Retain`) after `claim-fits` was deleted; `claimRef` still named `claim-fits` |
| `Failed` | automatic reclamation failed | not reproduced |

`Retain` keeps the PV and its data for manual cleanup, and a Released PV is not available to a new claim. `Delete` removes the PV object and, for plugins that support it, the real storage: after `kubectl delete pvc notes` the dynamically provisioned PV and its directory under `/var/local-path-provisioner/` were gone within 6 s. (`Recycle`, the old scrub-and-reuse policy, is deprecated; use dynamic provisioning instead.)

## How it works · Part 4: CSI, the plug-in interface for storage systems

The Container Storage Interface (CSI) is a gRPC contract that lets any storage vendor write one driver that works in Kubernetes without changing Kubernetes. CRI does the same for container runtimes and CNI for pod networks. A CSI driver runs as ordinary Pods, in two parts:

{{diagram ch-5-4-05.jsx | CSI driver deployment · controller side and node side}}

The four controller-side **sidecars** are standard containers maintained by the Kubernetes CSI project ([CSI sidecar docs](https://kubernetes-csi.github.io/docs/sidecar-containers.html)). Each one watches the API server and turns an object change into a driver call:

| Sidecar | Watches | Calls on the driver |
| --- | --- | --- |
| `external-provisioner` | PVC objects whose class names this driver | `CreateVolume` |
| `external-attacher` | `VolumeAttachment` objects | `ControllerPublishVolume` and `ControllerUnpublishVolume` |
| `external-resizer` | edits to a PVC that ask for more storage | `ControllerExpandVolume` |
| `external-snapshotter` | `VolumeSnapshot` objects | the snapshot calls |

On the node, the kubelet itself calls `NodeStageVolume` and `NodePublishVolume` on the driver, and the `node-driver-registrar` sidecar registers the driver with the kubelet so it can find the unix socket. The driver reports its capabilities, and sidecars act only on what it advertises.

Two API objects describe a driver to Kubernetes: `CSIDriver` (cluster-wide options) and `CSINode` (per-node registration). See Field Guide → 6 · Storage → CSIDriver, CSINode and CSIStorageCapacity and → VolumeAttachment.

kind's `local-path` provisioner is simpler: it is a single controller that watches PVCs and creates a directory, without CSI. That is why the lab works without a driver, and why its volumes are node-local.

**Expansion and snapshots, by pointer.** Growing a volume needs `allowVolumeExpansion: true` on the class and then an edit of the PVC's `spec.resources.requests.storage`; volumes can only grow, never shrink ([StorageClass docs](https://kubernetes.io/docs/concepts/storage/storage-classes/)). local-path does not support it. `VolumeSnapshot` objects are an add-on API served by a snapshot controller and the `external-snapshotter` sidecar ([Volume Snapshots](https://kubernetes.io/docs/concepts/storage/volume-snapshots/)). See Field Guide → 6 · Storage → VolumeSnapshot (add-on). Neither is run in this chapter.

## How it works · Part 5: the scheduler, one Pod at a time

The kube-scheduler has one job: write `spec.nodeName` for every Pod that has none. It does this with the same watch loop as every controller, and its method has two phases. The [kube-scheduler docs](https://kubernetes.io/docs/concepts/scheduling-eviction/kube-scheduler/) call them *filtering* (find the nodes where the Pod can run) and *scoring* (rank the survivors). If several nodes tie, "kube-scheduler selects one of these at random". The scheduler then tells the API server its choice in a step called *binding*.

Inside the scheduler, every step is a plugin attached to an *extension point*. Each attempt is split into a **scheduling cycle** (choose a node) and a **binding cycle** (write the choice). Scheduling cycles run one after another, and binding cycles may run concurrently ([Scheduling Framework](https://kubernetes.io/docs/concepts/scheduling-eviction/scheduling-framework/)). A Pod that cannot be placed goes back to a queue and is retried when the cluster changes.

{{diagram ch-5-4-06.jsx | kube-scheduler log, Pod newcomer · 2026-11-16 · data/54-scheduler-v10.txt}}

Which plugins ran? The [scheduler configuration reference](https://kubernetes.io/docs/reference/scheduling/config/) lists the defaults, and the log shows six of them scoring. Here are the plugins you meet most often:

| Plugin | Extension points | What it checks or prefers |
| --- | --- | --- |
| `NodeResourcesFit` | filter, score | enough free CPU, memory and so on for the Pod's *requests* |
| `NodeAffinity`, `NodeName` | filter, score | `nodeSelector`, node affinity, an explicit `nodeName` |
| `TaintToleration` | filter, preScore, score | taints the Pod does not tolerate |
| `PodTopologySpread` | filter, score | `topologySpreadConstraints` |
| `VolumeBinding` | preFilter, filter, reserve, preBind | the node has or can get the Pod's volumes |
| `NodeResourcesBalancedAllocation` | score | prefers nodes whose CPU and memory use stays balanced |
| `ImageLocality` | score | prefers nodes that already hold the image |

To watch the scheduler think, Lab 5.4 raises its log level to `--v=10` for one Pod. A Pod `newcomer` asked for 1 CPU on a cluster where `worker` already held a Pod that requested 6 CPUs. Trimmed to the lines that matter (times are seconds past 07:48:38):

```text
.121000 Attempting to schedule pod            pod=default/newcomer
.122432 node had untolerated taints           node=cnlab-vol5-control-plane  (TaintToleration filter)
.123484 Plugin scored node  TaintToleration   node=cnlab-vol5-worker   score=300
.123548 Plugin scored node  NodeResourcesFit  node=cnlab-vol5-worker   score=62
.123694 Plugin scored node  NodeResourcesFit  node=cnlab-vol5-worker2  score=89
.123724 Calculated node's final score         node=cnlab-vol5-worker   score=435
.123730 Calculated node's final score         node=cnlab-vol5-worker2  score=462
.124066 Attempting to bind pod to node        node=cnlab-vol5-worker2
.139460 Response POST .../pods/newcomer/binding  status="201 Created"
```

The control-plane node was removed in the Filter step by its `node-role.kubernetes.io/control-plane` taint, which `newcomer` does not tolerate. Two nodes were scored. The whole decision, from "Attempting" to the API server's answer to the binding request, took 18 ms. Binding is an ordinary API write: a `POST` to the Pod's `binding` subresource, which sets `spec.nodeName`. After that, the kubelet on `worker2` sees a Pod that is assigned to it and starts the containers, exactly as in Ch 5.1.

Lab 5.4 adds storage and scheduling commands to the Ch 5.1 toolkit (`kubectl get`, `describe`, `explain`, `get events`, `docker exec`). Read the table once so that no command in the lab is a surprise.

| Command | What it does |
| --- | --- |
| `kind create cluster --name <n> --config kind-vol5.yaml` | Create the lab cluster from a file: one control-plane node and two workers. |
| `docker save <image> \| docker exec -i <node> ctr -n k8s.io images import -` | Copy a local image into one kind node's container runtime; the lab runs it for each image and node. (`kind load docker-image` fails for `postgres:17` on Docker 29, see Lab 5.1.) |
| `kubectl get storageclass`, `kubectl get pv,pvc` | List the recipes, the volumes and the claims. `(default)` marks the class a claim gets when it names none. |
| `kubectl describe pvc <name>` | The claim's state plus the Events written by the PV controller and the provisioner. |
| `kubectl get pv <name> -o jsonpath='{.spec.nodeAffinity}'` | Print one field of an object; here, the node a volume is pinned to. |
| `kubectl patch pv <name> -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'` | Change one field of a live object; here, protect a volume from being deleted with its claim. |
| `kubectl get pods -o wide` | Add the `NODE` column: where the scheduler put each Pod. |
| `kubectl wait --for=condition=Ready pod/<name>` | Block until a Pod is Ready; fail when the timeout passes. |
| `kubectl exec -n wallet postgres-0 -- psql -U wallet -c "<sql>"` | Run a command inside a container; here, SQL against the database. |
| `kubectl cordon <node>`, `kubectl uncordon <node>` | Mark a node unschedulable (its Pods keep running) or schedulable again. |

| `kubectl get events --field-selector reason=FailedScheduling` | The scheduler's explanations for Pods it could not place. |
| `kubectl describe node <node>` | Capacity, allocatable and the sum of Pod requests ("Allocated resources"), which is what the scheduler compares. |
| `kubectl -n kube-system logs <kube-scheduler pod>` | Read the scheduler's log. Raise its verbosity by editing `--v` in its static Pod manifest on the control-plane node (`docker exec <node> sed -i ...`); the kubelet restarts it. |

## In production

Storage and scheduling failures are mostly waiting, not crashing: an object sits in `Pending` and the reason is written in an Event. Read the Event first.

| Symptom | Real cause | What engineers do |
| --- | --- | --- |
| PVC is `Pending` and the Pod waits | One of three causes: the class waits for a first consumer (normal until a Pod uses the claim), the named StorageClass does not exist (measured: `storageclass.storage.k8s.io "manual" not found`), or no PV fits the size, modes and class. | `kubectl describe pvc`, read the last Event; `kubectl get storageclass` for a default; fix the class name or create the PV. |
| Pod is `Pending` with `didn't match PersistentVolume's node affinity` | The volume is node-local or zonal, and the only node that can mount it is cordoned, tainted, full or gone (measured: `postgres-0` stayed Pending 2 min 23 s after its node was drained; Ch 5.5). | Free or uncordon that node. In production use replicated or network storage so the volume can attach elsewhere, and `WaitForFirstConsumer` so new volumes follow their Pod. |
| Pod is `Pending` with `Insufficient cpu` or `Insufficient memory` | The scheduler adds up requests, not usage, and no node has enough unrequested capacity (measured: a Pod that requested 64 CPUs fitted nowhere). | `kubectl describe node`, read "Allocated resources"; right-size the requests or add nodes. See Field Guide → 7 · Scheduling and capacity → Requests, limits and QoS, and 8 · Autoscaling → Cluster Autoscaler and Karpenter (add-on). |
| Pod is `Pending` with `didn't match Pod's node affinity/selector` | A `nodeSelector` or affinity names a label that no node carries: a typo, or a label never applied (measured: the Pod ran as soon as the label was added, with no restart). | `kubectl get nodes --show-labels`; fix the selector or label the node. Use a preferred (soft) rule for wishes and a required rule for needs. |
| Replicas are `Pending` with a topology spread message | `whenUnsatisfiable: DoNotSchedule` is a hard rule: a Pod that would break `maxSkew` waits (measured: on the 3-node lab cluster 2 of 4 replicas stayed Pending, because the tainted control-plane node counted as an empty domain). | Choose `ScheduleAnyway` when spread is a preference; check `nodeTaintsPolicy` and `minDomains`; add capacity in the missing domain. |
| Data is gone after `kubectl delete pvc` | A dynamically provisioned PV inherits the class policy, and the default is `Delete`: the PV and its directory were removed within 6 s (measured). | Patch the PV to `Retain`, or use a class with `reclaimPolicy: Retain`, for data you cannot lose; take snapshots or backups (see Going deeper). |
| PVC stays `Terminating` | Storage Object in Use protection: a claim that a Pod still uses is not removed until that Pod is gone (see the [PV docs](https://kubernetes.io/docs/concepts/storage/persistent-volumes/)). | `kubectl describe pvc` shows who uses it; remove the Pod first. Do not strip the finalizer by hand (Field Guide → 2 · API machinery → Finalizers). |
| One Pod slows down or kills its neighbours; the node reports pressure | Pods share the node's CPU and memory. A CPU limit is enforced by throttling and a memory limit by an out-of-memory kill, and under node pressure `BestEffort` Pods are evicted first, then `Burstable`, then `Guaranteed` ([resource docs](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/), [QoS docs](https://kubernetes.io/docs/concepts/workloads/pods/pod-qos/)). | Set requests on every container; set requests equal to limits for critical Pods (`Guaranteed`); give namespaces defaults with LimitRange and ceilings with ResourceQuota (Field Guide → 7 · Scheduling and capacity). |
| Pods leave a node about 5 minutes after it goes `NotReady` | Kubernetes adds a toleration for the `not-ready` and `unreachable` taints with `tolerationSeconds=300` unless you set your own ([taints docs](https://kubernetes.io/docs/concepts/scheduling-eviction/taint-and-toleration/)). A Pod with node-local data cannot restart elsewhere. | Shorten `tolerationSeconds` for latency-sensitive Pods; protect availability with a PodDisruptionBudget; keep stateful data on replicated storage. |

## Project cards

Local storage dies with its node, so clusters that run databases add a storage system that copies data across nodes. Two CNCF projects do this, and they sit at opposite ends of the effort scale.

**Longhorn**

| Field | Content |
| --- | --- |
| Problem | Replicated block storage for Kubernetes volumes, built from the disks already in your nodes, so a volume survives the loss of a node. |
| Layer / interface | A CSI driver (Ch 5.4, Part 4) plus a controller that follows the Kubernetes controller pattern: it watches Longhorn custom resources and acts on them. |
| Architecture | The Longhorn Manager runs on every node as a DaemonSet. Each volume gets its own storage controller, the Longhorn Engine, on the node where the Pod runs, and the engine "synchronously replicates the volume across the multiple replicas stored on multiple nodes". Instance Manager Pods host the engine and replica processes. With N replicas a volume tolerates N-1 replica failures. Snapshots and backups to NFS or S3-compatible storage; a web UI ([Longhorn architecture](https://longhorn.io/docs/latest/concepts/), docs 1.13.0, read 2026-11-16). |
| Alternatives | Rook with Ceph when you need block, shared filesystem and object storage at scale and can run at least three nodes. The CSI driver of your cloud's disks when you run on a cloud and one zone is enough. kind's `local-path` for tests only. Pick Longhorn for small and mid-size clusters that want a simple install and a UI. |
| CNCF maturity | Incubating, as listed on [cncf.io/projects/longhorn](https://www.cncf.io/projects/longhorn/) on 2026-11-16: accepted October 11, 2019, moved to Incubating November 4, 2021. |

**Rook**

| Field | Content |
| --- | --- |
| Problem | Run and operate a Ceph storage cluster as ordinary Pods, and hand its block, shared-filesystem and object storage to applications through the usual PVC. |
| Layer / interface | A Kubernetes operator (it reconciles custom resources such as the Ceph cluster definition) plus the Ceph-CSI driver for the CSI interface. |
| Architecture | "The Rook operator is a simple container that has all that is needed to bootstrap and monitor the storage cluster." It starts and fails over the Ceph monitors, and runs the OSDs (the storage daemons), the MDS (for CephFS, the shared filesystem) and the RGW (for S3-compatible object storage). A PVC for a `ReadWriteOnce` block volume is served by Ceph RBD, and one for `ReadWriteMany` by CephFS. "Rook is not in the Ceph data path." ([Rook storage architecture](https://rook.io/docs/rook/latest-release/Getting-Started/storage-architecture/), read 2026-11-16; the page was marked as not the latest release, so check the version you install.) |
| Alternatives | Longhorn when you want a smaller system and block volumes are enough. A managed cloud disk service when you do not want to operate storage at all. The docs say production clusters "must have three or more nodes", so Rook does not fit a single-node lab. |
| CNCF maturity | Graduated, as listed on [cncf.io/projects/rook](https://www.cncf.io/projects/rook/) on 2026-11-16: accepted January 29, 2018, Incubating September 25, 2018, Graduated October 7, 2020. |

*Neither project is installed in this chapter: both are meant for several nodes, and the lab machine is one 8 GB laptop. The tables above come from the project pages and docs, not from a lab run. See Field Guide → 6 · Storage → StorageClass and → CSIDriver, CSINode and CSIStorageCapacity for the Kubernetes objects they plug into.*
