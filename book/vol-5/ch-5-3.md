## The problem

A Pod's IP address is a temporary fact, so no client can hold on to it, and no image can hold the settings that differ per environment.

You saw this in Ch 5.2. When a StatefulSet Pod was deleted and recreated on the test cluster, it kept its name `ledger-1` but its IP changed from `10.244.1.25` to `10.244.1.26`. A Deployment is worse: a rolling update replaces every Pod, and each new Pod gets a new IP. Three things break if a client uses Pod IPs directly:

1. **Discovery.** The wallet API must reach Postgres. If it stores `10.244.1.13`, it fails the moment `postgres-0` is rescheduled.
2. **Load sharing.** Three API replicas have three IPs. Something must spread requests over them and stop sending to a replica that is not ready.
3. **Configuration.** The same image must run in a laptop cluster and in production. A database password baked into the image is in every copy of the image, forever.

Kubernetes answers with two families of objects. A **Service** gives a set of Pods one stable name and one stable virtual IP, and **EndpointSlices** track which Pods are ready behind it. **ConfigMaps** and **Secrets** keep settings outside the image and hand them to the Pod at start. This chapter opens each mechanism: who writes which object, who watches it, and what the kernel finally does with a packet.

**Why this matters.** Most "the app cannot reach the database" incidents are one of four things: the Service selector matches no Pod, the Pod is not ready, DNS returns something unexpected, or a ConfigMap change was never picked up. After this chapter you can tell which in about a minute, using the objects and rules shown here.

## How it works · A Service is a name and a virtual IP

A Service is a stable name and a virtual IP that stand in front of whichever Pods match its selector. It is an API object, not a process: nothing "runs" the Service.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web          # which Pods (by label)
  ports:
    - name: http
      port: 80        # what clients connect to
      targetPort: http  # the container's named port (8080)
```

```text
$ kubectl get svc web
NAME   TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)   AGE
web    ClusterIP   10.96.206.56   <none>        80/TCP    2s
```

The API server picks `10.96.206.56` from a reserved pool, the *service CIDR* (`10.96.0.0/16` on the test cluster, shown in the `kubeadm-config` ConfigMap). In iptables mode the address is never assigned to a network device. In the rule listing later in this chapter it appears only as a *match*: a packet addressed to it gets rewritten before it leaves the node.

The `type` field decides who can reach the Service ([Service docs](https://kubernetes.io/docs/concepts/services-networking/service/)):

| Type | What it adds | Tested on kind 1.37? |
| --- | --- | --- |
| `ClusterIP` (default) | The virtual IP above. Reachable only inside the cluster. | Yes: `10.96.206.56` |
| `NodePort` | Also opens one port on every node, from `--service-node-port-range` (default 30000-32767). | Yes: port `30385`, reached from another node |
| `LoadBalancer` | Also asks the cloud provider for an external load balancer, published in `.status.loadBalancer`. kind has no cloud provider. | No (needs a cloud) |
| `ExternalName` | No proxying at all: cluster DNS answers with a `CNAME` to a name you choose. | No |
| Headless (`clusterIP: None`) | No virtual IP. DNS returns the Pod IPs directly. StatefulSets use this (Ch 5.2). | Yes: `ledger` returned three Pod IPs, `ledger-1.ledger` one |

See Field Guide → 4 · Service networking → Service.

## How it works · EndpointSlices: the list of ready Pods

The list of Pods behind a Service is a separate object, an EndpointSlice, kept up to date by a controller. The diagram shows the chain. Every arrow is a *watch* (a long-lived request, Ch 5.1) and every box writes only its own output.

{{diagram ch-5-3-02.jsx | who watches and writes what · Service to iptables, 2 controllers + 3 consumers}}

The **EndpointSlice controller** watches Services and Pods. For each Service with a selector it writes EndpointSlice objects that list the IP of every matching Pod. It puts the label `endpointslice.kubernetes.io/managed-by: endpointslice-controller.k8s.io` on them ([EndpointSlice docs](https://kubernetes.io/docs/concepts/services-networking/endpoint-slices/)). The real object for the `web` Service:

```text
$ kubectl get endpointslice -l kubernetes.io/service-name=web
NAME        ADDRESSTYPE   PORTS   ENDPOINTS                             AGE
web-k4j29   IPv4          8080    10.244.2.40,10.244.1.31,10.244.2.41   3s
```

```yaml
  endpoints:
  - addresses: [10.244.2.40]
    conditions: {ready: true, serving: true, terminating: false}
    nodeName: cnlab-vol5-worker2
    targetRef: {kind: Pod, name: web-749fb7cfc9-r4qrd, namespace: default}
```

Each endpoint carries three conditions. The docs define them this way: `serving` means the endpoint "is currently serving responses" (for a Pod, its `Ready` condition); `terminating` is set when the Pod is first deleted; `ready` is a shortcut for "serving and not terminating".

**Readiness gates traffic.** A Pod that fails its readiness probe stays Running but its endpoint turns `ready: false`, and the rules that send traffic to it are removed. Section "How the rules follow the Pods" below measures how long that takes.

A slice holds at most 100 endpoints by default (up to 1000 with a controller-manager flag), so a Service with 5,000 Pods becomes about 50 slices instead of one huge object that every node must re-read on each change. The older `Endpoints` object still exists, and `kubectl` warns about it: `Warning: v1 Endpoints is deprecated in v1.33+; use discovery.k8s.io/v1 EndpointSlice`.

See Field Guide → 4 · Service networking → EndpointSlice and → Endpoints (deprecated).

## How it works · kube-proxy turns the list into packet rules

kube-proxy is a program on every node that watches Services and EndpointSlices and writes kernel rules; it does not carry traffic itself. On the test cluster it runs as a Pod of a DaemonSet, and its log says `Using iptables Proxier`. The Kubernetes 1.37 [virtual IPs documentation](https://kubernetes.io/docs/reference/networking/virtual-ips/) lists the modes:

| Mode | Platform | What the 1.37 docs say |
| --- | --- | --- |
| `iptables` | Linux | "In Kubernetes 1.37, this is `iptables`, but a future version of Kubernetes will change the default to `nftables`." |
| `nftables` | Linux, kernel 5.13 or later | The planned future default and the recommended replacement for `ipvs`. |
| `ipvs` | Linux | "Deprecated since Kubernetes v1.35"; disabled by default from v1.40, fully removed in v1.43. |
| `kernelspace` | Windows | The only Windows mode. |

The docs recommend setting the mode explicitly so that an upgrade does not change it silently. This chapter traces `iptables` mode because it is what the lab cluster runs and the one you will meet most often today. The nftables mode follows the same idea with a different kernel table.

Take the `web` Service from the lab with three ready Pods. A Pod runs `wget http://web`. Name resolution (next section) returns `10.96.206.56`, and the packet leaves the Pod addressed to that IP. Every packet from a Pod passes through the `nat` table's `PREROUTING` chain; packets made by a process on the node itself pass through `OUTPUT`. Both start with a jump into one shared chain:

{{diagram ch-5-3-03.jsx | packet path in iptables mode · real chains from the kind worker node, 3 endpoints}}

Here are the real rules, listed on the worker node (`iptables -t nat -S`, comments shortened):

```text
-A PREROUTING -m comment --comment "kubernetes service portals" -j KUBE-SERVICES
-A OUTPUT     -m comment --comment "kubernetes service portals" -j KUBE-SERVICES

$ iptables -t nat -S KUBE-SERVICES
-A KUBE-SERVICES -d 10.96.206.56/32 -p tcp -m comment --comment "default/web:http cluster IP" -m tcp --dport 80 -j KUBE-SVC-CDGGSHYLG3RE2FKL

$ iptables -t nat -S KUBE-SVC-CDGGSHYLG3RE2FKL
-A KUBE-SVC-CDGGSHYLG3RE2FKL ! -s 10.244.0.0/16 -d 10.96.206.56/32 -p tcp ... --dport 80 -j KUBE-MARK-MASQ
-A KUBE-SVC-CDGGSHYLG3RE2FKL ... "default/web:http -> 10.244.1.31:8080" -m statistic --mode random --probability 0.33333333349 -j KUBE-SEP-36V5QKA2DLDNNYIH
-A KUBE-SVC-CDGGSHYLG3RE2FKL ... "default/web:http -> 10.244.2.40:8080" -m statistic --mode random --probability 0.50000000000 -j KUBE-SEP-3EOAO7T7KM6VD4LE
-A KUBE-SVC-CDGGSHYLG3RE2FKL ... "default/web:http -> 10.244.2.41:8080" -j KUBE-SEP-A66XKCMH4O57UK7H

$ iptables -t nat -S KUBE-SEP-36V5QKA2DLDNNYIH
-A KUBE-SEP-36V5QKA2DLDNNYIH -s 10.244.1.31/32 ... -j KUBE-MARK-MASQ
-A KUBE-SEP-36V5QKA2DLDNNYIH -p tcp ... -m tcp -j DNAT --to-destination 10.244.1.31:8080
```

Read it as four steps:

1. **Match.** `KUBE-SERVICES` has one rule per Service port. It matches destination `10.96.206.56`, TCP, port 80. Only that exact address and port are rewritten.
2. **Pick a backend.** The `KUBE-SVC` chain tries its endpoint rules in order and the first match wins. The first rule matches one packet in three (`0.3333`). Of the two thirds left, the second matches half (`0.5`). The third has no condition and takes the rest. Each Pod gets one third, and kube-proxy keeps no counter.
3. **Rewrite.** The `KUBE-SEP` chain (service endpoint) holds a `DNAT` rule: destination NAT replaces `10.96.206.56:80` by `10.244.1.31:8080`. The packet now routes to a Pod like any other.
4. **Remember.** The kernel's *connection tracker* (conntrack) stores the rewrite. The reply is translated back automatically, so the client believes it talked to `10.96.206.56`. The real entry from the lab, with the original tuple first and the reply tuple second:

```text
$ conntrack -L -d 10.96.206.56
tcp  6 117 TIME_WAIT src=10.244.1.32 dst=10.96.206.56 sport=38588 dport=80 src=10.244.2.40 dst=10.244.1.32 sport=8080 dport=38588 [ASSURED]
```

Because the choice is stored per connection, the random pick happens once per TCP connection, not per packet. The `KUBE-MARK-MASQ` rules mark packets that need masquerade (source NAT) so replies return through the node that rewrote them. The first `KUBE-SVC` rule marks traffic that does *not* come from the Pod network (`! -s 10.244.0.0/16`). The first `KUBE-SEP` rule marks a Pod that reaches its own Service and is picked as its own backend.

See Field Guide → 1 · Architecture → kube-proxy.

## How it works · How the rules follow the Pods

Because rules are rebuilt from the EndpointSlice, the traffic split and the set of backends change when the Pods change, with no one touching a load balancer. Two measurements show it.

**An even split, by chance.** The lab sends 300 requests from one client Pod to the Service and counts which Pod answered. The chart compares the counts to a perfectly even 100 each.

{{diagram ch-5-3-04.jsx | lab 5.3 Part B · 300 wget requests from one client Pod, 2026-11-16, kind v1.37.0}}

A random pick with probability one third gives a count with a standard deviation of about 8 (`sqrt(300 x 1/3 x 2/3)`). The measured gaps, -8, +9 and -1, are what chance predicts. Random choice evens out over many connections, but it does not give round-robin and it does not look at load: one long-lived connection stays on its Pod for as long as it lives.

**A Pod that stops being ready.** In the lab one Pod's readiness file is deleted. The test polls the node's rules every 0.25 s and notes when the Pod's `DNAT` rule is gone.

{{diagram ch-5-3-05.jsx | lab 5.3 Part C · one run, iptables-save polled every 0.25 s on worker2, 2026-11-16}}

The readiness probe in the lab runs every 2 seconds and the default `failureThreshold` is 3, so the kubelet needs up to 6 seconds of failures before it marks the Pod not ready. The rest of the measured time covers the rest of the chain in the diagram: the kubelet writes the Pod status, the EndpointSlice controller flips `ready` to `false`, and kube-proxy on the node rewrites its rules. Treat the split as approximate: the first failed probe can come up to 2 seconds after the file is deleted, and this is a single run. The practical lesson is that a Pod stays in the rotation for several seconds after it breaks. Production Services therefore combine readiness probes with retries on the client side and graceful shutdown (Ch 1.2).

**A Service with no ready Pods.** If the selector matches nothing, the rules do not disappear. kube-proxy replaces the Service rule with a rejection:

```text
-A KUBE-SERVICES -d 10.96.206.56/32 -p tcp -m comment --comment "default/web:http has no endpoints" -m tcp --dport 80 -j REJECT --reject-with icmp-port-unreachable
```

The client gets an immediate refusal (ICMP port unreachable) instead of a silent drop. The `has no endpoints` comment is the quickest clue when you debug a Service with an empty EndpointSlice. Lab 5.3 "Break it" causes exactly this.

**NodePort.** A `NodePort` Service adds a second entrance to the same chains. The last rule of `KUBE-SERVICES` sends packets whose destination is a local address to `KUBE-NODEPORTS`; that chain matches the node port and jumps to a `KUBE-EXT` chain, which marks the packet for masquerade and then joins the normal `KUBE-SVC` chain:

```text
-A KUBE-NODEPORTS -p tcp -m comment --comment "default/web:http" -m tcp --dport 30385 -j KUBE-EXT-CDGGSHYLG3RE2FKL
-A KUBE-EXT-CDGGSHYLG3RE2FKL -m comment --comment "masquerade traffic for default/web:http external destinations" -j KUBE-MARK-MASQ
-A KUBE-EXT-CDGGSHYLG3RE2FKL -j KUBE-SVC-CDGGSHYLG3RE2FKL
```

On the test cluster, `curl http://<worker2 IP>:30385/` from the control-plane node returned a Pod name. The docs warn that for NodePort traffic "the client IP address does get altered", which is the masquerade rule above at work.

See Field Guide → 4 · Service networking → Service and → 5 · Configuration.

## How it works · DNS: names for Services

A Pod finds a Service by name because the kubelet points every Pod at the cluster DNS server and CoreDNS answers from the API. CoreDNS runs as a Deployment in `kube-system` (two replicas on the test cluster) behind a Service called `kube-dns`, whose IP `10.96.0.10` is the `nameserver` line in every Pod. Its `kubernetes` plugin watches Services and EndpointSlices through the API ([CoreDNS kubernetes plugin](https://coredns.io/plugins/kubernetes/)); nothing is copied into a zone file. The cluster's Corefile from the test cluster:

```text
.:53 {
    errors
    health { lameduck 5s }
    ready
    kubernetes cluster.local in-addr.arpa ip6.arpa {
       pods insecure
       fallthrough in-addr.arpa ip6.arpa
       ttl 30
    }
    prometheus :9153
    forward . /etc/resolv.conf { max_concurrent 1000 }
    cache 30 {
       disable success cluster.local
       disable denial cluster.local
    }
    loop
    reload
    loadbalance
}
```

Each line is a plugin, and a query passes through them in a fixed order:

| Plugin | What it does here |
| --- | --- |
| `kubernetes` | Answers `cluster.local` names (and reverse lookups) from Services and EndpointSlices. `ttl 30` sets the answer lifetime; `fallthrough` passes unknown reverse names on instead of failing. `pods insecure` answers IP-style Pod names without checking (kept for kube-dns compatibility). |
| `forward . /etc/resolv.conf` | Sends every other name to the resolvers the node itself uses ([forward plugin](https://coredns.io/plugins/forward/)). |
| `cache 30` | Caches upstream answers for 30 s, but not `cluster.local` ones: those are already served from memory. |
| `health`, `ready`, `prometheus` | Liveness endpoint, readiness endpoint and metrics on `:9153`. |
| `loop`, `reload`, `loadbalance` | Detects forwarding loops, reloads the Corefile when its ConfigMap changes, and shuffles the order of A records. |

The names follow a fixed pattern ([DNS for Services and Pods](https://kubernetes.io/docs/concepts/services-networking/dns-pod-service/)): a Service is `my-svc.my-namespace.svc.cluster.local` and resolves to its cluster IP. A headless Service has the same name but resolves to the set of Pod IPs. On the test cluster `ledger` returned three IPs and `ledger-1.ledger` returned one. A named port also gets an SRV record, `_port-name._port-protocol.my-svc.my-namespace.svc.cluster-domain.example`.

**The search path.** Typing the full name every time would be tedious, so the kubelet writes a `resolv.conf` with a search list and `ndots:5`. A name with fewer than five dots is tried with each search suffix appended, in order, before it is tried as written. The real log shows it. These are CoreDNS's own log lines, captured after adding the `log` plugin to the Corefile:

{{diagram ch-5-3-06.jsx | CoreDNS query log · 3 lookups from a busybox Pod, 2026-11-16, kind v1.37.0}}

```text
[INFO] 10.244.1.32:45752 "A IN web.default.svc.cluster.local. udp 47 false 512" NOERROR ...
[INFO] 10.244.1.32:44130 "A IN web.default.default.svc.cluster.local. udp 55 false 512" NXDOMAIN ...
[INFO] 10.244.1.32:36672 "A IN web.default.svc.cluster.local. udp 47 false 512" NOERROR ...
[INFO] 10.244.1.32:55015 "A IN example.com.svc.cluster.local. udp 47 false 512" NXDOMAIN ...
[INFO] 10.244.1.32:57993 "A IN example.com. udp 29 false 512" NOERROR ...
```

The lines come from two CoreDNS replicas, so a single lookup's earlier attempts can be in the other replica's log; the diagram shows only what was captured. The cost is visible: a lookup for an *external* name makes extra failed queries first. Two common fixes are a trailing dot (`example.com.` is absolute, so no search happens) and a lower `ndots` in the Pod's `spec.dnsConfig`. See Field Guide → 4 · Service networking → DNS for Services and Pods.

## How it works · ConfigMaps and Secrets: settings outside the image

A ConfigMap holds non-secret settings as key-value pairs, a Secret holds sensitive ones, and a Pod picks them up as environment variables or as files. A ConfigMap's data may not exceed 1 MiB ([ConfigMap docs](https://kubernetes.io/docs/concepts/configuration/configmap/)). The wallet keeps `POSTGRES_USER`, `POSTGRES_DB` and `POLL_SECONDS` in a ConfigMap and `POSTGRES_PASSWORD` in a Secret (Milestone 5). The database URL is built from the password with `$(POSTGRES_PASSWORD)`, which the kubelet expands from an env entry defined earlier in the same container.

The two delivery paths behave differently after the object changes. The test edited the ConfigMap `demo-config` while a Pod used it both ways:

{{diagram ch-5-3-07.jsx | lab 5.3 Part E · ConfigMap edit, one run, 2026-11-16}}

The mounted directory shows how the refresh works. Each key is a symlink into a timestamped directory, and the kubelet publishes an update by building a new directory and moving the `..data` symlink in one step, so a reader never sees half a file:

```text
$ kubectl exec config-demo -- ls -l /etc/demo
lrwxrwxrwx 1 root root 16 Nov 16 07:43 LOG_LEVEL -> ..data/LOG_LEVEL
lrwxrwxrwx 1 root root 21 Nov 16 07:43 app.properties -> ..data/app.properties
$ kubectl exec config-demo -- ls -la /etc/secret
...
lrwxrwxrwx 1 root root 32 Nov 16 07:43 ..data -> ..2026_11_16_07_43_50.3455029277
```

In one run the file changed 68 seconds after the edit, while `LOG_LEVEL` in the environment stayed `info`. Treat the 68 s as an example, not a guarantee: the delay depends on the kubelet's sync period and cache. The rule to keep is simpler. Environment variables need a Pod restart (in a Deployment: a new rollout) to change, and files change by themselves, but your program must re-read them. Starting with v1.19 a ConfigMap can be marked `immutable: true`; it can then no longer be edited, only replaced, which protects against accidental changes.

**A Secret is encoded, not encrypted.** The API returns `data` as base64, and anyone can decode it. The lab then reads the same Secret straight from etcd:

```text
$ kubectl get secret demo-secret -o jsonpath='{.data.DB_PASSWORD}' | base64 -d
s3cr3t-value
$ etcdctl get /registry/secrets/default/demo-secret | grep -a -o s3cr3t-value | sort | uniq -c
      2 s3cr3t-value
```

The plain value appears twice in etcd. One copy is the stored data. The other is the `kubectl.kubernetes.io/last-applied-configuration` annotation, because the Secret was created with `kubectl apply` from a manifest that used `stringData`. The Kubernetes docs say so directly: "Kubernetes Secrets are, by default, stored unencrypted in the API server's underlying data store (etcd)" ([Secret docs](https://kubernetes.io/docs/concepts/configuration/secret/)). Real protection comes from RBAC, from encryption at rest, and from keeping the Secret manifest out of version control. Vol 6 covers them; see Field Guide → 9 · Security and access → Encrypting Secrets at rest.

Two further ways to feed a Pod deserve a name. The *downward API* exposes the Pod's own metadata, for example `fieldRef: spec.nodeName`, which the Ch 5.2 DaemonSet used to print its node. A *projected volume* merges several sources (ConfigMaps, Secrets, tokens) into one directory. See Field Guide → 5 · Configuration → ConfigMap, → Secret and → Downward API and projected volumes.

## In production

Service and configuration incidents are mostly small mismatches between three lists: the Service's selector, the Pods' labels and the endpoints that are ready. Check the lists in that order.

| Symptom | Real cause | What engineers do |
| --- | --- | --- |
| The Service refuses connections at once | No ready Pod matches the selector (measured: the Service rule became `REJECT ... icmp-port-unreachable` and the EndpointSlice showed `ENDPOINTS <unset>`). A wrong `targetPort` gives a different error: the Pod is found but nothing listens on that port. | `kubectl get endpointslices -l kubernetes.io/service-name=<svc>`, then `kubectl get pods --show-labels` and compare. Follow [Debug Services](https://kubernetes.io/docs/tasks/debug/debug-application/debug-service/). |
| A few failed requests while a Pod breaks or is replaced | The Pod stays in the rotation until probe failures, the status write, the slice update and the rule rewrite have all happened (measured: 7.8 s in one run with a 2 s probe and `failureThreshold` 3). | Short readiness periods, graceful shutdown on `SIGTERM` (Ch 1.2), and client retries with timeouts. Never rely on the Service to hide a broken Pod instantly. |
| One replica is hot while others are idle | The pick is random once per connection, not per request (measured: 92, 109 and 99 of 300). A long-lived connection, such as HTTP/2 or gRPC, stays on one Pod. | Let the client open several connections, or put a layer-7 proxy or service mesh in front, which balances requests instead of connections. |
| `Name or service not known` for a Service name | A short name resolves only in the Pod's own namespace through the search list. From another namespace, write `web.other-ns`. A missing Service or an unhealthy CoreDNS gives the same error. | From a Pod run `cat /etc/resolv.conf` and `nslookup <name>`; read the CoreDNS Pods and log. See [Debugging DNS Resolution](https://kubernetes.io/docs/tasks/administer-cluster/dns-debugging-resolution/). |
| External lookups are slow, or time out under load | `ndots:5` sends a name such as `example.com` through the search list first (measured: `example.com.svc.cluster.local` returned NXDOMAIN before the real answer). Every extra query is a UDP packet through conntrack. | Use a trailing dot or a lower `ndots` for hot paths, add CoreDNS replicas, or run [NodeLocal DNSCache](https://kubernetes.io/docs/tasks/administer-cluster/nodelocaldns/). |
| The ConfigMap was edited but the app still uses the old value | Environment variables are copied once at container start. Files refresh after the kubelet sync period plus cache delay (measured: 68 s), and a `subPath` mount never refreshes. The program may also read the file only at start ([ConfigMap docs](https://kubernetes.io/docs/concepts/configuration/configmap/)). | Restart the Deployment after a config change (`kubectl rollout restart`), or make the name or a hash of the ConfigMap part of the Pod template so every change causes a rollout. Mark stable config `immutable: true`. |
| A Secret's value is visible to people who should not see it | The base64 in `data` is an encoding. Anyone allowed to `get` the Secret can decode it. In etcd it is plain unless encryption at rest is on, and a Secret made by `kubectl apply` from `stringData` is stored a second time in the `last-applied-configuration` annotation (measured: two copies). | Grant `get secrets` sparingly with RBAC, turn on [encryption at rest](https://kubernetes.io/docs/tasks/administer-cluster/encrypt-data/), keep Secret manifests out of git, and rotate a value that has leaked. Vol 6 builds these. |
| The server sees a node IP instead of the real client IP on a NodePort | The packet is source-NATed (masqueraded) so the reply returns through the node that rewrote it. The [source-IP tutorial](https://kubernetes.io/docs/tutorials/services/source-ip/) says packets to a `NodePort` Service "are source NAT'd by default". | Set `externalTrafficPolicy: Local` to keep the client IP, accepting that a node with no local endpoint drops the packet. Or read the IP from a header set by an external load balancer. |

## Project cards

**CoreDNS**

| Field | Content |
| --- | --- |
| Problem | Answer "what is the IP behind this name?" for every Pod in the cluster, from live API state, and pass every other name to an outside resolver. |
| Layer / interface | Cluster DNS add-on. Pods reach it over plain DNS (UDP and TCP port 53) at the address in their `resolv.conf`; it reads Services and EndpointSlices through the Kubernetes API. |
| Architecture | One Go program configured by a Corefile, which is a chain of plugins run in a fixed order (`kubernetes`, `forward`, `cache`, `log`, `health` and so on). It runs as a Deployment in `kube-system` behind a Service named `kube-dns`; the Corefile is the `coredns` ConfigMap, and the `reload` plugin applies edits without a restart. The Kubernetes docs keep the name `kube-dns` for the Service "to ensure greater interoperability" with workloads built for the older DNS add-on ([custom DNS tasks](https://kubernetes.io/docs/tasks/administer-cluster/dns-custom-nameservers/)). |
| Alternatives | The legacy `kube-dns` add-on, which CoreDNS replaced. NodeLocal DNSCache (stable since v1.18) runs a CoreDNS caching agent on every node, so Pods skip the iptables rewrite and the conntrack entry for DNS; pick it when DNS query volume is high or UDP drops show up as multi-second lookups ([NodeLocal DNSCache](https://kubernetes.io/docs/tasks/administer-cluster/nodelocaldns/)). |
| CNCF maturity | Graduated, as listed on [cncf.io/projects/coredns](https://www.cncf.io/projects/coredns/) on 2026-11-16: accepted February 27, 2017, Incubating February 26, 2018, Graduated January 24, 2019. |

*The card is also in the Field Guide as "CoreDNS and cluster add-ons" (1 · Architecture).*
