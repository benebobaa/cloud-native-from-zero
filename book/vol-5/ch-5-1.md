# Chapter 5.1 · Architecture and the API

## At a glance

{{diagram ch-5-1-01.jsx | Ch 5.1 at a glance · the parts and who watches whom}}

Read it left to right: you send a spec, the API server stores it in etcd, and three kinds of loop watch for changes and act. The rest of the chapter opens each box.

## The problem

One machine can run a few containers by hand; fifty machines running five hundred containers need a system that decides where each one goes, notices when one dies, and keeps doing it while you sleep.

Try it with a script. A loop of `ssh` commands can start containers, but it breaks at the first real event:

1. **A machine dies at 03:00.** Nobody told the script. The containers on it are gone and no loop restarts them elsewhere.
2. **Two people run the script at once.** Both read "alice needs 2 replicas" and you end up with 4, or with 0.
3. **The script stops half way.** Some machines run version 2, some run version 1, and nothing records which.
4. **Services must find each other.** The wallet API needs Postgres, but Postgres moves to another machine and gets a new IP address.

Kubernetes answers with one idea: **store what you want (the desired state) in a database, and let many small loops compare it with what exists (the actual state) and fix the difference.** The script has no memory; Kubernetes has. A dead machine is only a difference that a loop sees and corrects.

**Why this matters to you.** Every Kubernetes error message is one loop telling you what it sees. When you know which loop owns an object, you know where to look. This chapter names every part and proves each claim on a real 3-node cluster.

The node side has three parts. The **kubelet** is the agent on each node: it watches the API for Pods assigned to its node and makes sure their containers run. The **container runtime** (containerd 2.3.4 on the test cluster) actually creates the containers; the kubelet talks to it through the *Container Runtime Interface* (CRI), a gRPC API (Ch 5.5). **kube-proxy** programs the packet-forwarding rules that make Services work (Ch 5.3).

## How it works · the API server and its objects

The API server is the only component that talks to etcd, and the only door every other component and every human uses. Clients, even the scheduler and the kubelet, send ordinary HTTPS requests to it.

A write request passes the gates in the [access-control docs](https://kubernetes.io/docs/concepts/security/controlling-access/), in this order:

{{diagram ch-5-1-03.jsx | API request pipeline · four gates, then etcd}}

1. **Authentication**: "If the request cannot be authenticated, it is rejected with HTTP status code 401."
2. **Authorization**: if every module denies the request, it is denied with status 403 (RBAC, Vol 6).
3. **Admission control**: plug-ins that can change the object (defaults) or reject it. "Unlike Authentication and Authorization modules, if any admission controller module rejects, then the request is immediately rejected."
4. **Validation**: "it is validated using the validation routines for the corresponding API object, and then written to the object store."

Everything the API serves is an **object**: a record of intent. Every object has the same four top-level parts, and two of them matter most:

| Field | Who writes it | Meaning |
| --- | --- | --- |
| `apiVersion`, `kind` | you | which type, for example `apps/v1` and `Deployment` |
| `metadata` | you and the system | `name`, `namespace`, `labels`, `uid`, `resourceVersion`, `ownerReferences` |
| `spec` | **you** | the **desired state**: what you want |
| `status` | **controllers and kubelets** | the **current state**: what exists now |

The docs put it as: "The `status` describes the current state of the object, supplied and updated by the Kubernetes system and its components" ([working with objects](https://kubernetes.io/docs/concepts/overview/working-with-objects/)). Here are both halves of the `web` Deployment from the lab, after scaling to 4:

```text
spec:
  replicas: 4
  strategy:
    rollingUpdate: {maxSurge: 25%, maxUnavailable: 25%}
status:
  availableReplicas: 4
```

URLs follow the object type. `kubectl get deploy web -v=6` prints the request it made:

```text
"Response" verb="GET" url="https://127.0.0.1:39167/apis/apps/v1/namespaces/default/deployments/web" status="200 OK"
```

```bash

```


## How it works · etcd, the memory

etcd is "a consistent and highly-available key value store used as Kubernetes' backing store for all cluster data" ([etcd task page](https://kubernetes.io/docs/tasks/administer-cluster/configure-upgrade-etcd/)). Only the API server reads or writes it. Open it up on the lab cluster. `etcdctl` ships inside the etcd Pod, so run it there (the three certificate flags are the API server's way in, too):

```bash
kubectl create configmap hello --from-literal=greeting=hello-etcd
E="kubectl -n kube-system exec etcd-cnlab-vol5-control-plane -- etcdctl --endpoints=https://127.0.0.1:2379 --cacert=/etc/kubernetes/pki/etcd/ca.crt --cert=/etc/kubernetes/pki/etcd/server.crt --key=/etc/kubernetes/pki/etcd/server.key"
$E get /registry/configmaps/default/hello | strings
```

```text

default"
```

Three facts are visible. The **key** is a path: `/registry/<resource>/<namespace>/<name>`. The **value** is binary (Kubernetes stores objects as protocol buffers; the stored bytes start with the four bytes `k8s` and a zero, which is why `strings` is needed). And the data is **plain text**: anyone who can read etcd can read every Secret (Ch 5.3).

**Revisions.** etcd keeps one counter for the whole store. Every write to any key raises it, and each key records the revision that created it and the revision that last changed it. Kubernetes exposes the second one as `metadata.resourceVersion`. Create `hello`, patch it, and compare:

```bash
kubectl get cm hello -o jsonpath='{.metadata.resourceVersion}{"\n"}'      # after create: 939
kubectl patch cm hello -p '{"data":{"greeting":"hello again"}}'
kubectl get cm hello -o jsonpath='{.metadata.resourceVersion}{"\n"}'      # after patch: 1003
$E get /registry/configmaps/default/hello -w fields | grep -E "ModRevision|CreateRevision|Version"
```

```text
"CreateRevision" : 939
"ModRevision" : 1003
"Version" : 2
```

`ModRevision` equals `resourceVersion`, and `Version` counts the writes to this one key. Treat `resourceVersion` as an opaque token in your own code: the API docs say it must be "passed unmodified back to the server" ([API concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/#resource-versions)).

**Why a majority.** etcd copies every write to its members with the Raft protocol and acknowledges it only when a majority (a *quorum*) has stored it. The [etcd FAQ](https://etcd.io/docs/latest/faq/) says a cluster "operates so long as a member quorum can be established", and the Kubernetes docs tell you to "run etcd as a cluster with an odd number of members".

| Members | Majority needed | Failures tolerated |
| --- | --- | --- |
| 1 | 1 | 0 (the kind lab cluster: `etcdctl member list` shows one) |
| 3 | 2 | 1 |
| 5 | 3 | 2 |

An even count adds a machine without adding tolerance: 4 members still need 3. The test cluster's single member reported `IS LEADER true`, etcd 3.7.0, database size 1.7 MB with a quota of 2.1 GB. *See Field Guide → 1 · Architecture → etcd.*

## How it works · watch and reconcile

Controllers do not poll. They **watch**: the API server keeps an HTTP connection open and streams every change to the objects they ask about. Try it by hand against the `hello` ConfigMap, then patch it from a second terminal:

```bash
kubectl get --raw "/api/v1/namespaces/default/configmaps?watch=1&fieldSelector=metadata.name=hello&resourceVersion=0"
```

```text
{"type":"ADDED","object":{"kind":"ConfigMap","apiVersion":"v1","metadata":{"name":"hello","namespace":"default","uid":"77266e3f-...","resourceVersion":"1011", ...}, "data":{"greeting":"third"}}}
{"type":"MODIFIED","object":{"kind":"ConfigMap", ... "resourceVersion":"1028", ... "data":{"greeting":"fourth"}}}
```

The docs describe the contract: a watch "allows a client to fetch the current state and then subscribe to subsequent changes, without missing any events". Events are `ADDED`, `MODIFIED` and `DELETED`, plus `BOOKMARK` progress markers. The server keeps only a window of history: "Clusters using etcd 3 preserve changes in the last 5 minutes by default". A client that falls behind gets HTTP `410 Gone`, throws away its copy, lists again and restarts the watch. ([API concepts: efficient detection of changes](https://kubernetes.io/docs/reference/using-api/api-concepts/#efficient-detection-of-changes)).

A controller is that watch plus one rule. The [controller docs](https://kubernetes.io/docs/concepts/architecture/controller/) define it: "controllers are control loops that watch the state of your cluster, then make or request changes where needed. Each controller tries to move the current cluster state closer to the desired state." In pseudocode, every controller is this:

```text
forever:
    key     = next changed object from my watch      # e.g. Deployment default/web
    desired = key.spec                                # what the user wants
    actual  = what exists now (ReplicaSets I own)     # what the world looks like
    if actual != desired: create, delete or update objects through the API server
    write key.status                                  # report what I see
```

The rule is the same one a thermostat follows. It does not matter how the difference arose (a user edit, a crashed node, a restart of the controller itself). The loop compares and corrects, and a second run on a correct state changes nothing. That is why Kubernetes recovers from partial failures without a human.

The chain below is what really happens when you run `kubectl create deployment web --replicas=2`. Nobody calls anybody: each loop reacts to an object that appeared in the API.

## How it works · how long the chain takes

We recorded the chain with a small script (`watchtl.py`, a `watch` on Pods and ReplicaSets, timestamps taken when each event arrived) and repeated it three times.

{{diagram ch-5-1-05.jsx | measured on the lab cluster, 2026-11-16 · 3 runs · data/51-create-timeline-*.csv}}

The control-plane steps, from the ReplicaSet to a Pod with a node, take tens of milliseconds, because each is one small write plus one event. The slow step is on the node: the kubelet learns about the Pod, asks containerd to create the sandbox and the container, and reports `Ready`. Do not expect a Kubernetes rollout to be instant, and do not assume the control plane is the slow part.

## How it works · leaders, leases and heartbeats

High-availability clusters run several copies of the scheduler and the controller manager, but two copies of a loop would fight. The copies elect one leader through a `Lease` object. The [leases docs](https://kubernetes.io/docs/concepts/architecture/leases/) say Kubernetes "uses Leases to ensure only one instance of a component is running at any given time", the other instances "on stand-by". The same object type carries node heartbeats: "For every `Node`, there is a `Lease` object with a matching name in the `kube-node-lease` namespace", and each kubelet heartbeat is an update of it. On the lab cluster:

```bash
kubectl -n kube-system get lease
```

```text
NAME                                   HOLDER                                                                      AGE
apiserver-w5cpdnfsz2xcbh3fdok3zuj5ya   apiserver-w5cpdnfsz2xcbh3fdok3zuj5ya_bf50f770-ed96-48bc-b743-cd3860defdda   5m14s
kube-controller-manager                cnlab-vol5-control-plane_a28824c4-292f-4f12-91a3-872b2d017225               5m11s
kube-scheduler                         cnlab-vol5-control-plane_0b1a8d78-04b9-4cd1-a3ea-3be01c574518               5m10s
```

The holder is the identity of the running copy (node name plus a random suffix). `kubectl -n kube-system get lease kube-scheduler -o jsonpath='{.spec.leaseDurationSeconds}'` printed `15`. If the leader stops renewing, another copy takes over after the lease runs out. *See Field Guide → 2 · API machinery → Lease.*

## How it works · proof: stop one component at a time

The fastest way to learn what a component does is to remove it. Because the control plane is static Pods, moving a manifest out of `/etc/kubernetes/manifests` stops that component within seconds, and moving it back starts it. Break it in Lab 5.1 repeats all three experiments. These are the measured results:

| We stopped | What we did next | What happened |
| --- | --- | --- |
| **kube-controller-manager** | Deleted one `web` Pod, then scaled the Deployment from 2 to 4 | No replacement Pod. `kubectl get deploy` showed `2/4`: the API accepted the new `spec` but nobody acted. After the manifest was restored, 4 Pods ran within 25 s, three of them 6 s old. |
| **kube-scheduler** | Created a Pod with `kubectl run lonely` | Pod `Pending`, `NODE <none>`, `Events: <none>`. Not even a `FailedScheduling` event, because nobody tried. After the restore: `Scheduled` by `default-scheduler`, then `Running` on `cnlab-vol5-worker`. |
| **kube-apiserver** | Ran `kubectl get pods`, then `curl` against a `web` Pod IP from a worker node | `kubectl` failed (`connection reset by peer`). The `curl` returned `200`. The control plane was gone and the application kept serving. `kubectl` worked again within 30 s of the restore. |

Three lessons follow. A `spec` is a promise that nothing keeps until a loop runs. A Pod stuck `Pending` with *no events* points at the scheduler; one with a `FailedScheduling` event means the scheduler is alive and unhappy (Ch 5.4). And control plane and data plane fail separately: running Pods do not need the API server to keep running, but nothing can heal or change until it is back.

## In production

Big-tech teams treat the control plane as a database service: three or five control-plane machines, etcd on fast disks, and monitoring on the API server and etcd before anything else. Many teams do not run it at all and use a managed Kubernetes service; they still own the nodes, the workloads and every manifest in this volume. The failure modes below appear on both kinds of cluster.

| Symptom | Real cause | What engineers do |
| --- | --- | --- |
| `kubectl` hangs or says `connection refused` or `reset by peer`; running apps still answer | The API server or its etcd is down. Pods keep running because the kubelet and kube-proxy work from their last known state (measured in Lab 5.1, Break it, experiment 3). | `kubectl get --raw "/readyz?verbose"` if reachable; on the node, check the `kube-apiserver` and `etcd` static Pods and their logs; check etcd health before restarting anything. |
| `kubectl apply` succeeds, `kubectl get deploy` shows `2/4`, no new Pods, no events | The controller manager is not running or no instance holds its lease. | `kubectl -n kube-system get pods,lease`; read the `kube-controller-manager` logs on the node. |
| New Pod stays `Pending`, `NODE <none>`, **no events** | The scheduler is not running (a `FailedScheduling` event would mean it is running but finds no fit, Ch 5.4). | Check the `kube-scheduler` Pod and the `kube-scheduler` lease holder. |
| Writes fail, cluster seems read-only | etcd has no quorum, or its database passed its space quota: etcd "raises a cluster-wide alarm" and then "only accepts key reads and deletes" ([etcd maintenance](https://etcd.io/docs/latest/op-guide/maintenance/)). | `etcdctl endpoint status` and `alarm list`; compact and defragment, then clear the alarm. Take a snapshot first (Ch 5.5). |
| A custom controller logs `too old resource version` or `410 Gone` | It fell behind the roughly 5-minute watch history window (API concepts page). | Nothing to fix: a correct controller relists and restarts the watch. If it loops, the client library is misused. |
| After an upgrade a node refuses to join or Pods misbehave | Version skew: the kubelet "must not be newer than kube-apiserver"; it "may be up to three minor versions older" ([version skew policy](https://kubernetes.io/releases/version-skew-policy/)). | Upgrade the control plane first, then the nodes, never the other way round (Ch 5.5). |

## Project cards

**Kubernetes**

| Field | Content |
| --- | --- |
| Problem | Run containers across many machines as one system: place them, heal them, connect them, change them safely. |
| Layer / interface | The orchestration layer. Its own interface is the Kubernetes API (REST over HTTPS); it talks down to the CRI (runtimes), CNI (networking) and CSI (storage), and up to every tool in Vol 6-7. |
| Architecture | Control plane: kube-apiserver, etcd, kube-scheduler, kube-controller-manager (and cloud-controller-manager on clouds). Node: kubelet, kube-proxy, a container runtime. Everything else is a controller or add-on watching the API. |
| Alternatives | HashiCorp Nomad and Docker Swarm mode are simpler schedulers with smaller ecosystems; pick them when the team runs few services and does not need the CNCF tool ecosystem. A managed Kubernetes service removes the control plane from your care without changing the API. |
| CNCF maturity | Graduated, as listed on [cncf.io/projects](https://www.cncf.io/projects/) on 2026-11-16 (the project page gives graduation on March 6, 2018). |

**etcd**

| Field | Content |
| --- | --- |
| Problem | Store the cluster's state so that every control-plane member sees the same data, even when a machine fails. |
| Layer / interface | A distributed key-value store with a gRPC API (`get`, `put`, `watch`, leases). Kubernetes uses it only through the API server. |
| Architecture | A cluster of members that replicate writes with the Raft consensus protocol; one leader, the rest followers; a write needs a majority. Data lives in a bbolt file plus a write-ahead log. |
| Alternatives | ZooKeeper and Consul are other coordination stores. K3s ships SQLite as its default datastore and also supports external MySQL, MariaDB and PostgreSQL ([k3s datastore docs](https://docs.k3s.io/datastore)), which trades the multi-member Raft design for simpler small clusters. |
| CNCF maturity | Graduated, as listed on [cncf.io/projects](https://www.cncf.io/projects/) on 2026-11-16 (the project page gives graduation on November 24, 2020). |
