# Chapter 6.2 · Ingress, Gateway API and Service Mesh

{{diagram ch-6-2-01.jsx | Ch 6.2 at a glance}}

## The problem: a Service gets traffic to Pods, but not into the cluster or between teams safely

A Service gives Pods a stable address inside the cluster, but it cannot route by URL, terminate TLS, prove who is calling, or tell you which hop is slow.

The wallet from Vol 5 has a Service, so other Pods can reach it. Four needs are still open, and this chapter answers each:

1. **Reaching in from outside (north-south traffic).** Customers send `https://wallet.example.com/accounts/alice`. Something must accept that connection, pick the right Service by host and path, and handle TLS.
2. **Trusting callers inside (east-west traffic).** Pod-to-Pod traffic is plain text, and any Pod can claim to be any other. You want every connection encrypted and every caller identified.
3. **Resilience and visibility without code changes.** Timeouts, retries, per-route latency and error rates should not need a change in each of fifty services written in six languages.
4. **One portable way to say all this.** For years every ingress controller invented its own annotations, so a route written for one broke on another.

Kubernetes's first answer to need 1 was the `Ingress` API. The project now says plainly: "The Kubernetes project recommends using Gateway instead of Ingress. The Ingress API has been frozen" ([Ingress docs](https://kubernetes.io/docs/concepts/services-networking/ingress/)). It stays generally available and will not be removed, but it gets no new features. Its successor is Gateway API, which this chapter teaches, together with the service mesh that answers needs 2 and 3.

## How it works, part 1: from Ingress to Gateway API

Gateway API replaces the single Ingress object with three resources, so that the people who run the infrastructure, the cluster and the application each edit only their own part.

The [Gateway API project](https://gateway-api.sigs.k8s.io/docs) describes itself as "an official Kubernetes project focused on L4 and L7 routing in Kubernetes" and sets four goals: *role-oriented*, *portable*, *expressive* (header matching and traffic weighting are built in, not annotations) and *extensible*. Its resources are:

- **GatewayClass** "describes the actual kind of gateway controller that will handle traffic for the Gateway". A provider installs it once.
- **Gateway** "defines a point of access at which traffic can be routed": the listeners (port, protocol, hostname) and which namespaces may attach routes.
- **HTTPRoute** holds the routing rules. An application team writes one that matches a host and path and names the Service to send traffic to.

{{diagram ch-6-2-02.jsx | Gateway API · three resources, three roles}}

A route joins a Gateway with `parentRefs`; the Gateway joins a class with `gatewayClassName`. The controller for that class watches the objects and configures a proxy, usually Envoy (next part). The proxy does the actual forwarding; the Gateway API objects are only configuration.

Two more facts matter in practice. First, Gateway API is a set of CRDs, not part of the core API server, so you install the CRDs of a specific version before any controller will work; the Cilium 1.20.4 docs, for example, require the v1.6.3 CRDs. Second, the CRDs come in *standard* and *experimental* channels, and controllers differ in how much of each they implement. Always check the implementation's conformance list before relying on a feature.

## How it works, part 2: Envoy, the proxy under most gateways and meshes

Envoy is a general-purpose proxy that can be reconfigured while it runs, which is why gateways and meshes build on it instead of writing their own.

The [Envoy docs](https://www.envoyproxy.io/docs/envoy/latest/intro/what_is_envoy) define it as "an L7 proxy and communication bus designed for large modern service oriented architectures." Three design points matter here. It runs *out of process*, next to the application, so any language works and the proxy can be upgraded without touching the app. It has a *filter* architecture: network filters for TCP and UDP, and HTTP filters for buffering, rate limiting and routing. And it takes its configuration from *dynamic APIs* instead of only from a file.

The vocabulary is small. A **listener** is "a named network location that can be connected to by downstream clients"; a **cluster** is "a group of logically similar upstream hosts that Envoy connects to". A request enters a listener, passes through filters, is matched to a route, and is sent to a cluster, which picks one of its endpoints.

{{diagram ch-6-2-03.jsx | Envoy · listener to endpoints, configured over xDS}}

The dynamic APIs are collectively called [xDS](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/operations/dynamic_configuration), the "discovery service" APIs: LDS delivers listeners, RDS routes, CDS clusters, EDS the endpoints of a cluster, and SDS secrets such as certificates. When a Pod joins a Service, the control plane sends one EDS update and Envoy starts using the new endpoint with no restart. Istio and the Gateway API implementations in this chapter are, at heart, control planes that translate Kubernetes objects into Envoy configuration; Linkerd is the exception, with its own Rust proxy.

## How it works, part 3: the service mesh

A service mesh puts a proxy on the path of every service-to-service call, so that encryption, identity, retries and metrics become the proxy's job instead of the application's.

The call from `wallet-api` to `postgres` looks the same to the application, but both ends now talk to a local proxy, and the two proxies talk to each other. The application code does not change. There are two places to put the proxy.

{{diagram ch-6-2-04.jsx | service mesh data planes · sidecar vs ambient}}

**Sidecar.** A proxy container is added to every Pod. Linkerd's *proxy injector* is a Kubernetes admission controller that "receives a webhook request every time a pod is created" and adds the proxy; an init container, or Linkerd's CNI plugin, uses iptables to send the Pod's TCP traffic through it ([Linkerd architecture](https://linkerd.io/2-edge/reference/architecture/)). The proxy, `linkerd2-proxy`, is "an ultralight, transparent micro-proxy written in Rust". Istio's sidecar mode adds an Envoy proxy to each Pod instead. Because injection happens at Pod creation, Pods that already run must be restarted to join the mesh.

**Ambient.** Istio's [ambient mode](https://istio.io/latest/docs/ambient/overview/) removes the proxy from the Pod. A per-node proxy, *ztunnel*, handles "L3 and L4 functions such as mTLS, authentication, L4 authorization and telemetry" and does not parse HTTP. Only workloads that need Layer 7 features get an optional *waypoint*, "a deployment of the Envoy proxy". The stated benefits are incremental adoption and no change to application Pods; the stated cost is that a waypoint is heavier than ztunnel alone.

The mesh is not free. Every call now crosses two extra proxies, each consuming CPU and memory, and the mesh's control plane becomes something you must upgrade and keep healthy. Use a mesh when you need mTLS and per-service telemetry across many teams, not for three Pods.

## In production

Gateways fail at the edges of their configuration, and meshes fail when a certificate or an upgrade goes wrong.

| What you see | Real cause | What engineers do |
| --- | --- | --- |
| A `Gateway` exists but nothing answers; its status is not `Programmed` | No controller serves its `gatewayClassName`, the CRD versions do not match the controller, or the Service type `LoadBalancer` never gets an address (common on laptops) | Read `kubectl describe gateway` conditions first; install the CRD version the implementation documents (Cilium 1.20.4 asks for v1.6.3); on kind set `gatewayAPI.hostNetwork.enabled=true` so that Envoy listens on port 80 of each node (Lab 6.2), or give the Gateway an address pool. Without either, `kubectl get gateway` shows `PROGRAMMED False` and the reason `AddressNotAssigned` |
| A route returns 404 or is ignored | The `HTTPRoute` is not attached: wrong `parentRefs`, a hostname the listener does not allow, or a namespace the Gateway does not permit | Read the route's `status.parents` conditions; they state why it was not accepted |
| The whole mesh starts rejecting connections at a fixed time | Certificates expired. Proxy certificates "expire after 24 hours and are automatically rotated", but the issuer certificate and trust anchor above them have their own lifetimes (the Linkerd docs give 365 days for a trust anchor made by `linkerd install`) | Monitor expiry of the trust anchor and issuer; automate rotation (for example with cert-manager); rehearse replacing them before they expire |
| After meshing, a database or legacy client connection breaks | Linkerd's protocol detection "waits for up to 10 seconds to see bytes sent from the client", so a protocol where the server speaks first (the docs give SMTP) stalls unless its port is marked opaque; non-meshed clients are outside mTLS | Mark such ports opaque with the `config.linkerd.io/opaque-ports` annotation (PostgreSQL's 5432 is already on the default list); test each dependency after injection |
| New Pods start slowly or cost noticeably more CPU and memory | Every Pod now runs a proxy; every call crosses two extra hops | Measure before and after; set proxy resource requests; consider ambient mode or a smaller mesh scope |
| A mesh upgrade causes a partial outage | Control plane and proxies run different versions, and injected Pods keep their old proxy until restarted | Upgrade the control plane first, then restart workloads in waves; read the release notes; keep the previous version's rollback ready |
| Open source users cannot find a "stable" Linkerd chart | "As of February 2024, the Linkerd open source project itself no longer provides stable release artifacts"; edge releases are the open source channel and are "generally considered production ready" ([releases](https://linkerd.io/releases/)) | Pin an exact edge version in Git; read the release's notes before upgrading; or use a vendor distribution |

## Project cards

Maturity levels are as listed on [cncf.io/projects](https://www.cncf.io/projects/) and in the [CNCF landscape data](https://github.com/cncf/landscape), checked 2026-11-16.

### Envoy

| Field | Content |
| --- | --- |
| Problem | One programmable proxy that many gateways and meshes can build on, instead of each writing its own |
| Layer / interface | Data plane proxy; configured over the xDS APIs (LDS, RDS, CDS, EDS, SDS) |
| Architecture | One out-of-process proxy with listeners, filter chains (network and HTTP), routes and clusters; configuration arrives dynamically from a control plane ([what is Envoy](https://www.envoyproxy.io/docs/envoy/latest/intro/what_is_envoy)) |
| Alternatives | Linkerd's `linkerd2-proxy`, a micro-proxy written only for the mesh use case; a general reverse proxy such as NGINX or HAProxy when you need no dynamic xDS configuration |
| CNCF maturity | Graduated. Accepted 13 September 2017 at Incubating, Graduated 28 November 2018 ([cncf.io](https://www.cncf.io/projects/envoy/), as of 2026-11-16) |

### Gateway API

| Field | Content |
| --- | --- |
| Problem | One portable, role-oriented API for L4 and L7 traffic into and inside a cluster, replacing Ingress and its annotations |
| Layer / interface | Kubernetes API (CRDs in `gateway.networking.k8s.io`): `GatewayClass`, `Gateway`, `HTTPRoute` and others, each implemented by a controller |
| Architecture | Only an API specification. Implementations (Cilium, Envoy Gateway, Istio and others) watch the objects and program a proxy. CRDs come in standard and experimental channels ([Gateway API docs](https://gateway-api.sigs.k8s.io/docs)) |
| Alternatives | `Ingress` (frozen, no new features); the Service type `LoadBalancer` when you need only L4 |
| CNCF maturity | Not a separate CNCF project: it is developed by Kubernetes SIG Network inside the Kubernetes project, which is Graduated (accepted 10 March 2016, Graduated 6 March 2018). Cilium's docs require Gateway API CRDs v1.6.3 for Cilium 1.20.4 ([landscape data](https://github.com/cncf/landscape), as of 2026-11-16) |

### Linkerd

| Field | Content |
| --- | --- |
| Problem | Add mTLS, retries and per-service metrics to every connection with as little configuration and overhead as possible |
| Layer / interface | Service mesh: sidecar proxies injected by an admission controller; configured through CRDs (Server, AuthorizationPolicy and others) |
| Architecture | Control plane in the `linkerd` namespace: a destination service, an identity service that "acts as a TLS Certificate Authority", and a proxy injector. Data plane: `linkerd2-proxy`, "an ultralight, transparent micro-proxy written in Rust", per Pod ([architecture](https://linkerd.io/2-edge/reference/architecture/)). Certificates "expire after 24 hours and are automatically rotated" ([automatic mTLS](https://linkerd.io/2-edge/features/automatic-mtls/)) |
| Alternatives | Istio when you need Envoy's feature breadth or ambient mode; Cilium's own mesh features when you already run Cilium and want fewer moving parts |
| CNCF maturity | Graduated. Accepted 23 January 2017, Incubating 6 April 2018, Graduated 28 July 2021 ([cncf.io](https://www.cncf.io/projects/linkerd/), as of 2026-11-16). Release note: "as of February 2024, the Linkerd open source project itself no longer provides stable release artifacts"; open source users install edge releases ([releases](https://linkerd.io/releases/)) |

### Istio

| Field | Content |
| --- | --- |
| Problem | A full-featured mesh: traffic management, security and telemetry for many protocols and environments |
| Layer / interface | Service mesh; also a Gateway API implementation. Data plane is Envoy sidecars or, in ambient mode, per-node ztunnel plus optional waypoint proxies |
| Architecture | `istiod` is the control plane: it "provides service discovery, configuration and certificate management", converts routing rules into Envoy configuration and acts as the certificate authority for mTLS ([architecture](https://istio.io/latest/docs/ops/deployment/architecture/)). Ambient mode: ztunnel handles L4 and mTLS, a waypoint (Envoy) is deployed only where L7 features are needed ([ambient overview](https://istio.io/latest/docs/ambient/overview/)) |
| Alternatives | Linkerd when you want less to operate and need only mTLS and basic L7; Cilium service mesh features when the CNI is already Cilium |
| CNCF maturity | Graduated. Accepted 30 September 2022 at Incubating, Graduated 12 July 2023 ([cncf.io](https://www.cncf.io/projects/istio/), as of 2026-11-16) |
