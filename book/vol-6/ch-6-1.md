# Chapter 6.1 · Cluster Networking, CNI and eBPF

{{diagram ch-6-1-01.jsx | Ch 6.1 at a glance}}

## The problem: every Pod needs an address and a path, and Kubernetes ships neither

Kubernetes promises every Pod its own IP address and a direct path to every other Pod, but it does not contain the code that delivers the promise; a plug-in you install does.

The promise is short. The [Kubernetes network model](https://kubernetes.io/docs/concepts/services-networking/) says each Pod "gets its own unique cluster-wide IP address", and that all Pods "can communicate with all other Pods, whether they are on the same node or on different nodes" without "the use of proxies or address translation (NAT)". In Ch 2.5 you kept that promise by hand for two network namespaces on one machine: you made a veth pair, plugged one end into a bridge, and added routes. A real cluster has hundreds of nodes and Pods that start and die every few seconds, so a human with `ip` commands cannot keep up. Four questions follow, and this chapter answers each:

1. **Who wires a new Pod?** When the kubelet starts a Pod, something must create its interface, give it an address and add the routes. That something is a *CNI plugin*.
2. **How do packets cross nodes?** The nodes' own network knows nothing about Pod addresses. Either the plugin wraps Pod packets inside ordinary node-to-node packets (an *overlay*) or it teaches the network where each node's Pods live (*routing*).
3. **How does a Service address stay stable?** A Service IP is not on any interface. Something must rewrite it to a live Pod's IP; classically that was `kube-proxy`, and a modern plugin can do it in the kernel instead.
4. **Who may talk to whom?** Out of the box every Pod can reach every other Pod, including the database. A *NetworkPolicy* says otherwise, but it does nothing unless the plugin enforces it.

**Why this matters for operators.** A cluster with no working network plugin has nodes that stay `NotReady` and Pods stuck in `ContainerCreating`; a plugin that does not enforce NetworkPolicy gives you YAML that looks secure and is not. You will see the first one happen in Lab 6.1.

## How it works, part 1: the CNI contract

The Container Network Interface (CNI) is a small contract: when a Pod's sandbox is created, the container runtime runs a program from a list of plugins, passes it the Pod's network namespace, and the program must leave that namespace wired up.

A *network namespace* is the private copy of interfaces, addresses, routes and firewall rules that every Pod gets (Ch 1.5). The [CNI specification](https://github.com/containernetworking/cni/blob/main/SPEC.md) (version 1.1.0 at the time of writing) defines the conversation in four main verbs:

| Verb | Meaning in the spec |
| --- | --- |
| `ADD` | Create the interface in the container, or modify an existing one |
| `DEL` | Remove the interface or undo what `ADD` did; best-effort |
| `CHECK` | Verify the container's networking is still as expected |
| `VERSION` | Report which spec versions the plugin supports |

The runtime does not talk to a daemon. It starts the plugin executable, tells it what to do through environment variables (`CNI_COMMAND`, `CNI_CONTAINERID`, `CNI_NETNS`, `CNI_IFNAME`, `CNI_PATH`) and a JSON network configuration on standard input. On success the plugin exits with code 0 and prints a JSON result listing the `interfaces`, `ips` and `routes` it created. In a Kubernetes node that configuration is a file in `/etc/cni/net.d/`, and the plugin binaries sit in `/opt/cni/bin/`; the spec does not mandate those paths, but containerd's defaults use them and you will read both in Lab 6.1.

{{diagram ch-6-1-02.jsx | CNI ADD · one Pod start, four actors}}

Read it top to bottom: the kubelet asks the runtime for a sandbox over the CRI; the runtime creates an empty namespace and runs the plugin with `ADD`; the plugin builds `eth0`, the address and the routes inside that namespace and reports them; only then do the Pod's containers start.

Between Ch 2.5 and now one thing changes: *who* runs the commands. You typed `ip link add`, `ip netns` and `ip route add`; a CNI plugin runs the same kernel operations on every Pod start, in milliseconds, from the Pod's own namespace.

## How it works, part 2: crossing nodes, overlay or routing

To cross nodes a plugin either hides Pod addresses inside node packets (an overlay) or makes the network carry Pod addresses (routing); everything else about the choice follows from that.

Each node owns a slice of the cluster's Pod address range, the node's *PodCIDR*, so the IP alone says which node a Pod lives on. A plugin now needs to get a packet for `10.244.1.0/24`-style addresses to the right node. There are two designs.

{{diagram ch-6-1-03.jsx | Pod to Pod across nodes · overlay vs native routing}}

An **overlay** adds an outer header. Cilium's default is VXLAN: it wraps each Pod packet in a UDP packet to port 8472 between the two nodes, and the far node unwraps it ([Cilium routing docs](https://docs.cilium.io/en/stable/network/concepts/routing/)). The physical network only sees node-to-node UDP, so nothing there needs configuring. The price is about 50 bytes of header per packet, which lowers the usable MTU (the largest packet a link carries). **Native routing** adds nothing: the node hands the packet to the kernel's routing table, which needs a route to every other node's PodCIDR. If all nodes share one layer-2 network, the plugin can install those routes on each node itself (Cilium's `auto-direct-node-routes`); across routers, a BGP daemon must advertise them.

|  | Overlay (VXLAN, Geneve) | Native routing |
| --- | --- | --- |
| Network must | route node-to-node IP and UDP | route Pod ranges (shared L2, BGP or cloud routes) |
| Setup effort | lowest | higher |
| Per-packet cost | outer header, lower MTU | none |
| Debugging | tcpdump shows only node UDP unless you decode it | tcpdump shows the Pod addresses directly |
| Typical choice | laptops, kind, on-premises without BGP | cloud with native Pod routes, on-premises with BGP |

## How it works, part 3: eBPF and the end of kube-proxy

A Service address is virtual, so some component on every node must turn it into a real Pod address; kube-proxy does it with firewall rules, and Cilium can do it with small programs inside the kernel.

**kube-proxy.** For each Service, `kube-proxy` configures the node to capture traffic to the Service's `clusterIP` and redirect it to one of its endpoints. In Kubernetes 1.37 the default mode is `iptables`, and the [documentation](https://kubernetes.io/docs/reference/networking/virtual-ips/) warns that in clusters with tens of thousands of Pods and Services this means "tens of thousands of iptables rules" and slow updates. A future version is planned to default to `nftables`.

**eBPF.** *eBPF* lets you load a small, verified program into the kernel and attach it to a *hook*, a point where the kernel offers to run your code: a network driver (`XDP`), a network interface's traffic-control path (`tc`), or a socket operation inside a cgroup. Programs share data through *maps*, key-value tables in kernel memory that the agent fills and the programs read. Cilium's docs describe exactly these hooks and use maps to look up a packet's identity and policy, and a Service's backends ([Cilium eBPF datapath](https://docs.cilium.io/en/stable/network/ebpf/intro/)).

{{diagram ch-6-1-04.jsx | reaching a Service · iptables vs eBPF socket hook}}

**Kube-proxy replacement.** With `kubeProxyReplacement=true` Cilium handles ClusterIP, NodePort, LoadBalancer and external-IP Services itself. Its *socket-LB* feature selects the backend when the application calls `connect()`, so the connection goes straight to the Pod without extra NAT ([Cilium docs](https://docs.cilium.io/en/stable/network/kubernetes/kubeproxy-free/)). Because no kube-proxy exists to tell Cilium where the API server is, you must also give it `k8sServiceHost` and `k8sServicePort`. In Lab 6.1 you will install the cluster with no kube-proxy and check that Services still work.

## How it works, part 4: NetworkPolicy

By default every Pod accepts connections from everywhere; a NetworkPolicy changes that for the Pods it selects, and only a plugin that enforces it makes the change real.

The [Kubernetes documentation](https://kubernetes.io/docs/concepts/services-networking/network-policies/) is blunt: "Creating a NetworkPolicy resource without a controller that implements it will have no effect." Three rules explain almost every policy you will write:

1. **Selecting isolates.** A Pod is non-isolated until some policy selects it. A Pod is isolated for ingress if any policy selects it and lists `Ingress` in `policyTypes`; egress works the same way.
2. **Policies only add.** "Network policies do not conflict; they are additive." The allowed connections are the union of every applicable policy, so order never matters.
3. **Both ends must agree.** A connection needs the source's egress policy and the destination's ingress policy to allow it.

The pattern is therefore always the same: first a policy that selects every Pod and allows nothing (*default deny*), then one small policy per legitimate path.

{{diagram ch-6-1-05.jsx | NetworkPolicy · default deny plus three allowed paths}}

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
spec:
  podSelector: {}          # selects every Pod in the namespace
  policyTypes: [Ingress, Egress]
```

A rule's `from` or `to` entry can use `podSelector`, `namespaceSelector` or `ipBlock`. Put `namespaceSelector` and `podSelector` in the *same* entry and both must match (AND); put them in separate entries and either may match (OR). This single indentation difference is the most common NetworkPolicy bug.

**How Cilium enforces it.** Cilium does not match IP addresses, which change every time a Pod restarts. It derives a *security identity* from a Pod's labels, "entirely separates security from network addressing", and shares one identity between all Pods with the same labels ([identity docs](https://docs.cilium.io/en/stable/security/network/identity/)). Its eBPF programs look up the identity of the sender in a map and compare it with the policy for the receiver. That is also why `hubble observe` can print the verdict of every flow: the datapath already made the decision.

## In production

Most Pod-networking incidents come from four places: the address plan, the MTU, policy gaps and a missing way to see drops.

| What you see | Real cause | What engineers do |
| --- | --- | --- |
| New Pods stay `ContainerCreating` with a sandbox or network error, while old Pods run | The node has run out of Pod addresses. Each node owns one PodCIDR, and Kubernetes is designed for "no more than 110 pods per node" ([large clusters](https://kubernetes.io/docs/setup/best-practices/cluster-large/)); a small PodCIDR or leaked addresses exhaust it sooner | Plan PodCIDR size per node before the cluster exists; check the node's range against its Pod count; recreate nodes that leak addresses |
| Small requests work, large ones hang or reset | MTU mismatch: an overlay adds about 50 bytes (VXLAN) to every packet, so a Pod that sends full-size packets exceeds the link's MTU somewhere on the path | Let the plugin detect the MTU or set it explicitly; test with `ping -M do -s <size>`; remember tunnels inside tunnels (VPN, cloud overlay) add up |
| A NetworkPolicy exists but traffic is still open | The plugin does not enforce it, or the rule's selector does not match (labels differ, wrong namespace, AND versus OR) | Check enforcement with a deliberate deny test; use `kubectl get pods --show-labels`; read the selector indentation |
| Everything breaks after default deny, starting with DNS | No egress rule to `kube-dns`; every name lookup is dropped, so every connection that uses a name fails first | Ship one `allow-dns` policy with every default deny; test names, not only IPs |
| "It worked yesterday" after a node reboot or CNI upgrade | The agent or its eBPF programs restarted, or stale programs remain from an earlier install. The Cilium kind guide says to recreate the cluster and reinstall if API-server calls fail with "no route to host" after a reinstall | Roll CNI upgrades node by node; watch the agent's health; keep the CNI's version pinned in Git |
| A policy drops traffic and nobody knows which | No flow-level visibility | Turn on Hubble before you need it; filter by `--verdict DROPPED`; the verdict names the policy direction that denied the flow |

**The debugging order that saves time.** First prove the Pod has an address (`kubectl get pod -o wide`). Then prove Pod-to-Pod on the same node, then across nodes, then to a Service, then through policy. Each step removes one layer from the suspect list, and Hubble turns the last two from guesses into evidence.

## Project cards

Maturity levels below are as listed on [cncf.io/projects](https://www.cncf.io/projects/) and in the [CNCF landscape data](https://github.com/cncf/landscape), checked 2026-11-16. A project can be popular and still not hosted by the CNCF; the cards say so where it applies.

### Cilium

| Field | Content |
| --- | --- |
| Problem | Give Pods addresses, connect them across nodes, enforce policy and replace kube-proxy, all with kernel eBPF programs instead of long rule lists |
| Layer / interface | CNI plugin (`cilium-cni`), plus a Kubernetes API controller for NetworkPolicy, Services and Gateway API |
| Architecture | Per node: `cilium-agent` (watches Kubernetes, manages the eBPF programs) with the embedded Hubble server and a local CLI, `cilium-dbg`. Cluster-wide: `cilium-operator` for tasks that run once, such as IP address management; it is "not in the critical path for any forwarding or network policy decision". Optional: Hubble Relay and Hubble UI for flow visibility, and an Envoy proxy for Layer 7 features ([component overview](https://docs.cilium.io/en/stable/overview/component-overview/)) |
| Alternatives | Calico when you want its BGP-based routing and policy tiers; Flannel when you want the smallest possible network and no policy; the cloud provider's own CNI when Pod addresses must be native VPC addresses |
| CNCF maturity | Graduated. Accepted 13 October 2021 at Incubating, Graduated 11 October 2023 ([cncf.io](https://www.cncf.io/projects/cilium/), as of 2026-11-16) |

### Calico

| Field | Content |
| --- | --- |
| Problem | Route Pod traffic without an overlay where possible, and enforce rich network policy |
| Layer / interface | CNI plugin and IPAM plugin, plus a policy engine (Felix) on every node |
| Architecture | Felix "programs routes, ACLs, and other host settings" on its node; BIRD "gets routes from Felix and distributes to BGP peers"; confd regenerates BIRD's configuration; Typha sits between the datastore and many Felix instances to cut load at scale. The datastore is the Kubernetes API (recommended) or etcd ([architecture](https://docs.tigera.io/calico/latest/reference/architecture/overview)). Data planes listed on its feature page include eBPF, nftables, iptables, Windows and VPP ([about Calico](https://docs.tigera.io/calico/latest/about/about-calico)) |
| Alternatives | Cilium when you also want eBPF Services, Hubble and Gateway API in one agent; Flannel when you want no policy features at all |
| CNCF maturity | No CNCF maturity level: Project Calico is listed in the CNCF landscape as a member-company product, not as a CNCF-hosted project (as of 2026-11-16) |

### Flannel

| Field | Content |
| --- | --- |
| Problem | The simplest possible Pod network: one subnet per node and a tunnel (VXLAN) between nodes |
| Layer / interface | Network fabric for CNI: "a simple and easy way to configure a layer 3 network fabric designed for Kubernetes"; it "does not control how containers are networked to the host" ([README](https://github.com/flannel-io/flannel)) |
| Architecture | A `flanneld` agent on each node assigns that node a subnet from a larger range and forwards packets "using one of several backend mechanisms including VXLAN and various cloud integrations". Configuration and allocations live in the Kubernetes API (the *kube subnet manager*) or in etcd outside Kubernetes |
| Alternatives | Cilium or Calico as soon as you need NetworkPolicy: `flanneld` "does not natively enforce Network Policies", although its README mentions an optional integrated policy controller and pairing with Calico |
| CNCF maturity | No CNCF maturity level: Flannel is listed in the CNCF landscape without a CNCF project status (as of 2026-11-16) |

In this book the lab uses Cilium because one agent shows every idea in the chapter: the CNI contract, the datapath, kube-proxy replacement, NetworkPolicy and Hubble. That is a teaching choice, not a claim that it is right for every cluster.
