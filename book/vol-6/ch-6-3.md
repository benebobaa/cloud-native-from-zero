# Chapter 6.3 · Security and Supply Chain

{{diagram ch-6-3-01.jsx | Ch 6.3 at a glance}}

## The problem: a default cluster trusts everything it is given

Out of the box, Kubernetes runs any image it can pull, as any user the image names, and lets anyone with credentials do almost anything the credentials permit.

Security in a cluster is not one switch. An attacker needs only one weak step in a chain, so the defence is a chain of small checks, each assuming the one before it failed. Four questions organise this chapter:

1. **Is the software what we built?** Anyone who can push to your registry, or who tricks you into pulling a look-alike image, can run code in your cluster. You need proof of where an image came from.
2. **May this object enter the cluster at all?** A Pod that runs as root, mounts the host's disk or uses the host network can escape its container. You want a gate that rejects such Pods before they exist.
3. **Who may do what?** A leaked credential with broad rights is the most common way a cluster is lost. Rights must be small and reviewed.
4. **What is happening right now?** Prevention fails sometimes. You need something watching running containers for behaviour that should never occur, such as a shell inside the wallet's database Pod.

**Why this matters for the wallet.** The wallet moves money. After this chapter its images are signed, only signed images from your registry are admitted, its Pods must meet the *restricted* Pod Security level, and an alert fires if someone opens a shell inside it.

## How it works, part 1: one control per phase

The Kubernetes documentation organises cloud native security by the lifecycle of the software, and each phase has its own control; this chapter puts one tool on each.

The page [Cloud Native Security and Kubernetes](https://kubernetes.io/docs/concepts/security/cloud-native-security/) names four phases. **Develop** is "ensure the integrity of development environments". **Distribute** is "ensure the security of the supply chain for container images you execute". **Deploy** is "ensure appropriate restrictions on what can be deployed, who can deploy it, and where it can be deployed". **Runtime** has three areas: access, compute and storage.

{{diagram ch-6-3-02.jsx | controls by lifecycle phase · this chapter's tools}}

Read the drawing left to right: an image is built, then signed and stored, then checked when someone tries to deploy it, then watched while it runs. A weak earlier phase is only partly rescued by a strong later one, so the controls are cheapest when they stack.

## How it works, part 2: admission control

Admission control is a set of checks that run after a request is authenticated and authorized and before the object is stored, and any one of them can change the object or reject the request.

The [Kubernetes docs](https://kubernetes.io/docs/concepts/security/controlling-access/) give the order: the API server authenticates the caller, authorizes the action, runs admission control, validates the object against its schema and writes it to the store. In the [admission phase](https://kubernetes.io/docs/reference/access-authn-authz/admission-controllers/), "mutating admission controllers are run" first and "validating admission controllers" second. "If any admission controller module rejects, then the request is immediately rejected."

{{diagram ch-6-3-03.jsx | API request path · where admission policy plugs in}}

There are three ways to add your own rules, and you will use all of them:

| Mechanism | Where the rule runs | Written in | Use it for |
| --- | --- | --- | --- |
| Pod Security Admission | inside the API server (built in) | namespace labels | baseline Pod hardening, no extra software |
| ValidatingAdmissionPolicy | inside the API server, "a declarative, in-process alternative to validating admission webhooks" (stable since 1.30) | CEL expressions | simple checks on one object, no extra Pods to run |
| Admission webhook (Kyverno, Gatekeeper) | in a Pod the API server calls over HTTPS | YAML or CEL (Kyverno), Rego (Gatekeeper) | rules that need more than one field, mutation, image verification, reports |

**The webhook trade-off.** A webhook is another service that every matching request waits for. Its `failurePolicy` decides what happens when it is down: `Fail` rejects the request (safe, but a dead policy engine can block every deployment), `Ignore` lets it through (available, but unprotected). Production teams run several replicas, exclude the engine's own namespace from its rules, and test the failure case before relying on it.

## How it works, part 3: Pod Security Standards and RBAC

Two built-in mechanisms need no extra software: Pod Security Admission limits what a Pod may ask for, and RBAC limits what a caller may do.

**Pod Security Standards.** The [Pod Security Standards](https://kubernetes.io/docs/concepts/security/pod-security-standards/) define three levels:

| Level | The documentation's description | Typical use |
| --- | --- | --- |
| `privileged` | "Unrestricted policy, providing the widest possible level of permissions" | system components such as a CNI plugin |
| `baseline` | "Minimally restrictive policy which prevents known privilege escalations" | ordinary workloads with no hardening work |
| `restricted` | "Heavily restricted policy, following current Pod hardening best practices" | security-critical workloads such as the wallet |

The `restricted` level requires, among others: `allowPrivilegeEscalation: false`; running as non-root (`runAsNonRoot: true`, and no `runAsUser: 0`); a seccomp profile of `RuntimeDefault` or `Localhost`; capabilities that include `drop: [ALL]`; and only a short list of volume types (`configMap`, `emptyDir`, `secret`, `projected`, `persistentVolumeClaim` and a few others, but no `hostPath`).

[Pod Security Admission](https://kubernetes.io/docs/concepts/security/pod-security-admission/) applies a level to a namespace through labels of the form `pod-security.kubernetes.io/<MODE>: <LEVEL>`. The three modes are `enforce` ("Policy violations will cause the pod to be rejected"), `audit` (an annotation in the audit log) and `warn` (a warning shown to the user). Enforce applies to Pods only, "not to workload resources": a Deployment with a bad template is accepted, and its ReplicaSet then fails to create Pods. That is why a broken Deployment shows no error at `kubectl apply` and an event in `kubectl describe rs` instead.

**RBAC.** Role-based access control grants rights through four object kinds: `Role` and `ClusterRole` hold rules, `RoleBinding` and `ClusterRoleBinding` attach them to users, groups or ServiceAccounts. Per the [RBAC reference](https://kubernetes.io/docs/reference/access-authn-authz/rbac/), "permissions are purely additive (there are no "deny" rules)", so you shrink access by granting less, never by adding a deny. Four habits keep RBAC small:

1. **Bind to the narrowest scope.** Prefer a `RoleBinding` in one namespace over a `ClusterRoleBinding`.
2. **Treat some verbs as admin.** `escalate` and `bind` on roles let a user hand out rights they do not hold, and the API server only blocks that when those verbs are withheld. Reading Secrets (`get`, `list`) exposes every credential in the namespace.
3. **Give each workload its own ServiceAccount**, with no rights by default, instead of the shared `default` account.
4. **Ask the API server, not the YAML.** `kubectl auth can-i <verb> <resource> --as=<user> -n <ns>` answers what a subject can really do, after all bindings are combined.

## How it works, part 4: the supply chain, signatures and SBOMs

A signature proves who published an image and that it has not changed since; an admission policy that requires the signature turns that proof into a rule.

A container image is named by a *tag* (`wallet:v1`) that anyone with push rights can move to different content, and by a *digest* (`sha256:...`) that is a hash of the content and cannot move. Signing therefore targets the digest. [Sigstore's cosign](https://docs.sigstore.dev/cosign/signing/overview/) stores the signature in the same registry as the image, so no extra server is needed to hold it.

{{diagram ch-6-3-04.jsx | supply chain · sign at build, verify at admission}}

Cosign supports two ways to sign:

- **Key pair.** You make a private and a public key. CI signs with the private key; the cluster policy holds the public key. Simple and offline, but you must protect and rotate the private key. You will use this in Lab 6.3.
- **Keyless.** Sigstore's docs explain that it "associates identities, rather than keys, with an artifact signature": "Fulcio issues short-lived certificates binding an ephemeral key to an OpenID Connect identity", and signing events are logged in Rekor, a transparency log. There is no long-lived key to steal; the policy says *which identity* (for example, a specific CI workflow) is allowed to have signed.

A signature says who built an image, not that it is free of known flaws. Two further artifacts fill the gap. A *software bill of materials* (SBOM) lists every package inside an image, so you can search it when a new vulnerability is announced. A *vulnerability scan* compares that list with public databases. Registries such as Harbor "scan images regularly for vulnerabilities" and have "policy checks to prevent vulnerable images from being deployed" ([Harbor README](https://github.com/goharbor/harbor)).

## How it works, part 5: runtime detection

Prevention fails sometimes, so something must watch running containers for behaviour that should never happen and say so within seconds.

Falco "uses syscalls to monitor a system's activity" ([Falco docs](https://falco.org/docs/)). A *driver* in the kernel copies each system call event to Falco's user-space process. The default driver is the *modern eBPF probe*; a kernel module is the alternative. Falco enriches each event with container and Kubernetes metadata, so a rule can talk about "the wallet Pod in namespace wallet" rather than a bare process ID, and it compares the event with its *rules*: "the conditions under which an alert should be generated", written in YAML.

{{diagram ch-6-3-05.jsx | runtime detection · from syscall to alert}}

A runtime rule is a condition over events. "A shell started inside a container" is the classic one: a production wallet container never needs an interactive shell, so one that appears is either an engineer in a hurry or an intruder. Both deserve a message. The hard part in practice is not writing rules but tuning them, because a rule that fires a hundred times a day trains people to ignore it. Start with a few high-signal rules, route alerts somewhere a person reads, and widen later.

A driver needs kernel support. The [kernel-event docs](https://falco.org/docs/concepts/event-sources/kernel/) say the modern eBPF probe needs "BPF ring buffer support" and "a kernel that exposes BTF" (type information), and that kernels from 5.8 on are usually enough. A laptop kernel, a cloud kernel and a WSL2 kernel can all differ here, which is why Lab 6.3 checks before promising an alert.

## How it works, part 6: keeping Secrets out of Git

A Kubernetes `Secret` is only base64-encoded, so it cannot be committed as it is; secrets tools keep either ciphertext or a reference in Git instead.

The [Secrets page](https://kubernetes.io/docs/concepts/configuration/secret/) is direct: "Kubernetes Secrets are, by default, stored unencrypted in the API server's underlying data store (etcd)." It adds that "anyone who is authorized to create a Pod in a namespace can use that access to read any Secret in that namespace". Its minimum list is to enable encryption at rest, grant least-privilege RBAC on Secrets, restrict Secret access to specific containers, and consider external secret store providers.

Git makes the problem sharper. In Vol 7 the whole wallet is deployed from a Git repository, and a password pushed there stays in its history for good. Three tools answer the problem in three different places:

{{diagram ch-6-3-06.jsx | secrets management · three ways to keep values out of Git}}

Read each column top to bottom: what Git holds, who can turn it back into a value, and what reaches the cluster. The first row is the only thing a Git reader can see.

| Tool | What Git holds | Who can decrypt | Pick it when | CNCF status (landscape data, 2026-11-16) |
| --- | --- | --- | --- | --- |
| [Sealed Secrets](https://github.com/bitnami-labs/sealed-secrets) | A `SealedSecret`: "A Kubernetes controller and tool for one-way encrypted Secrets" | "only the controller running in the target cluster"; sealing keys "are automatically renewed every 30 days" | One cluster, no external secret store, plain GitOps | Not listed in the CNCF landscape |
| [External Secrets Operator](https://external-secrets.io/latest/) | An `ExternalSecret` that "describes what data should be fetched", and a `SecretStore` that says where from | The operator, using the store's credentials; `refreshInterval` is "the amount of time before the values reading again" | Your organisation already runs a vault or a cloud secret manager | Sandbox, accepted 26 July 2022 |
| [SOPS](https://getsops.io/docs/) | A file encrypted by "an editor of encrypted files" (YAML, JSON, ENV, INI, binary) with AWS KMS, GCP KMS, Azure Key Vault, age or PGP | Whoever, or whatever deploy step, can use the key | You also encrypt non-Kubernetes config, or your GitOps tool decrypts SOPS files | Sandbox, accepted 17 May 2023 |

None of the three removes the `Secret` object itself. The value still lands in etcd and is still readable by anyone with `get` on Secrets in that namespace, so encryption at rest and the RBAC habits of part 3 still apply. The labs pass the wallet's lab-only database password as a plain environment variable to stay short; Milestone 6 forbids committing any real secret.

## Commands you will use in the lab

Install `cosign` once, without root, with a pinned version: `GOBIN=$HOME/bin go install github.com/sigstore/cosign/v2/cmd/cosign@v2.6.1` (needs Go and, on the test machine, about 7 minutes; the project's release downloads are on GitHub).

| Command | What it does | Example |
| --- | --- | --- |
| `kubectl label ns <ns> pod-security.kubernetes.io/enforce=<level>` | Apply a Pod Security level to a namespace | `kubectl label ns wallet pod-security.kubernetes.io/enforce=restricted` |
| `kubectl describe rs <name>` | Read why a ReplicaSet could not create Pods | `kubectl describe rs -n wallet -l app=wallet-api` |
| `kubectl auth can-i <verb> <resource> --as=<subject> -n <ns>` | Ask the API server what a subject may do | `kubectl auth can-i list secrets --as=system:serviceaccount:wallet:default -n wallet` |
| `cosign generate-key-pair` | Create `cosign.key` (private) and `cosign.pub` (public) | `COSIGN_PASSWORD="" cosign generate-key-pair` |
| `cosign sign --key <key> <image>@<digest>` | Sign an image digest; the signature is stored in the registry | `cosign sign --key cosign.key --tlog-upload=false --yes $REF` |
| `cosign verify --key <pub> <image>` | Check a signature against a public key | `cosign verify --key cosign.pub --insecure-ignore-tlog=true $REF` |
| `kubectl get validatingpolicy,imagevalidatingpolicy` | List Kyverno policies and whether they are ready | `kubectl get validatingpolicy,imagevalidatingpolicy` |
| `kubectl logs -n falco -l app.kubernetes.io/name=falco` | Read Falco's alerts | `kubectl logs -n falco -l app.kubernetes.io/name=falco \| grep Notice` |
| `kubectl exec -it <pod> -- sh` | Open a shell in a container, the action Falco watches for | `kubectl exec -it deploy/wallet-api -n wallet -- sh` |

## In production

Security tooling fails in production for people reasons as often as technical ones: a policy that blocks everyone, rights nobody reviews, and alerts nobody reads.

| What you see | Real cause | What engineers do |
| --- | --- | --- |
| A new admission policy blocks a release at 5 pm | It went straight to enforcing mode on every namespace, and existing manifests were never checked against it | Roll out in stages: warn or audit first, read the report, fix the offenders, then enforce; scope by namespace with labels; always publish the rule and an exception process |
| Every `kubectl apply` hangs, then fails, when the policy engine is down | A fail-closed webhook (`failurePolicy: Fail`) with one replica and no exclusions | Run at least two replicas (Kyverno's install docs say high availability needs "2 or more replicas"), exclude the engine's own and system namespaces, and rehearse the outage |
| A service account can read every Secret in the cluster | A `ClusterRoleBinding` to a broad role, often added during an incident and never removed | Review bindings on a schedule; prefer `RoleBinding` per namespace; test with `kubectl auth can-i --as=` from the attacker's point of view |
| An image with a valid signature runs a known-vulnerable library | A signature proves origin, not quality | Pair signing with scanning (for example in the registry) and an SBOM, and rebuild images on a schedule |
| The signing key leaked, or CI can no longer sign | A long-lived private key stored as a plain CI secret, with no owner and no rotation plan | Prefer keyless signing tied to the CI identity; if you hold keys, keep them in a KMS or hardware module and rotate them |
| The runtime alert channel is muted | Too many alerts on normal behaviour, so people stopped reading them | Start with a few high-signal rules, route to a channel with an owner, tune rules against real baselines, and review what fired each week |
| Security tooling Pods themselves are rejected by the cluster's own policy | The Falco or CNI namespace needs privileges that the `restricted` level forbids | Give system namespaces an explicit, reviewed Pod Security exception; do not weaken the level for everyone |

**One rule of thumb.** Every control you add needs an owner, a way to test it, and a way to switch it to audit-only in a hurry. A control nobody can safely turn off will eventually be turned off permanently.

## Project cards

Maturity levels are as listed on [cncf.io/projects](https://www.cncf.io/projects/) and in the [CNCF landscape data](https://github.com/cncf/landscape), checked 2026-11-16.

### Kyverno

| Field | Content |
| --- | --- |
| Problem | Write admission, mutation, generation and image-verification rules in YAML and CEL, with no new language |
| Layer / interface | Kubernetes dynamic admission control (validating and mutating webhooks) plus reports; policies are CRDs |
| Architecture | An *admission controller* (required) handles the API server's webhook calls; a *background controller* (optional) processes generate and mutate-existing rules; a *reports controller* (optional) writes policy reports ([installation docs](https://kyverno.io/docs/installation/)). Policy kinds listed in the [introduction](https://kyverno.io/docs/introduction/): `ValidatingPolicy`, `MutatingPolicy`, `GeneratingPolicy`, `DeletingPolicy` and `ImageValidatingPolicy` |
| Alternatives | Gatekeeper if your organisation already writes Rego; built-in `ValidatingAdmissionPolicy` for simple single-object checks with nothing extra to run |
| CNCF maturity | Graduated. Accepted 10 November 2020, Incubating 13 July 2022, Graduated 16 March 2026 ([cncf.io](https://www.cncf.io/projects/kyverno/), as of 2026-11-16) |

### OPA Gatekeeper

| Field | Content |
| --- | --- |
| Problem | Enforce policy written once in Rego across many clusters, with an audit of what already violates it |
| Layer / interface | Kubernetes validating and mutating admission webhook; policies are CRDs |
| Architecture | "A validating and mutating webhook that enforces CRD-based policies executed by" Open Policy Agent. A `ConstraintTemplate` defines reusable policy logic; a `Constraint` instantiates it with parameters and match rules; *audit* reports resources that already violate a constraint ([Gatekeeper docs](https://open-policy-agent.github.io/gatekeeper/website/docs/)) |
| Alternatives | Kyverno for YAML-native policies and image verification; `ValidatingAdmissionPolicy` for simple CEL checks |
| CNCF maturity | Not listed on its own: the CNCF landscape lists OPA/Gatekeeper as a sub-entry without a maturity level, and the Open Policy Agent project it builds on is Graduated (accepted 29 March 2018, Incubating 2 April 2019, Graduated 29 January 2021; as of 2026-11-16) |

### Falco

| Field | Content |
| --- | --- |
| Problem | Notice, while it happens, that a container does something it should never do |
| Layer / interface | Runtime detection: a kernel driver (syscall events) feeding a userspace rules engine; alerts go to outputs |
| Architecture | "Falco uses syscalls to monitor a system's activity." It parses events from a driver (the modern eBPF probe is the default; a kernel module is the alternative), adds container and Kubernetes metadata, checks them against YAML rules, and writes alerts to stdout, a file, syslog, a program or an HTTP endpoint. `falcosidekick` forwards events to many channels; plugins add new event sources ([Falco docs](https://falco.org/docs/)) |
| Alternatives | Tetragon, "eBPF-based Security Observability and Runtime Enforcement" from the Cilium project, when you also want to block, not only alert |
| CNCF maturity | Graduated. Accepted 10 October 2018, Incubating 8 January 2020, Graduated 29 February 2024 ([cncf.io](https://www.cncf.io/projects/falco/), as of 2026-11-16) |

### Harbor

| Field | Content |
| --- | --- |
| Problem | A registry you run yourself, with access control, replication and vulnerability scanning on top of image storage |
| Layer / interface | OCI registry |
| Architecture | "An open source trusted cloud native registry project that stores, signs, and scans content", built on Distribution. Features include projects with role-based access, policy-based replication between registries, vulnerability scanning (the docs name Trivy as the scanner) with "policy checks to prevent vulnerable images from being deployed", LDAP and OIDC sign-in, audit logs and a REST API ([README](https://github.com/goharbor/harbor)). Deployed with Docker Compose or a Helm chart |
| Alternatives | A cloud provider's registry (ECR, GAR, ACR) when you do not want to operate one; the plain `registry:2` image for labs |
| CNCF maturity | Graduated. Accepted 31 July 2018, Incubating 14 November 2018, Graduated 15 June 2020 ([cncf.io](https://www.cncf.io/projects/harbor/), as of 2026-11-16) |

### cosign

| Field | Content |
| --- | --- |
| Problem | Prove who built a container image and that it has not changed, without running a signing server |
| Layer / interface | A command-line tool and Go library; signatures are stored in the OCI registry next to the image |
| Architecture | Part of the Sigstore project. Supports "keyless" signing with the Fulcio certificate authority and the Rekor transparency log (the default), signing with a cosign-generated key pair, hardware and KMS keys, and "bring-your-own PKI" ([README](https://github.com/sigstore/cosign)) |
| Alternatives | Notation, the CLI of the Notary Project (Incubating on the CNCF landscape), which "adds signatures as standard items in the OCI registry ecosystem" |
| CNCF maturity | No CNCF maturity level: Sigstore is listed in the CNCF landscape without a CNCF project status; its artwork lives under the OpenSSF (as of 2026-11-16) |
