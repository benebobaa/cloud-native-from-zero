# Chapter 7.3 · Extending Kubernetes and Platform Engineering

{{diagram ch-7-3-01.jsx | Ch 7.3 at a glance}}

## The problem

Kubernetes knows only the kinds of object it ships with, so every other job in your system stays manual work for a person.

Count the manual work around the wallet from Ch 7.1 and 7.2:

1. A new customer account exists only after someone runs `curl -X POST .../accounts`. No Kubernetes object stands for it, so nothing reviews it, versions it or repairs it.
2. The transfer backlog grows at month end. Someone watches a dashboard, runs `kubectl scale` by hand, and forgets to scale back.
3. A team asks for a database. A platform engineer follows a long runbook in a cloud console, and no two runs are quite the same.

Each job is knowledge that lives in a person's head. The cure is the one Kubernetes already uses for Pods: write the wish down as an object, and let a program make it true, again and again.

Kubernetes works this way inside. A Deployment says "three replicas"; the Deployment controller notices that only two Pods exist and creates the third. The [controller documentation](https://kubernetes.io/docs/concepts/architecture/controller/) describes controllers as control loops that watch the state of the cluster and move the current state closer to the desired state. Extension lets you add your own kinds of object (*custom resources*) and your own controllers. A controller that captures what a human operator knows about one application is called an *operator* ([operator pattern](https://kubernetes.io/docs/concepts/extend-kubernetes/operator/)).

**Why this matters.** Everything in this chapter is the same two ideas, a custom resource and a controller, used three ways. KEDA controls replica counts, Crossplane controls cloud resources, and Backstage is the front door that creates the objects. In Lab 7.3 you write one controller yourself, about 40 lines. The CKA 1.37 curriculum lists "Understand CRDs, install and configure operators" and the CKAD curriculum lists "Use the Helm package manager to deploy Kubernetes (CRD, Operators)" ([CNCF curricula](https://github.com/cncf/curriculum)).

## How it works · a new noun: the CustomResourceDefinition

A CustomResourceDefinition (CRD) teaches the API server a new kind of object; from then on `kubectl` treats it like a Pod.

The API server serves the new kind and stores its objects in etcd ([custom resources](https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/custom-resources/)). The CRD is itself an object, so you install one with `kubectl apply`. Lab 7.3 defines `WalletAccount`, one object per customer account:

```yaml
apiVersion: cnlab.example.com/v1
kind: WalletAccount
metadata: {name: carol}
spec: {owner: carol, openingBalance: 250}
```

The CRD that makes this object legal has six parts that matter. The CKA and CKAD exams ask you to read and edit them.

| Part of the CRD | What it decides | In Lab 7.3 |
| --- | --- | --- |
| `group`, `names`, `scope` | The API path, the kind and plural names `kubectl` accepts, and whether objects live in a namespace | group `cnlab.example.com`, kind `WalletAccount`, short name `wa`, `Namespaced` |
| `versions[]` with `served` and `storage` | Which versions the API answers; exactly one is the *storage version* written to etcd | one version, `v1`, both true |
| `schema.openAPIV3Schema` | The shape of every object: types, `required`, `minimum`, `default`, and CEL rules in `x-kubernetes-validations` | `owner` is required; `openingBalance` is an integer, at least 0, default 0 |
| `subresources.status` | A separate `/status` endpoint, so the controller writes status and users cannot overwrite it by editing the object | enabled |
| `subresources.scale` | Lets `kubectl scale` and the HPA resize a custom resource | not used |
| `additionalPrinterColumns` | Extra columns in `kubectl get` | `Balance` and `Ready`, read from `.status` |

The schema in the lab CRD looks like this:

```yaml
schema:
  openAPIV3Schema:
    type: object
    properties:
      spec:
        type: object
        required: [owner]
        properties:
          owner: {type: string, minLength: 1}
          openingBalance: {type: integer, minimum: 0, default: 0}
      status:
        type: object
        properties:
          phase: {type: string}
          balance: {type: integer}
```

The API server enforces this schema for you. It rejects a negative `openingBalance`, fills in the default, and *prunes* unknown fields: by default, fields the schema does not list are dropped before the object is stored ([CRD task](https://kubernetes.io/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/)). A typo such as `openingBalence: 250` vanishes silently when the client skips validation (for example kubectl apply --validate=false, or a script that posts JSON). kubectl 1.37 validates strictly by default and refuses such an object with strict decoding error: unknown field (tested in Lab 7.3), but other clients do not, so you still check with `kubectl get -o yaml`. The same schema feeds `kubectl explain walletaccount.spec`, so your CRD documents itself.

The status subresource matters for controllers. With it enabled, a `PUT` to `/status` changes only the status stanza, and writes to the main endpoint ignore status. A user edit and a controller update then cannot overwrite each other.

**Versions and conversion.** A CRD can serve several versions at once, such as `v1beta1` and `v1`, while etcd keeps one. The API server converts between them. If no field changes shape, the default `None` strategy only rewrites `apiVersion`; if it does, you must run a conversion webhook ([versioning](https://kubernetes.io/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definition-versioning/)).

**Danger.** Deleting a CRD deletes every object of that kind. The documentation says the server "will uninstall the RESTful API endpoint and delete all custom objects stored in it". Treat a CRD delete like `DROP TABLE`.

## How it works · a new verb: the controller loop

A controller is a loop that reads the wish, looks at the world, fixes the difference and writes down the result.

{{diagram ch-7-3-02.jsx | the controller loop · five steps, repeated}}

Read the loop with the wallet in mind. You create `WalletAccount carol` with `openingBalance: 250`. The loop reads that spec, asks the wallet API for `carol`, gets "no such account", posts the account, and patches the object's status to `Ready` with the balance it found. Run the loop again and nothing changes: the account exists, so there is nothing to fix. That property is *idempotence*, and every controller needs it, because the loop runs far more often than anything changes.

**Level-driven, not edge-driven.** An *edge-triggered* program reacts to each event ("a was created"). A *level-triggered* one compares the whole state each time it wakes ("a, b and c should exist; which are missing?"). The Kubernetes [controller-writing guide](https://github.com/kubernetes/community/blob/master/contributors/devel/sig-api-machinery/controllers.md) says controllers must be level driven because "your controller may be off for an indeterminate amount of time before running again".

{{diagram ch-7-3-03.jsx | edge-triggered against level-triggered · one outage, two outcomes}}

The same guide says informers can periodically *resync*, which replays every cached object to the handler so skipped work is retried. The Lab 7.3 operator gets the same effect more simply: it starts a fresh watch every minute, and a fresh watch replays existing objects as `ADDED` events.

## How it works · anatomy of an operator

A production operator wraps the loop in a cache, a queue and three kinds of output, so it stays fast and safe with thousands of objects.

{{diagram ch-7-3-04.jsx | operator anatomy · informer, queue, reconcile and three outputs}}

- **Informer.** One watch stream per kind fills a local cache, and the controller reads the cache instead of asking the API server each time. The [controller guide](https://github.com/kubernetes/community/blob/master/contributors/devel/sig-api-machinery/controllers.md) tells authors to use `SharedInformers`, so that controllers share one cache.
- **Work queue.** Events become keys such as `default/carol`. A queue guarantees that no two workers handle the same key at the same time, and the guide recommends a rate-limited queue so failed keys return with back-off.
- **Reconcile.** A function from key to outcome. It re-reads the object, so it never trusts the event that woke it.
- **Status.** After acting, the controller writes `status` through the `/status` subresource. The guide also recommends `observedGeneration`, so clients can tell which version of the spec a status describes.
- **Children.** Objects the controller creates carry an `ownerReference` to the custom resource. Delete the owner and the garbage collector deletes the dependents.

You rarely write this plumbing yourself. The Kubernetes [operator page](https://kubernetes.io/docs/concepts/extend-kubernetes/operator/) lists libraries for it, among them kubebuilder (Go), Kopf (Python), kube-rs (Rust) and the Java Operator SDK. The Lab 7.3 operator is the smallest honest version. It uses the Python client's watch, has no cache or queue, and handles one event at a time.

## How it works · owners, finalizers and cleanup

Kubernetes cleans up what it owns, but it cannot clean up what lives outside the cluster, and for that you need a finalizer.

An *owner reference* tells the control plane that one object depends on another. When you delete the owner, *cascading deletion* removes the dependents, either in the foreground or in the background ([garbage collection](https://kubernetes.io/docs/concepts/architecture/garbage-collection/)). A Deployment owns its ReplicaSets, and a ReplicaSet owns its Pods, in exactly this way.

A wallet account lives in Postgres, not in the Kubernetes API, so the garbage collector cannot see it. A *finalizer* is a key in `metadata.finalizers` that tells Kubernetes to wait before it fully deletes an object ([finalizers](https://kubernetes.io/docs/concepts/overview/working-with-objects/finalizers/)). On `kubectl delete` the API server sets `metadata.deletionTimestamp` and returns 202; the object stays in the terminating state until the controller has done its cleanup and removed its key.

{{diagram ch-7-3-05.jsx | deletion with a finalizer · three states, one controller}}

| Mechanism | Cleans up | Who acts | Example |
| --- | --- | --- | --- |
| `ownerReferences` | Other Kubernetes objects | The garbage collector, built in | Deployment, ReplicaSet, Pods |
| Finalizer | Anything outside the API, or work that must finish first | Your controller | Delete the external account, then remove the key |

The lab operator sets no finalizer. The wallet API has no delete endpoint, so deleting a `WalletAccount` leaves the account in the database. Decide on purpose what "delete" should mean for every operator you write.

## How it works · autoscaling on events: KEDA

The HPA scales on a metric; KEDA lets that metric be the thing your application really waits for, such as rows in a backlog table.

The Horizontal Pod Autoscaler compares a current metric with a target and sets the replica count by this rule ([HPA docs](https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale/)):

```latex
desiredReplicas = \lceil currentReplicas \times \frac{currentMetricValue}{desiredMetricValue} \rceil
```

If the current value is 200m and the target is 100m, the replicas double. The HPA reads metrics from aggregated APIs: `metrics.k8s.io` (served by Metrics Server), `custom.metrics.k8s.io` and `external.metrics.k8s.io`. Out of the box it knows only CPU and memory, a poor signal for a worker that mostly waits on a database. The real signal is the backlog.

{{diagram ch-7-3-06.jsx | classic HPA against KEDA · same HPA, different metric source}}

KEDA runs three components in the cluster ([KEDA concepts](https://keda.sh/docs/2.21/concepts/)):

- `keda-operator` watches `ScaledObject` resources, creates and manages the HPA, and scales a workload between zero and one replica.
- `keda-metrics-apiserver` serves the polled values (here, a SQL query result) to the HPA as external metrics.
- `keda-admission-webhooks` validate every KEDA resource when you apply it, for example by rejecting two `ScaledObject`s for one Deployment.

So two tracks share the work. KEDA itself handles 0 to 1 and 1 to 0. The HPA, driven by KEDA's metric, handles 1 to N and N to 1.

**Worked numbers (Lab 7.3 settings).** The trigger is `SELECT count(*) FROM transfers WHERE status = 'pending'` with `targetQueryValue: "2000"`. KEDA's default `metricType` is `AverageValue`, which means each replica should handle about 2,000 pending rows ([ScaledObject spec](https://keda.sh/docs/2.21/reference/scaledobject-spec/)). So a backlog of 7,000 gives ⌈7000 / 2000⌉ = 4 replicas. A backlog of 20,000 asks for 10, but `maxReplicaCount: 5` caps it at 5. A backlog of 1,500 gives 1, which is also the minimum.

**A trap on the way down.** `cooldownPeriod` is "the period to wait after the last trigger reported active before scaling the resource back to 0" ([spec](https://keda.sh/docs/2.21/reference/scaledobject-spec/)). The lab sets `minReplicaCount: 1`, so scaling never goes to 0 and `cooldownPeriod` never applies. Going from 5 replicas to 1 is the HPA's job, and its default scale-down stabilization window is 300 seconds. Expect replicas to stay high for about five minutes after the backlog is gone. That is the HPA protecting you from flapping, not a bug.

## How it works · control planes as APIs: Crossplane

Crossplane lets a platform team offer a new Kubernetes API without writing a controller for it.

The Crossplane documentation calls it "a control plane framework for platform engineering" and says its key value is that it "unlocks the benefits of building your own Kubernetes custom resources without having to write controllers for them" ([What's Crossplane?](https://docs.crossplane.io/latest/whats-crossplane/)). Instead of code, you configure a pipeline of functions that return the objects Crossplane should apply.

{{diagram ch-7-3-07.jsx | Crossplane composition · XRD, composite resource, composition, outputs}}

Four terms carry the idea:

- A **composite resource definition (XRD)** defines the schema of a new API. It works like a CRD with a few Crossplane options ([XRD docs](https://docs.crossplane.io/latest/composition/composite-resource-definitions/)).
- A **composite resource (XR)** is one object of that API, written by a developer.
- A **Composition** is the pipeline of functions that turns an XR into other objects.
- A **managed resource (MR)** represents an external service in a *provider*. When someone creates one, the provider reacts by creating the external resource ([managed resources](https://docs.crossplane.io/latest/managed-resources/managed-resources/)).

Crossplane v2 changed the vocabulary. Composite and managed resources are now namespaced, a Composition can produce any Kubernetes resource, and the documentation says v2 "removes the need for awkward abstractions like claims" ([What's new in v2](https://docs.crossplane.io/latest/whats-new/)). Older blog posts and videos still teach claims, so check which version they describe.

A wallet illustration, not run in the labs: a `WalletDatabase` XR with one field, `size`, could become a Postgres StatefulSet in a dev namespace and a managed cloud database in production. Helm (Ch 7.1) renders its templates once and stops. Crossplane keeps reconciling, so a deleted or drifted resource comes back. Your Lab 7.3 operator is the hand-written version of the same idea; Crossplane replaces the code with configuration.

## How it works · internal developer platforms and golden paths

A platform is a set of self-service APIs, tools and documentation that lets product teams ship without learning every layer under them.

The CNCF [Platforms white paper](https://tag-app-delivery.cncf.io/whitepapers/platforms/) quotes Martin Fowler and Evan Bottcher: "a digital platform is a foundation of self-service APIs, tools, services, knowledge and support which are arranged as a compelling internal product." It calls an initial project template plus documentation "a bundle often described as a golden path".

[Backstage](https://backstage.io/docs/overview/what-is-backstage) is an open source framework for building the portal on top. Its Software Catalog tracks ownership and metadata for all your software, using YAML files stored next to the code ([catalog](https://backstage.io/docs/features/software-catalog/)). Its Software Templates load a code skeleton, fill in variables and publish the result to a place such as GitHub or GitLab ([templates](https://backstage.io/docs/features/software-templates/)). TechDocs keeps documentation as code.

{{diagram ch-7-3-08.jsx | internal developer platform · one golden path from portal to cluster}}

Read the picture from left to right. A developer picks a template. The template creates a repository holding the Helm chart and Argo CD Application from Ch 7.1, a `/metrics` endpoint like the one in Ch 7.2, and a KEDA `ScaledObject` from this chapter. Argo CD syncs it, and operators in the cluster do the rest. The developer never wrote a manifest. Backstage is described here, not run in the labs.

## In production

Operators fail in a few repeatable ways, and nearly all of them concern deletion, upgrades and loops that never settle.

| Symptom | Real cause | What engineers do |
| --- | --- | --- |
| An object stays `Terminating` for hours | It carries a finalizer, and the controller that owns the key is down, crashed or lacks permission to patch the object | Read `metadata.finalizers`, then restart or fix the controller. Remove the key by hand only after you have cleaned up the external resource yourself |
| After a CRD upgrade, old objects are rejected or fields vanish | The new schema is stricter, a field was renamed, and unknown fields are pruned. Or a second version changed shape with no conversion webhook | Add the new version beside the old one, keep both `served`, convert with a webhook when shapes differ, and test with copies of real objects. Never delete the CRD to reset it: that deletes every object |
| `helm upgrade` of an operator leaves the old CRD in place | Helm installs CRDs from a chart's `crds/` directory but has "no support at this time for upgrading or deleting CRDs" ([Helm docs](https://helm.sh/docs/chart_best_practices/custom_resource_definitions/)) | Apply new CRD YAML yourself (`kubectl apply`) before the upgrade, or ship CRDs in a separate chart. Read the operator's upgrade notes |
| The operator burns a full CPU core and the API server logs throttling | A reconcile hot loop: the controller writes to the object it watches, for example a status field with a changing timestamp, and that write wakes it again | Patch only when a value really changed, use a rate-limited queue, and ignore events caused by your own status writes |
| The operator log shows `Forbidden` | Its ServiceAccount lacks a verb on the resource, or on the `/status` subresource | Test with `kubectl auth can-i --as system:serviceaccount:<ns>:<name>`, then grant a least-privilege Role for `walletaccounts` and `walletaccounts/status` |
| Duplicate side effects after the operator restarts or crashes mid-reconcile | The reconcile was not idempotent: it created things with random names, or without checking first | Derive names from the object, check before you create, and make external calls idempotent, as the wallet's repeated `POST /accounts` is. Level-driven restarts then repair the rest |
| KEDA scales up and down every few minutes | The target sits inside the normal noise of the metric, or the HPA scale-down window is short | Choose a target that matches one replica's real throughput, and tune the HPA `behavior` block of the ScaledObject |
| Replicas stay at the minimum although the backlog is large | KEDA cannot read the trigger: wrong credentials, a query that errors or returns null, or a ScaledObject that is not Ready | `kubectl describe scaledobject`, read the `keda-operator` log, and run the query by hand with the same credentials |
| The operator's memory grows with the cluster | Its cache holds every object it watches, and a cluster-wide watch lists everything | Watch only the namespaces or labels you need, keep objects small, set a memory limit and watch for `OOMKilled` (Ch 1.2) |
| One team's workload starves its neighbours | A shared cluster with no per-namespace limits | Give each tenant a namespace with a ResourceQuota and LimitRange (Vol 5), and scale on backlog rather than letting one team's burst take the node |

## Project cards

CNCF maturity levels below come from the [CNCF project pages](https://www.cncf.io/projects/) and the [landscape file](https://github.com/cncf/landscape/blob/master/landscape.yml), as of 2026-11-16.

**KEDA**

| Field | Content |
| --- | --- |
| Problem | Scale a workload on the backlog it must clear (queue length, table rows, events), including down to zero, instead of on CPU |
| Layer / interface | Kubernetes API: custom resources (`ScaledObject`, `ScaledJob`) with controllers, plus the external metrics API (`external.metrics.k8s.io`) that the HPA reads |
| Architecture | `keda-operator` (manages the HPA, scales 0 to 1 and back), `keda-metrics-apiserver` (serves the polled values), `keda-admission-webhooks` (validate resources); one *scaler* per event source, such as the PostgreSQL scaler in the lab ([concepts](https://keda.sh/docs/2.21/concepts/)) |
| Alternatives | Plain HPA on CPU or memory when load follows CPU. HPA with external or custom metrics through an adapter such as [Prometheus Adapter](https://github.com/kubernetes-sigs/prometheus-adapter) when the signal is already in Prometheus. Pick KEDA when the signal is a queue or database and a ready-made scaler exists |
| CNCF maturity | Graduated: accepted 2020-03-12, incubating 2021-08-18, graduated 2023-08-22 ([cncf.io](https://www.cncf.io/projects/keda/)) |

**Crossplane**

| Field | Content |
| --- | --- |
| Problem | Give teams a self-service API for infrastructure and applications, built from YAML, without writing and running a controller for each one |
| Layer / interface | Kubernetes API: CRDs generated from XRDs, reconciled by Crossplane's composition engine, and by providers for managed resources |
| Architecture | Four components: Composition, managed resources, Operations and a package manager. XRDs define APIs, Compositions run function pipelines, providers are packages that define managed resources ([docs](https://docs.crossplane.io/latest/whats-crossplane/)) |
| Alternatives | A hand-written operator (kubebuilder, Kopf) when the logic is specific to one application. Per-cloud controllers such as [AWS Controllers for Kubernetes](https://aws-controllers-k8s.github.io/community/docs/community/overview/). [Cluster API](https://cluster-api.sigs.k8s.io/introduction) when the thing you provision is a Kubernetes cluster |
| CNCF maturity | Graduated: accepted 2020-06-25, incubating 2021-09-14, graduated 2025-10-28 ([cncf.io](https://www.cncf.io/projects/crossplane/)) |

**Backstage**

| Field | Content |
| --- | --- |
| Problem | Make software, owners, documentation and "how do I start a new service" findable in one place |
| Layer / interface | A developer portal above the cluster, not a Kubernetes controller. Plugins connect it to Git hosts and delivery tools |
| Architecture | Software Catalog (metadata YAML kept with the code), Software Templates (skeleton, variables, publish), TechDocs (docs as code) and a plugin ecosystem ([overview](https://backstage.io/docs/overview/what-is-backstage)) |

## Platform engineering in five rules

A platform is a product for developers, and it pays off only when many teams share it.

1. **Treat it as a product.** The CNCF white paper lists as a challenge that "platform teams must treat their platforms like products and develop them together with users", and warns that teams that rely on top-down mandates for adoption "are almost certain to find resistance and resentment" ([Platforms white paper](https://tag-app-delivery.cncf.io/whitepapers/platforms/)).
2. **Start with common, undifferentiated needs.** The paper suggests pipelines, databases and observability as good first capabilities.
3. **Start with a few engaged teams.** Their feedback shapes the first version, and they become the champions for the next teams.
4. **Make the golden path the easy road.** A template plus documentation that holds the sensible defaults, as in the picture above.
5. **Know your team type.** In [Team Topologies](https://teamtopologies.com/key-concepts) the platform team is one of four fundamental team types. It provides "a compelling internal product to accelerate delivery by Stream-aligned teams", usually through the X-as-a-Service interaction mode.

**When not to build one.** The white paper's argument is that a few platform teams serve many product teams. With two product teams and one cluster, a shared Helm chart, a short README and good defaults in Git give most of the benefit at none of the running cost. This is our inference from that argument; the paper gives no threshold.
