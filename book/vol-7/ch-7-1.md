# Chapter 7.1 · Packaging and GitOps

{{diagram ch-7-1-01.jsx | Ch 7.1 at a glance}}

## The problem

A cluster is only as reliable as the way changes reach it, and `kubectl apply -f` from a laptop is the least reliable way there is. You have used that command since Vol 5. It works for one person and one cluster. It breaks the moment a team and three environments appear.

Three things go wrong, in this order:

1. **Copies.** The wallet needs almost the same YAML in dev (1 API replica) and prod (3 replicas, a bigger memory limit). Teams copy the files and edit them. After a month the copies differ in ways nobody remembers.
2. **Drift.** Someone runs `kubectl edit` at 2 a.m. to fix an incident. The cluster now differs from every file on disk, and nobody can say what is really running or who changed it.
3. **No way back.** A bad release needs the previous YAML. It is in somebody's shell history, or it is not anywhere.

Two ideas fix this. **Packaging** (Helm and Kustomize) generates the per-environment YAML from one source, so there are no copies. **GitOps** makes a git repository the only door into the cluster: a program inside the cluster pulls the desired state from git and keeps the cluster equal to it. Git then gives you history, review and rollback for free: a rollback is a `git revert`.

**Why this matters for the exams.** The CKA and CKAD 1.37 curricula both list Helm and Kustomize ([CKA](https://github.com/cncf/curriculum/blob/main/CKA_Curriculum_v1.37.pdf): "Use Helm and Kustomize to install cluster components"; [CKAD](https://github.com/cncf/curriculum/blob/main/CKAD_Curriculum_v1.37.pdf): "Use the Helm package manager to deploy Kubernetes" and "Kustomize"). Argo CD and Flux are not examined, but you will meet one of them in almost every team that runs Kubernetes.

## How it works · Helm: a chart is a template plus defaults

Helm turns one folder of templates and one file of default values into the YAML for a particular installation. The folder is a **chart**. A chart is "a collection of files that describe a related set of Kubernetes resources" ([Helm docs](https://helm.sh/docs/topics/charts/)). The wallet chart you build in Lab 7.1 looks like this:

```text
wallet/
  Chart.yaml          name, chart version, appVersion
  values.yaml         the defaults a user may override (no password in it)
  templates/
    _helpers.tpl      small named snippets, shared by the other templates
    api.yaml          Deployment + Service for the API
    worker.yaml       Deployment for the worker
    postgres.yaml     StatefulSet + Service, only if postgres.enabled
                      (no secret.yaml: the Secret wallet-db must already exist)
```

A template is a normal manifest with holes written in Go template syntax (`{{ ... }}`). Helm fills the holes from the **values** and prints plain YAML:

```yaml
# templates/api.yaml (excerpt)
spec:
  replicas: {{ .Values.api.replicas }}
  template:
    spec:
      containers:
      - name: api
        image: {{ include "wallet.image" . }}   # -> wallet:v1
```

A user overrides a default at install time: `helm install wallet ./wallet --set api.replicas=3` or `-f prod-values.yaml`. Later values win over earlier ones.

{{diagram ch-7-1-02.jsx | how Helm installs a chart · render, apply, record}}

Read it left to right: the two inputs meet in `helm`, the output is plain YAML, and the same YAML goes to the API server while Helm records the release.

Three words matter, and people mix them up:

| Word | Meaning | Example |
| --- | --- | --- |
| Chart | The package: templates plus defaults. Has a `version`; `appVersion` is the version of the app inside | `wallet-0.1.0`, app `v1` |
| Release | One named installation of a chart in one namespace. Each upgrade is a new numbered **revision** | `wallet`, revision 3 |
| Repository | A web server or OCI registry that hosts charts | `https://prometheus-community.github.io/helm-charts` |

Helm keeps the history of every release inside the cluster. "By default, release information is stored in Secrets in the namespace of the release" ([Helm docs](https://helm.sh/docs/topics/advanced/)). That is why `helm history wallet` and `helm rollback wallet 2` work from any laptop that can reach the cluster: the state is in the cluster, not on your machine.

**Render without a cluster.** `helm template` prints the final YAML and `helm lint` checks the chart. Both need no cluster, so they belong in CI. Most chart bugs are visible in the rendered YAML: wrong indentation, a value that is missing, a string that should have been quoted.

**Hooks and dependencies.** A chart can run a Job before an install or upgrade (for example a database migration) with a hook annotation, and it can list other charts as dependencies (a chart for the wallet could depend on a Postgres chart). Both are useful and both make charts harder to read; use them with care.

**One limit to remember.** Helm installs the CRDs in a chart's `crds/` folder once, but "there is no support at this time for upgrading or deleting CRDs using Helm" ([Helm docs, best practices](https://helm.sh/docs/chart_best_practices/custom_resource_definitions/)). Operators that ship CRDs (Ch 7.3) therefore need a separate CRD upgrade step.

## How it works · Kustomize: patch the YAML you already have

Kustomize builds each environment by laying small patches over a plain base, with no templates at all. The base is ordinary, valid YAML that you could `kubectl apply` as it is. An **overlay** is a folder with a `kustomization.yaml` that points at the base and lists what to change. Kustomize is built into kubectl (`kubectl kustomize` and `kubectl apply -k`); kubectl 1.37.1 ships Kustomize v5.8.1.

The wallet repo has one base and two overlays:

```text
kustomize/
  base/                  postgres.yaml api.yaml worker.yaml kustomization.yaml
                         (they read the password from Secret wallet-db, key POSTGRES_PASSWORD)
  overlays/dev/          kustomization.yaml   -> 1 API replica, label env=dev,
                                                 Secret wallet-db generated (LAB ONLY)
  overlays/prod/         kustomization.yaml   -> 3 API replicas, 256Mi limit, label env=prod
                                                 no Secret: it comes from outside git
```

The prod overlay is the whole difference between the environments, and it is short:

```yaml
# overlays/prod/kustomization.yaml
resources: [../../base]
labels:
- pairs: {env: prod}
patches:
- target: {kind: Deployment, name: wallet-api}
  patch: |-
    - {op: replace, path: /spec/replicas, value: 3}
    - {op: replace, path: /spec/template/spec/containers/0/resources/limits/memory, value: 256Mi}
```

The patch above uses the JSON Patch format (`op`, `path`, `value`). Kustomize also accepts a strategic-merge patch, which is a partial copy of the object. Other built-in transformers cover the common cases: `images` changes an image name or tag, `labels` adds labels, `namePrefix` and `namespace` rename and move everything, and `secretGenerator` and `configMapGenerator` create objects from literals or files. A generated name gets a hash suffix (the wallet's secret rendered as `wallet-db-dg6b9c9668` on the test machine); when the content changes, the name changes, so Pods that use it roll automatically.

**Where the password lives.** The base never contains the Postgres password. Each of the three workloads reads it from a Secret with `valueFrom.secretKeyRef` (name `wallet-db`, key `POSTGRES_PASSWORD`), and the Secret is generated only in the dev overlay, with a `purpose: lab-only` label and a comment saying so. A literal password in git is exactly what production must never have, because git history is forever. In production the overlay has no `secretGenerator`: the Secret `wallet-db` is created by a controller from an encrypted or external source, such as Sealed Secrets (an encrypted `SealedSecret` is safe to commit), the External Secrets Operator (it copies a value from a vault into a Secret) or SOPS (it encrypts the values inside a YAML file). Ch 6.3 [Security](https://benelabs.tech/cloud-native-from-zero/vol-6/ch-6-3.html) explains why a Kubernetes Secret is only base64, not encryption. The Helm chart follows the same rule: it has an `existingSecret` value and no password.

{{diagram ch-7-1-03.jsx | Kustomize layering · one base, two overlays}}

Helm and Kustomize solve the same problem from opposite sides. Pick by the question you are asking:

|  | Helm | Kustomize |
| --- | --- | --- |
| Idea | Template with values | Plain base plus patches |
| Best for | Software you ship to others (many users, many options) | Your own app in your own environments |
| Strength | Versioned packages, a public ecosystem, release history and rollback | No new language, base stays valid YAML, built into kubectl |
| Weakness | Go templates and indentation are easy to get wrong | Cannot express loops, conditions or a large option surface |
| State in the cluster | Yes: a release object per revision | No: output is plain YAML, tracking is left to kubectl or Argo CD |

They combine well. Argo CD can render a Helm chart for third-party software and a Kustomize overlay for your own services, in the same repository.

## How it works · GitOps: the cluster pulls its own state from git

In GitOps a program inside the cluster keeps the cluster equal to a git repository; nobody and nothing outside pushes changes in. The [OpenGitOps principles v1.0.0](https://opengitops.dev/) state it in four lines:

1. **Declarative.** The desired state is expressed declaratively (YAML, a Helm chart, a Kustomize overlay).
2. **Versioned and immutable.** It is stored so that it keeps a complete version history (git).
3. **Pulled automatically.** Software agents pull the desired state from the source.
4. **Continuously reconciled.** Agents continuously observe the actual state and try to apply the desired state.

Compare this with the classic **push** pipeline. A CI job builds an image, then runs `kubectl apply` or `helm upgrade` against the cluster. To do that the CI system holds cluster-admin credentials, usually outside the cluster, and it only acts when a pipeline runs. If someone edits the cluster by hand afterwards, nothing notices. In the **pull** model the credentials stay inside the cluster, and the agent checks all the time.

GitOps splits delivery into two jobs with a clean hand-off. **CI** (build, test, scan, push the image, then commit the new image tag to the config repository) ends at git. **CD** starts at git: the agent notices the commit and makes the cluster match. Two repositories are common: one for the application code, one for the deploy configuration, so that a config change does not trigger a rebuild.

{{diagram ch-7-1-04.jsx | push versus pull · where the credentials live}}

The agent runs the same loop as every Kubernetes controller (Vol 5): **observe, compare, act**. It renders the manifests from git (running Helm or Kustomize if needed), reads the live objects from the API server, and acts on the difference. Argo CD reports two separate answers:

| Status | Question | Values |
| --- | --- | --- |
| Sync status | Does live state equal git? | `Synced`, `OutOfSync` |
| Health status | Is what is running working? | `Healthy`, `Progressing`, `Degraded`, `Missing` |

The two are independent. A bad image tag is `Synced` (the cluster really equals git) and `Degraded` (the Pods cannot start). Seeing both in your head is half of GitOps debugging.

Two switches control how hard the agent works. **Auto-sync** applies git changes without a human pressing a button. **Self-heal** also reverts changes made directly in the cluster; **prune** deletes live objects that were removed from git ([Argo CD docs](https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/)). With all three on, git is the only way to change the cluster.

## How it works · Argo CD: the parts and the Application

Argo CD has three main components, and one custom resource ties them to your repository. The [architecture page](https://argo-cd.readthedocs.io/en/stable/operator-manual/architecture/) lists them:

- The **API server** serves the web UI, the CLI and the API, and enforces RBAC and login.
- The **repository server** keeps a local cache of the git repository and generates the manifests from a path, a revision and the Helm or Kustomize settings.
- The **application controller** "continuously monitors running applications and compares the current, live state against the desired target state", detects `OutOfSync`, and optionally corrects it.

{{diagram ch-7-1-05.jsx | Argo CD components · four numbered steps of one reconcile}}

The controller repeats steps 1 to 3 all the time. Step 4 happens on its own when auto-sync is on, or when a person presses Sync.

The unit of work is an **Application**: a Kubernetes object that says "take this path of this repository at this revision, and keep it equal to that namespace of that cluster". This is the Application you will apply in Lab 7.1:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: {name: wallet, namespace: argocd}
spec:
  project: default
  source:
    repoURL: git://git-server.git.svc:9418/wallet-gitops.git
    targetRevision: main
    path: kustomize/overlays/dev        # or a Helm chart: path: chart/wallet
  destination: {server: https://kubernetes.default.svc, namespace: wallet}
  syncPolicy:
    automated: {prune: true, selfHeal: true}
    syncOptions: [CreateNamespace=true]
```

Argo CD looks at the path and decides how to render it: a `Chart.yaml` means Helm, a `kustomization.yaml` means Kustomize, anything else is plain YAML. By default it "polls Git/OCI/Helm repositories every three minutes"; a webhook from the git server makes it immediate ([Argo CD docs](https://argo-cd.readthedocs.io/en/stable/operator-manual/webhook/)).

One Application per service is the usual start. To create many Applications from one place, teams use the **app-of-apps** pattern (an Application whose path contains other Applications) or an `ApplicationSet` generator; see Going deeper.

## How it works · Progressive delivery: ship to a few users first

A Deployment rolling update replaces Pods gradually but cannot judge whether the new version is good. [Argo Rollouts](https://argo-rollouts.readthedocs.io/en/stable/) lists the limits: few controls over the speed of the rollout, no control over how traffic is split, readiness probes that are "unsuitable for deeper, stress, or one-time checks", no way to query external metrics, and no automatic abort and rollback. A **Rollout** is a workload resource "equivalent to a Kubernetes Deployment" that adds canary and blue-green strategies. In a canary, a small share of traffic goes to the new version, a pause or an automated analysis (a query against Prometheus, Ch 7.2) decides whether to continue, and a failed check rolls back without a human. It needs a metric you trust, which is why observability comes next.

## Commands you will use in the lab

Install Helm from [helm.sh/docs/intro/install](https://helm.sh/docs/intro/install/) and git with `sudo apt install -y git`. kubectl and kind are already installed from Vol 0.

| Command | What it does |
| --- | --- |
| `helm lint ./wallet` | Checks a chart for mistakes; needs no cluster |
| `helm template wallet ./wallet` | Prints the YAML the chart would produce; needs no cluster |
| `helm install wallet ./wallet -n wallet --create-namespace` | Creates a release called `wallet` from a chart |
| `helm upgrade wallet ./wallet --set api.replicas=3` | Makes revision 2 of the release with a changed value |
| `helm history wallet` / `helm rollback wallet 1` | Lists revisions; goes back to one of them (as a new revision) |
| `helm uninstall wallet` | Deletes the release and its objects |
| `kubectl kustomize overlays/dev` | Prints the YAML an overlay produces; needs no cluster |
| `kubectl apply -k overlays/dev` | Builds the overlay and applies it |
| `git init`, `git add`, `git commit -m`, `git push` | Creates a repository, records a change, publishes it |
| `git revert HEAD` | Records a new commit that undoes the last one |
| `kubectl apply -n argocd --server-side -f <url>` | Installs Argo CD; server-side apply because its CRDs are too large for the client-side annotation |
| `kubectl -n argocd get applications` | Shows each Application's sync and health status |
| `kubectl port-forward svc/argocd-server -n argocd 8443:443` | Opens the Argo CD web UI on your laptop |

## In production

Most GitOps incidents come from the gap between what git says and what a controller does to the object afterwards. Read the symptom, then the cause.

| Symptom | Real cause | What engineers do |
| --- | --- | --- |
| The Application is `OutOfSync` forever, though nobody changed anything | Another controller rewrites a field that git also sets. A HorizontalPodAutoscaler or KEDA (Ch 7.3) changes `spec.replicas`; an admission webhook adds defaults | Remove `replicas` from the manifest when an autoscaler owns it, or add `ignoreDifferences` for `/spec/replicas` ([docs](https://argo-cd.readthedocs.io/en/stable/user-guide/diffing/)) |
| `Synced` but `Degraded` after a release | The manifest is valid but the app is not: wrong image tag, failing readiness probe | Read Pod events, then `git revert` the commit; the revert is the rollback and stays in the audit trail |
| A hotfix made with `kubectl edit` disappears | Self-heal reverted the live change to match git | Make the fix in git. Keep a documented break-glass step that pauses auto-sync for one Application |
| A password is visible in `values.yaml` | The chart took the secret as a plain value, so it lives in git history forever | Never commit secrets. The manifests only reference the Secret (secretKeyRef). Create it from Sealed Secrets (encrypted in git), External Secrets (copied from a vault) or SOPS (encrypted file); remove the old password from history and rotate it |
| Prune deleted a volume | The object was removed from git, or renamed, and prune followed git | Mark stateful objects with the `Prune=false` sync option ([docs](https://argo-cd.readthedocs.io/en/stable/user-guide/sync-options/)); review renames in pull requests |
| `helm upgrade` leaves a release stuck as `pending-upgrade` or `failed` | The upgrade was interrupted or a hook failed | `helm history` to see the state, then `helm rollback` to the last good revision |
| A new CRD field never appears after `helm upgrade` | Helm does not upgrade CRDs from `crds/` | Apply the CRDs yourself, or ship them in a separate chart that you upgrade first |
| The git server is down | Pull model: the agent cannot fetch | Nothing breaks: the cluster keeps running the last applied state. Only new deploys wait, and break-glass still works |

**Rolling back is a commit.** With Helm alone, `helm rollback` changes the cluster and git does not know, so the two now disagree. With GitOps you revert in git and the agent follows. Argo CD renders a chart itself and applies the result, so Helm's own release history is not what it uses.

## Project cards

Maturity levels are as listed in the [CNCF landscape data](https://github.com/cncf/landscape/blob/master/landscape.yml) and on [cncf.io/projects](https://www.cncf.io/projects/), as of 2026-11-16.

### Helm

| Field | Content |
| --- | --- |
| Problem | Package, version, install and roll back a set of Kubernetes manifests as one unit |
| Layer / interface | Client-side tool that talks to the Kubernetes API; the chart format; charts served from HTTP repositories or OCI registries |
| Architecture | The `helm` CLI (no server component), charts, repositories, and release records stored as Secrets in the release namespace |
| Alternatives | Kustomize for your own services; plain manifests for one-off installs |
| CNCF maturity | [Graduated](https://www.cncf.io/projects/helm/) (accepted 2018-06-01, graduated 2020-05-01) |

### Argo CD

| Field | Content |
| --- | --- |
| Problem | Keep a cluster equal to a git repository: pull, compare, report drift, sync, roll back |
| Layer / interface | Kubernetes API: controllers and CRDs (`Application`, `AppProject`, `ApplicationSet`); web UI, CLI and gRPC/REST API |
| Architecture | API server, repository server, application controller (plus Redis as a cache) ([architecture](https://argo-cd.readthedocs.io/en/stable/operator-manual/architecture/)) |
| Alternatives | Flux (no built-in UI, a toolkit of small controllers); a push pipeline with `kubectl` or `helm` when GitOps is more than the team needs |
| CNCF maturity | Part of the [Argo project](https://www.cncf.io/projects/argo/): graduated (accepted 2020-03-26, graduated 2022-12-06) |

### Flux

| Field | Content |
| --- | --- |
| Problem | The same as Argo CD: continuous delivery from git, OCI registries or buckets, with the cluster pulling |
| Layer / interface | Kubernetes API: the GitOps Toolkit controllers and CRDs (`GitRepository`, `OCIRepository`, `HelmRepository`, `Kustomization`, `HelmRelease`) |
| Architecture | Small single-purpose controllers: source-controller (fetches artifacts), kustomize-controller, helm-controller, notification-controller, and the image-reflector and image-automation controllers, which can commit new image tags back to git ([components](https://fluxcd.io/flux/components/)) |
| Alternatives | Argo CD (built-in UI, Application model) |
| CNCF maturity | [Graduated](https://www.cncf.io/projects/flux/) (accepted 2019-07-15, graduated 2022-11-30) |

### Argo Rollouts

| Field | Content |
| --- | --- |
| Problem | Safer releases than a rolling update: canary and blue-green with pauses and automated checks |
| Layer / interface | Kubernetes API: a `Rollout` resource that replaces a Deployment, plus `AnalysisTemplate` for metric checks; integrates with ingress controllers and service meshes for traffic splitting |
| Architecture | One controller that manages the old and new ReplicaSets, creates `AnalysisRun` objects during an update and promotes or aborts it ([architecture](https://argo-rollouts.readthedocs.io/en/stable/architecture/)) |
| Alternatives | Flagger (works with Flux); a plain Deployment with a manual canary |
| CNCF maturity | Part of the Argo project: graduated (see Argo CD) |

Argo Rollouts and Flux were not run in this lab (only Helm, Kustomize and Argo CD were); their cards come from the project documentation.
