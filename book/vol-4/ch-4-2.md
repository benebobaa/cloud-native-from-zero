## The problem: starting containers without being tied to one program

An orchestrator that starts containers on thousands of nodes cannot depend on one vendor's program to do it.

`docker run` hides a lot: a daemon, an image store, a network setup and, at the very end, a program that creates the process. Early Kubernetes talked to Docker through an adapter inside the kubelet, the dockershim, which was removed in Kubernetes v1.24 ([Kubernetes blog](https://kubernetes.io/blog/2022/02/17/dockershim-faq/)). What replaced it is a layered design with a standard at every joint. Four questions explain why each layer exists:

1. **How does the kubelet ask for a container without knowing who starts it?** It speaks one gRPC protocol, the Container Runtime Interface (CRI). Any program that implements the CRI can serve a node.
2. **What does "start" mean at the lowest level?** A directory with a root filesystem and a `config.json`, defined by the OCI runtime spec (Ch 4.1). One small program, `runc`, turns that bundle into a process.
3. **What happens to your containers when the runtime daemon restarts?** They must not die. A small per-Pod process, the shim, keeps them alive.
4. **What if the code inside is not trusted?** A container shares the host kernel (Ch 1.5), so a kernel bug can become an escape. The same interfaces let you swap runc for a runtime that adds a second wall.

**Why this matters for Kubernetes.** A Pod spec names an image and nothing else. Yet messages such as `failed to create containerd task`, `OCI runtime create failed` and `no runtime for "kata" is configured` each come from one layer of this chain, and you will meet all three in Lab 4.2. In Lab 4.1 the distroless image already failed with an error printed by `runc`. Knowing which layer printed an error tells you where to look.

## How it works, part 1: the programs between the kubelet and your process

A running container is the end of a chain of five programs, and each one does a single job.

| Program | Its one job | It talks to the next one with | You meet it in Lab 4.2 as |
| --- | --- | --- | --- |
| kubelet | Decides that a Pod must run on this node | the CRI (gRPC) | the program `crictl` stands in for (Part D) |
| containerd or CRI-O | Pulls and stores images, builds the Pod sandbox, keeps the state of every container | one shim per Pod | `ctr` and `nerdctl` (Part C), `crictl` (Part D) |
| shim (`containerd-shim-runc-v2`) | Holds the container's input, output and exit code, so the daemon can restart | the OCI runtime | the parent process in `ps` |
| low-level runtime: runc, gVisor's `runsc`, Kata | Creates the process from a bundle: namespaces, cgroups, mounts, `exec` | the Linux kernel | `runc` by hand (Part B) |
| your process | The wallet |  | `python3 api.py` |

"High-level runtime" and "low-level runtime" are common names, not terms from a specification. On your laptop the path starts one step earlier: the `docker` command calls the Docker daemon, which uses the same containerd, shim and runc (`docker info` lists `runc` as a runtime and the containerd image store you saw in Lab 4.1).

The diagram is a real `ps` listing from Lab 4.2. One detail matters later: the shim's parent is PID 1, not containerd. The daemon starts the shim, then the shim detaches and runs on its own.

## How it works, part 2: the bundle and the low-level runtime

An OCI runtime does one thing: it reads a bundle and makes a process from it.

In Ch 4.1 you met the bundle as a directory with a root filesystem and a `config.json`. The `config.json` is the whole instruction. Here is an abridged one, the file you will write for the wallet in Lab 4.2:

```json
{
  "ociVersion": "1.3.0",
  "process": {
    "terminal": false,
    "user": {"uid": 10001, "gid": 10001},
    "args": ["python3", "api.py"],
    "env": ["PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin", "DATABASE_URL=..."],
    "cwd": "/app",
    "capabilities": {"bounding": ["CAP_AUDIT_WRITE", "CAP_KILL", "CAP_NET_BIND_SERVICE"]}
  },
  "root": {"path": "rootfs", "readonly": true},
  "linux": {
    "namespaces": [{"type": "pid"}, {"type": "ipc"}, {"type": "uts"}, {"type": "mount"}, {"type": "cgroup"}],
    "resources": {"memory": {"limit": 134217728}}
  }
}
```

Every field is something you did by hand in Ch 1.5. `linux.namespaces` is the list of namespaces to create, the flags you gave to `unshare`. `linux.resources` is what you wrote into cgroup files. `root` is the directory that becomes `/`. `process` is the program, its user and its environment. A Docker flag such as `--memory 128m` or a Kubernetes `resources.limits.memory` ends up as one number in this file.

The [runc README](https://github.com/opencontainers/runc) calls runc "a CLI tool for spawning and running containers on Linux according to the OCI specification" and says you must give it an OCI bundle. `runc spec` writes a template `config.json` for you to edit, and runc can also run without root privileges ("rootless"), which needs user namespaces in the kernel.

The runtime spec splits starting into two steps and defines four states ([runtime spec](https://github.com/opencontainers/runtime-spec/blob/main/runtime.md)). `create` builds the environment from `config.json` but must not run the user program. `start` runs it. The gap between them is deliberate: other programs get a moment to work on a container that exists but has not begun, for example to wire up its network, and the spec defines hook points for that. A stopped container keeps its state until someone deletes it, which is why you will see `stopped` containers in `runc list` and `Exited` ones in `crictl ps -a`.

## How it works, part 3: containerd, and why a shim sits below it

containerd keeps images and state; the shim keeps one Pod's processes, so that the daemon can be restarted without killing anything.

The [containerd project](https://containerd.io/) describes itself as managing "the complete container lifecycle of its host system, from image transfer and storage to container execution". Three pieces of that matter in the lab:

- **Content store and snapshotter.** The content store holds the blobs you opened in Ch 4.1, named by digest. The snapshotter turns layers into directories: one committed snapshot per layer, each with the previous one as its parent, and one active snapshot per running container, which is the writable layer. `ctr snapshots ls` shows exactly this chain.
- **containerd namespaces.** These are labels that keep different users of one daemon apart, not the Linux namespaces of Ch 1.5 ([getting started](https://github.com/containerd/containerd/blob/main/docs/getting-started.md)). Kubernetes uses the namespace `k8s.io`; `ctr` and `nerdctl` use `default`. An image you import into one is invisible in the other, which surprises everyone once.
- **Tools.** `ctr` ships with containerd and, in the project's words, "is solely made for debugging containerd". `nerdctl` is a separate project with a Docker-like command line. `crictl` is maintained by Kubernetes SIG Node and speaks the CRI, so it works with any CRI runtime.

The shim exists because a daemon is a single point of failure. If the processes were children of containerd, every upgrade or crash of the daemon would kill every container on the node. Instead containerd starts a shim, the shim starts runc and then stays as the parent of the container's process. Lab 4.2 tests both directions:

| Event on the node | What happened to the wallet container | What it shows |
| --- | --- | --- |
| containerd restarted with `systemctl restart containerd` | Kept running with the same PID; `ctr tasks ls` still listed it | The shim, not the daemon, owns the process |
| the shim killed with `kill -9` | The container exited, the Pod sandbox became `NotReady`, and the containerd log said `cleaning up dead shim` | Without its shim a container is not supervised; containerd tidies up |
| the container's process exits | The state stays until someone deletes it (`Exited` in `crictl ps -a`) | Exit status is kept for whoever asks later, such as the kubelet |

The last row is why a crashed container can be inspected after it dies: `kubectl describe` can show an exit code because the runtime kept it.

## How it works, part 4: the CRI, the kubelet's one interface to every runtime

The CRI is a gRPC API with an image service and a runtime service, and the kubelet is its client.

The Kubernetes documentation calls it "a plugin interface which enables the kubelet to use a wide variety of container runtimes, without having a need to recompile the cluster components" ([CRI](https://kubernetes.io/docs/concepts/architecture/cri/)). The kubelet reaches the runtime through a Unix socket named by `--container-runtime-endpoint`. Kubernetes 1.37 requires a runtime that implements version 1 of the CRI, otherwise the kubelet will not register the node ([container runtimes](https://kubernetes.io/docs/setup/production-environment/container-runtimes/)). containerd and CRI-O are the two runtimes that page lists besides Docker Engine, which needs an extra adapter since the dockershim was removed.

The CRI starts a Pod in two levels. It first creates a **Pod sandbox**, the shared environment of the Pod, and then creates containers inside it. In Lab 4.2 the sandbox is a process named `/pause` that does nothing and sits in the same shim as your container. Vol 5 explains what the Pod shares through it. The diagram shows the calls for one Pod, with the `crictl` command that sends each one.

{{diagram ch-4-2-04.jsx | CRI calls for one Pod start · crictl commands from Lab 4.2 Part D}}
`crictl` "provides a CLI for CRI-compatible container runtimes" and lets runtime developers "debug their runtime without needing to set up Kubernetes components" ([cri-tools](https://github.com/kubernetes-sigs/cri-tools/blob/master/docs/crictl.md)). Its built-in default sockets are deprecated, so you pass the endpoint yourself; the kind node image does that in `/etc/crictl.yaml`. In Lab 4.2 you play the kubelet with it.

One rule from the same documentation surprises people: "It's critical that the kubelet and the container runtime use the same cgroup driver and are configured the same." With systemd as the init system, the documentation recommends the `systemd` driver, and with cgroup v2 it says to use it instead of `cgroupfs`. The node image used in Lab 4.2 configures containerd with `SystemdCgroup = true`. Under that setting a Pod's cgroup parent must be a systemd slice name, and your first `crictl runp` will fail with `expected cgroupsPath to be of format "slice:prefix:name" for systemd cgroups`. The kubelet supplies that name for you on a real node; with `crictl` you must supply it.

## How it works, part 5: runc, gVisor and Kata behind the same interface

Because the low-level runtime is replaceable, you can change how strongly a container is walled in without changing the image or the Pod.

A runc container is an ordinary Linux process in namespaces and cgroups, so the host kernel handles every system call it makes. A kernel bug that a malicious process can trigger from inside is then a way out. Two projects add a second wall:

- **gVisor** is an application kernel written in Go that runs in user space. Its component called the Sentry handles the container's system calls itself and does not pass them through to the host kernel; file access beyond the sandbox goes through a helper called the Gofer ([gVisor docs](https://gvisor.dev/docs/)). Its runtime is `runsc`, an OCI runtime.
- **Kata Containers** runs each workload in a lightweight virtual machine with its own kernel, using hardware virtualization as "a second layer of defense", with hypervisors such as QEMU, Cloud-Hypervisor and Firecracker ([Kata](https://katacontainers.io/)).

{{diagram ch-4-2-05.jsx | three isolation designs behind the same OCI interface · gVisor and Kata descriptions from their project sites, speed figure measured in Lab 4.2}}
The walls cost something. In Lab 4.2 you run the same Python workloads in a runc container and a gVisor container on the same node. Pure computation takes about the same time, but loops that make many system calls are 10 to 16 times slower under gVisor, because each call is handled by the Sentry instead of the host kernel. Kata trades memory and start-up work for a VM per Pod; it needs its own hypervisor, guest kernel and shim, and its release files could not be downloaded on the test network, so it is described and not run.

Kubernetes lets a Pod choose its runtime with a **RuntimeClass**, a cluster object that maps a name to a runtime handler configured on the nodes ([RuntimeClass](https://kubernetes.io/docs/concepts/containers/runtime-class/), stable since v1.20). Vol 5 teaches Pods; this preview only shows how little changes. It was not run on a cluster in this book:

```yaml
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: gvisor
handler: runsc          # the runtime name you add to containerd's config in Lab 4.2
---
apiVersion: v1
kind: Pod
metadata:
  name: wallet-untrusted
spec:
  runtimeClassName: gvisor
  containers:
  - name: api
    image: wallet:alpine
```

| Situation | Reasonable choice | What you pay |
| --- | --- | --- |
| Your own services, reviewed code | runc, the default | Nothing extra |
| Running other people's code: CI jobs, plugins, student submissions | gVisor or Kata | gVisor: slower system calls. Kata: a VM per Pod and virtualization hardware |
| An audit asks for hardware-level separation between tenants | Kata | A VM per Pod |

## Commands you will use in the lab

The lab runs inside a throwaway container that acts as a small Linux machine, so nothing touches your own system. `curl`, `jq` and `readlink /proc/<pid>/ns/pid` are known from Ch 1.5 and Ch 4.1; `ps`, `systemctl` and `kill` are listed because the lab uses them in a new way.

| Command | What it does | Example |

## In production

Most runtime incidents come from three things: the node's runtime configuration, the state kept below the kubelet, and the shared kernel.

| What you see | What really happened | What engineers do |
| --- | --- | --- |
| A Pod stays in `ContainerCreating` with `failed to create containerd task` or `OCI runtime create failed` in its events | runc refused the bundle: a missing executable (`exec: "sh": executable file not found`, as in Lab 4.1), a bad mount, or a cgroup path it could not use | Read the whole message to the last colon, since runc's reason is at the end; then `crictl ps -a` and `journalctl -u containerd` on the node |
| A node stays `NotReady` after a runtime upgrade | The runtime no longer implements CRI v1 or listens on another socket than the kubelet expects; Kubernetes 1.37 needs CRI v1 or the node does not register ([docs](https://kubernetes.io/docs/setup/production-environment/container-runtimes/)) | `crictl info` against the socket the kubelet uses; compare with `--container-runtime-endpoint` |
| Pods fail to start with a cgroup path error such as `expected cgroupsPath to be of format "slice:prefix:name"` | The kubelet and the runtime use different cgroup drivers; the documentation calls matching them "critical" | Set `cgroupDriver: systemd` in the kubelet and `SystemdCgroup = true` in containerd, then restart both |
| `no runtime for "runsc" is configured`, or a Pod stuck because its RuntimeClass names a handler the node lacks | The RuntimeClass exists in the cluster, but this node's containerd has no runtime of that name | Add the handler to every node that can run such Pods, or restrict scheduling to nodes that have it |
| Node disk fills up under `/var/lib/containerd` | Unused images and stopped containers pile up in containerd's store | The kubelet collects unused images every five minutes and unused containers every minute ([garbage collection](https://kubernetes.io/docs/concepts/architecture/garbage-collection/)); tune its thresholds and do not run external cleanup tools beside it |
| `ps` shows a shim that `crictl ps -a` does not list, or the reverse | State below and above the daemon disagree after a crash or a failed cleanup. When you kill a shim, containerd logs `cleaning up dead shim` | Compare `ps`, `crictl ps -a` and `ctr -n k8s.io tasks ls`; delete leftovers only after you know which Pod they belong to |
| A security review asks "can a container escape?" | Containers share the host kernel, and the runtime itself has had flaws: CVE-2019-5736 let attackers "overwrite the host runc" in runc up to 1.0-rc6 ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2019-5736), published 2019-02-11) | Patch the runtime on every node, drop capabilities and run as non-root (Ch 4.3), and put untrusted code behind gVisor or Kata |
| A service is fast on runc and slow under gVisor | The service makes many system calls, and each one is now handled by the Sentry | Measure with your own workload before choosing a sandbox, as in Lab 4.2 Part E |

## Project cards: containerd, CRI-O, runc, gVisor, Kata Containers

Two of the five are CNCF graduated projects; the other three are not CNCF projects, which is itself worth knowing. CNCF status below is from cncf.io, as of 2026-11-17.

### Project card: containerd

| Field | Content |
| --- | --- |
| Problem | A node needs one daemon that pulls and stores images and runs containers, shared by Docker, Kubernetes and other tools. |
| Layer / interface | High-level container runtime. It serves the CRI to the kubelet, uses the OCI image and runtime specs, and starts OCI runtimes through shims. |
| Architecture | One daemon made of plugins: content store, snapshotter, metadata with namespaces, and a CRI plugin. One shim (`containerd-shim-runc-v2`) per Pod. Clients: `ctr` (debugging), `nerdctl`, `crictl`. |
| Alternatives | CRI-O: a runtime scoped to Kubernetes. Docker Engine through the `cri-dockerd` adapter: only if you need Docker's own features on the node. Pick containerd when you want the widest tooling; it is what kind, and Lab 4.2, use. |
| CNCF maturity | Graduated: accepted 2017-03-29 at the Incubating level, moved to Graduated 2019-02-28 ([cncf.io/projects/containerd](https://www.cncf.io/projects/containerd/), as of 2026-11-17). |

### Project card: CRI-O

| Field | Content |
| --- | --- |
| Problem | Kubernetes needs a runtime only for the CRI, not the rest of Docker's features: run exactly what the kubelet asks for. |
| Layer / interface | A CRI server for the kubelet, with any OCI-compliant runtime below it. |
| Architecture | One daemon that implements the CRI, pulls images from any compliant registry and runs OCI containers; its site names runc and Kata Containers as supported runtimes ([cri-o.io](https://cri-o.io/)). Its install instructions use the same minor version for CRI-O and Kubernetes. |
| Alternatives | containerd: general purpose, also used outside Kubernetes. Pick CRI-O when your Kubernetes distribution ships it; the two are interchangeable for the kubelet because both speak the CRI. |
| CNCF maturity | Graduated: accepted 2019-04-08 at the Incubating level, moved to Graduated 2023-07-19 ([cncf.io/projects/cri-o](https://www.cncf.io/projects/cri-o/), as of 2026-11-17). |

### Project card: runc

| Field | Content |
| --- | --- |
| Problem | Turn an OCI bundle into a running Linux process in its namespaces and cgroups. |
| Layer / interface | Low-level OCI runtime and command line tool, the reference implementation of the OCI runtime spec. |
| Architecture | One binary, no daemon. It reads `config.json`, builds the environment and runs the user program; a `runc init` process waits inside the new namespaces between create and start. It can run rootless with user namespaces ([README](https://github.com/opencontainers/runc)). |
| Alternatives | youki, another OCI runtime (a CNCF sandbox project, accepted 2024-10-17), and the sandboxed runtimes gVisor and Kata. Pick runc as the default: every tool in this chapter expects it. |
| CNCF maturity | Not a CNCF project. Docker donated runc to the Open Container Initiative, which is formed under the Linux Foundation ([OCI](https://opencontainers.org/about/overview/)). It is absent from the CNCF graduated, incubating and sandbox lists ([projects](https://www.cncf.io/projects/), [sandbox](https://www.cncf.io/sandbox-projects/), as of 2026-11-17). |

### Project card: gVisor

| Field | Content |
| --- | --- |
| Problem | Run code you do not trust in a container without letting it reach the host kernel's full system call surface. |
| Layer / interface | An OCI runtime (`runsc`) with a containerd shim (`containerd-shim-runsc-v1`); Kubernetes selects it per Pod with a RuntimeClass. |
| Architecture | The Sentry, a kernel written in Go that handles the container's system calls in user space; the Gofer, which serves file access; and a platform that redirects the application's system calls to the Sentry ([gVisor docs](https://gvisor.dev/docs/)). On the node you see `runsc-sandbox`, `runsc-gofer` and `gvisor_sentry` processes (Lab 4.2). |
| Alternatives | runc: fastest, shared kernel. Kata Containers: a VM per Pod. Hardening runc with dropped capabilities and a seccomp filter (Ch 4.3, Vol 6) is the cheaper first step. |
| CNCF maturity | Not a CNCF project: it is not on the cncf.io graduated, incubating or sandbox lists (as of 2026-11-17). Project home: [gvisor.dev](https://gvisor.dev/). |

### Project card: Kata Containers

| Field | Content |
| --- | --- |
| Problem | Give each Pod the isolation of a virtual machine while keeping the container workflow and image format. |
| Layer / interface | An OCI-style runtime with a containerd shim that works with containerd and CRI-O; Kubernetes selects it per Pod with a RuntimeClass. |
| Architecture | A shim starts a lightweight virtual machine with a hypervisor (QEMU, Cloud-Hypervisor or Firecracker) and runs the container on the VM's own kernel, using hardware virtualization "as a second layer of defense" ([katacontainers.io](https://katacontainers.io/)). Not run in this book's labs. |
| Alternatives | gVisor: no VM, a user-space kernel, slower system calls. runc: shared kernel. Pick Kata when you need hardware-enforced separation between tenants and the nodes support virtualization. |
| CNCF maturity | Not a CNCF project: it is overseen by the Open Infrastructure Foundation ([katacontainers.io](https://katacontainers.io/)) and is not on the cncf.io lists (as of 2026-11-17). |
