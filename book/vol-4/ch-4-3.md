## The problem: one program is not one container

A real application is several programs that need each other, and `docker run` starts only one of them.

The wallet from Vol 3 is three programs: the API, the worker and Postgres. With `docker run` alone you would type three long commands, each with its network, volume and limit flags, in the right order, and repeat them on every machine. Five questions decide whether those containers work together:

1. **How do they find each other?** On Docker's default network a container cannot look up another by name; you will see `ping: bad address` in Lab 4.3.
2. **Where does the data live?** A container's writable layer is deleted with the container (Ch 4.1), so Postgres needs somewhere else to write.
3. **What stops one container from taking the whole machine?** The kernel can, if you give it limits (Ch 1.5), and it kills the offender when it crosses one.
4. **How do you know it works, not only that it runs?** A process can be alive and useless.
5. **What happens when something crashes, or starts too early?** Someone must restart it, and the database must be ready before the API asks it a question.

Docker Compose answers all five with one file that describes the whole application, and one command, `docker compose up`, that makes it so. The file is a declaration of the state you want, not a script of steps. That idea returns in Vol 5, where Kubernetes manifests do the same job for a whole cluster.

**Why this matters for Kubernetes.** Almost every key in this chapter has a Kubernetes twin that you will write in Vol 5: `healthcheck` becomes probes, `deploy.resources.limits` becomes `resources.limits`, `restart` becomes `restartPolicy`, a named volume becomes a PersistentVolumeClaim, and a service name on a network becomes a Service. If you understand what Docker does with each key on one machine, the Kubernetes versions are the same ideas spread over many.

## How it works, part 1: networks, names and published ports

Containers on the same user-defined network find each other by service name, and nothing outside reaches them unless you publish a port.

When Docker starts a network, it creates a Linux bridge and gives each container a network namespace with a virtual cable (a veth pair) into the bridge; you built the same thing by hand in Vol 2. Docker adds a small DNS server at `127.0.0.11` inside each container, which answers questions about the names of the other containers on that network. The [Docker documentation](https://docs.docker.com/engine/network/drivers/bridge/) states the difference: "User-defined bridges provide automatic DNS resolution between containers", while containers on the default bridge "can only reach each other by IP address". Compose creates a user-defined network for every project, so the API reaches the database at the host name `postgres`.

Three more rules decide what is reachable:

- **Containers on one network see all of each other's ports.** Nothing needs publishing for the API to reach port 5432 of the database.
- **A port reaches your machine only if you publish it.** `ports: ["127.0.0.1:18080:8080"]` opens port 18080 on your own address only, not on every interface. The Docker documentation says access from outside "must be *published*" with `-p`.
- **An `internal` network has no door out.** Compose says `internal: true` "lets you create an externally isolated network" ([networks](https://docs.docker.com/reference/compose-file/networks/)). Put the database and the worker only on such a network and a compromised worker cannot call home.

The diagram is the wallet stack of Lab 4.3. The API sits on both networks, because it must be reachable and must reach the database; the worker and the database sit only on the internal one.

## How it works, part 2: volumes and what survives

Data survives a container only if it is written to a mount that does not belong to the container's layers.

From Ch 4.1 you know that a container's files are the image's read-only layers plus one writable layer, and that the writable layer is deleted with the container. A database that writes there loses everything on the next `docker compose down`. Docker offers four places to write, and they differ in who owns the data:

| Kind | What it is | Survives `docker compose down`? | Use it for |
| --- | --- | --- | --- |
| Writable layer (the default) | The top layer of the container's overlay filesystem | No, it goes with the container | Scratch files you can lose |
| Named volume | A directory that Docker creates and manages outside the image layers, mounted into the container | Yes. Only `docker compose down -v` or `docker volume rm` removes it | Database files |
| Bind mount | A path on your host, mounted into the container | Yes, it is your host's directory | Source code while developing, configuration files |
| `tmpfs` | A memory-backed mount | No, it disappears when the container stops | `/tmp` in a container whose root is read-only |

In the wallet stack, `pgdata:/var/lib/postgresql/data` mounts the named volume `pgdata` where Postgres keeps its files. In Lab 4.3 you will write an account, run `docker compose down`, start the stack again and read the account back. Then you will run `docker compose down -v` and watch it disappear. The second command is the dangerous one: `-v` deletes the volume, and with it the database, without asking.

## How it works, part 3: limits, and what happens at the edge

A limit is a number in a cgroup file, and the two main ones behave very differently when a process hits them.

In Ch 1.5 you wrote limits into cgroup files by hand. Docker and Compose write the same files. The Docker documentation describes `--memory` as "the maximum amount of memory the container can use" and `--cpus` as "how much of the available CPU resources a container can use" ([resource constraints](https://docs.docker.com/engine/containers/resource_constraints/)). In the Compose file the same limits sit under `deploy.resources.limits`. In Lab 4.3 you will read the result on the node: `memory.max` is `134217728` for a limit of `128M`, and `cpu.max` is `50000 100000` for `cpus: 0.5`, which means 50,000 microseconds of CPU time in every 100,000-microsecond period.

- **Memory is a wall.** When the container's processes need more than `memory.max` and nothing can be reclaimed, the kernel's OOM killer ends a process. The documentation says it plainly: "if an out-of-memory (OOM) error occurs, the kernel kills processes in a container". The container exits with status 137, which is 128 plus signal 9 (Ch 1.2), and Docker records `OOMKilled=true`.
- **CPU is a speed limit.** A process that wants more CPU than `cpu.max` allows is paused until the next period. It is not killed; it is slower, and `cpu.stat` counts the pauses in `nr_throttled`. A CPU limit therefore shows up as latency, never as an error.

The practical lesson is to size a memory limit from measurement. The wallet's worker idles at about 25 MiB, so the 20 MiB limit you set in Break it kills it on every start. Two cautions: set `--memory-swap` equal to `--memory` if you want no swap, and do not trust `free` inside a container, since the documentation notes that such tools "report the host's available swap". Read `/sys/fs/cgroup/memory.max` instead.

## How it works, part 4: health, restarts and start order

Running is not working: a health check asks the container itself, and a restart policy reacts only when the process has exited.

A **health check** is a command that Docker runs inside the container on a timer. The Dockerfile reference defines its statuses: "This status is initially `starting`", it becomes `healthy` whenever a check passes, and "after a certain number of consecutive failures, it becomes `unhealthy`". Exit code 0 means healthy and 1 means unhealthy ([HEALTHCHECK](https://docs.docker.com/reference/dockerfile/)). The defaults are an interval of 30 s, a timeout of 30 s, a start period of 0 s and 3 retries. The wallet stack sets its own, shorter ones: the API's check requests `/readyz`, which touches the database, so it fails when the database is gone; the worker's check opens a database connection.

A **restart policy** is a different mechanism. `unless-stopped` starts a container again when it exits by itself, but it ignores containers you stopped: "the restart policy is ignored until the Docker daemon restarts or the container is manually restarted", which "prevents a restart loop" ([start containers automatically](https://docs.docker.com/engine/containers/start-containers-automatically/)). That has two consequences you will test in Lab 4.3. An unhealthy container is not restarted, because it has not exited. And a container you kill with `docker kill` stays down.

**Start order** is the third piece. Without help, Compose starts all services at once, and a client that connects before Postgres has finished starting is refused. `depends_on` with the condition `service_healthy` makes Compose wait until the dependency's check passes; the other conditions are `service_started` and `service_completed_successfully` ([services](https://docs.docker.com/reference/compose-file/services/)). The wallet hides the problem for the API and worker, because its `db.connect()` retries for up to 30 seconds, but most programs do not.

Kubernetes keeps the same split under other names. A readiness probe decides whether traffic may reach a Pod, a liveness probe decides whether the kubelet restarts it, and a restart policy covers exits. In Docker a failed health check is only a label; in Kubernetes a failed liveness probe has teeth. Vol 5 teaches both.

## How it works, part 5: reading the Compose file, and least privilege

A Compose file is a YAML description of services, networks and volumes; the repeated part of it is written once and reused.

The wallet stack in Lab 4.3 has three services. The API and the worker share most of their settings, so the file states them once in a block whose name starts with `x-` (Compose keeps such "extension" keys for your own use) and reuses it with a YAML anchor:

```yaml
x-wallet: &wallet                 # an anchor: a name for this block
  image: wallet:alpine
  restart: unless-stopped
  stop_grace_period: 10s          # SIGTERM first, SIGKILL after 10 s
  read_only: true                 # the root filesystem cannot be written
  tmpfs: [/tmp]                   # except a memory-backed /tmp
  cap_drop: [ALL]                 # no Linux capabilities
  security_opt: ["no-new-privileges:true"]
  networks: [backend]
  environment:
    DATABASE_URL: postgresql://wallet:${DB_PASSWORD:?set DB_PASSWORD in .env}@postgres:5432/wallet
  depends_on:
    postgres: {condition: service_healthy}

services:
  api:
    <<: *wallet                   # merge the shared block, then add or override
    ports: ["127.0.0.1:${API_PORT:-8080}:8080"]
```

Two details keep secrets and surprises out of the file. `${DB_PASSWORD:?message}` makes Compose stop with your message when the variable is empty, and `${API_PORT:-8080}` uses 8080 when it is not set. Compose reads both from a `.env` file next to the Compose file, and that file must never be committed (Ch 4.1, Break it).

The settings in the table below are **least privilege**: give a process only what it needs, so that a bug in it can do little. Each one removes something specific, and each can be checked from inside the container:

| Setting | What it removes | How you check it in Lab 4.3 |
| --- | --- | --- |
| `read_only: true`, with `tmpfs: [/tmp]` | The ability to write anywhere except `/tmp` | `touch /app/x` fails with `Read-only file system`; `touch /tmp/ok` works |
| `cap_drop: [ALL]` | Every Linux capability in the container's bounding set | `CapBnd` in `/proc/self/status` is `0000000000000000` instead of `00000000a80425fb` |
| `no-new-privileges:true` | Gaining privileges through set-user-ID programs | `NoNewPrivs: 1` in `/proc/self/status` |
| a non-root user (`USER 10001` in the image) | Root's rights on the host if the container is ever escaped | `id -u` prints `10001` |
| `internal: true` network | Any route to the internet | a request from the worker fails with `Network is unreachable` |

None of these is a sandbox. They shrink what a compromised process can do, and Vol 6 adds the Kubernetes versions (security contexts, Pod Security) on top of the same kernel features.

## Commands you will use in the lab

All of these run on your own machine. Commands from Ch 4.1 (`docker build`, `docker run`, `docker exec`) are not repeated.

| Command | What it does | Example |
| --- | --- | --- |
| `docker network create <name>` | Creates a user-defined bridge network | `docker network create lab43-net` |
| `docker run --network <name>` | Attaches a new container to that network | `docker run --rm --network lab43-net alpine ping -c1 lab43-db` |
| `docker compose -f <file> up -d --build` | Builds what is needed and starts every service in the background | `docker compose -f compose.stack.yaml up -d --build` |
| `docker compose ps`, `logs`, `stop <service>`, `start <service>` | Shows state; reads output; stops or starts one service | `docker compose -f compose.stack.yaml stop postgres` |
| `docker compose down`, `down -v` | Removes containers and networks; also removes volumes | `docker compose -f compose.stack.yaml down` |
| `docker inspect -f '<template>' <container>` | Prints chosen fields of a container's configuration and state | `docker inspect -f '{{.State.Health.Status}}' <container>` |
| `docker stats --no-stream` | One snapshot of memory, CPU and process counts per container | `docker stats --no-stream` |
| `docker update --memory <size> <container>` | Changes a running container's memory limit | `docker update --memory 20m --memory-swap 20m <container>` |
| `docker kill`, `docker stop` | Sends SIGKILL immediately; sends SIGTERM, then SIGKILL after a grace period | `docker stop <container>` |
| `cat /sys/fs/cgroup/memory.max` | Shows the container's own memory limit, from inside | `docker exec <container> cat /sys/fs/cgroup/memory.max` |

## In production

Most multi-container incidents come from limits set by guess, health checks that test the wrong thing, and data kept in the wrong place.

| What you see | What really happened | What engineers do |
| --- | --- | --- |
| A container restarts again and again with exit status 137 and `OOMKilled: true` | Its memory limit is below what the program needs: the wallet worker needs about 25 MiB, and with a 20 MiB limit it was killed and restarted 6 times in 20 seconds (Lab 4.3) | Measure real use under load, set the limit with headroom, alert on restart counts rather than waiting for a user report |
| A container shows `unhealthy` for hours and nothing happens | Docker only marks a failed health check; it does not stop or restart the container | Fix the cause, or run under an orchestrator whose probes act on failure (Kubernetes liveness probes) |
| The check is green, but requests fail | The check tests less than the service needs: the wallet's `/healthz` stays `200` with the database down, while `/readyz` fails | Make the check exercise the dependencies the service cannot work without, and keep a cheap liveness check separate |
| A service calls the database and gets `bad address` or no response | The two containers are on the default bridge, or on different networks, so there is no name lookup between them | Put them on one user-defined network and use the service name as host |
| The API crashes at start with `connection refused` | A start-order race: the client started before the database could accept connections; the wallet survives only because it retries for 30 seconds | `depends_on` with `condition: service_healthy`, and retries with a limit in the client |
| The database is empty after a redeploy | `docker compose down -v` deleted the named volume; or the data lived in the writable layer and was removed with the container | Never use `-v` outside a throwaway environment, back up the volume, and check which path the database writes to |
| After changing `DB_PASSWORD` in `.env`, the database refuses the new password | Postgres uses `POSTGRES_PASSWORD` only when it initialises an empty data directory; the existing volume keeps the old password | Change the password inside the database (`ALTER USER`), or remove the volume in a test environment only |
| A Compose service does not stop for ten seconds | The program ignores SIGTERM, so Docker waits for the grace period and then sends SIGKILL | Handle SIGTERM (the wallet does: `docker stop` took 405 ms) or run a small init process as PID 1 |
