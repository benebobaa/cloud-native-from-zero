# Chapter 4.1 · Images and the OCI Standard

{{diagram ch-4-1-01.jsx | Ch 4.1 at a glance}}
## The problem: shipping a program with everything it needs

An image packs a program together with every file it needs, so the same bytes run the same way on any machine that has a Linux kernel.

In Ch 1.5 you built a container by hand: a directory holding a root filesystem, started inside new namespaces and a cgroup. That worked on one laptop. To move it to a server you would copy the directory, and the wallet shows why that hurts. It needs Python 3.12, the `psycopg` library and the C library `libpq` underneath it. A server with Python 3.9 and another `libpq` runs it differently, or not at all. Three questions follow, and this chapter answers each:

1. **What goes in the box?** Every file the program touches below the kernel: interpreter, libraries, configuration, the program itself. Not the kernel, which containers share with the host (Ch 1.5).
2. **How does the box travel?** The wallet's root filesystem is about 146 MB, yet a new version changes 3 KB of Python. Sending 146 MB for 3 KB wastes time and bandwidth, so the format must send only what changed.
3. **How do you know it is the same box?** The test run on Monday must use exactly the bytes deployed on Friday. A name such as `wallet:v1` can be pointed at other content, so something stronger than a name is needed.

The answers are layers, content addressing and digests. The Open Container Initiative (OCI), hosted by the Linux Foundation, wrote them down as open specifications ([opencontainers.org](https://opencontainers.org/about/overview/)), so Docker, containerd, CRI-O and Kubernetes all read the same format.

**Why this matters for Kubernetes.** A Pod spec holds only an image name. `ErrImagePull`, `ImagePullBackOff`, slow node start-up, a vulnerability report on your base image and "it behaves differently in production" are all image problems, and everything in this chapter happens between that name and a running process.

## How it works, part 1: an image is layers, a config and a manifest

An image is three kinds of file: layers that hold the files, a config that says how to start them, and a manifest that lists both by their hash.

- A **layer** is a tar archive of filesystem changes: the files one build step added, changed or deleted.
- The **config** is a JSON file with the start command, user, working directory, environment variables, exposed ports, the ordered list of layer IDs and the build history.
- The **manifest** is a JSON file that names the config and every layer by digest and size. The OCI image spec requires the base layer at index 0 and later layers in stack order ([manifest spec](https://github.com/opencontainers/image-spec/blob/main/manifest.md)).
- A **digest** is the SHA-256 hash of a file's bytes, written `sha256:` and 64 hexadecimal characters. A blob stored under its digest cannot change without changing its name. This is *content addressing*: anyone can hash the bytes and compare.
- An **image index** lists one manifest per platform. Pulling `python:3.12-slim` fetches the index first, then only the manifest for your CPU.

{{diagram ch-4-1-02.jsx | anatomy of wallet:v1 · measured with docker save, 2026-11-16}}
These are the real files of `wallet:v1`, read from a `docker save` archive. The wallet's own code is the last 3 KB; everything below it belongs to Debian, Python and psycopg. You will open each file yourself in Lab 4.1.

A tag is not part of the image. `wallet:v1` is a name in a registry or in your local store that points at an index or manifest digest. Moving a tag changes nothing inside the image, which is why tags are risky (part 4).

Because blobs are named by their hash, identical layers are stored and sent once. `wallet:v1` and the Alpine build of the wallet (Lab 4.1) both end in the same 3,131-byte app layer, `sha256:85cc2c4c...`, and a registry keeps one copy.

## How it works, part 2: from layers to a container's filesystem

A container's root filesystem is its image's layers stacked read-only, with one writable layer on top, merged by the kernel's overlayfs.

You met overlayfs in Ch 1.3: a *lower* directory that is never modified and an *upper* one that takes every write. The container runtime mounts the image's layers as lower directories, adds an empty upper directory for this container, and shows the merged result to the process as `/`.

{{diagram ch-4-1-03.jsx | layers to root filesystem · overlayfs, 2 containers from 1 image}}
Three consequences follow, and each one shows up later.

- **Starting is cheap.** No file is copied at start: the layers are already on disk, shared by every container made from the image.
- **A delete is a hiding, not a removal.** Deleting a file that lives in a lower layer writes a marker in the upper layer. The file is hidden from the process but still exists in the image. A `RUN rm` in a Dockerfile therefore saves no space and hides no secret from anyone who reads the layers (part 5, and the Break it of Lab 4.1).
- **The writable layer dies with the container.** Anything a container writes there is lost when it is removed, which is why a database needs a volume (Ch 4.3).

## How it works, part 3: the three OCI specifications

The OCI wrote three specifications, and each one fixes a single hand-off: what an image is, how it travels, and how it starts.

| Specification | The hand-off it fixes | You will meet it as |
| --- | --- | --- |
| [Image spec](https://github.com/opencontainers/image-spec) | What an image is: manifest, index, config, layers, and an on-disk "image layout" (`oci-layout`, `index.json`, `blobs/<alg>/<encoded>`) | The files inside a `docker save` archive |
| [Distribution spec](https://github.com/opencontainers/distribution-spec/blob/main/spec.md) | How a registry serves them: `GET /v2/<name>/manifests/<tag-or-digest>`, `GET /v2/<name>/blobs/<digest>`, `GET /v2/<name>/tags/list` | `docker pull`, `docker push`, `crane`, an `ImagePullBackOff` event |
| [Runtime spec](https://github.com/opencontainers/runtime-spec/blob/main/bundle.md) | What a runtime starts: a *bundle*, a directory with a root filesystem and a `config.json`, plus the commands create, start, kill and delete | `runc`, and the file your runtime writes for every container (Ch 4.2) |

Because each contract is a file format or an HTTP API rather than a program, the tools around it can change. BuildKit builds an image, Harbor stores it, containerd pulls it and runc starts it, each written by a different team. Kubernetes removed its built-in Docker support, the dockershim, in v1.24 ([Kubernetes blog](https://kubernetes.io/blog/2022/02/17/dockershim-faq/)); images built with Docker still run on a node because they follow the OCI image format. Lab 4.2 runs the image you build in Lab 4.1 with containerd and no Docker at all.

## How it works, part 4: registries, tags and digests

A registry is a web server that stores blobs and manifests and names them in two ways: by a tag that can be moved, and by a digest that cannot.

A full image name has four parts:

```text
docker.io/library/python:3.12-slim@sha256:<64 hex characters>
|registry-||repository-||---tag---||-----------digest-----------|
```

If you leave out the registry, Docker uses Docker Hub. If you leave out the tag, you get the tag `latest`, which is an ordinary name with no special promise. The Kubernetes documentation puts the rule plainly: "Digests are hashes of the image's content, and are immutable. Tags can be moved to point to different images, but digests are fixed", and it advises you to "avoid using the `:latest` tag when deploying containers in production" ([Images](https://kubernetes.io/docs/concepts/containers/images/)).

A pull is a short conversation of HTTP requests. The client resolves the tag once, then asks for everything else by digest, and skips every blob it already holds.

{{diagram ch-4-1-04.jsx | pull sequence · 4 request types · observed against a local registry:2, 2026-11-16}}
Public registries limit how fast you may pull. Docker Hub allows 100 pulls per six hours per IPv4 address (or IPv6 /64 subnet) without signing in, and 200 per six hours for a signed-in personal account ([Docker docs](https://docs.docker.com/docker-hub/usage/pulls/), checked 2026-11-16). A company cluster whose nodes share one address can hit that limit during a rollout, which is the first reason teams run their own registry (see the Harbor card).

## How it works, part 5: building small, fast and safe images

Every Dockerfile step makes a layer, so the order and content of your steps decide an image's size, its build time and what it leaks.

1. **Order for the cache.** BuildKit reuses a layer when its instruction and inputs are unchanged. "Once a layer changes, then all downstream layers need to be rebuilt as well" ([Docker docs](https://docs.docker.com/build/cache/)). Put slow, rarely changing steps (install dependencies) first and fast, often changing steps (copy your code) last.
2. **Deleting does not shrink.** A later `RUN rm` hides a file, but the earlier layer still holds it, in size and in what you push.
3. **Use multi-stage builds.** Build in one stage that has compilers and caches, then `COPY --from=<stage>` only the result into a small final stage. "None of the build tools required to build the application are included in the resulting image" ([Docker docs](https://docs.docker.com/build/building/multi-stage/)).
4. **Choose a small base** (table below).
5. **Run as a non-root user, one process per container.** The wallet image already sets `USER 10001`.
6. **Keep secrets out of layers.** Any file you ever copy into a layer stays in it. Pass build-time secrets with `RUN --mount=type=secret` and inject run-time secrets from outside.
7. **Send little, pin much.** A `.dockerignore` file keeps the build context small, and a base image pinned by digest keeps builds repeatable.

The diagram shows rule 1 on the wallet, with real times from Lab 4.1: the same one-line edit to `api.py` costs 12.2 s when the code is copied before `pip install`, and 3.6 s when it is copied after.

| Base image | What you get | What you give up |
| --- | --- | --- |
| `python:3.12-slim` | Debian 13 with glibc, a shell and apt: the usual default | The largest of the three; Debian's own layer is 29.9 MB compressed |
| `python:3.12-alpine` | Alpine Linux: musl libc and busybox tools | Software built only for glibc must be rebuilt for musl; the wallet's `psycopg` has a musl build |
| `gcr.io/distroless/python3-debian13` | "Only your application and its runtime dependencies", no shell and no package manager ([distroless](https://github.com/GoogleContainerTools/distroless)) | You cannot open a shell inside; the `:debug` tag adds a busybox shell for that. Its Python is 3.13, so build with 3.13 too |

## Commands you will use in the lab

All of these run on your own machine. `jq` reads JSON: install it once with `sudo apt install -y jq`.

| Command | What it does | Example |
| --- | --- | --- |
| `docker build -f <file> -t <name> .` | Build an image from a Dockerfile; the final `.` is the *build context* sent to the builder | `docker build -t wallet:v1 .` |
| `docker image ls`, `docker history <image>` | List local images with sizes; show one row per layer and the instruction that made it | `docker history wallet:v1` |
| `docker save <image> -o <file>` | Export an image as an archive in OCI image layout | `docker save wallet:v1 -o wallet-v1.tar` |
| `tar -xf <file> -C <dir>`, `tar -tzf <layer>` | Extract an archive into a directory; list the files inside one gzip layer | `tar -tzf blobs/sha256/<digest>` |
| `jq '<filter>' <file>` | Print parts of a JSON file | `jq .layers manifest.json` |
| `sha256sum <file>` | The SHA-256 digest of a file's bytes | `sha256sum blobs/sha256/*` |
| `docker tag`, `docker push` | Give an image a registry name; upload it | `docker push localhost:15000/wallet:v1` |
| `curl -H 'Accept: <media type>' <url>` | Call a registry's HTTP API by hand | `curl localhost:15000/v2/_catalog` |
| `docker build --secret id=<id>,src=<file>` | Give one build step a secret that is not stored in any layer | used in Break it |

## In production

Most image incidents come from three properties: names that move, layers that never shrink, and bases nobody maintains.

| What you see | What really happened | What engineers do |
| --- | --- | --- |
| Pod status `ErrImagePull`, then `ImagePullBackOff` | A wrong name or tag, missing registry credentials, an unreachable registry, or the pull limit of a public registry | Read the Pod's events (Vol 5), add an image pull secret, mirror public images into your own registry |
| Two nodes run different code from the same tag | The tag was moved between pulls, and a node that already holds an older copy may keep it because the default pull policy skips an image that is present | Deploy by digest or by a tag that is never reused; stop using `latest` |
| Rollouts are slow and nodes fill their disk | Images of 1 GB or more are pulled onto every node | Smaller bases, multi-stage builds, one base shared by many services so layers are reused, a registry or cache close to the nodes |
| A password turns up inside a public image | A file was copied in and deleted in a later step; the earlier layer still holds it | Rotate the secret first, then build with secret mounts and scan images for secrets in CI |
| A scanner reports hundreds of findings | Most come from operating-system packages in the base image that the application never uses | A smaller base, frequent rebuilds so the base gets patches, scanning inside the registry, a severity gate in CI |
| `exec format error` when a container starts | The image was built for another CPU, for example on an ARM laptop and run on an x86-64 server | Publish a multi-platform image so its index lists every architecture you run |
| Every build takes minutes | The layer order defeats the cache, or CI starts each build with an empty cache | Reorder as in part 5; keep the BuildKit cache between CI runs |

## Project card: Harbor

Harbor is the registry many companies run themselves when Docker Hub's limits and public visibility are not acceptable.

| Field | Content |
| --- | --- |
| Problem | A team needs its own registry that stores images, controls who may push and pull, scans images for vulnerabilities and copies them between sites. |
| Layer / interface | Registry. It speaks the OCI distribution API to Docker, containerd, CRI-O and the kubelet, and adds its own REST API and web portal. |
| Architecture | Core (REST API, authentication, projects, quotas, replication) · Web Portal · Job Service (asynchronous jobs) · Docker Registry, the Distribution server that stores the blobs · PostgreSQL for metadata · Redis · Trivy as the vulnerability scanner ([Harbor architecture](https://github.com/goharbor/harbor/wiki/Architecture-Overview-of-Harbor)). Its README lists role-based access control, policy-based replication, vulnerability scanning with policy checks, LDAP and OIDC sign-in, garbage collection and auditing ([README](https://github.com/goharbor/harbor)). |
| Alternatives | Distribution (`registry:2`, used in Lab 4.1): the smallest registry, with no portal or scanning. zot: an OCI-native registry that ships as one binary. A cloud provider's registry: nothing to operate, but tied to that provider. Docker Hub: public images, with pull limits. |
| CNCF maturity | Graduated: accepted 2018-07-31, graduated 2020-06-15 ([cncf.io/projects/harbor](https://www.cncf.io/projects/harbor/), as of 2026-11-16). Distribution and zot are both CNCF sandbox projects ([sandbox list](https://www.cncf.io/sandbox-projects/), as of 2026-11-16). |
