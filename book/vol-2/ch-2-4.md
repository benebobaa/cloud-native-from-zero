# Chapter 2.4 · DNS, HTTP and TLS

{{diagram ch-2-4-01.jsx | Ch 2.4 at a glance}}
## The problem: a client must find, ask and trust a service it cannot see

Before a client can send one byte of real work to the wallet, it must solve three problems, and each one has its own protocol.

The earlier chapters of this volume moved packets from one address to another. A person, a phone app or another service does not know the wallet's address; it knows a name, writes a request, and hopes nobody is listening in or pretending to be the wallet. Three questions follow:

1. **Where is it?** Programs use names such as `wallet.lab.test`; networks route numeric addresses. The Domain Name System (DNS) turns one into the other, and caches the answer so the lookup is cheap next time.
2. **How do we talk?** Client and server need an agreed format for "give me Alice's balance" and "here it is". That format is HTTP, and the interesting question is how many requests share one connection.
3. **Who is it, and who can listen?** Anyone on the path can read or change plain traffic, and anyone can claim to be the wallet. Transport Layer Security (TLS) encrypts the connection, and a certificate lets the client check the server's identity.

A fourth question appears once the wallet runs on many machines: **who picks the machine?** A load balancer does, and what it can see (only addresses, or the whole HTTP request) decides what it can do.

**Why this matters for Kubernetes.** Every Service in a cluster is a DNS name answered by CoreDNS. Every Ingress or gateway speaks HTTP and ends TLS. Service meshes put an L7 proxy and mutual TLS beside every Pod. Messages such as `no such host`, `certificate has expired` and `connection reset` are this chapter's mechanisms failing, and engineers who can read them fix the problem in minutes instead of hours.

## How it works, part 1: DNS, from a name to an address

DNS is a worldwide, cached database that answers "which records does this name have?", and every answer carries a *time to live* (TTL) saying how long anyone may reuse it.

A name reads from right to left. In `wallet.lab.test.` the final dot is the root, `test` is a top-level domain (TLD), `lab` is a zone under it, and `wallet` is a host in that zone. Different servers run each level, and the *authoritative* server of a zone holds its real records. No program walks this tree itself. Its *stub resolver*, a few lines in the C library, sends one question to a *recursive resolver*, which does the walking, remembers what it learned and replies. The recursive resolver's address is the `nameserver` line of `/etc/resolv.conf`.

{{diagram ch-2-4-02.jsx | DNS resolution · stub, recursive resolver, root, TLD, authoritative}}
Steps 2 to 4 run only when the recursive resolver has no fresh answer. Ask again and it answers from its cache, and the TTL it reports counts down. On the test machine, `dig example.com` run twice, two seconds apart, printed TTL `300` and then `298` ([RFC 1034](https://www.rfc-editor.org/rfc/rfc1034.html) and [RFC 1035](https://www.rfc-editor.org/rfc/rfc1035.html) define the system).

The record types you will meet most often, each from a real answer:

| Record | It answers | A real answer |
| --- | --- | --- |
| `A` | The IPv4 address of a name | `wallet.lab.test. 60 IN A 10.20.0.80` (Lab 2.4) |
| `AAAA` | The IPv6 address of a name ([RFC 3596](https://www.rfc-editor.org/rfc/rfc3596.html)) | `getent` asks for it too; the lab server answers "no data" |
| `CNAME` | "This name is an alias of another name" | `www.github.com. 2458 IN CNAME github.com.` |
| `NS` | Which servers are authoritative for a zone | `example.com. 86400 IN NS elliott.ns.cloudflare.com.` |
| `TXT` | Free text, used for ownership proofs and mail policy | `example.com. 300 IN TXT "v=spf1 -all"` |
| `SRV` | Host and port of a service, with priority and weight ([RFC 2782](https://www.rfc-editor.org/rfc/rfc2782.html)) | a query for `_ldap._tcp.example.com` returns server names |

**resolv.conf, search and ndots.** The stub resolver reads three settings from `/etc/resolv.conf`: `nameserver` (who to ask), `search` (domains to append to short names) and `options ndots:N`. A name with fewer than N dots is tried with each search domain first; the default N is 1 ([resolv.conf(5)](https://man7.org/linux/man-pages/man5/resolv.conf.5.html)). A Kubernetes Pod gets this file ([Kubernetes docs](https://kubernetes.io/docs/tasks/administer-cluster/dns-debugging-resolution/)):

```text
search default.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.0.0.10
options ndots:5
```

**Kubernetes preview.** With `ndots:5`, a name such as `wallet.lab.test` has only two dots, so the stub tries every search domain before the real name. Each failed try is a query and a round trip. In Lab 2.4 one `getent hosts wallet.lab.test` becomes six queries (A and AAAA for each of three names) and only the last one succeeds. Vol 5 returns to this when you debug slow lookups inside a cluster.

## How it works, part 2: HTTP, one conversation at a time or many at once

HTTP is a text conversation: the client sends a request (a method, a path, headers), the server sends a reply (a status, headers, a body), and the open question is how many of these share one TCP connection.

This is a real HTTP/1.1 exchange, typed by hand with `nc` against the wallet's nginx in Lab 2.4 (trimmed to the point):

```text
GET /alice HTTP/1.1
Host: wallet.lab.test
Connection: close

HTTP/1.1 200 OK
Server: nginx/1.24.0 (Ubuntu)
Content-Type: application/json
Transfer-Encoding: chunked
Connection: close

25
{"account": "alice", "balance": 100}
0
```

- The **request line** holds the method (`GET`), the path and the version. Headers follow, one per line, and a blank line ends them.
- `Host` names the site. One IP address can serve many names, and nginx uses `Host` to choose which `server` block answers.
- The **status line** carries the result: `200 OK`, or `404` for an unknown account.
- `Transfer-Encoding: chunked` sends the body in pieces: a length in hexadecimal (`25` is 37 bytes), the bytes, and a final `0`.
- HTTP/1.1 is defined in [RFC 9112](https://www.rfc-editor.org/rfc/rfc9112.html), and the meaning of methods and status codes in [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html).

**Keep-alive.** A new TCP connection costs a round trip before any request is sent, so clients reuse one. In the lab, `curl` fetched two URLs and printed `Re-using existing connection`: one connection, two requests. HTTP/1.1 still answers one request at a time on a connection, so a client that wants three requests in flight opens three connections.

**HTTP/2** removes that limit. It sends binary frames instead of text, compresses repeated headers, and gives each request/reply pair its own *stream* on one connection, so streams interleave without waiting for each other ([RFC 9113](https://www.rfc-editor.org/rfc/rfc9113.html)). The client does not guess; the choice is made inside the TLS handshake by *ALPN*, a TLS extension in which the client lists protocols and the server picks one ([RFC 7301](https://www.rfc-editor.org/rfc/rfc7301.html)). The lab's `curl -v` shows both sides: `ALPN: curl offers h2,http/1.1` and `ALPN: server accepted h2`. The request line and `Host` header become `:method`, `:path` and `:authority` fields.

{{diagram ch-2-4-03.jsx | HTTP/1.1 versus HTTP/2 on the wire · connections and streams}}
**HTTP/3** keeps the HTTP meaning but replaces TCP with QUIC, a transport that runs over UDP and provides the streams itself ([RFC 9114](https://www.rfc-editor.org/rfc/rfc9114.html), [RFC 9000](https://www.rfc-editor.org/rfc/rfc9000.html)). You will meet it in browsers and CDNs. Lab 2.4 does not run it: the nginx in Ubuntu 24.04 was not tested with HTTP/3.

**HTTP versions are per hop.** In the lab the Python wallet speaks HTTP/1.0 to nginx, and nginx speaks HTTP/1.1 or HTTP/2 to the client. A proxy translates; that is why putting one in front of a simple service is so common.

## How it works, part 3: TLS, privacy and identity in one round trip

TLS wraps a TCP connection so that the client learns who it is talking to and nobody on the path can read or change the traffic; TLS 1.3 sets this up in one round trip ([RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html)).

The handshake does three jobs. The two sides **agree on secret keys** by exchanging *key shares*, so the keys themselves never cross the wire. The server **proves its identity** with a certificate and a signature made with its private key. Then both sides **encrypt** everything with the agreed keys. The diagram below is built from a real trace of the wallet's nginx in Lab 2.4.

{{diagram ch-2-4-04.jsx | TLS 1.3 handshake · sequence built from the Lab 2.4 trace}}
On the wire, `tshark` read from a packet capture of that connection shows only this (columns trimmed):

```text
 4  10.20.0.10 -> 10.20.0.80  TLSv1    Client Hello (SNI=wallet.lab.test)
 6  10.20.0.80 -> 10.20.0.10  TLSv1.3  Server Hello, Change Cipher Spec, Application Data x4
 8  10.20.0.10 -> 10.20.0.80  TLSv1.3  Change Cipher Spec, Application Data
 9  10.20.0.10 -> 10.20.0.80  TLSv1.3  Application Data
```

Three things follow from it:

- **The Client Hello is readable, including the server name.** *SNI* (server name indication) tells a server or proxy which site the client wants, before any certificate is chosen. It also tells anyone watching the link which name you asked for.
- **Everything after the Server Hello is encrypted**: "All handshake messages after the ServerHello are now encrypted" ([RFC 8446, section 1.2](https://www.rfc-editor.org/rfc/rfc8446.html)). The four `Application Data` records in packet 6 are the messages `curl -v` labels Encrypted Extensions, Certificate, CertVerify and Finished. `tshark` finds no Certificate message in this capture.
- **TLS 1.2 shows more and takes longer.** The same connection forced to TLS 1.2 (`--tls-max 1.2`) shows `Server Hello, Certificate, Server Key Exchange, ...` in the clear, and the client's `Client Key Exchange` needs a second round trip before the request can leave. Lab 2.4 Part D measures this: TLS 1.3 adds about one round trip to a connection, TLS 1.2 about two.

The handshake costs time, so clients keep connections open and reuse them. That is the same reason HTTP keep-alive and HTTP/2 matter.

## How it works, part 4: certificates and the chain of trust

A certificate is a public key bound to a name and signed by a certificate authority (CA); a client accepts it only if the signature chain ends at a root it already trusts and the name, dates and purpose all fit.

A CA signs with its private key, and anyone holding the CA's own certificate can check that signature. Operating systems and browsers ship a list of trusted roots, the *trust store*. A *root* certificate is self-signed: its issuer is itself, so trust in it cannot come from a signature and must be installed. In Lab 2.4 you make your own root, `Lab Root CA`, and your own server certificate for `wallet.lab.test`; only clients that you give `ca.crt` will trust it. The format and the path-validation algorithm are defined in [RFC 5280](https://www.rfc-editor.org/rfc/rfc5280.html).

{{diagram ch-2-4-05.jsx | chain of trust and the client's checks · the lab's own CA}}
Three of the five checks cause most real outages:

- **Name.** Modern clients compare the name they dialled with the certificate's *Subject Alternative Name* (SAN) list; the rules are in [RFC 9525](https://www.rfc-editor.org/rfc/rfc9525.html), which replaces RFC 6125. A certificate for `wallet.lab.test` does not match the IP address `10.20.0.80`, so `curl https://10.20.0.80/` fails even though the server is the right one.
- **Dates.** The client compares `notBefore` and `notAfter` with its own clock. A certificate that expired yesterday, or a client whose clock is wrong, produces the same error.
- **Chain.** A client that does not hold your root cannot verify the signature. It says `unable to get local issuer certificate`.

The lab makes you cause each of these on purpose in Break it.

**Preview: mTLS.** In ordinary TLS only the server shows a certificate. In *mutual TLS* the server also sends a `CertificateRequest`, and the client answers with its own certificate and signature (the braces in Figure 1 of RFC 8446, section 2). Kubernetes uses this between its own components: kubelets, the controller manager, the scheduler and the API server authenticate with client certificates, and etcd "implements mutual TLS to authenticate clients and peers" ([Kubernetes PKI certificates and requirements](https://kubernetes.io/docs/setup/best-practices/certificates/)). Service meshes in later volumes use the same idea between Pods.

**Preview: ACME.** Certificates expire, so someone must renew them. The *ACME* protocol ([RFC 8555](https://www.rfc-editor.org/rfc/rfc8555.html)) lets a CA and an applicant automate both proving that the applicant controls a domain and issuing the certificate. [Let's Encrypt](https://letsencrypt.org/about/) is a free, automated CA that works this way, and cert-manager (project card below) runs the same dance inside a Kubernetes cluster. Vol 6 and 7 use it.

## How it works, part 5: L4 and L7 load balancing, and gRPC

A load balancer spreads clients over several copies of a service; an L4 balancer sees only addresses and ports, an L7 balancer reads the HTTP request, and that difference decides what it can do.

"L4" and "L7" count layers: layer 4 is the transport (TCP connections and ports), layer 7 is the application protocol (HTTP). Where the balancer sits in that stack decides what it can see.

{{diagram ch-2-4-06.jsx | L4 versus L7 load balancing · what each sees, who gets the requests}}
|  | L4 (TCP) balancer | L7 (HTTP) balancer |
| --- | --- | --- |
| Sees | IP addresses and ports | The same, plus method, path, `Host` and headers (after ending TLS) |
| Picks a backend | Once per connection | Once per request |
| TLS | Can pass the encrypted bytes through untouched | Must end TLS, so it holds the certificate; may encrypt again to the backend |
| Can do | Spread connections quickly, for any TCP protocol | Route by host or path, retry a failed request, rate-limit, add headers |
| Costs | Little CPU, no certificates | More CPU, certificates, knowledge of HTTP |

**gRPC** is a remote-procedure-call framework: it sends calls over HTTP/2 ([gRPC over HTTP/2](https://github.com/grpc/grpc/blob/master/doc/PROTOCOL-HTTP2.md)) and, by default, encodes messages with Protocol Buffers, a compact binary format ([gRPC introduction](https://grpc.io/docs/what-is-grpc/introduction/)). A gRPC client opens one long-lived HTTP/2 connection and sends every call as a stream on it. An L4 balancer sees one connection, picks one backend, and that backend receives all of the client's calls, as the top row of the diagram shows.

The gRPC project names two fixes ([gRPC load balancing](https://grpc.io/blog/grpc-load-balancing/)). With **proxy** balancing the client talks to a central balancer that spreads requests; this adds a hop and a throughput limit. With **client-side** balancing the client knows several backends and chooses one for each call; this removes the hop but makes the client more complex and requires trusting it. The same fault hits any long-lived HTTP/2 client behind an L4 balancer: connection reuse, a feature, defeats connection-level balancing.

## In production

Most network incidents at this layer are caching, clocks and names, not broken networks; the table lists the ones that recur.

| What you see | What really happened | What engineers do |
| --- | --- | --- |
| A DNS change "did not work": some clients still reach the old address for minutes or hours | Resolvers and clients cached the old answer and keep it until its TTL ends; lowering the TTL now only affects caches filled later | Lower the TTL a full old-TTL before a planned change, keep the old target running until it has passed, and compare `dig` against the authoritative server and against the resolver |
| A name you just created still gives `NXDOMAIN` or `no such host` | *Negative caching*: a resolver remembers "does not exist" for a while ([RFC 2308](https://www.rfc-editor.org/rfc/rfc2308.html)) | Create the record before anything asks for it; when testing, query a different resolver or wait |
| Slow lookups inside a Pod, CoreDNS busy with `NXDOMAIN` answers | `ndots:5` sends every name with fewer than five dots through each search domain first; Lab 2.4 shows six queries for one lookup | Use fully qualified names for outside hosts, lower `ndots` in the Pod's DNS settings, and read Vol 5 on DNS policy |
| Every client fails at once with `certificate has expired` | The certificate passed its `notAfter` date; renewal was manual or its automation broke without anyone noticing | Monitor days left on every certificate and alert weeks ahead, automate renewal with ACME or cert-manager, and check by hand with `openssl s_client` (Lab 2.4 Break it) |
| `no alternative certificate subject name matches target host name` | The name the client dialled is not in the certificate's SAN list: an IP address, an old name after a rename, or a wildcard that does not cover it | List every name clients use in the SAN, call services by name, and test with `curl --resolve` instead of by IP |
| "Not yet valid" or "expired" on one machine only, with a good certificate | *Clock skew*: the client compares the dates with its own wrong clock | Keep clocks synchronised and compare `date` on both sides; `faketime` reproduces the error safely |
| Works from your laptop, fails inside a container with `unable to get local issuer certificate` | The container's trust store lacks your private CA | Add the CA to the image's trust store, or pass the CA file to the client, as `--cacert` does |
| One backend is hot while others idle, with gRPC or other HTTP/2 clients | Connection reuse: an L4 balancer picks a backend once per connection, and one long-lived HTTP/2 connection carries every call | Balance per request with an L7 proxy such as Envoy, or let the client balance across backends |

**Choosing L4 or L7.** Pick L4 for plain TCP services such as a database: it is fast, generic and holds no certificates. Pick L7 for HTTP and gRPC APIs when you need routing by path or host, retries, or per-request metrics, and accept that the balancer now holds the certificate and does more work.

## Project cards

Four CNCF projects sit on the mechanisms of this chapter. Maturity levels are as listed on each project's page at [cncf.io/projects](https://www.cncf.io/projects/), checked on 2026-11-16.

**CoreDNS**

| Field | Content |
| --- | --- |
| Problem | Answer DNS queries for a cluster, so Services and Pods have names |
| Layer / interface | DNS (UDP and TCP port 53); the cluster DNS of Kubernetes, behind the Service `kube-dns` ([Kubernetes docs](https://kubernetes.io/docs/tasks/administer-cluster/dns-debugging-resolution/)) |
| Architecture | A DNS server written in Go. Nearly all functions are plugins, run in a fixed order per server block of the Corefile; the `kubernetes` plugin reads Services from the Kubernetes API ([CoreDNS manual](https://coredns.io/manual/toc/)) |
| Alternatives | BIND or PowerDNS for authoritative zones on the public internet; dnsmasq for a small host or a lab, as in Part A |
| CNCF maturity | [Graduated](https://www.cncf.io/projects/coredns/) (as of 2026-11-16) |

**Envoy**

| Field | Content |
| --- | --- |
| Problem | One programmable proxy that does routing, retries, TLS and metrics for service traffic |
| Layer / interface | L3/L4 network filters and L7 HTTP/gRPC filters; configured live through APIs ([Envoy docs](https://www.envoyproxy.io/docs/envoy/latest/intro/what_is_envoy)) |
| Architecture | Listeners with filter chains, routes and clusters of upstream hosts; supports HTTP/1.1 and HTTP/2 and translates between them; used as the data plane of many gateways and meshes |
| Alternatives | NGINX when a static reverse proxy is enough, as in this lab; HAProxy or Traefik for simpler setups; pick Envoy when a control plane must reconfigure many proxies without restarts |
| CNCF maturity | [Graduated](https://www.cncf.io/projects/envoy/) (as of 2026-11-16) |

**gRPC**

| Field | Content |
| --- | --- |
| Problem | Typed, efficient calls between services, with client code generated from one interface file |
| Layer / interface | Application RPC over HTTP/2, Protocol Buffers by default ([protocol](https://github.com/grpc/grpc/blob/master/doc/PROTOCOL-HTTP2.md)) |
| Architecture | A service defined in a `.proto` file, generated client and server code, and one long-lived HTTP/2 connection per client; load-balancing policies live in the client ([gRPC load balancing](https://grpc.io/blog/grpc-load-balancing/)) |
| Alternatives | REST with JSON over HTTP: easy to read and call from a browser; choose gRPC for internal, many-language services that need streaming or strict types |
| CNCF maturity | [Incubating](https://www.cncf.io/projects/grpc/) (as of 2026-11-16) |

**cert-manager**

| Field | Content |
| --- | --- |
| Problem | Issue TLS certificates for workloads and renew them before they expire |
| Layer / interface | Kubernetes API: a controller that watches `Certificate` resources and stores the result in a Secret ([cert-manager docs](https://cert-manager.io/docs/)) |
| Architecture | Controllers plus issuers that talk to a CA; the docs name Let's Encrypt (ACME), HashiCorp Vault and private PKI as sources |
| Alternatives | Renew by hand or with a cron job on each server; let a cloud load balancer or a mesh manage certificates; pick cert-manager when workloads run in Kubernetes and need many short-lived certificates |
| CNCF maturity | [Graduated](https://www.cncf.io/projects/cert-manager/) (as of 2026-11-16) |
