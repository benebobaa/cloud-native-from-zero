# Chapter 2.3 · TCP and UDP

{{diagram ch-2-3-01.jsx | Ch 2.3 at a glance}}
## The problem: a reliable byte stream on top of unreliable IP

IP delivers single packets with no promise; an application wants a pipe that delivers every byte, once, in order, and TCP builds that pipe in software at the two ends.

Chapters 2.1 and 2.2 showed what IP gives you: a packet addressed to a machine, forwarded hop by hop. Along the way a router with a full queue may drop it, two paths may deliver packets out of order, and a retry may deliver one twice. IP also names a machine, not a program. Three questions follow, and this chapter answers each:

1. **Which program?** One machine runs many network programs. A 16-bit *port* number picks the program, and a *socket* is the kernel object a program holds for one end of a conversation.
2. **Did it all arrive, in order?** TCP numbers every byte, the receiver acknowledges what arrived, and the sender resends what was not acknowledged.
3. **How fast may I send?** A sender that is too fast overruns the receiver (*flow control*) or the network (*congestion control*). TCP measures both and slows down.

**UDP** keeps the first answer (ports) and drops the other two. It is what you use when the application prefers to handle loss itself, or when late data is worthless.

**Why this matters for Kubernetes.** Every Service, Ingress and database connection in the book is TCP, or UDP for DNS. "Connection refused", "connection timed out", "connection reset by peer" and "cannot assign requested address" are TCP messages with exact meanings. Engineers who know them find the broken layer in minutes; everyone else restarts Pods and hopes.

## How it works, part 1: ports, sockets and the 5-tuple

A TCP connection is named by five values, and the kernel gives your program a file descriptor for each end of it.

A *port* is a number from 0 to 65535 that says which program on a machine should get a packet. A *socket* is the kernel's object for one end of a conversation; your program holds it as a file descriptor, exactly like the descriptor 4 that `accept4` returned in the wallet's `strace` in Ch 1.2. The kernel identifies one TCP connection by its **5-tuple**: protocol, source IP, source port, destination IP, destination port.

A server uses two kinds of socket. First it makes one *listening socket* bound to a port (`bind`, `listen`); it never carries data. Each time a client connects, `accept` returns a brand-new *accepted socket* with its own descriptor. All accepted sockets share the server's local port, and the 5-tuple still differs because each client has a different address or port. That is how thousands of clients share port 443.

The client does not choose its port. At `connect` the kernel picks an *ephemeral port* from `ip_local_port_range`, which defaults to 32768 to 60999 ([kernel ip-sysctl](https://docs.kernel.org/networking/ip-sysctl.html)). That is 28 232 ports. Remember this number; it comes back in "In production".

A listening socket also has a queue of connections that finished the handshake but that the program has not yet accepted. `listen(fd, backlog)` sets its length, and the kernel caps it at `net.core.somaxconn`, which is 4096 since Linux 5.4 ([listen(2)](https://man7.org/linux/man-pages/man2/listen.2.html)). In `ss -tl` output, `Send-Q` is that limit and `Recv-Q` is how many connections wait right now.

## How it works, part 2: the handshake and the teardown

Before any data moves, the two ends exchange three packets to agree on starting sequence numbers and options; to finish, each end sends a FIN that the other acknowledges.

The opening is the *three-way handshake* ([RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html), section 3.5). The client sends **SYN** ("synchronize") with a random starting sequence number. The server answers **SYN-ACK**, with its own random number and an acknowledgement of the client's. The client sends **ACK**. Each end now knows the other is alive and where its byte count starts. A SYN uses up one sequence number, which is why the acknowledgement is the client's number plus one.

The drawing below is not a textbook figure. It is the packet trace from Lab 2.3 Part B: `curl` fetched a 12 000-byte file from a Python web server, and `tcpdump` on the server's side of the link recorded 15 packets.

{{diagram ch-2-3-03.jsx | handshake, request, response and teardown · real tcpdump trace, Lab 2.3 Part B}}
Black arrows open the connection, grey arrows carry data, dark grey arrows close it. Times are read from the server's capture, so they measure the server's view: the 9 ms gap is Python preparing the response.

Packets with the SYN flag carry options that each side offers once, at the start:

| Option in the trace | Meaning |
| --- | --- |
| `mss 1460` | Maximum segment size: the most payload bytes the sender accepts in one segment. 1500 (Ethernet MTU) minus 20 (IP header) minus 20 (TCP header). |
| `sackOK` | Selective acknowledgement is allowed: the receiver may report exactly which byte ranges arrived, so the sender resends only the holes ([RFC 2018](https://www.rfc-editor.org/rfc/rfc2018.html)). |
| `wscale 10` | Window scale: the 16-bit window field is multiplied by 2^10 = 1024. A bare 16-bit field caps the window at 65 535 bytes; scaling allows up to 1 GiB ([RFC 7323](https://www.rfc-editor.org/rfc/rfc7323.html)). The scale is fixed during the handshake. |
| `TS val ... ecr ...` | Timestamps: each packet carries the sender's clock and echoes the peer's, so each side can measure round-trip time, and old duplicates are recognised ([RFC 7323](https://www.rfc-editor.org/rfc/rfc7323.html)). They take 12 bytes, so the real payload per segment is 1448; `ss -ti` shows `mss:1448`. |

Read the middle of the drawing as data flowing. The request is 84 bytes (`seq 1:85`) and the server answers `ack 85`: **an acknowledgement number is the next byte the receiver expects**, not the last one it got. After the handshake `tcpdump` prints sequence numbers relative to the start, which is why the numbers shrink from nine digits to `1`.

Two details can confuse you. The data segments of 7240 and 4760 bytes are larger than `mss 1460`: on this virtual link the kernel hands the capture a batch of segments at once (7240 = 5 x 1448), whereas a real wire would carry five packets. And the closing is a *crossed* close: the FINs left within microseconds of each other, so each side acknowledged the other's FIN after sending its own.

## How it works, part 3: the state machine and TIME\_WAIT

Each end of a connection is a small state machine, and the state that surprises people most is TIME\_WAIT: a closed connection stays in the kernel's table for 60 seconds.

`ss` prints the state of every socket, so you can see where a connection is. The names come from [RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html), section 3.3.2: LISTEN, SYN-SENT, SYN-RECEIVED, ESTABLISHED, FIN-WAIT-1, FIN-WAIT-2, CLOSE-WAIT, CLOSING, LAST-ACK and TIME-WAIT (`ss` writes SYN-RECV and TIME-WAIT). The drawing shows the path of a normal connection; the side that closes first takes the left branch.

{{diagram ch-2-3-04.jsx | TCP connection states · normal open and close}}
Read the drawing from the top: the client enters SYN\_SENT, the server's accepted socket SYN\_RECV, both reach ESTABLISHED. After that the first side to call `close` walks the left column and ends in TIME\_WAIT; the other side walks the right column.

Two states are worth knowing by heart because they point at bugs. A pile of **CLOSE\_WAIT** sockets means the other end closed and *your program* has not called `close` yet: a file-descriptor leak in the application. A pile of **TIME\_WAIT** sockets means connections are being opened and closed very often.

**Why TIME\_WAIT exists.** The end that sends the last ACK must wait before it forgets the connection. RFC 9293 (section 3.3.2) gives two reasons: to make sure the peer received the acknowledgement of its FIN (if that ACK is lost, the peer resends its FIN and needs an answer), and to stop delayed packets of an old connection from being mistaken for part of a new one that reuses the same 5-tuple. The RFC fixes the wait at twice the maximum segment lifetime, and takes that lifetime to be 2 minutes (section 3.4.2). Linux waits 60 seconds; Lab 2.3 shows `timer:(timewait,59sec,0)` on a connection that had just closed.

TIME\_WAIT sits on whichever side sent the first FIN. In the crossed close of part 2 both sides hold one. For a *server* that closes first, TIME\_WAIT is harmless, because the server's port is shared by every connection. For a *client* that closes first, each TIME\_WAIT keeps one of its 28 232 ephemeral ports busy for a minute. That is the root of port exhaustion, in "In production".

## How it works, part 4: reliability, flow control and congestion control

TCP turns loss into delay: it resends what is not acknowledged, and it limits how much unacknowledged data may be in flight to what the receiver and the network can take.

**Retransmission.** The sender keeps every byte until it is acknowledged. If an acknowledgement does not arrive within the *retransmission timeout* (RTO), the sender sends the data again. Before it has measured any round trip, the RTO starts at 1 second, and each further timeout doubles it ([RFC 6298](https://www.rfc-editor.org/rfc/rfc6298.html), sections 2.1 and 5.5). You will see this: a SYN that gets no answer is repeated after about one second. Waiting for a timer is slow, so TCP has a shortcut. When the receiver gets a segment after a gap, it repeats its last acknowledgement. Three such duplicates make the sender resend at once, without waiting (*fast retransmit*, [RFC 5681](https://www.rfc-editor.org/rfc/rfc5681.html), section 3.2). With SACK the acknowledgement also lists the ranges that did arrive, as in `sack 1 {393046:393422}` in the lab's lossy trace.

**Flow control: do not overrun the receiver.** Every acknowledgement carries a *receive window*: how many more bytes the receiver has room for. Data the application has not yet read sits in the socket's receive buffer, and the window shrinks as it fills. In the handshake trace the server advertised `win 64`; with `wscale 10` that means 64 x 1024 = 65 536 bytes. A slow application therefore slows the sender; this is why `Recv-Q` in `ss` grows when a program does not read.

**Congestion control: do not overrun the network.** The receiver cannot know how much the *path* can carry, so the sender keeps its own limit, the *congestion window* (`cwnd`). At any time it may have at most `min(cwnd, receive window)` unacknowledged bytes in flight. Linux starts `cwnd` at 10 segments (`cwnd:10` in `ss -ti`; [RFC 6928](https://www.rfc-editor.org/rfc/rfc6928.html) proposed 10). The algorithm then reacts to loss, which it reads as a sign that a queue overflowed:

- **Slow start:** `cwnd` grows by one segment per acknowledgement, which doubles it every round trip, until it reaches a threshold or a loss occurs ([RFC 5681](https://www.rfc-editor.org/rfc/rfc5681.html), section 3.1). It is "slow" only compared with sending everything at once.
- **Congestion avoidance:** past the threshold `cwnd` grows by about one segment per round trip.
- **On loss:** the threshold is set to half of the data in flight, and `cwnd` shrinks (RFC 5681, equation 4). After a timeout it drops to one segment.

The algorithm is replaceable. **CUBIC** is the Linux default (`sysctl net.ipv4.tcp_congestion_control` prints `cubic`; [RFC 9438](https://www.rfc-editor.org/rfc/rfc9438.html) says Linux, Windows and Apple use it). After a loss it regrows `cwnd` along a cubic curve of the time since the loss: fast at first, flat near the old peak, then probing beyond it. **BBR** takes another approach: it builds a model of the path from measured delivery rate and round-trip time and paces its sending from that model ([IETF draft](https://datatracker.ietf.org/doc/html/draft-ietf-ccwg-bbr), still an Internet-Draft). `sysctl net.ipv4.tcp_available_congestion_control` lists what your kernel offers; the test kernel offered `reno cubic`.

{{diagram ch-2-3-05.jsx | congestion window over time · schematic, not measured}}
The saw-tooth is the signature of TCP on a busy path: the sender keeps pushing until a queue overflows, then retreats and tries again. The charts in Lab 2.3 Part D show what this costs.

**Bandwidth-delay product.** To keep a link full, the sender needs a window as large as the data that fits in the pipe: the *bandwidth-delay product* (BDP).

```latex
BDP = bandwidth x round-trip time
throughput <= window / round-trip time
```

A 1 Gbit/s path with a 20 ms round trip holds 1e9 / 8 x 0.02 = 2.5 MB. If the window is smaller, the sender stops and waits for acknowledgements, and the link sits partly idle however fast it is. Lab 2.3 Part D measures this: throughput falls almost in proportion to the round-trip time, because the window stays about the same size.

## How it works, part 5: UDP and a preview of QUIC

UDP adds only ports and a checksum to IP: it sends independent datagrams with no handshake, no retransmission and no congestion control.

[RFC 768](https://www.rfc-editor.org/rfc/rfc768.html) is three pages long. The UDP header has four fields: source port, destination port, length and checksum, 8 bytes in all. The RFC states plainly that "delivery and duplicate protection are not guaranteed". One `sendto` produces one datagram; if it is lost, nobody notices unless the application does.

That sounds like a defect, and for a file transfer it would be. It is a feature when the application knows better than TCP:

| Use | Why UDP fits |
| --- | --- |
| DNS (Ch 2.5) | One small question, one small answer. A handshake would double the round trips; the client simply asks again after a timeout. |
| Live audio, video, games | A packet that arrives late is worthless. Waiting for a resend would stall everything behind it. |
| QUIC and HTTP/3 | The application builds reliability, encryption and several independent streams on top of UDP, in user space. |

**What happens when nobody listens.** A TCP SYN to a closed port is answered with a RST (*reset*) packet, and the client sees "connection refused". UDP has no connection, so the kernel answers an unwanted datagram with an ICMP message, *port unreachable*. Lab 2.3 Part C captures one: `ICMP 10.2.0.2 udp port 5999 unreachable`. The sender only learns of it if its socket is *connected* (as `nc -u` is); a plain `sendto` socket usually never hears.

**QUIC.** [RFC 9000](https://www.rfc-editor.org/rfc/rfc9000.html) defines "a UDP-based multiplexed and secure transport": QUIC packets travel inside UDP datagrams, one connection carries several independent streams, and the TLS handshake is part of the protocol. HTTP/3 is HTTP carried over QUIC ([RFC 9114](https://www.rfc-editor.org/rfc/rfc9114.html)). A lost packet then delays only its own stream instead of every stream on the connection. For you as an operator it means one practical change: web traffic may arrive on UDP port 443, so a firewall that allows only TCP 443 forces clients back to HTTP/2 over TCP.

## How it works, part 6: conntrack, the kernel's connection table

The Linux kernel keeps a table of every flow that crosses it, called *connection tracking* (conntrack), so that firewall rules and address translation can talk about connections instead of single packets.

In Ch 2.4 you will write firewall rules such as "accept packets that belong to an established connection" (`ct state established`). The kernel can only answer "is this packet part of one?" because it recorded the first packet of each flow. NAT, the address rewriting in Ch 2.4, uses the same table to rewrite the replies. UDP gets entries too: with no handshake, the kernel treats the first datagram as a new flow and expires it after a quiet period.

Lab 2.3 Part E prints one entry with `conntrack -L`:

```text
tcp  6 431999 ESTABLISHED src=10.2.0.1 dst=10.2.0.2 sport=44844 dport=9300 src=10.2.0.2 dst=10.2.0.1 sport=9300 dport=44844 [ASSURED] mark=0 use=1
```

Read it left to right: protocol `tcp` (protocol number 6); **431999 seconds left** before the entry expires; the TCP state; then the 5-tuple as the client sent it; then the 5-tuple of the *reply*, which is the same with the two ends swapped. With NAT the reply tuple is where the rewritten addresses show up.

Every entry has a timeout that depends on its state. These are the kernel defaults ([nf\_conntrack sysctl docs](https://docs.kernel.org/networking/nf_conntrack-sysctl.html)):

| Sysctl (`net.netfilter.`) | Default | Meaning |
| --- | --- | --- |
| `nf_conntrack_tcp_timeout_established` | 432000 s (5 days) | An idle established connection is forgotten after this. |
| `nf_conntrack_tcp_timeout_time_wait` | 120 s | Closed connection, kept to match stragglers. |
| `nf_conntrack_tcp_timeout_syn_sent` | 120 s | A SYN was seen, no answer yet. |
| `nf_conntrack_tcp_timeout_close_wait` | 60 s | One side has closed. |
| `nf_conntrack_udp_timeout` | 30 s | A UDP flow seen in one direction only. |
| `nf_conntrack_udp_timeout_stream` | 120 s | A UDP flow detected as a stream. |

The table has a fixed size, `nf_conntrack_max`, which by default equals the number of hash buckets, themselves sized from total memory (between 1024 and 262 144). When it is full the kernel cannot track a new flow and drops its first packet, logging `nf_conntrack: table full, dropping packet` (from `__nf_conntrack_alloc` in [nf\_conntrack\_core.c](https://github.com/torvalds/linux/blob/master/net/netfilter/nf_conntrack_core.c); inside a non-initial network namespace the message reads `table full in netns N, dropping packet`). Existing connections keep working; *new* ones time out. `nf_conntrack_count` shows how full the table is.

All of these are in Ubuntu 24.04's packages: the lab's `apt-get install` line is in Lab 2.3. Inside a network namespace, run any command as `ip netns exec NAME <command>`; `ip -n NAME <args>` is the short form for the `ip` command alone.

| Command | What it does | Example |
| --- | --- | --- |
| `ss -tlnp` | List listening TCP sockets with numeric addresses (`-n`) and the owning process (`-p`) | `ip netns exec srv ss -tlnp` |
| `ss -tan`, `ss -tan state time-wait` | List all TCP sockets, or only those in one state | `ip netns exec cli ss -tan state time-wait` |

| `nc -l PORT`, `nc -lk PORT`, `nc HOST PORT` | Listen once, listen and keep accepting (`-k`), or connect. Add `-u` for UDP and `-w N` to stop after N seconds | `ip netns exec srv nc -lk 9100` |
| `tcpdump -Z root -n -ttt -i IF -w FILE 'FILTER'` | Capture packets to a file, as root (see the gotcha below). Read back with `-r FILE`; `-ttt` prints the time since the previous packet; `-c N` stops after N packets | `tcpdump -n -ttt -r /tmp/hs.pcap` |
| `nstat -n`, then `nstat` | Kernel network counters. `-n` records a baseline and prints nothing; the next plain `nstat` prints only what changed since | `ip netns exec srv nstat \| grep Retrans` |

| `curl -sS -m 5 URL` | Fetch a URL quietly but show errors (`-sS`), giving up after 5 seconds (`-m`) | `ip netns exec cli curl -sS -m 5 http://10.2.0.2:9200/` |

Stop a background capture with `pkill -x tcpdump`; never `pkill -f` with a pattern that also appears in your own command line, or you kill your own shell.

## In production

Most network incidents between services are one of nine TCP behaviours; the symptom tells you which, if you know the table below.

| What you see | What really happens | What engineers do |
| --- | --- | --- |
| `connect: Cannot assign requested address` (errno 99), thousands of `TIME_WAIT` sockets | A client has 28 232 ephemeral ports by default for one destination IP and port. Each closed connection holds its port for 60 s, so the sustainable rate is about 470 new connections per second (28 232 / 60). Lab 2.3 Break it hits the wall at a range of 100 ports. | Stop opening a connection per request: keep-alive and connection pools. Spread load over more destination IPs. A wider `ip_local_port_range` or `tcp_tw_reuse` only buys time. |
| New connections time out at random; `nf_conntrack: table full, dropping packet` in `dmesg` | The conntrack table has reached `nf_conntrack_max`. The kernel drops the first packet of every new flow; established flows keep working. Short-lived connections and the 5-day `established` timeout fill it. This cannot be reproduced in a network namespace: `nf_conntrack_max` is read-only there (Lab 2.3 Part E shows the refusal). | Watch `nf_conntrack_count` against `nf_conntrack_max`. Raise the maximum, knowing every entry costs memory. Shorten timeouts for idle flows. Reduce connection churn. Exclude very high-volume traffic from tracking. |
| Connects are slow under load (first SYN answered after 1 s or 3 s), or clients get resets; `ss -tl` shows `Recv-Q` at `Send-Q` | The *accept queue* is full: the application does not call `accept` fast enough, or its `listen` backlog is small. The kernel caps the backlog at `net.core.somaxconn` (4096 since Linux 5.4). When the SYN queue overflows, `tcp_syncookies` (on by default) lets connections continue without queue memory. | Make the accept loop quicker or add workers. Raise the application's backlog and `somaxconn` together. Check `nstat` for `TcpExtListenOverflows` and `TcpExtListenDrops`. |
| `Connection refused` | A RST came back: the host is up and nothing listens on that port, or a firewall rule says `reject`. It fails at once (0.05 s in the lab). | Check that the process listens (`ss -tlnp`), on the right address and port. In Kubernetes, check that the container listens on the port the Service targets. |
| `Connection timed out` | Nothing came back at all. A firewall *drops* the SYN, the route is wrong, or the host is down. The SYN is repeated about 1 s apart; with the defaults the kernel gives up after 131 s (`tcp_syn_retries` = 6; the first `tcp_syn_linear_timeouts` = 4 retries are 1 s apart). | Capture at both ends. SYN arrives, RST leaves: a closed port. SYN arrives, nothing leaves: a local firewall. SYN never arrives: the network in between, such as a security group or NetworkPolicy. |
| Fast link, slow transfer to a far-away server | Throughput is window divided by round-trip time. With about 3 MB in flight, a 200 ms path gives about 110 Mbit/s whatever the link speed (Lab 2.3 chart 1). | Read `ss -ti` for `rtt`, `cwnd` and whether the sender or the receiver is the limit. Raise `tcp_rmem` and `tcp_wmem` maxima, try BBR, use several parallel streams, or move the data closer (a regional replica, a CDN). |
| One percent packet loss makes a fast link crawl | TCP reads every loss as congestion and cuts `cwnd`, again and again. At 20 ms round trip the lab fell from 1517 to 11 Mbit/s at 1% loss (Lab 2.3 chart 2). | Count retransmissions with `nstat`; find the real loss (a bad cable, Wi-Fi, an overloaded queue) and fix that. Tuning TCP does not repair a broken link. |
| Small requests work, large responses hang after the handshake | Oversized packets are dropped on the path and the ICMP "too big" message that would tell the sender is filtered out, so the sender keeps retrying packets that never fit (a *path MTU black hole*). | Let ICMP through the firewall. As a workaround set `tcp_mtu_probing`: 0 is off, 1 turns probing on after a black hole is detected, 2 keeps it always on ([ip-sysctl](https://docs.kernel.org/networking/ip-sysctl.html)). |
| Thousands of `CLOSE_WAIT` sockets on a service | The peers closed, the application never called `close`. It leaks descriptors and will eventually hit its file limit. | Fix the code path that skips `close` (a missing `finally` or context manager); `ss -tanp state close-wait` names the process. |
