# Chapter 2.5 · Linux Networking Internals

{{diagram ch-2-5-01.jsx | Ch 2.5 at a glance}}
## The problem: many private networks on one machine

Linux gives every container its own private network by splitting one kernel's networking into isolated copies, then joining the copies with virtual cables, switches and tunnels.

A Kubernetes node is one Linux machine with one physical network card, yet it runs dozens of containers. Each container believes it has its own network card, its own IP address and its own port 80. Four questions follow, and this chapter answers each:

1. **How can two containers both listen on port 80?** The kernel keeps a separate copy of the network stack for each container.
2. **How does a container reach its neighbour, and the outside world?** Virtual cables and a virtual switch connect the copies; address translation (NAT) lets them share the node's address.
3. **How does a packet reach a container on another node?** The physical network knows nothing about container addresses, so the packet is either wrapped in a tunnel or routed.
4. **Who builds all this for every new container?** A small program called a CNI plugin, started by the container runtime through a fixed contract.

**Why this matters for Kubernetes.** A Pod is a network namespace plus a virtual cable. When Kubernetes shows `NotReady` nodes, Pods that cannot reach each other, or Services that time out, the cause is one of the mechanisms below. In Lab 2.5 you build a working pod network by hand with a few shell functions; Vol 6 turns those functions into a real CNI plugin and then replaces it with Cilium.

## How it works, part 1: network namespaces

A network namespace is a private copy of the kernel's network stack: its own interfaces, IP addresses, routing table, firewall rules and port numbers.

Vol 1 Ch 1.5 introduced namespaces as the kernel feature behind containers. The network one isolates "system resources associated with networking": network devices, routing tables, firewall rules, the `/proc/net` view and port numbers ([network\_namespaces(7)](https://man7.org/linux/man-pages/man7/network_namespaces.7.html)). Two namespaces can both run a server on port 80 because each has its own table of sockets. A physical network card lives in exactly one namespace at a time, so a container cannot own the node's card; it needs a virtual one.

{{diagram ch-2-5-02.jsx | three network namespaces on one node · the addresses are those of Lab 2.5}}
The pod boxes use the addresses you will assign in Lab 2.5. Nothing connects them yet.

A new namespace starts almost empty. This is the output of `ip netns add demo` followed by two `ip -n demo` commands on the test machine:

```text
$ ip -n demo -br link
lo               DOWN           00:00:00:00:00:00 <LOOPBACK>
$ ip -n demo route
$
```

One loopback device that is down, and no routes. The namespace cannot talk to anything yet. A process joins a namespace when it is created inside it, or later with `setns`. When the last process in a namespace ends, the kernel frees it and destroys the virtual devices inside ([network\_namespaces(7)](https://man7.org/linux/man-pages/man7/network_namespaces.7.html)). `ip netns add` keeps the namespace alive without a process by pinning it as a named file, `/run/netns/NAME`; the CNI contract later in this chapter hands that path to plugins.

## How it works, part 2: veth pairs and the Linux bridge

A pod is a namespace plus a virtual cable, and the cable plugs into a virtual switch on the node: a veth pair joins the pod to a Linux bridge.

A **veth pair** is two virtual Ethernet devices created together. "Packets transmitted on one device in the pair are immediately received on the other device" ([veth(4)](https://man7.org/linux/man-pages/man4/veth.4.html)). Put one end inside the pod's namespace, where it is named `eth0`, and leave the other end on the node. Now the pod has a network card, and the other end of its cable is on the node.

A **Linux bridge** is a virtual switch. It "transparently forwards traffic between multiple network interfaces", looking only at the Layer 2 header ([kernel docs, Ethernet Bridging](https://docs.kernel.org/networking/bridge.html)). In other words, it reads the destination MAC address (the hardware address of an Ethernet interface) of each frame, and sends the frame out of the one port behind which that address was last seen. Plugging the node-side end of each veth into the bridge makes all pods on the node one small Ethernet network. The bridge's table of addresses is its *forwarding database*; on the test machine, after two pods had pinged each other, `bridge fdb show br cni0` listed one entry per pod:

```text
ee:5e:9f:7d:b1:44 dev veth-p1 master cni0
c6:4b:6a:26:e3:8b dev veth-p2 master cni0
```

The bridge also gets an IP address on the node, `10.244.1.1/24`. Pods use it as their default gateway: traffic to a pod on the same bridge is switched, never routed; traffic for any other subnet goes to the gateway, and the node's routing table takes over. The node must have IP forwarding switched on (`net.ipv4.ip_forward=1`) or it will drop such packets instead of routing them ([ip-sysctl](https://docs.kernel.org/networking/ip-sysctl.html) lists the default as 0, disabled). This is the exact topology of Lab 2.5 on one node:

{{diagram ch-2-5-03.jsx | one node of Lab 2.5 · two pods, two veth pairs, one bridge}}
Read it left to right. A frame from p1 to p2 turns around inside the bridge. A packet from p1 to anywhere else is addressed to `10.244.1.1`, enters the node's routing code, and leaves through `eth0`.

## How it works, part 3: netfilter, nftables, NAT and conntrack

Netfilter is a set of checkpoints in the kernel's packet path, nftables attaches rules to those checkpoints, and conntrack remembers connections so that address translation can undo itself on the reply.

**Hooks.** A packet entering the node from a network card passes the *prerouting* hook. The kernel then decides by its destination address: a packet for the node itself passes *input* and reaches a local process; any other packet passes *forward* (only if forwarding is on). Every packet leaving the node, whether forwarded or created by a local process (which first passes *output*), passes *postrouting* last ([nftables wiki, Netfilter hooks](https://wiki.nftables.org/wiki-nftables/index.php/Netfilter_hooks)).

{{diagram ch-2-5-04.jsx | the netfilter packet path · five hooks}}
A pod talking to another node takes the top row: prerouting, routing decision, forward, postrouting. A sixth hook, *ingress*, sits on one interface and runs even earlier; this chapter does not use it.

**Tables, chains, rules.** "nftables predefines no chains at all": you create a table (a named container tied to an address family; `ip` means IPv4), then a *base chain* in it that names a hook and a priority, then rules in the chain. A rule is a match plus a statement, such as `masquerade`. Within one hook, chains run in order of increasing priority number ([same page](https://wiki.nftables.org/wiki-nftables/index.php/Netfilter_hooks)):

| Priority | Keyword | What runs there |
| --- | --- | --- |
| -300 | `raw` | before connection tracking |
| -200 | (built in) | connection tracking itself |
| -100 | `dstnat` | destination NAT (prerouting) |
| 0 | `filter` | ordinary filtering |
| 100 | `srcnat` | source NAT (postrouting) |

Several tables can attach to the same hook: Docker's, kube-proxy's, a CNI plugin's and yours all see the same packet. Priority decides who goes first, and a `drop` in any of them ends the packet's journey.

**NAT with masquerade.** A pod's address `10.244.1.2` means nothing outside its node, so a reply from the outside world would never find its way back. *Masquerade* fixes this at postrouting: "a special case of SNAT, where the source address is automagically set to the address of the output interface" ([nftables wiki, NAT](<https://wiki.nftables.org/wiki-nftables/index.php/Performing_Network_Address_Translation_(NAT)>)). The packet leaves with the node's address instead of the pod's.

**Conntrack.** To turn the reply back into a packet for the pod, the kernel keeps a *connection tracking* table: one entry per flow, written with both directions. Only the first packet of a flow is matched against NAT rules; "the NAT engine uses the NAT binding information already set up by the first packet" for the rest (same NAT page). This is one real entry from Lab 2.5, a pod pinging host B (`conntrack -L`):

```text
icmp 1 29 src=10.244.1.2 dst=172.29.0.3 type=8 code=0 id=2670 src=172.29.0.3 dst=172.29.0.2 type=0 code=0 id=2670 mark=0 use=1
```

The left half is the original direction: pod to host B. The right half is what the reply will look like: host B to the node's own address. The difference between the halves is the NAT, written down. When the reply arrives addressed to `172.29.0.2`, conntrack finds this entry and rewrites the destination back to `10.244.1.2`.

**Watching a packet cross the hooks.** `meta nftrace set 1` marks matching packets, and `nft monitor trace` prints every chain and rule that each marked packet meets ([nftables wiki, tracing](https://wiki.nftables.org/wiki-nftables/index.php/Ruleset_debug/tracing)). In the lab, a trace chain at priority -300 marked one ping from the pod to host B (lines shortened at `...`):

```text
trace id d581cc21 ip cni pre packet: iif "cni0" ... ip saddr 10.244.1.2 ip daddr 172.29.0.3 ... ip ttl 64 ... icmp type echo-request ...
trace id d581cc21 ip cni pre rule ip saddr 10.244.1.2 ip daddr 172.29.0.3 meta nftrace set 1 (verdict continue)
trace id d581cc21 ip cni pre policy accept
trace id cca7a789 ip cni post packet: iif "cni0" oif "eth0" ... ip saddr 10.244.1.2 ip daddr 172.29.0.3 ... ip ttl 63 ... icmp type echo-request ...
trace id cca7a789 ip cni post rule ip saddr 10.244.1.0/24 ip daddr != 10.244.0.0/16 oifname != "cni0" masquerade (verdict accept)
```

Read it as the packet's diary. In chain `pre` (prerouting) it arrives from `cni0` with TTL 64. In chain `post` (postrouting) it leaves through `eth0` with TTL 63: the node routed it, and each routing step lowers the TTL by one. The masquerade rule fires there. The two trace ids differ on this kernel, so follow the chain names, not the id.

## How it works, part 4: the VXLAN overlay

An overlay carries pod-to-pod frames across the node network by wrapping each frame inside an ordinary UDP packet between the two nodes.

The physical network between two nodes knows the nodes' addresses, such as `172.29.0.2` and `172.29.0.3`, and nothing about pod subnets like `10.244.2.0/24`. There are two ways out. In a *routed* design you teach the network where each pod subnet lives, usually with a routing protocol such as BGP. In an *overlay* design you hide the pod traffic inside packets between node addresses, which the network already carries.

**VXLAN** (Virtual eXtensible LAN, [RFC 7348](https://www.rfc-editor.org/rfc/rfc7348.html), an Informational RFC from 2014) carries Ethernet frames inside UDP. A 24-bit network identifier, the *VNI*, names the virtual network; the RFC says this allows "up to 16 M VXLAN segments". "IANA has assigned the value 4789 for the VXLAN UDP port". Each node runs one endpoint (a *VTEP*) that wraps outgoing frames and unwraps incoming ones. On Linux the endpoint is a device of type `vxlan`; the lab calls it `vxlan0`. The kernel documentation notes that Linux's own default port predates the IANA number ([VXLAN, kernel docs](https://docs.kernel.org/networking/vxlan.html)), so some tools still use another one: Cilium's default is UDP 8472 ([Cilium routing docs](https://docs.cilium.io/en/stable/network/concepts/routing/)). The lab sets 4789 explicitly.

The path of one packet from pod p1 on node A to pod p3 on node B: p1 sends to its gateway `cni0`; node A's routing table says "`10.244.2.0/24` is behind `vxlan0`"; `vxlan0` wraps the frame and sends a UDP packet to node B; node B's `vxlan0` unwraps it; B's routing sends it into `cni0` and on to p3. This is a real capture of one such ping on the underlay (`tcpdump -e -v`, lines shortened):

```text
32:7c:d9:50:c8:1f > b6:30:28:4c:2d:44, ethertype IPv4 (0x0800), length 148: ... proto UDP (17), length 134
    172.29.0.2.40891 > 172.29.0.3.4789: VXLAN, flags [I] (0x08), vni 100
9a:c1:37:81:45:b6 > f6:74:aa:4c:59:05, ethertype IPv4 (0x0800), length 98: ... proto ICMP (1), length 84
    10.244.1.2 > 10.244.2.2: ICMP echo request, id 2709, seq 1, length 64
```

The first two lines are the outer packet, between the two nodes' `eth0` cards. The last two lines are the pod's own frame, carried inside as UDP payload. Its MAC addresses belong to the two `vxlan0` devices, not to the pods.

{{diagram ch-2-5-05.jsx | a VXLAN frame · drawn to scale from the capture above, bytes 1 to 148}}
The segments are drawn in proportion to their bytes. Parts 1 to 4 are the overhead: 14 + 20 + 8 + 8 = 50 bytes. Parts 5 to 7 are what the pod sent: 14 + 20 + 64 = 98 bytes. The capture's `length 148` and `length 98` are exactly these sums.

**Why the pod MTU is 1450.** The *MTU* (maximum transmission unit) is the largest IP packet an interface sends without fragmenting it. The outer IP packet is the inner IP packet plus 50 bytes: the inner Ethernet header (14), the VXLAN header (8), UDP (8) and the outer IP header (20). On a 1500-byte underlay a pod can therefore send at most 1450-byte packets; Cilium's documentation also gives 50 bytes as the VXLAN overhead ([Cilium routing docs](https://docs.cilium.io/en/stable/network/concepts/routing/)). RFC 7348 section 4.3 says VTEPs "MUST NOT fragment VXLAN packets" and recommends raising the physical MTU to fit. If a pod keeps MTU 1500, its largest packets do not fit after wrapping. The sender must then learn the real limit from an ICMP "fragmentation needed" message (path MTU discovery, Ch 2.2). If a firewall drops that message, large packets vanish while small ones still work: a *PMTU black hole*. Lab 2.5 builds one on purpose.

**A limit of the lab.** The lab's tunnel has one fixed `remote` address, so it joins exactly two nodes. With more nodes, each node needs one forwarding entry and one route per peer, and something must keep them current as nodes come and go. That bookkeeping is a main job of an overlay CNI plugin (Vol 6).

## How it works, part 5: the CNI contract

CNI, the Container Network Interface, is a contract between a container runtime and a network plugin: the runtime creates the namespace, then runs the plugin as a program that gets its inputs from environment variables and standard input.

The contract is written down in the [CNI specification](https://github.com/containernetworking/cni/blob/main/SPEC.md) (version 1.1.0 when this chapter was written). Its first sentence of substance: "The CNI protocol is based on execution of binaries invoked by the container runtime." The rules, in the order they happen:

1. The runtime creates a new network namespace for the container *before* it calls any plugin. The spec says so in as many words, and makes the runtime responsible for cleaning the namespace up.
2. The runtime runs the plugin binary named by the `type` field of the network configuration, looked up in the directories of `CNI_PATH`.
3. The operation and its inputs travel in **environment variables**; the network configuration travels on **standard input** as JSON.
4. On success the plugin prints a **result as JSON on standard output** and exits with code 0. Any other exit code means failure.

The environment variables, as the spec defines them:

| Variable | Meaning |
| --- | --- |
| `CNI_COMMAND` | The operation: `ADD`, `DEL`, `CHECK`, `GC` or `VERSION` |
| `CNI_CONTAINERID` | A unique identifier for the container, allocated by the runtime; must not be empty |
| `CNI_NETNS` | A reference to the container's isolation domain; for a network namespace, a path such as `/run/netns/NAME` |
| `CNI_IFNAME` | The name of the interface the plugin must create inside the container (`eth0` in this chapter) |
| `CNI_ARGS` | Extra arguments from the user, as `KEY=value` pairs separated by semicolons |
| `CNI_PATH` | The directories to search for plugin executables, separated by `:` on Linux |

{{diagram ch-2-5-06.jsx | one CNI ADD call · the real plugin of Lab 2.5 Part D}}
`ADD` attaches the container to the network. `DEL` undoes it when the container ends; the spec requires plugins to accept repeated `DEL` calls and succeed even if resources are already gone. `CHECK` lets the runtime probe that an attachment still looks right. `VERSION` lists the spec versions the plugin speaks. `GC` tells the plugin which attachments are valid so that it can remove stale resources, such as leaked address reservations. The configuration always names a `type`; an `ipam` section names a second plugin that hands out addresses, which the first plugin runs in turn. In Kubernetes the kubelet does not call CNI itself: it asks the container runtime to create the Pod sandbox, and the runtime performs steps 1 to 4 ([Kubernetes network model](https://kubernetes.io/docs/concepts/services-networking/)).

This is the result the reference `bridge` plugin printed in Lab 2.5 Part D for one `ADD` (MAC addresses left out). Interface `2` in `ips` means the third entry of `interfaces`, the `eth0` inside the namespace:

```json
{ "cniVersion": "1.0.0",
  "interfaces": [ { "name": "cni1" },
                  { "name": "veth66238962" },
                  { "name": "eth0", "sandbox": "/var/run/netns/real1" } ],
  "ips":    [ { "interface": 2, "address": "10.250.1.2/24", "gateway": "10.250.1.1" } ],
  "routes": [ { "dst": "0.0.0.0/0" } ],
  "dns": {} }
```

That is the whole contract. A CNI plugin is any program that can read those inputs, change the network inside that namespace and print that JSON.

## How it works, part 6: eBPF in one page (concept only)

eBPF lets you load small, checked programs into the running kernel and attach them to events, so the kernel's behaviour changes without a new kernel or a kernel module. There is no lab for it in this chapter; Vol 6 uses it through Cilium.

[ebpf.io](https://ebpf.io/what-is-ebpf/) describes eBPF as sandboxed programs that run inside the Linux kernel. They are event-driven: they "run when the kernel or an application passes a certain hook point". Four ideas are enough for now:

- **Hooks** are the events a program attaches to. Pre-defined hooks include system calls, function entry and exit, kernel tracepoints and network events; a *kprobe* attaches to almost any kernel function.
- **Maps** are tables that let a program "store state" and share it with other programs and with user space. Hash tables and arrays are two of the map types.
- **The verifier** checks a program before it is attached. It makes sure that, among other things, "the program always runs to completion". A just-in-time (JIT) compiler then turns the bytecode into native machine code. ebpf.io adds that the verifier "is not a security tool inspecting what the programs are doing".
- **Helper calls** are the only way a program touches the kernel: a "well-known and stable API", not arbitrary kernel functions.

For networking, two hooks matter most. Both are described in Cilium's [BPF and XDP reference guide](https://docs.cilium.io/en/stable/reference-guides/bpf/progtypes/):

| Hook | Where it runs | Why it matters for networking |
| --- | --- | --- |
| XDP | In the network driver, "at the earliest possible point in software", before the kernel allocates a packet buffer (`skb`); ingress only | Drop or redirect packets very cheaply, for example for load balancing |
| tc (traffic control) | On ingress and on egress, after the driver and before protocol processing; the program sees an `sk_buff` with metadata the stack already extracted | Enforce policy and rewrite packets on a pod's virtual interface |
| kprobe, tracepoint | Entry of a kernel function, or a fixed kernel tracepoint ([program types](https://docs.kernel.org/bpf/libbpf/program_types.html)) | Observe the kernel without changing its behaviour |

**How Cilium uses it.** Cilium describes itself on cncf.io as "eBPF-based Networking, Observability, and Security". It is still a CNI plugin: the runtime still creates the namespace and calls it with `ADD`. What changes is the data path. With Cilium's kube-proxy replacement, Service entries live in eBPF maps, and the destination is translated when a program connects or sends, so the node shows "no `iptables` rule for the service" ([Cilium kube-proxy-free guide](https://docs.cilium.io/en/stable/network/kubernetes/kubeproxy-free/)). A Service lookup becomes a map lookup, not a walk down a list of rules. Namespaces, veth pairs and the CNI contract from this chapter all remain.

## How it works, part 7: how Kubernetes uses all of this (preview)

Kubernetes does not add a networking mechanism of its own: it asks Linux for a namespace per Pod and a CNI plugin to wire it, and it uses netfilter for Services. [The Kubernetes network model](https://kubernetes.io/docs/concepts/services-networking/) states three rules: "A pod has its own private network namespace which is shared by all of the containers within the pod"; each Pod gets its own cluster-wide IP; and "Pods can communicate with each other directly, without the use of proxies or address translation (NAT)".

That last rule explains one line of Lab 2.5. The masquerade rule skips destinations inside `10.244.0.0/16`, because pod-to-pod traffic must keep its real source address. Only traffic leaving the pod network is translated.

| In this chapter | In Kubernetes |
| --- | --- |
| A named network namespace (`ip netns add p1`) | The Pod sandbox, shared by all containers of the Pod |
| veth pair, one end in a bridge | The Pod's `eth0` and its host-side device, created by the CNI plugin |
| Node subnet `10.244.N.0/24` | The node's Pod range, `spec.podCIDR` on the Node object: "the pod IP range assigned to the node" ([Node API](https://kubernetes.io/docs/reference/kubernetes-api/cluster-resources/node-v1/)) |
| `pod_add` and `pod_del` | The runtime's CNI `ADD` and `DEL` calls |
| VXLAN tunnel or routes between nodes | The overlay or routed design of your CNI plugin |
| Masquerade at postrouting | Traffic from Pods to destinations outside the cluster |
| NAT rules that rewrite a destination | kube-proxy implementing a Service |

**Services.** A Service's virtual IP is not on any interface. kube-proxy makes it work by programming netfilter: in iptables mode, "for each endpoint, it installs iptables rules which, by default, select a backend Pod at random" ([Virtual IPs and Service proxies](https://kubernetes.io/docs/reference/networking/virtual-ips/)). kube-proxy also has `ipvs` and `nftables` modes; in Kubernetes 1.37 the default is still `iptables`, and a future version will change it to `nftables` (same page). Vol 5 builds Services and Vol 6 compares the data paths.

## In production

Most pod-network incidents come from four places: the MTU of the overlay, the conntrack table, the size of the NAT rule set, and a missing or half-finished CNI step. Each row is a symptom you will meet, the mechanism from this chapter behind it, and what engineers do.

| Symptom | Real cause | What engineers do |
| --- | --- | --- |
| Small requests between pods on different nodes work; large uploads or big responses hang, then time out | The pod MTU is 1500 on a 1500-byte underlay, so wrapped packets are 50 bytes too big; a firewall drops the ICMP "fragmentation needed" reply: a PMTU black hole (RFC 7348 section 4.3) | Set the pod MTU to underlay minus overhead (1450 for VXLAN on 1500), or raise the underlay MTU; allow ICMP type 3 code 4; test with `ping -M do -s` sizes, as in Lab 2.5 Break it |
| New connections fail at random under load; old ones keep working; the kernel log says `table full, dropping packet` | The conntrack table is full. `nf_conntrack_max` defaults to the number of hash buckets, which is sized from RAM ([nf\_conntrack sysctl](https://docs.kernel.org/networking/nf_conntrack-sysctl.html)) | Watch `nf_conntrack_count` against `nf_conntrack_max`; raise the maximum or shorten timeouts. kube-proxy sets the maximum itself: 32768 per CPU core, at least 131072 by default ([kube-proxy flags](https://kubernetes.io/docs/reference/command-line-tools-reference/kube-proxy/)) |
| With thousands of Services, a Service change takes long to reach every node, and kube-proxy burns CPU | In iptables mode the rules grow with Services and endpoints, every packet walks them, and an update rewrites the whole rule set: "This becomes slower and slower as the ruleset increases in size" ([KEP-3866](https://github.com/kubernetes/enhancements/tree/master/keps/sig-network/3866-nftables-proxy)) | Move kube-proxy to `nftables` mode, or to an eBPF data path such as Cilium's kube-proxy replacement (part 6) |
| A new cluster's nodes stay `NotReady` and CoreDNS Pods stay `Pending` | No CNI plugin is installed yet, so the runtime cannot run `ADD` for any Pod. kubeadm's guide: "Cluster DNS (CoreDNS) will not start up before a network is installed" ([kubeadm](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/create-cluster-kubeadm/)) | Install the CNI plugin (usually a DaemonSet that drops a config in `/etc/cni/net.d` and a binary in the CNI path); choose a Pod range that does not overlap the host networks |
| Pods reach other Pods but not the internet; `conntrack -L` shows `[UNREPLIED]` entries | Traffic leaves the node with the pod address because masquerade is missing or matches the wrong range; replies are routed elsewhere (Lab 2.5 Part B) | Check the `nat` postrouting rules and the source address on the node's card with `tcpdump`; fix the masquerade range |
| A node runs out of Pod addresses although it runs few Pods; host-side veths or NAT rules pile up | `DEL` was never called, or ran when it could not see the Pod's interface any more, so reservations and rules leak (the bridge plugin's state lives in `/var/lib/cni/networks/NAME`) | Compare that directory with the running Pods; the CNI `GC` operation (spec 1.1) exists to remove such leaks |
| Pods on the same node talk; pods on different nodes do not, after a firewall change between nodes | The overlay's UDP port is blocked: 4789 for standard VXLAN, 8472 for Cilium's default | Capture on the node's card for `udp port 4789` (or 8472) on both sides; open the port between nodes only |

## Project cards

Two CNCF projects belong to this chapter: CNI, the contract you call by hand in Lab 2.5 Part D, and Cilium, the plugin Vol 6 installs. Maturity levels are from each project's page on [cncf.io/projects](https://www.cncf.io/projects/), checked 2026-11-16.

**CNI (Container Network Interface)**

| Field | Content |
| --- | --- |
| Problem | Every container runtime needs to attach containers to some network, and every network needs to be attachable from any runtime |
| Layer / interface | CNI itself: a specification plus reference plugins, called by the runtime (containerd, CRI-O) once per Pod sandbox |
| Architecture | The [specification](https://github.com/containernetworking/cni/blob/main/SPEC.md) (operations `ADD`, `DEL`, `CHECK`, `STATUS`, `VERSION`, `GC`), the `libcni` Go library for runtimes, and the [reference plugins](https://github.com/containernetworking/plugins) (`bridge`, `host-local`, `ptp`, `portmap` and others) that Lab 2.5 Part D runs |
| Alternatives | None at this layer in Kubernetes: every Pod network plugin is a CNI plugin. The choice is which plugin: a simple bridge plus routes for a lab, an overlay plugin for a network you cannot change, a full plugin such as Cilium or Calico for policy and observability |
| CNCF maturity | Incubating, accepted 23 May 2017 ([cncf.io](https://www.cncf.io/projects/container-network-interface-cni/), as of 2026-11-16) |

**Cilium**

| Field | Content |
| --- | --- |
| Problem | iptables-based Pod networking and Services slow down as rules grow, and they cannot see or filter by application identity |
| Layer / interface | CNI plugin; optional kube-proxy replacement; network policy and observability (Hubble) on top |
| Architecture | An agent on every node that compiles and loads eBPF programs on the tc hooks of Pod interfaces and keeps state in eBPF maps; an operator for cluster-wide tasks; VXLAN (UDP 8472 by default) or native routing between nodes ([routing docs](https://docs.cilium.io/en/stable/network/concepts/routing/)) |
| Alternatives | Calico (iptables or eBPF data path, BGP routing; not a CNCF project); Flannel (a small VXLAN overlay, no network policy); the cloud provider's own plugin when Pods should get VPC addresses. Pick Cilium when you want eBPF Services, L7-aware policy and flow visibility |
| CNCF maturity | Graduated: accepted 13 October 2021, graduated 11 October 2023 ([cncf.io](https://www.cncf.io/projects/cilium/), as of 2026-11-16) |
