## The problem: how hosts on one link find and address each other

A network card can only send bits onto a wire, so two computers on the same link need three agreements before a single wallet request can cross it: how to wrap the data, how to name the receiver, and how to learn that name from an IP address.

In Vol 1 the wallet listened on `127.0.0.1`, an address that never leaves the machine. The moment the API and its database run on two machines, or in two containers, a request must travel over a real link: a cable, a Wi-Fi hop or a virtual cable inside the kernel. Three questions follow, and this chapter answers each:

1. **How is a message wrapped for the wire?** An HTTP request is only the innermost layer. TCP, IP and Ethernet each add a header so that the next device knows what to do with it.
2. **How does one machine out of many get the frame?** Every network card has a hardware address, and a *switch* learns which card sits behind which port so it can deliver a frame to one port instead of all of them.
3. **How does a host that only knows an IP address find the hardware address?** It asks the whole link, "who has 10.0.1.2?", using the *Address Resolution Protocol* (ARP), and remembers the answer.

Two limits complete the picture: a *VLAN* tag lets one wire carry several separate networks, and the *MTU* caps how big one frame's payload may be.

**Why this matters for Kubernetes.** A common way to connect containers on one machine is a Linux bridge with one virtual cable (a *veth pair*) per container. Lab 2.1 builds exactly that by hand. When a Pod cannot reach a neighbour, or large responses hang while small ones work, the cause is often one of the things in this chapter: a missing ARP answer, a duplicate IP address or an MTU mismatch.

## How it works, part 1: layers and encapsulation

A network message is built in layers: each layer wraps the one above it in its own header, and the receiver unwraps the headers in reverse order.

A *protocol* is an agreed message format plus the rules for using it. To keep protocols manageable, networking splits the job into layers, each with one task. Two naming schemes exist. The OSI model has seven layers: physical, data link, network, transport, session, presentation, application ([ITU-T X.200](https://www.itu.int/rec/T-REC-X.200-199407-I/en); layer list as given on [Wikipedia](https://en.wikipedia.org/wiki/OSI_model)). The Internet's own model has four: application, transport, internet and link ([RFC 1122, section 1.1.3](https://www.rfc-editor.org/rfc/rfc1122.txt)). Engineers mix both: "L2" means the link layer (Ethernet), "L3" the IP layer, "L4" TCP or UDP, "L7" the application.

*Encapsulation* is the wrapping itself. The wallet's HTTP request is handed to TCP, which adds a header with port numbers and sequence numbers. IP adds source and destination addresses. Ethernet adds hardware addresses and a checksum. A TCP piece of data is a *segment*, an IP piece a *packet*, an Ethernet piece a *frame*. This chapter lives at the bottom of the picture: the frame, and how it reaches the next machine on the same link.

## How it works, part 2: MAC addresses and the Ethernet frame

Every network card has a 6-byte hardware address, its *MAC address*, and an Ethernet frame names two of them: the destination first, then the source.

A MAC address is written as six pairs of hex digits, such as `46:4c:1d:d1:30:9f`. Physical cards usually ship with one; virtual interfaces such as a *veth* (a virtual Ethernet device, always created as a linked pair, with packets sent into one end "immediately received on the other": [veth(4)](https://man7.org/linux/man-pages/man4/veth.4.html)) get a random one from the kernel. The address `ff:ff:ff:ff:ff:ff` is the *broadcast* address: a frame sent to it is delivered to every card on the link ([Wireshark wiki, Ethernet](https://wiki.wireshark.org/Ethernet)).

The frame itself has five fields. The *EtherType* says what the payload is: `0x0800` for IPv4, `0x0806` for ARP, `0x8100` for a VLAN tag ([IANA registry](https://www.iana.org/assignments/ieee-802-numbers/ieee-802-numbers.xhtml)). The payload runs from 46 to 1500 bytes; a shorter one is padded with zeros, and the padding is not part of the IP packet ([RFC 894](https://www.rfc-editor.org/rfc/rfc894.txt)). The FCS (frame check sequence) is a 4-byte checksum the receiving card uses to drop damaged frames; the smallest legal frame is 64 bytes: header, payload and FCS ([Wireshark wiki](https://wiki.wireshark.org/Ethernet)).

## How it works, part 3: a switch learns where each MAC lives

A switch sends each frame out of the one port where its destination MAC lives, and it learns that map by reading the source MAC of every frame it receives.

A *switch* joins many cables into one link. Inside it keeps a *MAC table* (the Linux bridge calls it the *forwarding database*, FDB) that maps a MAC address to a port. It follows three rules for every frame, in this order:

1. **Learn.** Record the frame's source MAC against the port it arrived on, and refresh that entry's age.
2. **Flood** if the destination is the broadcast address or is not in the table: send the frame out of every port except the one it came from.
3. **Forward** if the destination is in the table: send the frame out of that one port only.

Entries expire. The Linux bridge keeps a learned address for its *ageing time* after the last frame from it ([kernel bridge documentation](https://docs.kernel.org/networking/bridge.html)), so a host that moves is eventually found at its new port. A Linux bridge is simply a switch implemented in the kernel; you create one with `ip link add sw0 type bridge` and attach cables to it, as the lab does.

## How it works, part 4: ARP turns an IP address into a MAC address

Before a host can send a frame to an IP address on its own link it needs that address's MAC, and ARP finds it by asking the whole link.

IP packets are addressed by IP address but frames by MAC address, so something must translate. The *Address Resolution Protocol* does it ([RFC 826](https://www.rfc-editor.org/rfc/rfc826.txt), November 1982). The asker broadcasts a request, "who has 10.0.0.2? tell 10.0.0.1". Only the owner replies, straight to the asker: "10.0.0.2 is at `0e:b0:f4:b8:4f:b5`". Both are frames with EtherType `0x0806`.

An ARP packet carries a hardware address type (1 means Ethernet), a protocol address type, two length bytes, an opcode (1 = request, 2 = reply) and then the sender's and target's MAC and IP addresses ([RFC 826](https://www.rfc-editor.org/rfc/rfc826.txt)). For IPv4 on Ethernet that adds up to 28 bytes, the length `tcpdump` printed in the previous diagram.

The host keeps the answers in a *neighbour cache* (Linux's name for the ARP table) so it asks once, not for every packet. RFC 826's receive rule has a neat side effect: a host updates an entry it already has for the sender, but only the *target* of a request adds a new one. A bystander that merely overhears a broadcast learns nothing; Lab 2.1 Part B shows this. The next diagram is a real trace from the lab.

{{diagram ch-2-1-05.jsx | ARP sequence · the four frames of Lab 2.1 Part A, from a real capture}}
The times are offsets from the first captured frame, in microseconds. The first ping pays the cost of ARP; the second finds the answer in the cache.

**The neighbour cache has states.** `ip neigh` prints one per entry. [ip-neighbour(8)](https://man7.org/linux/man-pages/man8/ip-neighbour.8.html) defines them: `INCOMPLETE` (not yet resolved), `REACHABLE` (valid until the reachability timeout), `STALE` (valid but suspicious), `DELAY` (validation delayed), `PROBE` (being probed) and `FAILED` (max probes exceeded). The timers come from [arp(7)](https://man7.org/linux/man-pages/man7/arp.7.html): `base_reachable_time` defaults to 30 seconds, `delay_first_probe_time` to 5 seconds, and the kernel makes up to 3 broadcast attempts (`mcast_solicit`) or 3 unicast probes (`ucast_solicit`) before giving up.

A `STALE` entry is still used at once; the kernel re-checks it afterwards with a unicast request. Lab 2.1 Part A shows the cycle from `REACHABLE` to `STALE` and back, and Part C shows `INCOMPLETE`.

A confirmation while in `DELAY`, or a reply while in `PROBE`, returns the entry to `REACHABLE`. Which state an entry is in tells you whether the host has recently heard from the neighbour.

## How it works, part 5: VLAN tags and the MTU

A VLAN tag lets one wire carry several separate networks by adding four bytes to each frame, and the MTU caps how large the payload of one frame may be.

A *VLAN* (virtual LAN) splits one physical link into separate *broadcast domains*: a broadcast sent in VLAN 10 reaches only members of VLAN 10. The 802.1Q tag is 4 bytes inserted after the source MAC. Its first two bytes are the value `0x8100`, which takes the place of the EtherType; the next two hold 3 priority bits, 1 flag bit and a 12-bit VLAN ID. A tagged frame is 4 bytes longer than an untagged one ([Wireshark wiki, VLAN](https://wiki.wireshark.org/VLAN); the standard itself is [IEEE 802.1Q-2022](https://standards.ieee.org/ieee/802.1Q/10323/), which is paywalled). On Linux you give a host a tagged interface with `ip link add link eth0 name eth0.10 type vlan id 10` ([ip-link(8)](https://man7.org/linux/man-pages/man8/ip-link.8.html)).

The *MTU* (maximum transmission unit) is the largest packet a link carries in one frame. For Ethernet that is 1500 bytes of payload ([RFC 894](https://www.rfc-editor.org/rfc/rfc894.txt)). Larger *jumbo frames* exist on some networks, but there is no single standard size and every device on the link must agree; check your own equipment.

When sizes disagree, a router that cannot forward a too-large packet sends back an ICMP message "fragmentation needed and DF set", and the sender shrinks its packets: *Path MTU Discovery* ([RFC 1191](https://www.rfc-editor.org/rfc/rfc1191.txt)). A switch forwards frames and sends no ICMP, and firewalls often drop ICMP, so on a mismatch large packets can vanish silently while small ones still work: a *PMTUD black hole* ([RFC 2923, section 2.1](https://www.rfc-editor.org/rfc/rfc2923.txt)). Lab 2.1 Part D reproduces both the loud and the silent failure.

## Commands you will use in the lab

Everything runs as root on Ubuntu 24.04 with `iproute2`, `tcpdump` and `iputils` installed (Lab 2.1 lists the one-line install). A *network namespace* is a private copy of the network stack: its own interfaces, addresses and ARP cache. Namespaces let one machine play several hosts. `ip -n NAME` runs an `ip` command inside namespace `NAME` ([ip(8)](https://man7.org/linux/man-pages/man8/ip.8.html)); every other tool runs as `ip netns exec NAME <command>`. In `10.0.0.1/24` the `/24` says that the first 24 bits name the network, so `10.0.0.x` addresses share one link; Ch 2.2 explains it.

| Command | What it does | Example |
| --- | --- | --- |
| `ip netns add NAME`, `ip netns del NAME` | Create or delete a network namespace (a host for the lab) | `ip netns add h1` |
| `ip link add A type veth peer name B` | Create a virtual cable: a linked pair of interfaces, [veth(4)](https://man7.org/linux/man-pages/man4/veth.4.html) | `ip link add veth-h1 type veth peer name veth-h2` |
| `ip link set DEV netns NS`, `up`, `master BR`, `mtu N` | Move an interface into a namespace; bring it up; attach it to a bridge; set its MTU ([ip-link(8)](https://man7.org/linux/man-pages/man8/ip-link.8.html)) | `ip -n s1 link set eth0 mtu 1400` |
| `ip link add NAME type bridge` | Create a Linux bridge, the software switch | `ip link add sw0 type bridge` |
| `ip link add link eth0 name eth0.10 type vlan id 10` | Create a VLAN sub-interface that tags its frames with VLAN ID 10 | `ip -n s1 link add link eth0 name eth0.10 type vlan id 10` |
| `ip addr add 10.0.0.1/24 dev DEV` | Give an interface an IP address | `ip -n h1 addr add 10.0.0.1/24 dev veth-h1` |
| `ip -br link`, `ip -br addr`, `ip -d link` | Show interfaces briefly (`-br`) or with details such as the VLAN ID (`-d`); the MAC address is in the `link` view | `ip -n h1 -br link show veth-h1` |
| `ip -s link show DEV` | Show counters, including frames dropped on receive | `ip -n s2 -s link show eth0` |
| `ip neigh`, `ip neigh show dev DEV`, `ip neigh flush all` | Show the neighbour (ARP) cache with its states; empty it ([ip-neighbour(8)](https://man7.org/linux/man-pages/man8/ip-neighbour.8.html)) | `ip -n h1 neigh` |
| `bridge link show` | List the bridge's ports and their STP state ([bridge(8)](https://man7.org/linux/man-pages/man8/bridge.8.html)) | `bridge link show` |
| `bridge fdb show br sw0`, `bridge fdb del MAC dev PORT master` | Show the switch's MAC table; delete one entry | `bridge fdb show br sw0` |
| `tcpdump -Z root -n -e -i IF -c N -w FILE "FILTER"` | Capture N frames on an interface into a file: `-e` prints MAC addresses, `-n` skips name lookups, `-Z root` keeps root as the writing user ([tcpdump(1)](https://www.tcpdump.org/manpages/tcpdump.1.html)) | `tcpdump -Z root -n -e -i eth0 -c 4 -w /tmp/x.pcap "arp or icmp"` |
| `tcpdump -n -e -r FILE` | Read a capture file back and print it | `tcpdump -n -e -r /tmp/x.pcap` |
| `ping -c N -W S IP` | Send N echo requests; wait S seconds for an answer | `ping -c 2 10.0.0.2` |
| `ping -M do -s SIZE IP` | Set the "do not fragment" flag and use SIZE bytes of data; the kernel refuses packets larger than the MTU ([ping(8)](https://man.archlinux.org/man/ping.8)) | `ping -c 1 -M do -s 1472 10.0.1.2` |
| `arping -c N -I IF IP` | Send ARP requests and print every reply with its MAC ([arping(8)](https://man.archlinux.org/man/arping.8)) | `arping -c 3 -I eth0 10.0.1.2` |
| `pkill -x tcpdump`, `wait` | Stop leftover captures; wait for a background job | `pkill -x tcpdump` |

## In production

Most link-layer incidents come down to a loop, a size mismatch, or two machines claiming one address.

| What you see | What is really happening | What engineers do |
| --- | --- | --- |
| Every host on a network segment becomes slow or unreachable at once; switch ports show constant traffic | A *broadcast storm*: a loop in the switch topology. Ethernet frames carry no hop count, so a flooded broadcast circles the loop forever and multiplies | Run spanning tree, which blocks redundant links so the topology is a tree and elects the switch with the lowest bridge ID as root ([kernel bridge docs](https://docs.kernel.org/networking/bridge.html)); on a Linux bridge `stp_state` is 0 (off) by default, so turn it on when the topology can loop |
| Ping works and small requests work, but large responses or TLS handshakes hang | An MTU mismatch hides a *PMTUD black hole*: full-size packets are dropped and the ICMP "fragmentation needed" message never reaches the sender ([RFC 2923](https://www.rfc-editor.org/rfc/rfc2923.txt)). Tunnels and overlays add headers, so their inner MTU is smaller | Probe with `ping -M do -s` at several sizes; set one consistent MTU on every link of the path; let ICMP "fragmentation needed" through firewalls |
| A service reachable by IP works for some clients and fails for others, or flips between working and not | A *duplicate IP address*: two MACs answer the same ARP request, and each client's cache keeps whichever it heard first or last ([RFC 5227](https://www.rfc-editor.org/rfc/rfc5227.txt) tells hosts to probe before using an address) | `arping` the address and count distinct MACs; find the second machine through the switch's MAC table; fix the static or DHCP overlap |
| After a failover the new machine holds the shared IP but clients still talk to the dead one for a while | Clients keep the old MAC in a `REACHABLE` or `STALE` entry until it is re-checked | The new owner sends a gratuitous ARP, an unrequested announcement of its address, so neighbours update at once; Linux can do it when an interface comes up (`arp_notify`, [kernel sysctl docs](https://docs.kernel.org/networking/ip-sysctl.html)) |
| `ip neigh` shows `INCOMPLETE` or `FAILED` for a host on the same subnet; ping gets no replies | Nobody answered the who-has: the target is down, in another VLAN, behind a dead port, or filtering ARP | Run `tcpdump -n -e arp` at both ends to see where the request vanishes; check VLAN IDs and port state |
| Random drops on a very large flat network, kernel log complaints about the neighbour table | The ARP cache hit its limits: by default the garbage collector keeps at least 128 entries, becomes aggressive above 512 and refuses new ones above 1024 ([arp(7)](https://man7.org/linux/man-pages/man7/arp.7.html), [sysctl docs](https://docs.kernel.org/networking/ip-sysctl.html)) | Raise the `gc_thresh` limits as a stop-gap; the real fix is smaller subnets, so fewer hosts share one broadcast domain |
| Traffic from a host crosses an unexpected machine; the gateway's MAC in `ip neigh` changed | *ARP spoofing*: ARP has no authentication, and a host accepts an update from any reply it hears ([RFC 826](https://www.rfc-editor.org/rfc/rfc826.txt)), so an attacker can claim the gateway's IP | Use switch features that check ARP against known bindings, pin critical entries, segment with VLANs, and encrypt traffic (TLS, Ch 2.4) so interception reveals nothing |
