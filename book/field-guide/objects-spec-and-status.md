# Objects, spec and status

## What and why

Everything you create in Kubernetes is an **object**: a record stored by the API server with a `kind`, a `metadata` block, a `spec` and a `status`. The split is the core idea of the whole system. `spec` is the **desired state** you write; `status` is the **observed state** that controllers and the kubelet write back. A controller's whole job is to make status match spec.

The API server validates and stores objects in etcd. It gives each one a `uid`, a `resourceVersion` and a `generation`. Because `spec` and `status` are separate, you can re-apply a manifest without overwriting what the cluster has observed, and many controllers can cooperate on one object without stepping on each other.

## Minimal example

Tested on kind v0.33.0, node image `kindest/node:v1.37.0`, kubectl v1.37.1 (2026-11-16). Read the three parts of a live Deployment, then change its spec:

```
$ kubectl create deploy web --image=nginx:1.31.8 --replicas=2; kubectl rollout status deploy/web
$ kubectl get deploy web -o yaml | grep -E "^(apiVersion|kind)|^  (name|namespace|uid|resourceVersion|generation)|^spec:|^status:|observedGeneration|readyReplicas"
apiVersion: apps/v1
kind: Deployment
  generation: 1
  name: web
  namespace: t2
  resourceVersion: "726"
  uid: c5104415-9e90-434b-8fbe-fef9fd61fb07
spec:
status:
  observedGeneration: 1
  readyReplicas: 2
$ kubectl scale deploy web --replicas=3
$ kubectl get deploy web -o jsonpath='{.metadata.generation} observed={.status.observedGeneration}'
2 observed=2
```

`generation` went from 1 to 2 because the spec changed; `observedGeneration` shows the deployment controller has seen that change.

## Key fields

| Field | Meaning | Default |
| --- | --- | --- |
| `apiVersion`, `kind` | Which API group, version and type this is | required |
| `metadata.name` | Name, unique within the namespace for this kind; cannot change | required (or use `generateName`) |
| `metadata.namespace` | Namespace of a namespaced object | `default` |
| `metadata.uid` | Unique ID generated by the server; read-only | set by the server |
| `metadata.resourceVersion` | Opaque version used for change detection and conflict checks | set by the server |
| `metadata.generation` | Counter of desired-state changes; read-only | set by the server |
| `metadata.labels`, `annotations` | Selectable labels; free-form annotations | none |
| `metadata.ownerReferences`, `finalizers`, `deletionTimestamp` | Ownership and deletion state | none |
| `spec` | Desired state, written by you | per kind |
| `status` | Observed state, written by controllers through the `/status` subresource | per kind |

Field meanings are from the v1.37.0 OpenAPI spec (`ObjectMeta`) and `kubectl explain`.

## kubectl

```
kubectl get deploy web -o yaml                     # whole object: metadata, spec, status
kubectl get deploy web -o jsonpath='{.status.readyReplicas}'
kubectl explain deploy.spec                        # fields of the desired state
kubectl explain pod.status.phase                   # fields of the observed state
kubectl api-resources --api-group=apps -o wide     # kinds, verbs and short names
kubectl apply --dry-run=server -f x.yaml           # validate against the API server without saving
kubectl get deploy web -o yaml --show-managed-fields   # who wrote which field
```

## How it fails

All three were reproduced on the test cluster.

| Symptom | Cause | Fix |
| --- | --- | --- |
| Error from server (BadRequest): ... Pod in version "v1" cannot be handled as a Pod: strict decoding error: unknown field "spec.containers\[0\].imagePullPolicyy" | A misspelled field; kubectl asks the server to reject unknown fields | Fix the spelling; check names with `kubectl explain` |
| The Pod "noimg" is invalid: spec.containers\[0\].image: Required value | A required field is missing | Add it; `kubectl explain` marks required fields |
| The Pod "imm" is invalid: spec: Forbidden: pod updates may not change fields other than spec.containers\[\*\].image, spec.initContainers\[\*\].image, spec.activeDeadlineSeconds, spec.tolerations (only additions to existing tolerations) ... | Most of a Pod's `spec` is immutable after creation | Delete and re-create the Pod, or change a Deployment's template instead |
